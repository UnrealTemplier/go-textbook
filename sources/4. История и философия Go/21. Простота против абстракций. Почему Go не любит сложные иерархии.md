Выходцы из корпоративных энтерпрайз-экосистем (Java, C#, PHP) десятилетиями впитывали фундаментальную догму: **любая абстракция полезна по умолчанию**. Нас приучали строить программные системы «на вырост», проектируя каждый модуль так, будто завтра базу данных заменит блокчейн, а бизнес-требования перевернутся с ног на голову.

В результате рождались грандиозные башни из слоев косвенности: входящий HTTP-запрос принимает `Controller`, передает его в `Facade`, тот обращается к `Service`, сервис делегирует логику в `Manager`, который просит `Repository` извлечь данные, а репозиторий обращается к `DAO`. И каждая граница между этими звеньями запечатана персональным интерфейсом.

Когда разработчик с таким багажом пытается перенести привычный стиль в Go, он натыкается на глухое сопротивление платформы. Проект мгновенно тонет в десятках однострочных файлов, чтение исходников превращается в утомительный квест по переходам между интерфейсами, а производительность начинает деградировать. 

В Go действует противоположное правило: **любая абстракция имеет высокую цену — как для умственных усилий человека, так и для машинных циклов процессора. Простота, прямота и прозрачность здесь всегда ценятся выше гипотетической гибкости.**

## Mechanical Sympathy: Цена глубокого стека вызовов

В классических ООП-языках глубина стека вызовов (`Call Stack`) редко привлекает внимание архитектора. Добавить еще один класс-обертку кажется бесплатным действием. Но с точки зрения рантайма Go и аппаратного обеспечения компьютера каждый дополнительный слой косвенности создает вполне измеримые накладные расходы.

### 1. Рост стека горутины (Stack Growth) и `runtime.morestack`

В операционных системах потоку ядра (OS Thread, на которых исторически работают потоки в Java и C#) выделяется фиксированный и сравнительно щедрый стек — обычно **1 МБ** или даже больше. Память под него резервируется виртуально, а страницы физической RAM подтягиваются по мере необходимости.

В Go архитектура принципиально иная: минимальный стартовый стек легковесной горутины составляет всего **2 КБ**! Именно этот микроскопический размер позволяет веб-сервису держать сотни тысяч и миллионы горутин одновременно без исчерпания памяти сервера.

Но что происходит, если бизнес-логика размазана по цепочке из десяти слоев абстракций? Каждому вызову функции требуется собственный кадр стека (`Stack Frame`) для сохранения адреса возврата, аргументов и локальных переменных. 

```
Вызов: Handler -> UseCase -> Service -> Manager -> Adapter -> Repository -> Driver
Стек: [ 2 KB ] ──> ПЕРЕПОЛНЕНИЕ! ──> runtime.morestack ──> [ 4 KB ] (Копирование)
```

В прологе каждой компилируемой функции компилятор Go генерирует быструю проверку: хватит ли текущего стека для выполнения функции. Если 10 слоев абстракции исчерпывают лимит в 2 КБ, управление мгновенно передается служебной процедуре `runtime.morestack`:

1. Рантайм аллоцирует новый, непрерывный фрагмент памяти, увеличенный в два раза (например, **4 КБ**).
2. **Копирует** все кадры из старого стека в новый.
3. Аккуратно корректирует все внутренние указатели на стек (`Stack Roots`), чтобы сборщик мусора (`GC`) сохранял корректность графа памяти.
4. Освобождает старый сегмент стека.

Если код разбит на десятки микро-функций и слоев оберток, горутины под нагрузкой вынуждены непрерывно расширять стек. Это порождает непредсказуемые всплески задержек (`Latency Spikes`), которые невозможно отловить на синтетических тестах с пустой базой.

### 2. Блокировка инлайнинга (Inlining Budget)

Компилятор Go оснащен эффективным оптимизатором встраивания функций (`Inlining`). Если вызываемая функция достаточно компактна (простой геттер, валидация или арифметическая операция), компилятор не генерирует дорогостоящую инструкцию вызова `CALL` с сохранением регистров на стек — он напрямую подставляет машинный код функции в точку ее вызова.

Однако оптимизатор Go работает в рамках строгой системы ограничений — так называемого «бюджета сложности» (`Inlining Budget`, оцениваемого по `Inlining Cost` в узлах абстрактного синтаксического дерева):

* Если ваша логика завернута в цепочку `Wrapper -> Adapter -> Decorator`, суммарная сложность быстро превышает доступный лимит, и компилятор прекращает инлайнинг на верхних уровнях.
* Если же между слоями стоит интерфейс, инлайнинг блокируется полностью: вызов превращается в динамическую диспетчеризацию через таблицу методов `itab`. Процессор выполняет косвенный переход по указателю, конвейер инструкций сбрасывается, а процессорный кэш инструкций L1i получает лишние промахи.

## Проблема «Преждевременной Абстракции»

Самая распространенная ошибка инженера, пытающегося с порога реализовать Clean Architecture («Чистую архитектуру»), — создание абстракций «про запас».

### Антипаттерн «Интерфейс-одиночка»

```go
// Разработчик думает: "А вдруг завтра бизнес решит сменить базу данных?"
// И создает интерфейс для сущности, у которой существует ЕДИНСТВЕННАЯ реализация:
type IUserRepository interface {
    Save(u *User) error
}

type PostgresUserRepository struct {
    db *sql.DB
}

func (r *PostgresUserRepository) Save(u *User) error {
    // Реализация сохранения в PostgreSQL...
    return nil
}
```

В Go подобное проектирование считается грубым нарушением фундаментального принципа простоты (см. [[5. Философия Go. Простота, читаемость и прагматизм]]). Если у вас есть конкретная база данных PostgreSQL, и вы не пишете юнит-тесты для вызывающего сервиса, требующие мокирования в изолированной среде, — **удалите интерфейс**.

Пишите прямой, прозрачный и конкретный код. Интерфейс должен появляться в кодовой базе **только тогда**, когда в системе физически возникает вторая реализация (например, `RedisUserRepository` в дополнение к `PostgresUserRepository`) или когда изоляция потребителя действительно необходима для тестов (причем сам интерфейс объявляется на стороне потребителя, как мы разбирали в лекции [[16. Почему маленькие интерфейсы лучше больших]]).

> [!tip] Собеседование
> **Вопрос:** Что в Go-сообществе подразумевают под правилом «Rule of Three» (Правило трех) при проектировании абстракций?
> **Ответ:** Это прагматичный инженерный принцип защиты от оверинжиниринга. Не создавайте абстракцию, интерфейс или общую функцию-хелпер, когда встречаете дублирование логики в первый или второй раз. Небольшое копирование кода на этом этапе обходится экосистеме дешевле, чем неверно угаданная абстракция (*«A little copying is better than a little dependency»*). И только тогда, когда логика дублируется в **третий раз**, у вас появляется достаточный контекст для понимания ее истинной природы. Лишь на третьем повторении оправдано выделение общего интерфейса или пакета. Преждевременная абстракция обходится во много раз дороже дублирования.

## Легкость удаления кода (Deletability)

Сложные, глубоко эшелонированные иерархии абстракций создают код, к которому страшно прикасаться. 

Представьте проект, где бизнес-логика размыта по каноническим паттернам Банды четырех: `Factory` порождает `Strategy`, которая внедряется в `Facade`, делегирующий задачи через `Adapter`. Спустя год требование бизнеса меняется. Разработчик открывает код и понимает: удалить эту логику целиком невозможно, не сломав добрый десяток связующих интерфейсов. Код покрывается флагами условий и медленно загнивает.

**Плоский код на Go обладает свойством легкой удаляемости (Deletability):**

```
HTTP Route -> Service Function -> SQL Query
   │                 │                 │
   └────── Легко прочитать (Local Reasoning)
   └────── Легко протестировать
   └────── Легко стереть целиком, когда фича устарела!
```

Если HTTP-хендлер напрямую обращается к конкретной функции `Service`, а та выполняет конкретный SQL-запрос через базу, разработчик охватывает взглядом весь путь исполнения от входа до выхода (принцип локального понимания кода — `Local Reasoning`). Когда функциональность выводится из эксплуатации, вы просто удаляете соответствующий маршрут, хендлер и запрос к базе. Никакие «абстрактные репозитории» или базовые классы при этом не ломаются, потому что их попросту нет.

## Шаблоны проектирования (Design Patterns) в Go

Поскольку Go намеренно избегает сложных иерархий наследования, классические паттерны ООП здесь либо трансформируются в элементарные конструкции, либо теряют всякий смысл.

* **Decorator (Декоратор):** В ООП требует возведения целой иерархии классов-оберток. В Go декоратор элегантно реализуется через функции высшего порядка (`Higher-Order Functions`). Самый яркий и каноничный пример — цепочки HTTP-мидлварей:
  ```go
  // Декоратор в одну функцию без громоздких классов и интерфейсов
  func WithLogging(next http.Handler) http.Handler {
      return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
          log.Println("Incoming request:", r.Method, r.URL.Path)
          next.ServeHTTP(w, r)
      })
  }
  ```
* **Strategy (Стратегия):** Вместо объявления интерфейса `IStrategy` и создания отдельных классов `StrategyA` и `StrategyB`, в Go в 90% случаев достаточно передать аргументом обычное **замыкание** (`Closure` / `func`-тип) с нужным алгоритмом.
* **Template Method (Шаблонный метод):** Категорически неприменим в Go, так как жестко завязан на механизм наследования и переопределения защищенных (`protected`) методов предка.

> [!warning] Ловушка / Gotcha: Чрезмерная генерация (Over-engineering)
> Разработчики, перешедшие в Go из мира Enterprise Java, нередко приносят с собой культуру тяжелых кодогенераторов многослойной архитектуры (когда на каждую доменную сущность генерируется пятерка файлов: интерфейс, реализация, мок, DTO и адаптер-маппер). Подобный оверинжиниринг убивает главное преимущество Go — прозрачность и скорость разработки. Идиоматичный Go опирается на лаконичный рукописный код. Кодогенерация в Go применяется точечно и только там, где она опирается на строгие формальные схемы: бинарные протоколы `protobuf/gRPC`, сверхбыстрые парсеры JSON (`easyjson`) или строго типизированные SQL-запросы (`sqlc`).

## Резюме: Инженерный баланс между гигиеной и скоростью

Отказ от многоуровневых слоев абстракции вовсе не означает, что весь проект следует писать гигантским полотном в единственном файле `main.go`. Это означает, что **каждый уровень абстракции обязан оправдывать свое существование в коде**:

1. Каждый неоправданный интерфейс (`interface{}`) — это усложнение навигации для человека и лишний косвенный переход через `itab` для процессора.
2. Каждый искусственный слой вызовов (`Facade`, `Proxy`, `Adapter`) — это дополнительная нагрузка на стек горутины и потенциальный триггер `runtime.morestack`.
3. Плоский, прямой и предсказуемый («скучный», boring) код читается и поддерживается в разы легче, чем мнимо «чистый» код, распыленный по двадцати абстрактным файлам.

Возникает закономерный вопрос: если мы не возводим архитектуру через слои классов и интерфейсов, как нам структурировать крупную систему? Как изолировать домены и запретить компонентам несанкционированно вмешиваться в чужое состояние?

В Go фундаментальным кирпичиком архитектуры, изоляции и управления зависимостями выступает **Пакет (Package)**. О том, как проектировать систему пакетов в соответствии с духом языка, мы подробно поговорим в следующей статье: [[22. Пакеты и структура проекта как часть философии Go]].
