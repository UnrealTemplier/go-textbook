Разработчики, приходящие из Python, PHP или Node.js, привыкли к быстрому интерактивному циклу: изменил строку кода -> нажал Enter -> моментально увидел результат в консоли. В классических компилируемых языках (C, C++, Rust) этот цикл традиционно ощутимо длиннее: изменил код -> запустил сборщик -> подождал компиляцию всех модулей и линковку -> запустил бинарник -> увидел результат.

Команда `go run` — это инженерный мост между этими мирами. Она создает полную иллюзию интерпретации, хотя под капотом происходит бескомпромиссная компиляция в машинный код. Скорость компилятора Go настолько высока, что запуск программы ощущается мгновенным. Однако понимание того, как устроена `go run`, позволяет использовать её эффективно и не попадать в коварные ловушки накладных расходов и утечек дискового пространства.

## Как работает `go run` (Under the hood)

Многие начинающие программисты ошибочно полагают, что `go run` — это специальный интерпретатор или виртуальная машина. Это опасное заблуждение. `go run` — это автоматизированный сценарий компиляции, линковки и запуска процесса.

Когда вы запускаете `go run main.go` или `go run .`, происходит следующее:

1.  **Анализ и компиляция**: Go тулчейн компилирует исходный код во временный бинарный файл. Это полноценная компиляция со всеми фазами оптимизации SSA.
2.  **Временное хранилище**: Бинарник создается во временной директории операционной системы (обычно `/tmp` в Linux/macOS или `%TEMP%` в Windows).
3.  **Исполнение**: Запускается дочерний процесс вашего скомпилированного бинарника (через системный вызов `exec` / `fork+exec`), при этом драйвер `go` транслирует в него потоки `stdin`, `stdout`, `stderr` и системные сигналы (`SIGINT`, `SIGTERM`).
4.  **Очистка**: После завершения работы программы (или если она была прервана сигналом), временный файл и каталог сборки автоматически удаляются.

## Разница между файлом и пакетом

Это классическая ошибка разработчиков любого уровня:

*   `go run main.go` — компилирует и запускает **только этот единственный файл**. Если в вашей директории рядом лежат другие файлы того же пакета `package main` с функциями, типами или переменными, которые вызывает `main.go`, вы получите ошибку компиляции `undefined`.
*   `go run .` — компилирует и запускает **весь пакет** в текущей директории со всеми его файлами. Это единственный правильный и идиоматичный способ запуска локальных программ.

Также можно запускать пакеты по полному пути импорта, если они находятся в `GOPATH` или объявлены в `go.mod`:
```bash
go run github.com/myuser/myproject/cmd/server
```

Начиная с Go 1.16, вы можете запускать даже удаленные утилиты без предварительного клонирования репозитория, указав версию модуля: `go run golang.org/x/tools/cmd/stringer@latest`.

## Аргументы и флаги

Частая путаница возникает при передаче флагов приложению. `go run` принимает свои собственные флаги (например, `-race`, `-work` или `-tags`) строго **до** имени файла/точки, а аргументы и флаги вашего собственного приложения — **после**.

```bash
# Неправильно: go run попытается интерпретировать -config как свой флаг и завершится с ошибкой
go run main.go -config=dev.yaml

# Правильно: флаги go run идут до точки/файла, аргументы приложения — после
go run . -config=dev.yaml
```

Если имя передаваемого аргумента совпадает с флагом самого Go, можно использовать стандартный разделитель `--`:
```bash
go run . -- -tags myvalue
```

## Инструментарий для разработки (Dev Tools)

`go run` отлично подходит для быстрых экспериментов, но для реальной разработки на бэкенде (HTTP-серверы, gRPC-сервисы) перезапускать сервер вручную после каждого изменения утомительно.

В экосистеме Go стандартом де-факто стали инструменты **Live Reload**. Они используют `go run` или `go build` под капотом, но автоматически перезапускают процесс при изменении файлов.

Самый популярный инструмент — **Air** (cosmtrek/air).

Пример `.air.toml` конфигурации:
```toml
[build]
  cmd = "go build -o ./tmp/main ."
  bin = "./tmp/main"
  include_ext = ["go", "tpl", "tmpl", "html"]
  exclude_dir = ["assets", "tmp", "vendor"]
```

Air следит за файловой системой (используя библиотеку `fsnotify`), при изменении `.go` файлов вызывает `go build`, убивает старый процесс и запускает новый.

> [!warning] Ловушка / Gotcha
> При использовании `go run` с флагом `-race` (детектор гонок данных) программа работает медленнее (иногда в 5-10 раз) и потребляет больше памяти.
> *   В продакшене `-race` обычно не используют из-за оверхеда.
> *   Но в разработке (`go run -race main.go` или в тестах `go test -race`) это обязательно для отлова ошибок конкурентности на ранних стадиях.

> [!tip] Вопрос с собеседования: Почему `go run` категорически запрещен в Production (например, в Docker)?
> **Вопрос:** Почему в `Dockerfile` для продакшна нельзя писать `CMD ["go", "run", "main.go"]`?
> **Ответ:** По четырем фундаментальным причинам:
> 1. **Размер образа:** Придется тащить в продакшн весь Go SDK (компилятор, линкер, заголовки, исходники) размером >500 МБ вместо микро-образа на базе `scratch` (15–20 МБ).
> 2. **Поверхность атак (Security):** Наличие компилятора в проде позволяет злоумышленнику скомпилировать любой эксплойт на лету при уязвимости RCE.
> 3. **Время холодного старта:** При перезапуске пода в Kubernetes время тратится на компиляцию, что недопустимо при высоких требованиях к SLA.
> 4. **Обработка сигналов (PID 1):** `go run` порождает дочерний процесс и не всегда корректно пробрасывает `SIGTERM` от Kubernetes, что ломает Graceful Shutdown.

## `go run` vs `go build`: Что выбрать?

| Характеристика | `go run` | `go build` |
| :--- | :--- | :--- |
| **Результат** | Запуск программы, артефакт удаляется. | Создание бинарника на диске. |
| **Скорость старта** | Чуть медленнее (нужно скомпилировать). | Мгновенный запуск готового файла. |
| **Использование** | Локальная разработка, скрипты, прототипирование. | CI/CD, продакшн, распространение. |
| **Отладка** | Удобно для быстрых проверок. | Требует сборки и запуска дебаггера (Delve). |

## Итог

1.  **`go run`** не является интерпретатором, он компилирует код во временный файл и запускает его.
2.  Всегда запускайте весь пакет (`go run .`), а не один файл (`go run main.go`), чтобы избежать проблем с необъявленными символами.
3.  Используйте флаг `-work`, чтобы понять, куда Go складывает временные файлы и изучить промежуточный бинарник.
4.  Для разработки серверов используйте инструменты Live Reload (Air), которые автоматизируют процесс перезапуска `go run`.
