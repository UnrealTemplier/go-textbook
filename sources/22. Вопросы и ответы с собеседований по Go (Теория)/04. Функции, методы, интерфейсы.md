## Что такое функция?

### Краткий ответ (30–60 секунд)
Функция в Go — самостоятельный именованный блок кода с сигнатурой, который можно многократно вызывать. Она принимает параметры, возвращает результаты и может быть объявлена на уровне пакета или внутри другой функции. Функции являются значениями первого класса, что открывает дорогу к функциональным паттернам.

### Развёрнутый ответ
Функция в Go определяется ключевым словом `func`, после которого идёт имя, список параметров в скобках и, опционально, список возвращаемых типов. Например:
```go
func Add(a, b int) int {
    return a + b
}
```
Go поддерживает множественный возврат значений (`func divmod(a, b int) (int, int)`), именованные результаты, которые работают как локальные переменные, инициализируемые нулями, и `defer`-функции для очистки ресурсов. Функции могут быть анонимными и присваиваться переменным или вызываться немедленно.

Отсутствие перегрузки функций компенсируется вариативными параметрами и разными именами. Парадигма «принимай интерфейсы, возвращай структуры» широко опирается именно на функции как точки входа модулей.

### Под капотом (internals)
На уровне runtime вызов функции сводится к манипуляциям со стеком: сохранение `BP`/`SP`, размещение аргументов, `CALL` и `RET`. С точки зрения компилятора Go функция компилируется в объектный код с определённым соглашением вызова (Go ABI). В Go 1.17+ внедрён register-based calling convention на amd64: параметры и возвращаемые значения передаются через регистры, а не только через стек, что ускоряет вызовы. Для escape analysis функция анализируется: если указатель на локальную переменную не покидает фрейм, переменная выделяется на стеке; иначе — в куче. Замыкания создаются как структуры с захваченными переменными, а анонимные функции не обязательно приводят к выделению на куче, если компилятор может их инлайнить.

### Типичные ошибки кандидатов
1. **Путаница с множественным возвратом и ошибками.** Новички игнорируют возвращаемую ошибку, нарушая контракт. Исправление: всегда проверять ошибку, линтеры типа `errcheck` помогут в этом.
2. **Использование именованных результатов как внезапного `return`.** Голый `return` ухудшает читаемость, особенно при вложенных функциях и `defer`. Исправление: применять явный `return` с перечислением значений, когда функция сложнее 3-5 строк.
3. **Передача больших структур по значению без надобности.** Копирование крупного аргумента при каждом вызове ведёт к нагрузке на стек и GC. Исправление: использовать указатели или, если значение не изменяется, обдумать, действительно ли структура настолько велика; зачастую компилятор копирует эффективно, но лучше профилировать.

### Возможные дополнительные вопросы интервьюера
*Можно ли объявить функцию внутри функции в Go?* Да, можно создать анонимную функцию и присвоить её переменной или сразу вызвать; именованную функцию внутри другой объявить нельзя, только анонимную.
*Что такое `init()`?* Специальная функция без параметров и возврата, автоматически вызываемая при инициализации пакета; редко рекомендуется к использованию, так как усложняет контроль порядка выполнения.
*Разница между `func f()` и `var f = func()`?* Первая — объявление функции, вторая — присваивание анонимной функции переменной; во втором случае `f` можно переопределять во время выполнения, но это не идиоматично.

## Что такое функции первого класса (first-class function)?

### Краткий ответ (30–60 секунд)
Функции первого класса — это функции, которые могут быть присвоены переменной, переданы в другие функции как аргументы, возвращены из функций и храниться в структурах данных. В Go функции являются полноценными значениями, что позволяет строить абстракции высшего порядка и паттерны типа функционального программирования.

### Развёрнутый ответ
В Go функции — это first-class citizens. Пример:
```go
var add = func(a, b int) int { return a + b }
result := add(1, 2) // 3
```
Можно объявить тип функции:
```go
type Transformer func(int) int
func apply(nums []int, t Transformer) []int { ... }
```
Функции могут быть не только аргументами, но и возвращаемыми значениями, создавая замыкания и паттерны типа Middleware. Go не поддерживает перегрузку, но first-class функции позволяют делать обёртки и адаптеры. Идиоматические примеры: обработчики HTTP (`http.HandlerFunc`), сортировка (`sort.Slice`), обход коллекций (`sql.Rows.Scan` с передачей замыкания). Такая гибкость — фундамент для композиции поведения без наследования.

### Под капотом (internals)
В runtime функция представлена указателем на код и, если это замыкание, контекстом захвата. При присвоении переменная-функция хранит два слова: указатель на инструкции и указатель на контекст (структуру захваченных переменных). Компилятор может инлайнить простые анонимные функции при соблюдении порогов инлайнинга. Когда анонимная функция используется как значение, создаётся `funcval` — структура, описывающая функцию. Для замыканий, захватывающих переменные, ссылающиеся на внешний фрейм, происходит escape в кучу этих переменных, чтобы продлить их время жизни за пределы фрейма.

### Типичные ошибки кандидатов
1. **Изменение захваченной переменной цикла в замыкании, созданном внутри `for`.** Если использовать `i` без копирования, все замыкания будут ссылаться на одну и ту же переменную. Исправление: создать локальную копию `i := i` (с Go 1.22 это поведение изменилось — переменная цикла теперь новая на каждой итерации, но всё равно важно понимание).
2. **Сравнение функций с `nil` без учёта закрытого контекста.** Переменная типа `func()` со значением `nil` не равна функции с `nil`-контекстом. Исправление: аккуратно проверять `!= nil` и понимать, что не-nil функция с захватом может вести себя неочевидно.
3. **Перерасход памяти из-за ненужного создания замыканий в горячих циклах.** Каждое создание анонимной функции с захватом может вызывать аллокацию. Исправление: использовать обычные функции или выносить состояние в поля структуры, если аллокация критична.

### Возможные дополнительные вопросы интервьюера
*Какие паттерны проектирования становятся возможны благодаря функциям первого класса?* Стратегия, команда, декоратор, цепочка обязанностей (middleware), часто реализуются без интерфейсов, только функциями-обёртками.
*Чем функция отличается от метода?* Метод привязан к типу через получатель, а функция свободна; это ортогональные концепции.

## Можно ли передавать функции как аргументы?

### Краткий ответ (30–60 секунд)
Да, в Go функции можно передавать как аргументы в другие функции, потому что они являются значениями первого класса. Это позволяет писать гибкие обобщённые алгоритмы: например, сортировку с пользовательским компаратором или обход дерева с callback-функцией.

### Развёрнутый ответ
Передача функций как аргументов — основа функционального программирования в Go. Сигнатура:
```go
func Filter(s []int, predicate func(int) bool) []int {
    var out []int
    for _, v := range s {
        if predicate(v) {
            out = append(out, v)
        }
    }
    return out
}
// использование:
even := Filter(numbers, func(n int) bool { return n%2 == 0 })
```
Можно определить тип функции, чтобы улучшить читаемость:
```go
type Predicate func(int) bool
func Filter(s []int, p Predicate) []int { ... }
```
Частые кейсы: `http.HandleFunc` принимает `func(http.ResponseWriter, *http.Request)`, `sort.Slice` принимает `func(i, j int) bool`. Благодаря передаче функций достигается слабая связанность: алгоритм не знает деталей проверки. При использовании дженериков можно записать обобщённую `Filter[T any](s []T, p func(T) bool) []T`, что ещё более универсально.

### Под капотом (internals)
Передача функции как аргумента компилируется в передачу двухмашинных слов (указатель на код + контекст). Компилятор видит, что `predicate` — это не-интерфейсное значение типа `func(int) bool`, поэтому вызов не проходит динамическую диспетчеризацию: он идёт напрямую через сохранённый указатель, если функция не замыкание. Для чистых функций (без контекста) указатель контекста `nil`, что позволяет оптимизировать вызовы и иногда инлайнить. Для замыканий контекст хранит захваченные переменные, которые, как правило, уже размещены в куче (результат escape analysis). На уровне ассемблера это обычный косвенный вызов `CALL (AX)` с подготовленным `DX`=контекст, если нужен.

### Типичные ошибки кандидатов
1. **Передача `nil` функции без проверки внутри.** Если передан нулевой аргумент-функция и нет проверки `if predicate != nil`, произойдёт паника. Исправление: всегда проверять перед вызовом или возвращать ошибку.
2. **Создание в цикле замыканий, передаваемых как аргументы, с захватом переменной цикла (до Go 1.22).** Это классическая ловушка: все замыкания разделяют одну переменную `i`, и к моменту их вызова она примет финальное значение. Исправление: либо копировать `i := i`, либо использовать `go func(v int) { ... }(i)`.
3. **Необоснованное использование указателей на функции.** Попытка передать `*func()` не нужна; значение функции само по себе уже включает ссылочную семантику.

### Возможные дополнительные вопросы интервьюера
*Как передать метод как аргумент?* Можно использовать `method value`: `obj.Method` создаёт функцию с зашитым получателем, которую можно передать напрямую.
*В чем разница между передачей функции и интерфейса с одним методом?* Функция проще, без накладных расходов интерфейсной таблицы, но не позволяет использовать полиморфизм с разными структурами, которые могут быть конвертированы в интерфейс.

## Что такое замыкание (closure)?

### Краткий ответ (30–60 секунд)
Замыкание в Go — это анонимная функция, которая захватывает переменные из своего лексического окружения и сохраняет к ним доступ даже после выхода из области видимости. Это позволяет создавать функции с состоянием, генераторы и паттерны типа каррирования.

### Развёрнутый ответ
Замыкание создаётся, когда анонимная функция ссылается на переменные, объявленные вне её тела. Например:
```go
func counter() func() int {
    count := 0
    return func() int {
        count++
        return count
    }
}
c := counter()
fmt.Println(c()) // 1
fmt.Println(c()) // 2
```
Здесь `count` покидает стековый фрейм `counter`, но остаётся жив, потому что захвачен замыканием. Замыкания используются для итераторов, конвейеров обработки, встраивания состояния в обработчики HTTP (middleware, кеширование). В Go замыкания захватывают переменные по ссылке, а не по значению, что приводит к классической ошибке с циклом `for`. Важно понимать, что каждое замыкание захватывает именно ту переменную, которая видна в момент создания, поэтому изменение переменной после создания влияет на замыкание.

### Под капотом (internals)
При компиляции замыкания создаётся неявная структура-контекст, содержащая указатели на все захваченные переменные. Функция внутри замыкания имеет сигнатуру, принимающую этот контекст неявно. Когда замыкание возвращается, переменные, захваченные по ссылке, должны пережить родительский кадр стека: escape analysis обнаруживает, что `count` переживает стековый кадр `counter`, и помечает её как heap-allocated. В runtime функция представлена `funcval` (указатель на код + указатель на контекст). Если переменная не выходит за пределы функции (например, замыкание только вызывается внутри, но не возвращается), она может остаться на стеке. Компилятор также может инлайнить простые замыкания, если они удовлетворяют критериям.

### Типичные ошибки кандидатов
1. **Захват переменной цикла до Go 1.22.** Все замыкания, созданные в цикле `for i, v := range slice`, разделяют одни и те же `i` и `v`. Решение: делать копию `i := i` или использовать параметр функции. В Go 1.22 поведение изменено, и на каждой итерации создаются новые переменные, но старый код всё ещё встречается.
2. **Утечка памяти из-за долгоживущего замыкания.** Замыкание захватывает указатель на большую структуру и живёт долго, удерживая её от сборки мусора. Исправление: скопировать необходимые поля в локальные переменные перед созданием замыкания, или профилировать.
3. **Случайное изменение захваченной переменной в нескольких горутинах.** Горутины, запущенные в цикле с замыканием, могут ссылаться на одну переменную и без синхронизации порождать гонку данных. Исправление: передавать копию аргументом.

### Возможные дополнительные вопросы интервьюера
*Как работают замыкания с `defer`?* `defer` захватывает переменные так же, но выполняется при выходе; нужно следить, что захваченные переменные могут измениться к моменту выполнения `defer`. Для корректности часто передают параметр по значению: `defer func(v int) { ... }(x)`.
*Можно ли сравнивать замыкания?* Замыкания не сравнимы в общем случае (кроме `nil`), попытка сравнения вызовет ошибку компиляции.

## Как замыкание влияет на escape analysis?

### Краткий ответ (30–60 секунд)
Замыкание, ссылающееся на локальную переменную, заставляет компилятор считать, что эта переменная может «убежать» за пределы стекового фрейма, поэтому она выделяется в куче. Это основная причина, по которой замыкания могут повышать нагрузку на сборщик мусора.

### Развёрнутый ответ
Escape analysis решает, может ли переменная быть выделена на стеке или должна уйти в heap. Когда анонимная функция захватывает переменную по ссылке и сама возвращается или сохраняется в структуру, переменная должна жить дольше, чем функция, в которой она объявлена, — она сбегает. Пример:
```go
func makeClosure() func() int {
    var x int
    return func() int { x++; return x }
}
```
Переменная `x` не может быть на стеке `makeClosure`, потому что к ней обращается возвращённое замыкание. Анализ побега помечает `&x` как escaping, и `x` размещается в куче. Напротив, если замыкание вызывается только внутри той же функции и не возвращается, анализатор может удержать переменные на стеке и даже заинлайнить всё тело.

Это напрямую влияет на производительность: куча увеличивает GC-нагрузку. В высоконагруженных системах необходимо осознанно контролировать escape: профилировать с `-gcflags="-m"`, избегать возврата замыканий в горячих путях, предпочитать передачу состояния через структуры.

### Под капотом (internals)
Escape analysis в Go выполняется на этапе компиляции пакета. Он строит граф потока указателей и определяет, достигает ли каждый объект кучи или только локального стека. Для замыканий создаётся структура захвата с полями-ссылками. Если адрес структуры или захваченной переменной «убегает», переменная помечается как heap-allocated. Команда `go build -gcflags='-m -m'` покажет точные причины escape. С Go 1.22 улучшен анализ для замыканий: в некоторых случаях, когда замыкание не возвращается, но сохраняется в локальную переменную и вызывается в пределах функции, может не происходить выделения в кучу; компилятор преобразует вызов в прямой, меняя сигнатуру.

### Типичные ошибки кандидатов
1. **Микрооптимизация без профилирования.** Кандидаты могут избегать любых замыканий, опасаясь аллокаций, но в большинстве приложений это не бутылочное горлышко. Исправление: использовать профайлер и флаги `-m`, принимать решения на основе данных.
2. **Незнание, что захват указателя тоже вызывает escape.** Если замыкание захватывает `*T`, даже если сам `T` не меняется, это тоже может вызвать heap-аллокацию для `T`. Исправление: по возможности захватывать значения или передавать их как параметры, чтобы анализ видел, что они не удерживаются.
3. **Использование замыкания в цикле для создания горутин без буфера и ожидание, что все переменные локальны.** Переменная цикла часто убегает в кучу, потому что горутина живёт дольше итерации. Исправление: передавать её как аргумент.

### Возможные дополнительные вопросы интервьюера
*Как проверить, где происходит аллокация?* Использовать `go build -gcflags="-m"`, бенчмаркинг с `testing.B` и `pprof`.
*Может ли замыкание быть инлайнировано?* Да, если оно мало и не возвращается как значение; тогда весь код встраивается, и escape не происходит.

## Что такое вариативные функции (variadic functions)?

### Краткий ответ (30–60 секунд)
Вариативная функция принимает переменное число аргументов определённого типа. В Go это достигается с помощью `...` перед типом последнего параметра. Внутри функции этот параметр доступен как срез. Классический пример — `fmt.Printf(format string, args ...interface{})`.

### Развёрнутый ответ
Синтаксис: `func sum(nums ...int) int`. При вызове `sum(1,2,3)` внутри `nums` — срез `[]int{1,2,3}`. Можно также передать срез, распаковав его с `...`: `numbers := []int{1,2,3}; sum(numbers...)`. Вариативные параметры часто используют с интерфейсами: `...interface{}` для форматирования. Ограничение: можно иметь только один вариативный параметр, и он должен быть последним. Go 1.18+ позволяет вариативные параметры в дженериках: `func Print[T any](items ...T)`. Также вариативные функции могут принимать только определённые типы, в отличие от `interface{}`.

### Под капотом (internals)
Компилятор при вызове вариативной функции выделяет срез на стеке (если аргументов мало и они не убегают) и копирует переданные значения в этот срез. Если количество аргументов велико или достигает порога (обычно около 12-16 элементов), срез размещается в куче. При передаче существующего среза с `...` проверяется, можно ли передать его базовый массив напрямую без копирования (если внутри функции не изменяется ёмкость). На уровне runtime используется обычная сигнатура со срезом, поэтому стоимость вызова сравнима с явной передачей среза.

### Типичные ошибки кандидатов
1. **Изменение вариативного параметра внутри функции и ожидание, что исходный срез не изменится.** Если передан срез с `...`, то внутри функции это тот же базовый массив. Мутации внутри отразятся на исходном срезе. Исправление: делать копию внутри при необходимости.
2. **Передача `nil` среза с `...`.** Допустимо: `sum(nil...)` эквивалентно `sum()` — `nil` срез не вызовет панику. Однако может сбить с толку.
3. **Использование `...interface{}` и передача конкретных типов без анализа производительности.** Это ведёт к боксингу значений, созданию `interface{}` обёрток и потенциальным аллокациям. Исправление: в горячих путях рассмотреть дженерики с нужным типом.

### Возможные дополнительные вопросы интервьюера
*Можно ли иметь несколько вариативных параметров?* Нет, только один и последний.
*Чем `...interface{}` отличается от `...any`?* Ничем, `any` — алиас для `interface{}`.

## Что такое метод (method)?

### Краткий ответ (30–60 секунд)
Метод — это функция, привязанная к конкретному типу (получателю) и предоставляющая поведение этого типа. Методы определяются вне тела структуры, что позволяет добавлять поведение к любому типу, определённому в том же пакете.

### Развёрнутый ответ
Определение метода:
```go
type Counter struct { val int }
func (c Counter) Value() int { return c.val }
func (c *Counter) Increment() { c.val++ }
```
Метод задаёт получатель (receiver) — value или pointer. Его можно вызывать как на значении, так и на указателе, если метод определён для value-получателя (Go автоматически разыменовывает или берёт адрес). Методы делают возможным реализацию интерфейсов: тип автоматически удовлетворяет интерфейсу, если его методы совпадают с сигнатурами интерфейса. Методы можно определять только для типов, объявленных в том же пакете, что и метод. Таким образом достигается инкапсуляция: внешний пакет не может «навесить» методы на ваш тип, но может реализовать ваш интерфейс для своего типа.

### Под капотом (internals)
На уровне компиляции метод — это обычная функция, первым параметром которой является получатель. Сигнатура превращается в `func (mov *Counter) Increment()` -> `func Increment(c *Counter)`. Компилятор поддерживает таблицы методов (method sets) для каждого типа. Для интерфейсов создаётся itab (interface table), связывающая тип и его методы. Вызов метода через интерфейс проходит динамическую диспетчеризацию. Если метод определён на значении и вызывается на указателе, компилятор автоматически разыменовывает; если на указателе и вызывается на значении, то значение должно быть адресуемым, чтобы взять адрес (для временных значений это невозможно, например, `MyType{}.PointerMethod()` не скомпилируется).

### Типичные ошибки кандидатов
1. **Определение метода на не локальном типе.** Попытка `func (t otherpackage.Type) Method()` вызовет ошибку компиляции. Исправление: создать свой тип-обёртку.
2. **Путаница с адресуемостью.** Вызов pointer-метода на неадресуемом временном значении (`GetStruct().Mutate()`) не скомпилируется. Исправление: сохранить в переменную или возвращать указатель из функции.
3. **Неверный выбор value/pointer receiver для удовлетворения интерфейса.** Если метод определён на указателе, а переменная интерфейса хранит значение, удовлетворения интерфейса не будет. Нужно передавать указатель или менять получатель.

### Возможные дополнительные вопросы интервьюера
*Можно ли объявить метод для встроенного типа (int)?* Нет, только для типов, определённых в текущем пакете. `type MyInt int` — да.
*Метод с nil-получателем: валидно ли это?* Да, при pointer receiver метод может быть вызван на nil, это идиоматично для некоторых типов (например, `(*LinkedList) Len()`).

## Чем метод отличается от функции?

### Краткий ответ (30–60 секунд)
Метод привязан к типу через получатель (receiver) и вызывается как `value.Method(params)`, тогда как функция независима и вызывается напрямую по имени. Методы определяют поведение типа и позволяют реализовывать интерфейсы; функции же — строительные блоки без такой привязки.

### Развёрнутый ответ
Функция: `func Add(a, b int) int`. Метод: `func (c *Counter) Add(delta int) int`. Вызов метода: `c.Add(5)`. Оба являются вызываемыми блоками, но разница в области видимости и назначении. Метод получает доступ к полям получателя и может изменять его (если pointer receiver). Методы могут быть экспортированы/неэкспортированы. Функции первого класса можно передавать, как и method values: `var f func(int) int = c.Add` (значение метода). Method expression: `Counter.Add` — это функция, принимающая получатель как первый аргумент: `Counter.Add(counter, delta)`. Это показывает, что метод — синтаксический сахар над функцией, которая получает контекст.

### Под капотом (internals)
В компиляторе Go метод транслируется в обычную функцию с дополнительным первым параметром, соответствующим receiver. Имя метода включает пакет и тип. Во время выполнения используется таблица методов (method set). This table позволяет связывать вызовы через интерфейсы (itab). Для method value компилятор генерирует специальную обёртку, которая встраивает конкретный получатель в замыкание. Method expression порождает функцию, просто ожидающую receiver первым аргументом. В обоих случаях на уровне ассемблерного кода всё сводится к вызову `CALL` с правильной подготовкой аргументов.

### Типичные ошибки кандидатов
1. **Создание циклических вызовов через method value без осознания, что получатель фиксируется.** Если `c.Add` используется как коллбек, и в процессе изменяется `c`, это работает ожидаемо; но некоторые полагают, что получатель «пересчитывается» при каждом вызове — нет, он фиксирован.
2. **Путаница при рефлексии:** попытка вызвать метод через reflect с передачей receiver как обычного аргумента может привести к ошибкам, если не учитывать метод expression семантику.
3. **Игнорирование разницы в получении адреса:** метод expression `MyType.Method` требует в качестве первого аргумента `MyType` или `*MyType` в зависимости от определения получателя.

### Возможные дополнительные вопросы интервьюера
*Можно ли переопределить метод для типа-алиаса?* Тип-алиас `type A = B` разделяет те же методы; переопределить нельзя.
*Зачем нужен method expression?* Полезен, когда нужно передать метод нескольких разных получателей одной сигнатуре, например, для таблиц коллбеков или функций сортировки.

## Что такое получатель (receiver)?

### Краткий ответ (30–60 секунд)
Получатель (receiver) — это специальный параметр метода, который связывает метод с конкретным типом. Он может быть значением (value receiver) или указателем (pointer receiver) и определяет, будет ли метод работать с копией или с оригиналом.

### Развёрнутый ответ
Receiver записывается перед именем метода: `func (r *Reader) Read(p []byte) (int, error)`. Имя получателя обычно короткое (1-2 буквы), отражает тип. Value receiver получает копию значения, изменения не отражаются на оригинале. Pointer receiver получает указатель, изменения видны снаружи. Можно смешивать value и pointer методы для одного типа, но для удовлетворения интерфейса важны наборы методов: методы value receiver доступны и для `T`, и для `*T`; методы pointer receiver доступны только для `*T`. Receiver позволяет эмулировать ООП: методы как «послания» объекту. Кроме структур, получателем может быть любой определенный в пакете тип: `type Path []string`, `func (p Path) Join() string`.

### Под капотом (internals)
Как уже говорилось, на уровне функций receiver — это первый параметр. Компилятор автоматически генерирует обёртки для вызова методов через интерфейсы: если у типа `T` есть метод `M` на value receiver, а интерфейс требует `M`, то для значения `T` используется прямой вызов; для `*T` компилятор создаёт обёртку, которая разыменовывает указатель и вызывает метод. Если метод определён на указателе, для `*T` всё просто, а для `T` требуется адресуемость, иначе компилятор отказывается генерировать обёртку для интерфейса (невозможно удовлетворить). Таблицы интерфейсов (`itab`) хранят указатели на фактические реализации методов.

### Типичные ошибки кандидатов
1. **Несоответствие receiver при реализации интерфейса.** Часто кандидат реализует метод с pointer receiver, а потом пытается присвоить значение (не указатель) переменной интерфейса, получая ошибку. Решение: использовать конструктор, возвращающий указатель.
2. **Мутация в value receiver.** Ожидание, что метод изменит структуру, а изменений нет. Исправление: использовать pointer receiver.
3. **Игнорирование nil receiver.** Для pointer receiver допустимо вызвать метод на nil-значении и обрабатывать это внутри, если это осмысленно (например, `func (l *List) Length()`), иначе паника. Не все кандидаты предусматривают защиту.

### Возможные дополнительные вопросы интервьюера
*Можно ли определить метод с получателем-интерфейсом?* Нет, нельзя. Получатель должен быть конкретным типом или указателем на конкретный тип, но не интерфейсом.
*Что такое nil-безопасный ресивер?* Это когда метод обрабатывает `nil` как валидное состояние, возвращая разумное значение или ошибку.

## Value receiver vs pointer receiver?

### Краткий ответ (30–60 секунд)
Value receiver работает с копией значения, безопасен для иммутабельности, но не может изменять оригинал и копирует структуру. Pointer receiver оперирует оригиналом, позволяет модификации, избегает копирования больших структур, но требует внимания к nil и гонкам данных. Выбор зависит от семантики и размера типа.

### Развёрнутый ответ
Сравнение:
| Критерий | Value receiver | Pointer receiver |
|----------|---------------|------------------|
| Изменяемость | Нельзя изменить оригинал | Можно |
| Копирование данных | Копируется | Копируется только адрес (8 байт) |
| Согласованность | Всегда безопасен для конкурентного доступа (копия) | Требует синхронизации |
| Nil-безопасность | Никогда не nil (кроме указательных полей) | Может быть nil |
| Удовлетворение интерфейсов | Для `T` и `*T` доступны методы с v-receiver | Для `*T` доступны p-receiver методы, для `T` — нет |
| Производительность | Дорого для больших структур | Дешево |
| Идиоматика | Для малых неизменяемых типов (время, точка) | Для большинства типов, особенно с состоянием |

Правило: если метод меняет состояние или структура велика, используйте pointer receiver. Если тип — маленькая value-семантика (например, `time.Time`), и методы не мутируют, value receiver предпочтительнее. Смешивать можно, но для внутреннего единообразия часто все методы делают с pointer.

### Под капотом (internals)
Компилятор решает вопрос адресуемости. Вызов value-метода на значении копирует структуру (может быть оптимизировано, если адрес не берётся и структура не убегает). При pointer receiver на значении компилятор берёт адрес значения (если оно адресуемо) и вызывает метод. Создание интерфейса сvalue-receiver-методом на значении `T` создаёт копию `T` внутри интерфейса; при присваивании указателя `*T` интерфейс хранит указатель и использует обёртку для удовлетворения value-метода. В случае pointer-receiver-методов значение `T` не удовлетворяет интерфейсу, потому that компилятор не может автоматически взять адрес, если значение не адресуемо.

### Типичные ошибки кандидатов
1. **Выбор pointer receiver для маленьких неизменяемых типов «чтобы быстрее».** Преждевременная оптимизация без профилирования; копирование 8-16 байт часто быстрее, чем разыменование указателя + нагрузка на GC.
2. **Смешивание receiver-типов внутри одного типа без понимания последствий для интерфейсов.** Это порождает неочевидное поведение: часть методов доступна только через указатель. Лучше унифицировать, если тип используется с интерфейсами.
3. **Забывают, что value receiver с изменяемыми полями-указателями может изменить данные через указатель.** Кандидат считает, что value receiver гарантирует иммутабельность, а мутирует shared структуру. Исправление: явно документировать.

### Возможные дополнительные вопросы интервьюера
*Можно ли mix value и pointer receivers для одного интерфейса?* Да, тип может удовлетворить интерфейс, если все методы есть в его наборе; набор методов зависит от того, как переменная передаётся в интерфейс.
*Как выбрать между value и pointer receiver для time.Time?* `time.Time` использует value receiver, так как это неизменяемая структура.

## Когда использовать pointer receiver?

### Краткий ответ (30–60 секунд)
Pointer receiver нужно использовать, когда метод должен мутировать состояние получателя, когда структура крупная и копирование дорого, для поддержания единообразия в наборе методов (если хотя бы один метод требует указатель) или когда тип представляет сущность с идентичностью (например, семафор, файловый дескриптор), которую нельзя копировать.

### Развёрнутый ответ
Критерии:
1. **Мутация.** Необходимо изменить поля получателя, чтобы изменения были видны после вызова метода.
2. **Производительность.** Если структура большая (ориентир > 64 байт) и вызывается часто в горячем пути, избегаем дорогостоящего копирования.
3. **Единообразие.** Если у типа уже есть pointer-receiver методы, рекомендуется все методы делать pointer, чтобы избежать путаницы с набором методов и интерфейсами.
4. **Защита от копирования.** Некоторые типы инкапсулируют ресурсы (мьютексы, файловые дескрипторы), неправильное копирование которых ведёт к ошибкам. В этом случае стоит сделать pointer receiver и, возможно, запретить копирование с помощью `sync.Mutex` (встроенного) или `noCopy`.
5. **Семантика разделяемой сущности.** Если экземпляры должны быть уникальными, pointer receiver подчёркивает это.

Не используем pointer receiver для маленьких value-типов только ради производительности, не профилируя.

### Под капотом (internals)
Pointer receiver передаёт адрес структуры (8 байт на 64-битных системах). При вызове метода компилятор проверяет адресуемость. Если значение хранится в map, оно не адресуемо, поэтому вызвать pointer-метод на map value напрямую нельзя (нужно присвоить в переменную). Для срезов элементы адресуемы, можно вызвать метод на `&s[i]`. Под капотом интерфейс, хранящий указатель на `T`, будет иметь в `itab` указатели на фактические методы. Если все методы pointer, то `T` не удовлетворяет интерфейсу — только `*T`.

### Типичные ошибки кандидатов
1. **Игнорирование nil-получателя.** При pointer receiver `r` может быть nil; вызов `r.Method()` без проверки приведёт к панике при попытке доступа к полям. Идиоматически следует либо документировать допустимость nil, либо паниковать с осмысленным сообщением.
2. **Использование pointer receiver только потому что «так делают».** Необдуманное использование увеличивает нагрузку на GC (больше указателей — больше работы для сборщика). Нужно аргументировать.
3. **Возврат значения из конструктора, а не указателя, когда методы требуют pointer receiver для интерфейса.** Тогда код не скомпилируется при попытке присвоить интерфейс. Нужно возвращать указатель.

### Возможные дополнительные вопросы интервьюера
*Можно ли вызвать pointer-метод на неадресуемом значении?* Нет, например, `MyStruct{}.Mutate()` или `map[key].Mutate()` не скомпилируется. Нужно использовать переменную.
*Что будет, если у типа есть и value и pointer методы?* Набор методов для `T` включает только value receivers; для `*T` — оба.

## Что такое интерфейс (interface)?

### Краткий ответ (30–60 секунд)
Интерфейс в Go — это абстрактный тип, определяющий набор методов, которые должен реализовать конкретный тип. Он не накладывает никаких требований на структуру данных, только на поведение. Реализация интерфейса происходит неявно, что способствует слабой связанности и гибкости.

### Развёрнутый ответ
Синтаксис:
```go
type Reader interface {
    Read(p []byte) (n int, err error)
}
```
Любой тип, имеющий метод `Read(p []byte) (int, error)`, автоматически реализует `Reader`. Это фундаментальный принцип полиморфизма в Go. Интерфейсная переменная хранит пару (динамический тип, динамическое значение). Пустой интерфейс `interface{}` (или `any`) не требует методов и может содержать значение любого типа. Интерфейсы позволяют писать код, который опирается на поведение, а не на конкретные типы, и являются основой для инверсии зависимостей, тестирования с моками и композиции.

### Под капотом (internals)
Интерфейсное значение представлено структурой `iface` (для ненулевых интерфейсов) или `eface` (для пустого интерфейса). `iface` содержит два указателя: `tab *itab` и `data unsafe.Pointer`. `itab` хранит метаданные: тип, интерфейс, хеш-таблицу для утверждений типа, указатели на реализованные методы. При присваивании значения интерфейсу компилятор генерирует вызовы runtime для создания `itab` и копирования данных (или обёртки для мелких значений). Динамическая диспетчеризация при вызове метода: загрузка указателя на метод из `itab`, затем `CALL`. Для пустых интерфейсов `eface` хранит `_type` и `data`. Преобразование из не-интерфейса в интерфейс часто вызывает аллокацию, если значение не помещается в слово (боксинг). Компилятор применяет escape-анализ.

### Типичные ошибки кандидатов
1. **Определение интерфейса на стороне библиотеки (пакета), который реализует поведение.** Это создаёт излишние зависимости. Правило: «принимайте интерфейсы там, где они используются» — пакет-потребитель определяет нужный интерфейс.
2. **Интерфейс с большим числом методов, который делает код жестким.** Предпочитайте маленькие интерфейсы (1–3 метода).
3. **Неверная проверка nil-интерфейса.** Интерфейс может быть nil, но не nil, если его динамический тип не nil, а значение nil. Это частая причина багов.

### Возможные дополнительные вопросы интервьюера
*Можно ли встроить интерфейс в другой интерфейс?* Да, это композиция интерфейсов: `type ReadWriter interface { Reader; Writer }`.
*Что такое “Interface segregation principle” в Go?* Из SOLID, принцип разделения интерфейса — большие интерфейсы разбиваются на мелкие, каждый клиент зависит от нужного ему набора методов.

## Как реализуются интерфейсы в Go (неявная реализация)?

### Краткий ответ (30–60 секунд)
Go использует структурную типизацию: тип автоматически реализует интерфейс, если он обладает всеми методами, описанными в интерфейсе, без необходимости явного объявления (`implements`). Компилятор проверяет соответствие на этапе компиляции при присваивании переменной интерфейсного типа.

### Развёрнутый ответ
Пример:
```go
type Speaker interface { Speak() string }
type Dog struct{}
func (d Dog) Speak() string { return "Woof" }
var s Speaker = Dog{} // неявно реализует
```
Никакого ключевого слова `implements` нет. Это даёт огромную гибкость: можно создать интерфейс позже, когда появляется несколько реализаций, и старый код, не знавший об интерфейсе, автоматически подходит. Обратная сторона — интерфейс документально не «привязан» к типам, что требует чёткой спецификации в комментариях. Неявная реализация упрощает тестирование: легко подменить реальный тип моком, реализующим тот же интерфейс. Структурная типизация позволяет писать библиотеки, не зависящие от пакетов с реализациями.

### Под капотом (internals)
На уровне компиляции проверка соответствия интерфейсу выполняется при присваивании. Компилятор сравнивает набор методов типа (или указателя на тип) с требуемыми методами интерфейса, используя сигнатуры (имя, параметры, возвращаемые значения). При успехе генерируется `itab` — таблица, связывающая методы интерфейса с фактическими функциями. `itab` создаётся во время выполнения при первом присваивании конкретному типу, используя алгоритм поиска или генерации. `itab` кэшируется. Это обеспечивает высокую производительность последующих вызовов. Реализация через неявное соответствие означает, что компилятор не требует наличия импорта пакета с интерфейсом для того, чтобы тип его реализовал; при компиляции фактического использования интерфейса стороны должны быть скомпонованы.

### Типичные ошибки кандидатов
1. **Путаница с методами pointer receiver.** Думают, что `Dog` реализует `Speaker`, если метод на указателе, а присваивают значение `Dog{}` — ошибка. Исправление: использовать `&Dog{}`.
2. **Несовпадение сигнатур из-за имён параметров или разных пакетов.** В Go типы сравниваются по полному пути; `myio.Reader` и `io.Reader` — разные интерфейсы, даже если сигнатуры идентичны, потому что это разные типы. Часто кандидаты пытаются передать `myio.Reader` туда, где нужен `io.Reader`, ожидая автоматического приведения. Необходимо явное преобразование или общая зависимость.
3. **Создание интерфейса с методом, сигнатура которого почти совпадает, но отличается (например, отсутствие ошибок).** Кандидат считает, что реализован интерфейс, а нет. Лучше использовать линтеры и явные проверки `var _ MyInterface = (*MyType)(nil)`. Это компилируемое объявление гарантирует соответствие.

### Возможные дополнительные вопросы интервьюера
*Как убедиться на этапе компиляции, что тип реализует интерфейс?* Использовать идиому `var _ io.Reader = (*MyReader)(nil)`. Это глобальная проверка без выделения памяти.
*Можно ли реализовать интерфейс для типа из другого пакета без его изменения?* Только определив свой тип на основе него или через делегирование.

## Что такое неявная реализация (implicit implementation)?

### Краткий ответ (30–60 секунд)
Это механизм, при котором тип автоматически становится реализацией интерфейса, если его method set включает все методы интерфейса, без явного указания отношения. В Go это называется структурной типизацией и является ключевым отличием от языков с номинативной типизацией (Java, C#).

### Развёрнутый ответ
Неявная реализация освобождает от необходимости объявлять «класс реализует интерфейс». Это упрощает эволюцию кода: можно определить интерфейс позже, чем типы, и уже существующие типы автоматически подходят. Статическая проверка всё равно существует: при попытке передать тип, не реализующий интерфейс, в функцию, ожидающую этот интерфейс, компилятор выдаст ошибку. Таким образом, безопасность сохраняется, но уровень связанности снижается.

Пример: пакет `io` определяет `Reader`, а пакет `os` предоставляет `os.File`, который её реализует, не импортируя `io` (хотя фактически импортирует из-за зависимостей, но концептуально не требуется явного указания). Неявная реализация позволяет легко создавать адаптеры и декораторы.

### Под капотом (internals)
Аналогично предыдущему пункту. Важно отметить, что таблица `itab` содержит информацию о том, что конкретный тип реализует данный интерфейс; она генерируется динамически, но может быть встроена компилятором при оптимизации. Неявность означает, что в скомпилированном коде нет специального «сертификата» реализации; просто в нужных местах есть проверка и создание `itab`.

### Типичные ошибки кандидатов
1. **Предположение, что неявная реализация означает отсутствие статической проверки.** Ошибка: кандидат думает, что ошибки не будет до времени выполнения. Исправление: проверка всегда во время компиляции при использовании.
2. **Игнорирование того, что методы с одинаковыми именами, но разными пакетами, не дают интерфейса.** Подразумевается осведомлённость о типах.
3. **Попытка реализовать интерфейс с несовместимыми методами через неявное приведение несуществующего.** Например, думать, что `string` реализует `io.Reader`? Нет.

### Возможные дополнительные вопросы интервьюера
*Чем структурная типизация отличается от номинативной?* В номинативной нужно явно указать `class X implements Y`, в структурной достаточно совпадения сигнатур.
*Можно ли реализовать интерфейс без импорта пакета, где он определён?* Теоретически, если код ссылается на интерфейс, пакет должен быть импортирован, но тип сам может быть определён без знания об интерфейсе, он не обязан импортировать пакет с интерфейсом (однако его пакет может его не импортировать, но при связывании в итоговой программе обе стороны слинкованы).

## Что такое пустой интерфейс ( `interface{}` )?

### Краткий ответ (30–60 секунд)
Пустой интерфейс `interface{}` (ныне синоним `any`) не требует ни одного метода. Поэтому ему может быть присвоено значение любого типа. Он выступает аналогом `Object` в Java, но с сохранением типобезопасности через утверждения типа или type switch.

### Развёрнутый ответ
Объявление: `var v interface{}`. Можно присвоить `v = 42`, `v = "hello"`, `v = MyStruct{}`. Чтобы извлечь конкретное значение, нужно использовать утверждение типа: `s, ok := v.(string)`. Безопасный pattern: type switch. Пустой интерфейс широко применяется в функциях форматирования, контейнерах (до дженериков), десериализации JSON (`interface{}` для произвольной структуры). После появления дженериков в Go 1.18 многие сценарии заменяются параметризованными типами, но `interface{}` остаётся для работы с неизвестным типом на этапе компиляции (например, `reflect`). `any` — просто алиас, улучшающий читаемость.

### Под капотом (internals)
Пустой интерфейс реализован структурой `eface`:
```go
type eface struct {
    _type *_type   // указатель на метаданные типа
    data  unsafe.Pointer
}
```
При присваивании значения конкретного типа в `interface{}` компилятор генерирует код для упаковки: значение размещается в куче или копируется в word, если его размер <= размер указателя. Метаданные типа (`_type`) хранят информацию для reflect и GC. Динамическая диспетчеризация не требуется, так как нет методов. Преобразование обратно требует проверки, реализованной через сравнение `_type` или через кэшированный хеш.

### Типичные ошибки кандидатов
1. **Злоупотребление `interface{}` при наличии дженериков.** Это возвращает нас к runtime-проверкам и снижению безопасности. Исправление: использовать generics для контейнеров с сохранением типа.
2. **Неправильное извлечение:** `i.(string)` без проверки `ok` ведёт к панике, если тип не совпадает. Всегда использовать двухзначную форму.
3. **Неожиданное поведение при `nil`:** пустой интерфейс, хранящий `nil` конкретного типа, не равен `nil`. Это сложный момент.

### Возможные дополнительные вопросы интервьюера
*Как `interface{}` используется в `fmt.Printf`?* Параметры `...interface{}` позволяют принимать любые типы, внутри используется отражение для форматирования.
*Что быстрее: `interface{}` с последующим type switch или дженерики?* Дженерики избегают boxing/unboxing и работают на этапе компиляции, обычно быстрее и предпочтительнее для однотипных операций.

## Чем `interface{}` отличается от `any`?

### Краткий ответ (30–60 секунд)
`any` — это встроенный алиас для `interface{}`, появившийся в Go 1.18. С точки зрения семантики и runtime они идентичны. Разница исключительно синтаксическая: `any` улучшает читаемость кода, делая намерения яснее, особенно при использовании дженериков.

### Развёрнутый ответ
В Go 1.18 ввели `any` как предопределённый идентификатор в `builtin` пакете. Можно писать `func Print(args ...any)` вместо `...interface{}`. Это более лаконично и современно. Технически `any` является просто `interface{}`, и они полностью взаимозаменяемы. Использование `any` в дженериках: `func Map[T any](s []T, f func(T) T) []T` — здесь `any` обозначает ограничение "любой тип". Без дженериков `interface{}` также означает любой тип. В старом коде преобладает `interface{}`, в новом рекомендуется `any` как более выразительный.

### Под капотом (internals)
Никакой разницы в runtime. Тип `any` при компиляции разворачивается в `interface{}`. В рефлексии `reflect.TypeOf` покажет `interface {}`. В бинарном коде вызовы абсолютно одинаковы.

### Типичные ошибки кандидатов
1. **Считать, что `any` — это новый тип, отличный от `interface{}`.** Это не так, путаница может привести к использованию неверного синтаксиса, но в общем безвредна; главное — не пытаться определять методы на `any` и т.п.
2. **Полагать, что `any` решает проблему nil-интерфейса.** Нет, `any` точно так же хранит динамический тип. Ошибка остаётся.
3. **Использовать `any` в местах, где нужен именно пустой интерфейс с дополнительной семантикой.** Всегда корректно, но иногда в документировании лучше писать `interface{}` в старом коде для консистентности.

### Возможные дополнительные вопросы интервьюера
*Можно ли использовать `any` как ограничение типа?* Да, `[T any]` эквивалентно `[T interface{}]`. Это стандартное ограничение.
*Что будет, если объявить свой тип `any`?* Нельзя, это зарезервированный идентификатор (предопределённый), компилятор выдаст ошибку.

## Что такое утверждение типа (type assertion)?

### Краткий ответ (30–60 секунд)
Утверждение типа — это операция `x.(T)`, которая проверяет, что конкретный динамический тип интерфейсного значения `x` совместим с `T`, и возвращает значение этого типа. Если проверка не проходит и не используется вторая переменная `ok`, генерируется паника.

### Развёрнутый ответ
Синтаксис: `v := x.(T)` — паническая форма; `v, ok := x.(T)` — безопасная. `x` должен быть интерфейсного типа. `T` — либо конкретный тип, либо интерфейс. Если `T` — конкретный тип, утверждение извлекает значение этого типа. Если `T` — интерфейс, проверяется, реализует ли динамический тип `x` этот интерфейс, и возвращается новое интерфейсное значение того же типа. Пример:
```go
var i interface{} = "hello"
s := i.(string)       // "hello"
s, ok := i.(string)   // ok true
n, ok := i.(int)      // ok false, n = 0
```
Утверждение типа используется для безопасного извлечения значений из пустых интерфейсов, для приведения к более конкретному интерфейсу (например, из `io.Reader` в `io.ReadCloser`). В дженериках утверждение типа пока работает с интерфейсами; для параметров типа (`T`) используется `switch` с ограничениями.

### Под капотом (internals)
Операция type assertion реализована функциями runtime, например `assertE2I` (для интерфейс -> интерфейс), `assertI2I` и т.д. Во время выполнения сравнивается `itab` или `_type` хранящегося значения с требуемым типом. Используется кэширование `itab` для быстрых проверок. Если утверждение к интерфейсу не удаётся, возвращается nil-интерфейс (во втором значении false). Если утверждение к конкретному типу не удаётся, при одноаргументной форме паника с сообщением. Компилятор может генерировать специальные проверки, избегая runtime-вызовов.

### Типичные ошибки кандидатов
1. **Использование панической формы без явной уверенности в типе.** Особенно при работе с JSON произвольной структуры. Исправление: всегда использовать `v, ok := x.(T)` и обрабатывать `ok`.
2. **Попытка сделать type assertion на не-интерфейсном типе.** `var x int; x.(string)` — ошибка компиляции. Можно только на интерфейсах.
3. **Путаница с утверждением на интерфейс, когда динамический тип nil.** Даже если динамическое значение nil, утверждение на конкретный тип провалится, если тип не совпадает. Утверждение на интерфейс может создать nil-интерфейс с ненулевым типом — нужно помнить про ловушки сравнения с nil.

### Возможные дополнительные вопросы интервьюера
*Как утверждение типа работает с дженериками?* Параметр типа `T` не является интерфейсом времени выполнения, поэтому `x.(T)` не компилируется, нужно использовать преобразование `T(x)` после проверки типа.
*Можно ли использовать type assertion для приведения `error` к более конкретному типу?* Да, часто: `if e, ok := err.(*os.PathError); ok { ... }`.

## Что такое переключатель типа (type switch)?

### Краткий ответ (30–60 секунд)
Type switch — это конструкция `switch v := x.(type)`, которая сопоставляет динамический тип интерфейсного значения с несколькими case-ветками по типам. Это позволяет выполнять разное поведение в зависимости от конкретного типа, избегая цепочек `if-else` с утверждениями типа.

### Развёрнутый ответ
Синтаксис:
```go
switch v := x.(type) {
case int:
    fmt.Println("integer:", v)
case string:
    fmt.Println("string:", v)
default:
    fmt.Printf("unknown type %T\n", v)
}
```
Здесь `v` в каждом case имеет соответствующий тип. Можно также использовать `case int, int64:` и т.п. Type switch поддерживает утверждения на интерфейсы: `case io.Reader:`, тогда `v` будет `io.Reader`. `nil` case: `case nil:` сработает, если `x` — nil-интерфейс. Type switch широко применяется при разборе JSON неизвестной структуры, реализации `fmt.Stringer` и обработке ошибок. Это более читаемая альтернатива каскаду type assertion.

### Под капотом (internals)
Компилятор преобразует type switch в серию сравнений `itab` или `_type`. Используется временная переменная, хранящая извлечённое значение. В runtime получается таблица переходов в зависимости от типа. Для нескольких типов в case генерируются проверки с использованием хеша типов. Это эффективно, поскольку проверки оптимизированы и кэшируются. Для пустого интерфейса — сравнение `_type`.

### Типичные ошибки кандидатов
1. **Использование type switch без переменной: `switch x.(type)`** — тогда внутри case нет доступа к значению с уточнённым типом; приходится снова применять утверждение. Лучше присваивать переменную.
2. **Забывают добавить `case nil`.** Если интерфейс nil, ни один конкретный case не сработает, уйдёт в default. Это может привести к обработке nil как неизвестного типа. Исправление: предусмотреть `case nil`.
3. **Смешение type switch с fallthrough.** Нельзя использовать `fallthrough` внутри type switch. Нужно дублировать код или вынести.

### Возможные дополнительные вопросы интервьюера
*Можно ли использовать type switch с параметром типа дженерика?* Нет, параметр типа не интерфейс времени выполнения; switch по ограничениям недоступен. Вместо этого используют switch с конкретным типом после присвоения к `interface{}`.
*Какая разница между `switch x.(type)` и цепочкой `if x.(T); ok`?* Type switch компактнее и позволяет обрабатывать несколько типов, но для единичной проверки часто удобнее `if`.

## Что такое динамический тип (dynamic type)?

### Краткий ответ (30–60 секунд)
Динамический тип — это конкретный тип значения, которое хранится в интерфейсной переменной в данный момент. Интерфейсная переменная, имея статический тип интерфейса, обладает динамическим типом, который может изменяться во время выполнения при присваивании новых значений.

### Развёрнутый ответ
Переменная `var r io.Reader` имеет статический тип `io.Reader`. Когда мы присваиваем `r = os.Stdin`, её динамический тип становится `*os.File`. Динамический тип определяет, какой метод будет вызван при вызове интерфейсного метода. Его можно узнать с помощью `reflect.TypeOf(r)`. Проверка динамического типа лежит в основе type assertion и type switch. Понимание динамического типа критически важно для понимания поведения nil-интерфейса: если интерфейс не nil, но внутри хранится указатель с динамическим типом, но nil-значением, то интерфейс != nil.

### Под капотом (internals)
В структурах `iface` и `eface` поле `tab` или `_type` содержит указатель на метаданные динамического типа. Это `runtime._type` или `*itab`. При копировании интерфейсного значения копируются оба поля (тип и значение). Динамический тип участвует в GC для определения корневых указателей данных.

### Типичные ошибки кандидатов
1. **Путаница статического и динамического типа при удовлетворении интерфейса.** Важно, что соответствие интерфейсу определяется статическим типом значения, а не динамическим; но при использовании интерфейса всегда динамика.
2. **Предположение, что динамический тип всегда совпадает с типом переменной, переданной в интерфейс.** При передаче по значению может быть `T`, а при передаче указателя `*T`, и это разные динамические типы.

### Возможные дополнительные вопросы интервьюера
*Можно ли изменить динамический тип, не присваивая новое значение?* Нет, интерфейсная переменная иммутабельна в этом плане.
*Как динамический тип используется в GC?* GC сканирует динамическое значение согласно информации о типе из `_type`.

## Что такое статический тип (static type)?

### Краткий ответ (30–60 секунд)
Статический тип — это тип, известный во время компиляции и объявленный для переменной, поля структуры, возвращаемого значения. Для интерфейсной переменной статический тип — сам интерфейс, и именно он определяет, какие методы можно вызывать без утверждения типа.

### Развёрнутый ответ
Если объявлено `var w io.Writer`, статический тип — `io.Writer`. Компилятор гарантирует, что этой переменной можно присвоить только значения, реализующие `io.Writer`, и разрешает вызывать только методы `Write`. Даже если в рантайме там лежит `*os.File`, статический тип остаётся `io.Writer`, и нельзя вызвать `Readdir`. Статические типы обеспечивают типобезопасность. Для конкретных типов статический и динамический типы (при передаче в интерфейс) совпадают, но динамический тип может быть производным (например, если интерфейс хранит указатель на тип).

### Под капотом (internals)
Статический тип используется компилятором для генерации корректного кода и проверок. Он не представлен в сгенерированном коде как значение, в отличие от динамического типа, который присутствует в таблицах `itab`. Однако знание статического типа позволяет компилятору оптимизировать вызовы методов, минуя интерфейсное пересылка, когда конкретный тип известен статически.

### Типичные ошибки кандидатов
1. **Попытка вызвать метод, не принадлежащий статическому типу, требуя утверждения.** Кандидат удивляется ошибке компиляции.
2. **Передача переменной с одним статическим типом в функцию, ожидающую интерфейс, без учёта, что методы удовлетворяются только при определенном receiver.** Например, статический тип `MyType` может не реализовывать интерфейс `MyInterface`, а `*MyType` реализует — передача значения `myValue` вызовет ошибку.

### Возможные дополнительные вопросы интервьюера
*Может ли статический тип измениться после объявления?* Нет, он фиксирован.
*Как Go выводит статический тип при коротком объявлении `:=`?* На основе выражения справа.

## Что такое nil интерфейс (nil interface)?

### Краткий ответ (30–60 секунд)
Nil-интерфейс — это интерфейсная переменная, которая не содержит ни типа, ни значения; оба поля (`itab` и `data`) равны нулю. Она равна `nil` при сравнении. Напротив, интерфейс, хранящий nil-указатель с конкретным типом, nil-интерфейсом не является.

### Развёрнутый ответ
Пример:
```go
var r io.Reader // nil интерфейс
fmt.Println(r == nil) // true

var p *os.File = nil
r = p           // интерфейс не nil, динамический тип *os.File, значение nil
fmt.Println(r == nil) // false (!)
```
Это — одна из самых известных ловушек Go. Причина: интерфейсное значение — это пара (тип, значение). Если тип не nil, интерфейс не nil, даже если значение nil. Для проверки "хранится ли nil-значение" нужно использовать рефлексию или специально проверять. Методы, вызванные на nil-интерфейсе, вызовут панику. На интерфейсе с nil-указателем метод может быть вызван, если receiver обрабатывает nil (как в случае `(*bytes.Buffer)(nil).Len()` вернёт 0).

### Под капотом (internals)
Структура `iface` содержит `tab *itab` и `data unsafe.Pointer`. Когда оба поля равны нулю, интерфейс nil. Когда мы присваиваем типизированный nil-указатель, `data` равен nil, но `tab` указывает на реальный `itab` для `*os.File`, поэтому интерфейс не nil. Проверка `== nil` в коде сравнивает оба слова.

### Типичные ошибки кандидатов
1. **Возврат не-типизированного nil из функции, возвращающей интерфейс, но с конкретным типом.** Например, `func getFile() *os.File { return nil }` и последующее присвоение интерфейсу даёт non-nil интерфейс. Исправление: возвращать nil-интерфейс напрямую: `return nil` (не указатель).
2. **Неправильная обработка ошибки:** `if err != nil { return err }`, где `err` — переменная интерфейса `error`, но инициализирована как конкретный nil-тип (например, `*MyError`). Проверка пройдёт, хотя реальной ошибки нет. Классическое решение: возвращать `error` явно: `return nil` вместо `return (*MyError)(nil)`.
3. **Путаница в конструкциях `if err != nil` после вызова, возвращающего интерфейс, где тип не nil.** Решение: либо не возвращать типизированный nil, либо использовать `if err != nil` после приведения.

### Возможные дополнительные вопросы интервьюера
*Как отличить nil-интерфейс от интерфейса с nil-значением?* Только через `reflect.ValueOf(x).IsNil()` с осторожностью, либо избегать типизированных nil.
*Почему Go так спроектирован?* Чтобы сохранить информацию о типе, необходимую для динамической диспетчеризации.

## Почему интерфейс может быть `nil`, но не `nil` (interface with nil underlying value)?

### Краткий ответ (30–60 секунд)
Интерфейсное значение состоит из двух слов: указатель на описание типа и указатель на данные. Если тип не нулевой (не nil), а данные нулевые, то интерфейс как целое не равен nil. Поэтому `var r io.Reader = (*os.File)(nil)` не nil, так как `itab != nil`.

### Развёрнутый ответ
Это явление называют «nil, но не nil». Оно часто приводит к багам, когда функция возвращает ошибку. Например:
```go
func do() error {
    var p *MyError
    if someCondition {
        p = &MyError{}
    }
    return p // всегда возвращает error, не nil, даже если p == nil
}
```
Вызывающий код проверяет `if err != nil`, и оно истинно, даже если фактической ошибки нет, потому что `err` содержит `(*MyError)(nil)`. Идиоматическое решение — возвращать `nil` напрямую: `return nil`. Это требует объявлять возвращаемую переменную как интерфейс (`var err error`) или прямо использовать `return nil`. Или преобразовывать `p` в `error` только если не nil: `if p != nil { return p } return nil`.

### Под капотом (internals)
Проиллюстрируем: при `return p` переменная `p` типа `*MyError` со значением `nil` конвертируется в `error`. Компилятор создаёт `iface{tab: itab для *MyError, data: nil}`. При сравнении `err == nil` проверяются оба поля, `tab` не nil — результат false. Реализация `error` — интерфейс, поэтому та же механика.

### Типичные ошибки кандидатов
1. **Возврат конкретного nil из функции с возвращаемым типом-интерфейсом.** Самая распространённая. Исправление: никогда не возвращать типизированный nil, всегда `return nil`.
2. **Проверка ошибки в defer/recover:** паника nil указателя, если не учесть, что переменная может быть nil.
3. **Использование `reflect.DeepEqual` для сравнения с nil.** Не всегда корректно, так как нужно смотреть динамический тип.

### Возможные дополнительные вопросы интервьюера
*Как правильно написать функцию, возвращающую ошибку с конкретным типом, избегая ловушки?* `var err error` как локальную переменную и присваивать ей конкретный тип, затем `return err` (if it's nil, it stays nil interface).
*Можно ли создать обёртку, которая безопасно извлекает ошибку?* Да, например, `func wrapErr(err error) error { if err == nil { return nil } return myErr{err} }`.

## Что такое композиция (composition)?

### Краткий ответ (30–60 секунд)
Композиция — это принцип построения сложных типов путём объединения более простых, через встраивание полей или интерфейсов. В Go отсутствует наследование классов; вместо этого широко используется композиция, позволяющая переиспользовать код, делегируя поведение вложенным объектам.

### Развёрнутый ответ
Пример:
```go
type Engine struct { ... }
func (e Engine) Start() { ... }

type Car struct {
    Engine          // встроенное поле (embedding)
    Wheels int
}
car := Car{Engine: Engine{}}
car.Start()         // метод повышен до Car
```
В Go композиция реализуется через embedding (встраивание) — синтаксический сахар, который автоматически продвигает методы встроенного типа во внешний. Это даёт возможность строить богатое поведение без иерархий. Композиция интерфейсов: `type ReadWriter interface { Reader; Writer }` — объединяет методы без реализации. Принцип предпочтения композиции наследованию («Composition over inheritance») реализован на уровне языка.

### Под капотом (internals)
Встраивание — это просто поле с неявным именем (имя типа). Компилятор генерирует методы-обёртки для продвижения, которые вызывают методы встроенного поля. Если встроенный тип — указатель, метод продвигается, но вызывается через указатель. В таблице методов внешнего типа появляются методы встроенного. При конфликте имён компилятор требует явного разрешения. Для интерфейсов встраивание просто объединяет набор методов.

### Типичные ошибки кандидатов
1. **Путаница с “является” вместо “имеет”.** Некоторые воспринимают встраивание как наследование и ожидают полиморфизма подтипов: `var e Engine = car` не скомпилируется, потому что `Car` не является `Engine`, он содержит `Engine`. Нужно явно обращаться к полю.
2. **Непонимание продвижения методов при встраивании указателя.** Если встроено `*Engine`, то методы продвигаются, но поле доступно как `car.Engine`. Если `Engine` nil, вызов метода паникует.
3. **Конфликты имён без обработки.** Если два встроенных типа имеют метод `Start`, компилятор не продвигает его вообще, нужно явно вызывать `car.Engine.Start()`.

### Возможные дополнительные вопросы интервьюера
*Чем композиция отличается от агрегации?* Агрегация — обычное поле с именем, без продвижения методов; композиция через embedding автоматически продвигает.
*Можно ли встроить интерфейс в структуру?* Да, это позволяет частично реализовать интерфейс или создать «заглушку» с переопределением методов.

## Чем композиция лучше наследования?

### Краткий ответ (30–60 секунд)
Композиция обеспечивает слабую связанность, явное делегирование и гибкость без хрупких иерархий. В отличие от наследования, она не создаёт жёсткую иерархию, позволяет легко заменять компоненты и избегает проблемы «алмазной формы» и конфликтов методов. Go полностью построен на композиции, что упрощает дизайн и тестирование.

### Развёрнутый ответ
- **Отсутствие привязки к иерархии.** В наследовании изменение базового класса может сломать производные. В композиции зависимости явные и контролируемые.
- **Лучшая инкапсуляция.** Встроенные поля могут быть приватными, но продвигаемые методы — открытыми. Наследование часто требует раскрытия protected.
- **Гибкость замены.** Можно легко подменить одну часть поведения другой реализацией через интерфейс без изменения структуры.
- **Тестируемость.** Зависимости в виде интерфейсов легко мокировать. Наследование часто требует сложных мок-фреймворков.
- **Множественная композиция.** Можно встроить несколько типов, чего нельзя с наследованием без множественного наследования (которого нет в Go).
- **Избежание проблемы Fragile Base Class.** Изменения в базовом классе не затрагивают непреднамеренно код, использующий композицию.

Композиция интерфейсов позволяет строить мелкогранулярные абстракции, легко комбинируемые. Это прямое воплощение принципов SOLID, особенно Interface Segregation и Dependency Inversion.

### Под капотом (internals)
На уровне компилятора композиция через embedding генерирует обёртки, но не создаёт VTBL иерархии. Вызовы методов статически связываются с вложенным полем, если не используются интерфейсы. Это даёт предсказуемую производительность без накладных расходов на виртуальные вызовы базового класса.

### Типичные ошибки кандидатов
1. **Применение embedding как наследования с попыткой приведения типа.** Невозможно, нужно явно использовать поле.
2. **Избыточный embedding без необходимости.** Если нужны только несколько методов, лучше хранить интерфейс как поле и делегировать явно, чем встраивать всю структуру.
3. **Недооценка сложности из-за продвижения методов.** При большом количестве встроенных типов обилие автоматически продвинутых методов может запутать.

### Возможные дополнительные вопросы интервьюера
*Можно ли в Go реализовать паттерн «Стратегия» с помощью композиции?* Да, храним интерфейс стратегии как поле и вызываем его методы.
*Чем embedding отличается от наследования в Java?* В Java наследование даёт отношение “is-a”, а embedding в Go — “has-a” с автоматическим делегированием.

## Что такое встраивание (embedding)?

### Краткий ответ (30–60 секунд)
Встраивание — это декларация поля структуры или интерфейса без имени, указывающая только тип. В результате методы и поля встроенного типа становятся доступны напрямую через внешний тип, обеспечивая переиспользование кода без наследования.

### Развёрнутый ответ
В структурах:
```go
type Base struct { Value int }
func (b Base) Inc() { b.Value++ } // value receiver

type Extended struct {
    Base          // встраивание
    Extra string
}
e := Extended{}
e.Inc()          // метод продвинут
fmt.Println(e.Value) // доступ к полю напрямую
```
Можно встраивать указатели: `*Base`. При встраивании интерфейсов:
```go
type Reader interface { Read(p []byte) (n int, err error) }
type ReadWriter interface {
    Reader
    Write(p []byte) (n int, err error)
}
```
Интерфейс `ReadWriter` содержит все методы `Reader` и `Write`. Встраивание позволяет строить композитные интерфейсы и структуры без дублирования. Конфликты имён разрешаются явным обращением к встроенному типу.

### Под капотом (internals)
Embedding реализовано на уровне компилятора. Для каждого встроенного поля генерируются методы-обёртки (thunk), которые просто делегируют вызовы. Поле получает неявное имя, совпадающее с именем типа (например, `Base`). При конфликте метод не продвигается. В таблицу методов включаются все продвинутые методы, при необходимости с автоматической обёрткой value->pointer и pointer->value. Встраивание интерфейса — просто объединение наборов методов; итоговый интерфейс имеет все методы из составляющих.

### Типичные ошибки кандидатов
1. **Ожидание, что встраивание создаёт отношение is-a.** `e` нельзя присвоить переменной типа `Base`. Это по-прежнему has-a.
2. **Неучёт, что метод с value receiver не изменит встроенное поле при вызове на внешнем типе.** Так как продвигается value-метод, он получает копию поля `Base`, а не всю структуру.
3. **Неоднозначный выбор поля при одинаковых именах.** Если и внешний, и встроенный типы имеют поле `Name`, доступ `e.Name` возьмёт поле внешнего; к полю встроенного типа нужно обращаться явно `e.Base.Name`.

### Возможные дополнительные вопросы интервьюера
*Можно ли встроить срез?* Нет, только именованные типы.
*Как встраивание интерфейса влияет на обратную совместимость?* Добавление метода во встроенный интерфейс расширяет внешний, что может сломать реализации, если они не реализуют новый метод.

## Как работает встраивание методов и полей?

### Краткий ответ (30–60 секунд)
При встраивании типа в структуру все его экспортируемые и неэкспортируемые методы (кроме конфликтующих) становятся методами внешнего типа. Поля встроенного типа также продвигаются и могут быть доступны без указания полного пути. Компилятор генерирует код делегирования автоматически.

### Развёрнутый ответ
Детали:
- Продвигаются методы с любым receiver (value/pointer), но с учётом того, как встроен тип: если встроен `Base`, продвигаются только методы value receiver; если `Base` или `*Base`, продвигаются методы обоих видов, но вызываться могут по-разному.
- Если встроен указатель `*Base`, методы обоих receiver продвигаются, так как компилятор может разыменовать.
- При вызове метода внешнего типа, соответствующего встроенному, компилятор создаёт промежуточную функцию, которая принимает внешний тип, извлекает встроенное поле и вызывает его метод. Для value receiver будет копия этого поля; для pointer receiver — указатель на это поле внутри внешней структуры.
- Продвижение полей: если встроенный тип `Base` имеет поле `X`, то `ext.X` обращается к `ext.Base.X`. Если внешний тип имеет своё поле `X`, то `ext.X` ссылается на собственное поле.

### Под капотом (internals)
Методы-обёртки генерируются во время компиляции и могут быть инлайнированы. Таблица методов внешнего типа включает все эти обёртки. Если встроенный тип имеет множество методов, таблица растёт. При удовлетворении интерфейса компилятор проверяет набор методов внешнего типа, включая продвинутые. Механизм встраивания не требует дополнительных структур данных времени выполнения.

### Типичные ошибки кандидатов
1. **Считают, что при вызове продвинутого метода неявно передаётся вся внешняя структура.** Нет, метод получает только встроенную часть. Это важно, если метод ожидает изменить внешние поля.
2. **Пренебрежение nil-безопасностью при встраивании указателя.** Если `*Base` не инициализирован, вызов продвинутого метода вызовет панику.
3. **Использование встраивания для “наследования” конструктора.** Встраивание не вызывает конструкторы автоматически, необходимо инициализировать явно.

### Возможные дополнительные вопросы интервьюера
*Как встраивание влияет на JSON-сериализацию?* Если встроенное поле имеет теги JSON, они могут конфликтовать; `json.Marshal` будет выводить встроенные поля так же, как если бы они были на верхнем уровне.
*Можно ли переопределить метод встроенного типа?* Да, если определить метод с тем же именем на внешнем типе, он перекроет продвинутый метод (shadowing). Это не переопределение в смысле виртуальных функций, а просто затенение.

## Как разрешаются конфликты имен при встраивании?

### Краткий ответ (30–60 секунд)
Если при встраивании нескольких типов возникают конфликты имён (одинаковые имена методов или полей), компилятор не продвигает их вообще. Для доступа требуется явно указать встроенный тип (`ext.TypeA.Method()`). При конфликте поля/метода между внешним и встроенным типом внешний имеет приоритет (затенение).

### Развёрнутый ответ
Правила:
1. Конфликт между двумя встроенными типами на одном уровне: метод/поле не продвигается. Пример: `type A struct{} func (A) Do() {}; type B struct{} func (B) Do() {}; type C struct { A; B }`. `c.Do()` вызовет ошибку компиляции — ambiguous selector. Нужно явно `c.A.Do()`.
2. Если встроенный тип и внешний имеют одинаковые имена, внешний «затеняет». Доступ к встроенному через `c.A.Field`.
3. Если конфликт на разных уровнях вложенности (например, `A` встроено в `B`, `B` в `C`, и `C` имеет то же имя), опять же требуется уточнение.
Это обеспечивает предсказуемость и избегает случайного доступа не к тому методу.

### Под капотом (internals)
Компилятор при разрешении селекторов (`x.Name`) просматривает в порядке: собственные поля и методы, затем поля и методы встроенных типов в порядке объявления. Если находит несколько подходящих, сообщает об ошибке неоднозначности. Для интерфейсов с конфликтующими методами встроенных интерфейсов это допустимо, если сигнатуры совпадают, иначе ошибка.

### Типичные ошибки кандидатов
1. **Попытка использовать неоднозначный селектор без явного указания.** Исправление: добавлять квалификацию.
2. **Предположение, что методы с одинаковыми именами, но разными сигнатурами, могут сосуществовать как перегрузка.** Нет, это конфликт.
3. **Игнорирование конфликтов полей при сериализации.** JSON-теги с одинаковыми именами могут привести к панике или неопределённому поведению. Нужно явно тегировать их разными именами.

### Возможные дополнительные вопросы интервьюера
*Что если встроить интерфейсы с одинаковым методом?* Допустимо, если метод идентичный; иначе ошибка.
*Как избежать конфликтов при проектировании?* Используйте embedding осознанно, с разными именами методов; при необходимости оборачивайте.

## Как устроен интерфейс под капотом (пары указателей: тип, значение)?

### Краткий ответ (30–60 секунд)
Интерфейсное значение представлено структурой из двух указателей: `itab` (указатель на таблицу интерфейса) и `data` (указатель на сами данные), или для пустого интерфейса — `_type` и `data`. `itab` содержит метаинформацию о типе и список указателей на методы, что обеспечивает динамическую диспетчеризацию.

### Развёрнутый ответ
Ненулевой интерфейс (с методами) — `iface`:
```go
type iface struct {
    tab  *itab
    data unsafe.Pointer
}
type itab struct {
    inter *interfacetype
    _type *_type
    hash  uint32      // копия _type.hash для быстрых type assertions
    _     [4]byte
    fun   [1]uintptr  // массив указателей на методы, размер зависит от числа методов
}
```
Пустой интерфейс — `eface`:
```go
type eface struct {
    _type *_type
    data  unsafe.Pointer
}
```
При присваивании значения интерфейсу runtime создаёт `itab` (если его ещё нет), копируя таблицу методов типа. `data` указывает на оригинальное значение или его копию (если значение адресуемо и используется указатель, или происходит боксинг для маленьких значений). GC сканирует `data` на основе информации в `_type`.

Метод вызывает косвенно: загружается `itab.fun[methodIndex]`, затем `CALL`. Индекс метода известен во время компиляции для конкретного интерфейса.

### Под капотом (internals)
Исходники: `src/runtime/runtime2.go` (iface, eface), `src/runtime/iface.go`. Создание `itab` происходит в `getitab` — сначала поиск в хеш-таблице, затем создание через `itabAdd`. Для маленьких значений, помещающихся в слово, компилятор может хранить их прямо в `data` (без указателя), но обычно происходит выделение памяти для хранения указателя. Escape analysis может определить, что значение не покидает стек, и обойтись без аллокаций.

### Типичные ошибки кандидатов
1. **Сравнение интерфейсов с указателями на структуры без учёта `itab`.** Два интерфейса равны, только если оба `tab` и `data` равны.
2. **Непонимание, почему `var x interface{} = 5` не может быть изменено на месте.** `data` хранит указатель на копию значения 5, а не на оригинал.
3. **Утверждение, что `interface{}` всегда аллоцирует кучу.** Не всегда: для целых чисел до 64-бит, если они не убегают, может не быть аллокации (конвертация происходит в регистры), но обычно все же есть боксинг.

### Возможные дополнительные вопросы интервьюера
*Как `itab` кэшируется?* В глобальной хеш-таблице `itabTable` с атомарными операциями, чтобы минимизировать затраты на создание.
*Почему интерфейс нельзя сравнивать, если в `_type` указано, что тип несравним (например, срез)?* Go проверяет флаг `tflag` и паникует или не компилирует сравнение.

## Что такое `error` интерфейс?

### Краткий ответ (30–60 секунд)
`error` — это встроенный интерфейс с единственным методом `Error() string`. Любой тип, имеющий этот метод, может быть использован как ошибка. Это идиоматический механизм обработки ошибок в Go, основанный на возврате ошибки как последнего значения.

### Развёрнутый ответ
Определение:
```go
type error interface {
    Error() string
}
```
Простота даёт максимальную гибкость. Часто используют `errors.New("message")` или `fmt.Errorf("..." ).` Пользовательские типы ошибок могут нести контекст, поддерживать `Unwrap` (для цепочек), `Is` и `As` (из `errors` пакета). Go поощряет явную проверку ошибок: `if err != nil`. Конвенции: сообщения об ошибках не должны начинаться с заглавной буквы и не должны заканчиваться точкой. Интерфейс `error` — пример идеального однометодного интерфейса.

### Под капотом (internals)
`error` — обычный интерфейс, поэтому подчиняется всем правилам хранилища. `errors.New` возвращает `*errorString`, который реализует `error`. В рантайме обработка не специальная, всё на уровне компиляции. `fmt.Errorf` с `%w` создаёт обёртку, содержащую вложенную ошибку, что поддерживается через `errors.Unwrap`. Механизм `errors.Is` и `errors.As` использует рефлексию для проверки динамического типа и интерфейсной цепочки.

### Типичные ошибки кандидатов
1. **Возврат nil-указателя как ошибки.** Классика: `return (*MyError)(nil)`. Решение: `return nil`.
2. **Игнорирование ошибок.** `_ = file.Close()` — можно потерять важные данные. Исправление: обрабатывать всегда, возможно, с `defer` через замыкание: `defer func() { err = closeErr }`.
3. **Обёртывание ошибок без `%w`, теряя цепочку.** Исправление: использовать `fmt.Errorf("%w", err)` для поддержки `errors.Is`.

### Возможные дополнительные вопросы интервьюера
*Что такое `errors.Is`?* Проверяет, содержит ли цепочка ошибок конкретную ошибку (по равенству или интерфейсу `Is`).
*Как создать тип ошибки с дополнительным контекстом?* Определить структуру с полями и реализовать `Error() string`, часто с `Unwrap() error`.

## Какие есть стандартные интерфейсы в Go (`io.Reader`, `io.Writer`, `fmt.Stringer` и т.д.)?

### Краткий ответ (30–60 секунд)
Основные стандартные интерфейсы включают `io.Reader`, `io.Writer`, `io.Closer`, `fmt.Stringer`, `error`, `sort.Interface`, `http.Handler`, `net.Conn`, `encoding.BinaryMarshaler` и многие другие. Они формируют фундамент экосистемы, обеспечивая универсальную абстракцию для работы с данными, строками, сортировкой и сетью.

### Развёрнутый ответ
Ключевые интерфейсы:
- `io.Reader`: `Read(p []byte) (n int, err error)`
- `io.Writer`: `Write(p []byte) (n int, err error)`
- `io.Closer`: `Close() error`
- `io.Seeker`: `Seek(offset int64, whence int) (int64, error)`
- `fmt.Stringer`: `String() string` (аналог `.ToString()`)
- `error`: `Error() string`
- `sort.Interface`: `Len() int`, `Less(i, j int) bool`, `Swap(i, j int)`
- `http.Handler`: `ServeHTTP(ResponseWriter, *Request)`
- `http.HandlerFunc` — адаптер-функция.
- `hash.Hash` (комбинирует `io.Writer` с `Sum` и т.д.)
- `net.Conn` (комбинация `Reader`, `Writer`, `Closer`, ...)
- `context.Context` (4 метода)
- `encoding/json.Marshaler`/`Unmarshaler`

Эти интерфейсы делают возможной композицию: `io.TeeReader`, `io.LimitReader`, `io.MultiWriter` оперируют только интерфейсами, не зная конкретных реализаций. `fmt.Stringer` используется повсеместно для печати.

### Под капотом (internals)
Все они — обычные интерфейсы, не требуют специальных runtime-структур. Благодаря неявной реализации, любой тип из любого пакета может их удовлетворять. Это основа стандартной библиотеки.

### Типичные ошибки кандидатов
1. **Реализация `Read` с ошибкой `io.EOF` и положительным числом считанных байт.** Документация разрешает возвращать `io.EOF` вместе с данными; вызывающий должен обработать данные перед проверкой ошибки. Неправильно: сразу возвращать ошибку без данных.
2. **Забывают `io.Closer` и утечка ресурсов.** Всегда закрывать ресурсы, используя `defer`.
3. **Неправильная реализация `Len`, `Less`, `Swap` для `sort.Interface`:** Например, `Less` не антисимметричен.

### Возможные дополнительные вопросы интервьюера
*Какие интерфейсы используются для копирования данных?* `io.Copy` принимает `Writer` и `Reader`.
*Что делает `fmt.Stringer`?* Позволяет типу управлять строковым представлением при форматировании.

## Когда использовать интерфейс с одним методом (single-method interface)?

### Краткий ответ (30–60 секунд)
Интерфейс с одним методом идеален, когда требуется минимальная абстракция поведения. Он обеспечивает максимальную гибкость: реализовать его легко даже анонимными функциями, он следует принципу разделения интерфейсов (ISP) и позволяет строить композицию из мелких частей. Примеры: `io.Reader`, `error`, `fmt.Stringer`.

### Развёрнутый ответ
Однометодные интерфейсы — сердце Go-архитектуры. Они позволяют:
- Описывать единственное действие, которое может понадобиться разным клиентам.
- Легко адаптировать функции к интерфейсам: `http.HandlerFunc` (функция) реализует `http.Handler`.
- Снижать связанность: клиент зависит только от одного метода, а не от жирного объекта.
- Облегчать тестирование: достаточно замокать один метод.
- Упрощать декорирование: `io.LimitReader` — декоратор `Reader`.

Правило: если вы видите, что интерфейс содержит более трёх методов, стоит задуматься, не следует ли его разбить. Все стандартные интерфейсы малы: `io.Reader` (1 метод), `io.Writer` (1), `sort.Interface` (три, но это всё ещё мало). Исключения: `net.Conn` объединяет несколько, но он скомпонован из одного-двух-методных интерфейсов.

### Под капотом (internals)
Нет специальной реализации. `itab` для однометодного интерфейса содержит один указатель на метод. Вызов через такой интерфейс дёшев (одно косвенное обращение). Таблица занимает минимум памяти.

### Типичные ошибки кандидатов
1. **Создание огромного интерфейса “на всякий случай” вместо маленьких.** Это жёстко связывает реализацию и усложняет замену. Исправление: рефакторинг на мелкие.
2. **Не использование интерфейсов с одним методом для коллбеков, заменяя их функциями.** Иногда интерфейс предпочтительнее, если ожидается несколько реализаций с состоянием, но для простых случаев функция работает.
3. **Определение однометодного интерфейса, который дублирует уже существующий стандартный.** Например, свой `Stringer` вместо `fmt.Stringer`. Нужно переиспользовать стандартные.

### Возможные дополнительные вопросы интервьюера
*Можно ли конвертировать функцию в One-method interface?* Да, через адаптер тип: `type HandlerFunc func(...)`, добавив метод.
*Почему `sort.Interface` не однометодный?* Исторически сложилось; современный подход — `sort.Slice` с передачей функции Less, что убирает необходимость в интерфейсе в большинстве случаев.

## Что такое «утиная типизация» в контексте Go?

### Краткий ответ (30–60 секунд)
Утиная типизация — это принцип «если что-то выглядит как утка, плавает как утка и крякает как утка, то это, вероятно, утка». В Go это реализовано через неявную реализацию интерфейсов: тип является реализацией интерфейса, если он содержит все его методы, независимо от какого-либо явного объявления.

### Развёрнутый ответ
Утиная типизация даёт максимальную гибкость. Можно определить интерфейс `Quacker { Quack() }`, и любой тип с методом `Quack()` автоматически подойдёт: `Dog`, `Duck`, `RubberDuck`. Никакого дерева наследования. Это структурная типизация, а не номинативная. В динамических языках (Python, Ruby) утиная типизация проверяется во время выполнения; в Go она статически проверяется при присвоении, совмещая гибкость с безопасностью. Такой подход способствует созданию библиотек, которые определяют минимальные интерфейсы под свои нужды, а не подстраиваются под чужие.

### Под капотом (internals)
Механизм полностью опирается на описанный выше способ проверки соответствия набора методов. При присваивании компилятор сверяет сигнатуры. В рантайме это выражается в создании `itab`. Никаких дополнительных конструкций.

### Типичные ошибки кандидатов
1. **Ожидание, что утиная типизация сработает на основе структур (полей).** Интерфейсы определяют только методы, не поля. Нельзя требовать наличие поля `Name`.
2. **Смешение утиной типизации и наследования.** Думать, что если `Car` имеет `Engine`, то `Car` можно присвоить интерфейсу, требующему методы `Engine`, — только если `Car` продвигает эти методы.
3. **Проверка динамического типа через рефлексию вместо утверждения типа.** Хотя дух утиной типизации позволяет это, предпочтительнее type assertion.

### Возможные дополнительные вопросы интервьюера
*Почему Go выбрал структурную, а не номинативную типизацию?* Для простоты композиции, уменьшения зависимостей и облегчения рефакторинга.
*В чём разница между утиной типизацией в Go и в Python?* В Go статическая проверка, в Python ошибки во время выполнения.

## Можно ли реализовать интерфейс для типа из другого пакета?

### Краткий ответ (30–60 секунд)
Да, можно реализовать интерфейс, определённый в одном пакете, для типа из другого пакета, определив методы этого интерфейса для этого типа в своём пакете, при условии, что метод объявляется для типа, который вы контролируете (т.е. тип определён в вашем пакете, либо вы создали новый тип на основе стороннего). Непосредственно добавить метод к чужому типу нельзя, но можно создать свой тип на его основе или использовать обёртку.

### Развёрнутый ответ
Go не разрешает объявлять методы для типов из других пакетов. Но есть обходные пути:
1. Определить новый именованный тип: `type MyInt int` и добавить методы к `MyInt`.
2. Создать тип-обёртку, содержащий оригинальный тип, и реализовать методы, делегируя вызовы вложенному объекту. Это работает и для интерфейсов.
3. Использовать type alias? Нет, алиас `type A = B` не позволяет добавлять методы.

Пример реализации `fmt.Stringer` для `json.RawMessage`:
```go
type PrintableRaw json.RawMessage
func (p PrintableRaw) String() string { return string(p) }
```
Теперь `PrintableRaw` реализует `Stringer`. Если нужен интерфейс с несколькими методами, можно встроить оригинальный тип в структуру и реализовать требуемые методы, делегируя остальные.

### Под капотом (internals)
Ограничение введено для сохранения контроля над типами: только пакет-владелец типа может определять его поведение. Компилятор при проверке области видимости метода требует, чтобы тип и метод были в одном пакете.

### Типичные ошибки кандидатов
1. **Прямая попытка объявить метод для чужого типа: `func (t otherpkg.Type) Method()`.** Ошибка компиляции.
2. **Создание типа-обёртки и забывание о преобразовании туда/обратно при взаимодействии.** Это может потребовать явного приведения типов.
3. **Попытка удовлетворить интерфейс через алиас:** `type MyType = other.Type`. Метод добавить нельзя, так как `MyType` и `other.Type` — одно и то же, определение все равно будет в чужом пакете.

### Возможные дополнительные вопросы интервьюера
*Можно ли встроить чужой тип без создания собственного пакета и реализовать интерфейс?* Только если ваш пакет определяет тип, в который встраивается чужой тип. Методы продвигаются, но вы не можете добавить свои методы в чужой тип.
*Как тогда мокировать стороннюю библиотеку?* Через интерфейсы, определённые потребителем, и адаптеры.

## Как реализовать полиморфизм с помощью интерфейсов?

### Краткий ответ (30–60 секунд)
Полиморфизм в Go достигается через интерфейсы: объявляется переменная интерфейсного типа, которой можно присвоить любое значение, реализующее этот интерфейс. Вызов методов интерфейса динамически диспетчеризуется к конкретной реализации. Это заменяет традиционное наследование и виртуальные функции.

### Развёрнутый ответ
Пример:
```go
type Shape interface { Area() float64 }

type Rect struct { w, h float64 }
func (r Rect) Area() float64 { return r.w * r.h }

type Circle struct { r float64 }
func (c Circle) Area() float64 { return math.Pi * c.r * c.r }

func PrintArea(s Shape) { fmt.Println(s.Area()) }
```
Функция `PrintArea` работает с любым типом, реализующим `Shape`. Это полиморфизм времени исполнения. Комбинация интерфейсов и first-class функций позволяет реализовывать паттерны стратегии, команды и т.д. Также параметрический полиморфизм доступен через дженерики (статический полиморфизм). Интерфейсы дают динамический полиморфизм с низкими накладными расходами.

### Под капотом (internals)
Динамическая диспетчеризация реализована через `itab`. Компилятор для вызова `s.Area()` загружает указатель на метод из `itab.fun[0]` (индекс 0, если Area — единственный метод) и делает косвенный вызов. Это аналогично виртуальной таблице в C++, но без необходимости объявлять базовый класс. Благодаря мономорфизации не в дженериках?

### Типичные ошибки кандидатов
1. **Желание использовать type switch внутри полиморфной функции для определения типа и кастования.** Это ломает полиморфизм. Правильно: добавлять новый метод в интерфейс или использовать отдельный интерфейс.
2. **Создание интерфейса с десятком методов, когда для полиморфизма нужен только один.** Это ограничивает круг реализаций.
3. **Передача значения вместо указателя, когда метод определён на указателе.** Полиморфизм не сработает, тип не будет удовлетворять интерфейсу.

### Возможные дополнительные вопросы интервьюера
*Чем отличается динамический полиморфизм от статического в Go?* Статический через дженерики (разные инстанциации кода), динамический через интерфейсы.
*Можно ли эмулировать полиморфизм без интерфейсов?* С помощью функций первого класса, но интерфейсы естественнее для набора методов.

## Что такое дженерики (generics) в Go?

### Краткий ответ (30–60 секунд)
Дженерики (обобщения) — это возможность писать код, который работает с разными типами, с проверкой на этапе компиляции, без использования пустого интерфейса и приведения типов. В Go они появились в версии 1.18 и позволяют параметризовать функции и типы с помощью ти́повых параметров и ограничений.

### Развёрнутый ответ
Синтаксис:
```go
func Map[T any, R any](s []T, f func(T) R) []R { ... }
```
Здесь `T` и `R` — ти́повые параметры, `any` — ограничение (любой тип). Вызов: `result := Map[int, string](nums, strconv.Itoa)`, или с выводом типов. Дженерики позволяют создавать обобщённые структуры: `type Stack[T any] struct { data []T }`. Основная цель — сократить дублирование кода для срезов, map, структур данных, исключить `interface{}`. Go реализовал их через мономорфизацию (компиляция специализированного кода для каждого конкретного типа) с ленивой инстанциацией, что сохраняет высокую производительность.

### Под капотом (internals)
Дизайн основан на предложении Type Parameters. Компилятор выполняет проверку типов с помощью ограничений, а затем генерирует специализированные версии функций и методов для каждого набора типовых аргументов (мономорфизация). Это может увеличить размер бинарника, но не требует boxing. В runtime generic-функции не имеют общего кода; каждая инстанциация — отдельная функция. Также введены GCShape — разделение инстанциаций по форме типов (указатели, интерфейсы, маленькие скаляры) для уменьшения дублирования. Ограничения типа реализованы через интерфейсы с возможностью содержать список типов (union) и `comparable`.

### Типичные ошибки кандидатов
1. **Избыточное использование дженериков там, где достаточно интерфейса.** Преждевременная абстракция усложняет код. Правило: начинать с конкретных типов, обобщать при необходимости.
2. **Создание generic-функции, которая работает только с некоторыми типами, но ограничение `any`.** Теряется безопасность; нужно использовать правильные ограничения (например, `constraints.Ordered`).
3. **Использование параметра типа вне функции без инстанциации.** Дженерики требуют инстанцирования при использовании, явного или неявного.

### Возможные дополнительные вопросы интервьюера
*В чем отличие дженериков Go от Java?* В Go нет type erasure, используется мономорфизация, что даёт производительность, но увеличивает размер кода.
*Какие есть встроенные ограничения?* `any`, `comparable`, `constraints.Ordered` (в пакете `cmp` с Go 1.21), `constraints.Signed`, `Unsigned`, `Integer`, `Float`, `Complex`.

## Как работают дженерики в Go 1.18+?

### Краткий ответ (30–60 секунд)
Дженерики в Go реализованы через компиляцию специализированных версий кода для каждого использованного конкретного типа (мономорфизация). Ограничения задаются интерфейсами с элементами типов или специальными маркёрами (`comparable`). Вывод типов избавляет от явного указания аргументов типа.

### Развёрнутый ответ
Работа:
1. Объявление типа с параметром: `type Set[T comparable] map[T]struct{}`.
2. При использовании `Set[string]` компилятор создаёт конкретный тип, подставив `string` вместо `T`.
3. Ограничение `comparable` позволяет использовать `==` и `!=`. Ограничение в виде интерфейса с методами требует, чтобы T реализовал эти методы.
4. Компилятор делает мономорфизацию лениво: только когда тип действительно используется, генерируется специализированный код. Это снижает время компиляции по сравнению с полной мономорфизацией.
5. GCShape: если несколько типов имеют одинаковую базовую структуру (например, все указатели, все интерфейсы), они могут разделять одну скомпилированную версию для снижения раздувания кода.
6. Работает вывод типов: `Set[string]` можно опустить, если компилятор может вывести из аргументов.

### Под капотом (internals)
В компиляторе появились новые IR-узлы для дженериков. Создаётся словарь инстанцирований (inst dictionary), содержащий информацию о типе и вспомогательные функции (например, для хеширования, сравнения). При мономорфизации функции с ограничениями-интерфейсами (без методов) генерируется специализированная версия. Для ограничений с методами используется динамическая диспетчеризация через интерфейс, но тип T известен. Это компромисс. Исходники: `src/cmd/compile/internal/typecheck/`, `noder`, `syntax`.

### Типичные ошибки кандидатов
1. **Ожидание, что дженерики полностью устраняют использование интерфейсов.** Нет, для полиморфизма времени выполнения интерфейсы всё ещё нужны.
2. **Неправильное использование `comparable` для слайсов/мап.** Слайсы некварабелны, поэтому `comparable` их не допускает.
3. **Попытка передать параметр типа как ограничение для другого параметра без структурирования.** Не всегда возможно, нужно использовать интерфейсы с типами.

### Возможные дополнительные вопросы интервьюера
*Что такое GCShape и зачем?* Минимизация кода: типы с одинаковым представлением (указатели) разделяют код.
*Можно ли создать generic-метод с дополнительным параметром типа?* Да, методы могут иметь дополнительные ти́повые параметры, но не в интерфейсах, которые используются как ограничения (методы интерфейсов не могут иметь собственных ти́повых параметров в текущей версии).

## Что такое ограничение типа (type constraint)?

### Краткий ответ (30–60 секунд)
Ограничение типа — это интерфейс, который определяет множество допустимых типов для ти́пового параметра. Может включать перечисление конкретных типов (union) и/или набор методов. Основные ограничения: `any`, `comparable`, а также пользовательские.

### Развёрнутый ответ
Пример:
```go
type Number interface {
    int | float64
}
func Sum[T Number](a, b T) T { return a + b }
```
Типы `int` и `float64` перечислены через `|`. Также можно комбинировать с методами: `interface { String() string; int | float64 }` — тип должен быть и `int`/`float64`, и иметь метод `String`. Ограничение `comparable` разрешает только типы, поддерживающие `==` и `!=`. Можно использовать встроенные интерфейсы как ограничения: `[T io.Reader]` — T должен реализовывать `io.Reader`. Ограничения позволяют компилятору проверять допустимые операции над T (например, `+` для чисел) и генерировать корректный код.

### Под капотом (internals)
Реализовано через интерфейсы с дополнительной информацией: для union-типов добавляется список допустимых конкретных типов. При проверке типового аргумента компилятор смотрит, попадает ли он в union или/и реализует ли требуемые методы. Для union-ограничений операции вроде `+` компилятор проверяет по каждому типу из списка, и генерирует код для каждого типа при мономорфизации. Для ограничений с методами генерируется интерфейсное значение, и вызываются методы.

### Типичные ошибки кандидатов
1. **Использование `any` там, где нужны конкретные операции, и затем type switch.** Теряется смысл дженериков. Нужно сужать constraint.
2. **Перечисление в union типов, для которых планируемая операция не определена.** Например, `string | int`, и пытаться делать `T * T` — не скомпилируется.
3. **Забывание `comparable` для map ключей.** Ключ должен быть comparable; без этого дженерик не сработает.

### Возможные дополнительные вопросы интервьюера
*Что такое `constraints.Ordered`?* Ограничение, включающее все типы, поддерживающие `<`, `<=`, и т.д.
*Можно ли использовать интерфейс с методами как ограничение, не включая union?* Да, это будет просто интерфейс, и T должен его реализовывать.

## В чем разница между `interface{}` и `any` с появлением дженериков?

### Краткий ответ (30–60 секунд)
С появлением дженериков `any` стал официально предопределённым идентификатором для пустого интерфейса. Разницы в поведении нет; `any` — алиас `interface{}`. Дженерики не изменили механизм работы, но дали альтернативу для случаев, где раньше использовался `interface{}`, позволяя писать более типобезопасный код с параметризованными типами вместо пустого интерфейса.

### Развёрнутый ответ
До дженериков `interface{}` служил универсальным контейнером для любого значения. С дженериками появилась возможность точно задавать тип аргумента: вместо `func Print(v interface{})` можно `func Print[T any](v T)`. В большинстве новых сценариев предпочтительнее дженерики: они сохраняют конкретный тип, избегают утверждений типа и повышают производительность (нет boxing). Однако `interface{}`/`any` остаются необходимы для рефлексии, десериализации динамических данных и взаимодействия с кодом, не знающим конкретные типы на этапе компиляции. `any` был добавлен для ясности и облегчения чтения в параметрах типа: `[T any]` выглядит естественнее `[T interface{}]`.

### Под капотом (internals)
Никаких изменений в runtime. `any` обрабатывается как `interface{}`.

### Типичные ошибки кандидатов
1. **Думать, что `any` нельзя использовать вне дженериков.** Можно, везде, где допустим `interface{}`.
2. **Использовать `any` как ограничение по умолчанию без необходимости.** Иногда нужно `comparable` или более строгое. Лучше явно выбирать.
3. **Путаться в выводе типов:** `func F[T any](t T)` при вызове `F(5)` выведет `T = int`, а не `any`.

### Возможные дополнительные вопросы интервьюера
*Почему ввели `any`, если это просто алиас?* Для улучшения читаемости и маркетингового выделения поддержки дженериков.
*Можно ли определить свой тип `any`?* Нет, это предопределённый идентификатор.

## Как написать generic-функцию в Go?

### Краткий ответ (30–60 секунд)
Для создания generic-функции нужно объявить ти́повые параметры в квадратных скобках после имени функции, указав ограничения. Тело функции может использовать операции, разрешённые ограничениями. Пример: `func Min[T constraints.Ordered](a, b T) T { if a < b { return a } return b }`.

### Развёрнутый ответ
Пошагово:
1. Определить функцию с ти́повыми параметрами: `func F[T any](v T)`.
2. Выбрать подходящее ограничение. Для работы с `<` используем `constraints.Ordered` (или с Go 1.21 `cmp.Ordered`).
3. В теле использовать T как обычный тип.
4. Вызов: `Min[int](3, 5)` или просто `Min(3, 5)` с выводом типов.
Можно задавать несколько параметров: `func Convert[From, To any](from From) To`.
Для методов (не интерфейсных) можно добавлять ти́повые параметры: `func (s *Stack[T]) Push(val T)`. Важно: интерфейсы не могут содержать методы с ти́повыми параметрами (кроме как в качестве ограничений, но это отдельная тема).

### Под капотом (internals)
При инстанциации компилятор создаёт новую функцию с конкретными типами. Для `Min[int]` генерируется код, как если бы была функция `func Min_int(a, b int) int`. Для `Min[string]` аналогично. Мономорфизация происходит один раз на каждый набор типов. Если ограничение включает методы, то инстанцированный код содержит вызовы методов через интерфейс, но с известным статическим типом? На самом деле для ограничений-интерфейсов без union, T — это интерфейсный тип, т.е. функция будет принимать значение интерфейса. Это отличается от простой мономорфизации (boxing). Для union-ограничений мономорфизация создаёт отдельную функцию для каждого типа.

### Типичные ошибки кандидатов
1. **Забывают, что с `any` нельзя выполнять операции типа `+`, `==` (для несравнимых типов).** Код не скомпилируется.
2. **Попытка определить метод с ти́повым параметром на уровне типа:** `func (s Stack) Push[T any](val T)` — такое возможно, но нужно понимать отличия.
3. **Избыточное использование дженериков для функции, которая реально нужна только для пары типов.** Лучше написать две конкретные функции, если переиспользование не нужно.

### Возможные дополнительные вопросы интервьюера
*Как задать generic-функцию с ограничением, что тип должен поддерживать оператор `*`?* Создать интерфейс-ограничение с union числовых типов; для оператора `*` надо ограничить `Number`.
*Можно ли использовать дженерики в рекурсивных функциях?* Да, если ограничения позволяют.

## Что такое «слабая связанность» и как интерфейсы помогают её достичь?

### Краткий ответ (30–60 секунд)
Слабая связанность (loose coupling) — это принцип, при котором компоненты системы минимально зависят друг от друга, что упрощает замену, тестирование и поддержку. Интерфейсы в Go способствуют этому, определяя контракт поведения без ссылки на конкретную реализацию, а также через правило «принимай интерфейсы, возвращай структуры».

### Развёрнутый ответ
Интерфейсы разрывают жёсткую связь между потребителем и поставщиком. Клиент зависит от абстракции (интерфейса), а не от конкретной реализации. Это даёт:
- Возможность заменять реализацию без изменения клиентского кода.
- Лёгкое тестирование с помощью моков/стабов.
- Возможность создавать композицию: прокси, декораторы, цепочки обязанностей.
- Упрощение рефакторинга и независимого развития модулей.

Пример: пакет бизнес-логики определяет `type UserRepository interface { Find(id int) (User, error) }`. Прикладной уровень не знает, будет ли это Postgres, Mongo или заглушка в тестах. Слабая связанность — ключ к масштабируемой архитектуре.

### Под капотом (internals)
Никаких специальных механизмов. Это архитектурный принцип, полностью поддерживаемый языком.

### Типичные ошибки кандидатов
1. **Определение интерфейсов в пакете с реализацией.** Это связывает реализацию и интерфейс. Исправление: интерфейсы должны быть определены там, где они используются (пакет потребителя), а не там, где реализованы.
2. **Создание больших интерфейсов, которые заставляют реализацию тащить множество методов.** Это повышает связанность. Решение: интерфейсы должны быть маленькими.
3. **Возврат интерфейсов из функций без необходимости.** Клиент вынужден зависеть от интерфейсного типа, хотя мог бы использовать конкретный, а интерфейс определить у себя, если нужно. Исправление: возвращать конкретные типы, принимать интерфейсы.

### Возможные дополнительные вопросы интервьюера
*Какие паттерны помогают достичь слабой связанности кроме интерфейсов?* Внедрение зависимостей (dependency injection), события, шина сообщений.
*Как интерфейсы помогают в реализации принципа инверсии зависимостей?* Высокоуровневый модуль определяет интерфейс, низкоуровневый его реализует; детали зависят от абстракций.

## Почему говорят «принимайте интерфейсы, возвращайте структуры»?

### Краткий ответ (30–60 секунд)
Это идиома Go, которая максимизирует гибкость и минимизирует связанность: функции должны принимать параметры как интерфейсы (чтобы допускать любые реализации), но возвращать конкретные типы (чтобы вызывающие могли выбирать, использовать ли им этот тип напрямую или обернуть в интерфейс). Это предотвращает «загрязнение интерфейсами» и сохраняет свободу клиента.

### Развёрнутый ответ
Принимать интерфейс: `func Read(r io.Reader)`. Тогда функция работает с любым потоком чтения, а не привязывается к `*os.File`. Возвращать структуру: `func NewFile(name string) *os.File`. Возвращая конкретный тип, вы позволяете клиенту использовать методы, специфичные для этого типа (например, `Fd()`), не требуя type assertion. Если клиенту нужен интерфейс, он может легко преобразовать: `var r io.Reader = f`. Если бы вы возвращали `io.Reader`, клиент потерял бы доступ к специфике. Исключения: когда тип действительно должен быть скрыт или реализация должна меняться динамически. Но правило разумно как дефолт.

### Под капотом (internals)
Никакой магии, это дизайн-решение, экономящее интерфейсные boxing и упрощающее документацию.

### Типичные ошибки кандидатов
1. **Возврат интерфейса, особенно из пакетов-реализаций.** Это навязывает клиенту интерфейс, сковывая его. Исправление: возвращать конкретный тип.
2. **Создание функции, принимающей конкретную структуру, когда достаточно интерфейса.** Это усложняет тестирование и переиспользование. Исправление: принимать минимальный интерфейс.
3. **Возврат интерфейса внутри приватной логики — обычно допустимо, но публичный API должен следовать правилу.**

### Возможные дополнительные вопросы интервьюера
*Всегда ли нужно возвращать структуру?* Нет, иногда возврат интерфейса оправдан (например, `hash.Hash`), но это исключения, подтверждающие правило.
*Как эта идиома соотносится с внедрением зависимостей?* Она облегчает DI, так как потребитель сам решает, какой интерфейс ему нужен.

## Как использовать `defer` для метода с pointer receiver?

### Краткий ответ (30–60 секунд)
`defer` с методом на pointer receiver фиксирует получатель в момент выполнения `defer`, а не в момент вызова отложенной функции. Если получатель — указатель, defer запоминает этот указатель, и значения его полей на момент фактического выполнения могут измениться. Для сохранения значений нужно передавать аргументы явно.

### Развёрнутый ответ
Пример:
```go
type Counter struct { v int }
func (c *Counter) Inc() { c.v++ }

func main() {
    c := &Counter{v: 10}
    defer c.Inc()     // здесь c зафиксирован
    c.v = 20
    // при выходе c.Inc() увеличит c.v, который уже 20
}
```
`c` — указатель, он фиксирован, но данные, на которые он указывает, могут измениться до вызова `defer`. Это отличается от `defer` с value receiver, где делается копия значения в момент `defer`:
```go
func (c Counter) Inc() { ... } // не меняет оригинал, но defer сохранит копию
```
Для гарантии неизменности параметров перед defer можно захватить их в замыкание или передать в функцию: `defer func() { c.Inc() }()`.

### Под капотом (internals)
При `defer c.Inc()` компилятор вычисляет `c` (указатель) и сохраняет его в отложенном вызове. Метод `Inc` имеет сигнатуру `Inc(c *Counter)`. Сохранённый указатель передаётся при фактическом вызове. Если `c` — nil в момент выполнения — паника. Для `defer c.Inc()` с value receiver: получатель копируется немедленно в record deferred call.

### Типичные ошибки кандидатов
1. **Ожидание, что `defer c.Inc()` использует копию значения.** Изменения полей до выполнения отразятся, что может быть неочевидно.
2. **Забывание, что получатель указатель может стать nil после defer, но до вызова.** Повлечёт панику. Исправление: проверять на nil внутри метода или не допускать nil.
3. **Использование `defer` в цикле с получателем-указателем без учёта, что все отложенные вызовы будут использовать последнее значение указателя.** Это ведёт к багу. Решение: копировать указатель или использовать параметры.

### Возможные дополнительные вопросы интервьюера
*Как отложить метод с параметрами?* Аргументы метода вычисляются немедленно, даже если получатель — указатель; т.е. `defer obj.Method(arg)` — `arg` вычисляется сразу, `obj` фиксируется.
*Чем отличается `defer obj.Method()` от `defer func() { obj.Method() }()`?* Замыкание захватывает `obj` по ссылке, что может дать тот же эффект; но если `obj` — переменная, которая переназначается, замыкание увидит последнее значение, а прямой defer — значение на момент defer.

## Что такое `method value` и `method expression`?

### Краткий ответ (30–60 секунд)
`method value` — это когда вы сохраняете метод конкретного экземпляра в переменную: `f := obj.Method`. Это замыкание, запоминающее получатель. `method expression` — это выражение, которое берёт метод типа и превращает его в функцию, где получатель становится первым параметром: `f := Type.Method`, вызов `f(obj, args...)`.

### Развёрнутый ответ
Method value:
```go
c := &Counter{v: 10}
inc := c.Inc      // type: func()
inc()             // увеличит c.v
```
Здесь `inc` — функция, которая уже привязана к `c`. Под капотом — замыкание, хранящее `c`.

Method expression:
```go
inc := (*Counter).Inc // type: func(*Counter)
inc(c)                // вызов с явным получателем
```
Полезно, когда нужно вызвать метод для нескольких получателей или передать метод как обычную функцию, определяя получатель позже.

### Под капотом (internals)
Method value реализуется как замыкание, компилятор создаёт структуру, содержащую указатель на получатель и указатель на функцию метода. Method expression — это просто функция с дополнительным первым аргументом, компилятор делает прямую ссылку на метод, игнорируя получатель в момент объявления. Для value receiver method expression сигнатура будет `func(Type, args...)`. Для pointer receiver — `func(*Type, args...)`.

### Типичные ошибки кандидатов
1. **Попытка изменить получатель при method value, когда получатель value.** `inc` будет работать с копией.
2. **Путаница с типами:** `Counter.Inc` и `(*Counter).Inc` могут иметь разные сигнатуры в зависимости от receiver. Нужно внимательно смотреть, какой метод нужен.
3. **Использование method expression с неверным числом аргументов** — компилятор подскажет.

### Возможные дополнительные вопросы интервьюера
*Можно ли передать method value в горутину?* Да, это обычная функция.
*Как method expression помогает обходить ограничения выбора метода при конфликтах?* Можно явно указать, метод какого встроенного типа вызывать.

## Как интерфейсы влияют на производительность (динамическая диспетчеризация)?

### Краткий ответ (30–60 секунд)
Вызов метода через интерфейс требует динамической диспетчеризации: загрузки указателя на метод из таблицы `itab` и косвенного вызова, что медленнее прямого вызова. Также создание интерфейсного значения может вызвать аллокацию (boxing) и увеличить давление на GC. Однако для большинства приложений это не является проблемой; критические участки можно оптимизировать, избегая ненужных интерфейсов в горячих путях.

### Развёрнутый ответ
Накладные расходы:
1. **Косвенный вызов:** невозможность инлайнинга в большинстве случаев, потому что компилятор не знает конкретную реализацию. Это может замедлить вызовы мелких методов.
2. **Боксинг:** при присваивании значения интерфейсу, если значение не помещается в слово, оно копируется в кучу (или создаётся указатель на копию). Это вызывает аллокацию.
3. **Размер интерфейсного значения:** передача интерфейса как аргумента копирует два слова (16 байт), что больше чем указатель (8 байт).
4. **Проверка типов:** type assertion и type switch требуют сравнения `itab`, но кэширование делает это быстрым.

Когда интерфейс оправдан: полиморфизм, разделение зависимостей, тестирование. В горячих циклах можно передавать интерфейс, но хранить преобразованный конкретный тип для интенсивных операций, если это критично.

### Под капотом (internals)
Динамический вызов: `MOVQ itab + offset(fun[0]), AX; CALL AX`. Отсутствие инлайнинга может замедлять код до 2-3x для тривиальных методов. Компилятор иногда способен девиртуализировать вызов, если может доказать, что интерфейс хранит единственный конкретный тип (после анализа). Go 1.22 улучшил devirtualization для некоторых сценариев. Боксинг минимизируется escape-анализом: если интерфейсная переменная не покидает функцию, значение может быть размещено на стеке и указатель передан в `data`.

### Типичные ошибки кандидатов
1. **Преждевременная оптимизация:** отказ от интерфейсов без профилирования. В 99% случаев интерфейсы не являются узким местом.
2. **Создание интерфейса в цикле с последующим вызовом метода:** аллокация на каждой итерации может быть проблемой. Лучше создать интерфейс вне цикла, если значение статично.
3. **Использование пустых интерфейсов для передачи больших структур без необходимости:** каждое присвоение боксит структуру.

### Возможные дополнительные вопросы интервьюера
*Когда компилятор может деви-интерфейс?* Когда видит, что интерфейсная переменная всегда содержит одно конкретное значение, и может заменить вызов прямым.
*Что такое escape analysis и как он помогает интерфейсам?* Позволяет хранить данные на стеке и избегать аллокации при создании интерфейса.

## Как работают интерфейсы с дженериками (Generic Interfaces)?

### Краткий ответ (30–60 секунд)
В Go обобщённые интерфейсы не могут иметь методы с собственными ти́повыми параметрами (пока). Но интерфейсы могут быть параметризованы типом: `type Container[T any] interface { Get() T; Set(T) }`. Такой интерфейс используется как ограничение или для создания переменных с конкретным типом-аргументом: `var c Container[int]`.

### Развёрнутый ответ
Объявить generic-интерфейс можно:
```go
type Setter[T any] interface {
    Set(value T)
}
type IntHolder struct { val int }
func (h *IntHolder) Set(v int) { h.val = v }
// Создание: var s Setter[int] = &IntHolder{}
```
Использовать такой интерфейс как ограничение: `[T any, S Setter[T]]` — параметр `T` должен быть каким-то типом, а `S` — типом, реализующим `Setter[T]`. Это мощный паттерн для обобщённых контейнеров. Однако, в текущем Go (1.22) интерфейс не может содержать метод с собственным ти́повым параметром: `type Fooer interface { Foo[T any](t T) }` — недопустимо. Это ограничение может быть снято в будущем.

### Под капотом (internals)
При инстанцировании `Setter[int]` создаётся конкретный интерфейсный тип с методами, как если бы был определён `type Setter_int interface { Set(int) }`. В таблицах `itab` для `*IntHolder` создаётся запись, реализующая `Setter[int]`. Всё работает через обычную механику `itab`, просто типы интерфейсов разные для разных аргументов. Мономорфизация применяется и к интерфейсам.

### Типичные ошибки кандидатов
1. **Попытка объявить метод с ти́повым параметром внутри интерфейса.** Ошибка компиляции. Обход: использовать generic-тип на уровне самого интерфейса.
2. **Смешение параметризованного интерфейса с union-ограничением.** Когда у интерфейса есть методы и параметр T, его нельзя использовать как union.
3. **Создание переменной неинстанцированного интерфейса:** `var x Setter` без `[T]` запрещено.

### Возможные дополнительные вопросы интервьюера
*Можно ли использовать generic-интерфейс в type switch?* Да, но нужно указать конкретный аргумент типа: `switch v := x.(type) { case Container[int]: ... }`.
*Как generic-интерфейсы взаимодействуют с `comparable`?* Можно создать `type C[T comparable] interface { ... }`.

## Что такое «прокси-интерфейс» и для чего он может применяться?

### Краткий ответ (30–60 секунд)
Прокси-интерфейс — это интерфейс, который реализуется типом-посредником (прокси), делегирующим вызовы реальному объекту, добавляя дополнительное поведение: логирование, кеширование, контроль доступа, трассировка, обогащение. Это классический паттерн «Прокси», легко реализуемый благодаря неявной реализации интерфейсов.

### Развёрнутый ответ
Пусть есть `interface DataStore { Get(key string) (string, error) }`. Прокси:
```go
type LoggingStore struct {
    next DataStore
}
func (l *LoggingStore) Get(key string) (string, error) {
    log.Println("Get", key)
    return l.next.Get(key)
}
```
Теперь `LoggingStore` реализует `DataStore` автоматически. Можно обернуть реальное хранилище, добавив логирование, без изменения клиентского кода. Применяется для:
- Кеширования (Cache Proxy)
- Трассировки и профилирования
- Rate limiting
- Retry логики
- Авторизации
- Тестовых заглушек, которые оборачивают реальную реализацию с инжекцией ошибок.
Этот паттерн — прямое следствие интерфейсов и композиции.

### Под капотом (internals)
Никаких дополнительных механизмов. Реализация сводится к хранению поля типа интерфейса и вызову его методов.

### Типичные ошибки кандидатов
1. **Создание прокси, который не реализует спрятанных методов.** Если в будущем интерфейс расширится, прокси может не скомпилироваться. Решение: встраивать интерфейс в структуру прокси (`LoggingStore struct { DataStore }`), тогда по умолчанию все новые методы будут делегированы, если не переопределены.
2. **Забывание обработки ошибок при делегировании.** Прокси может подавить ошибку или исказить её.
3. **Глубокая цепочка прокси, приводящая к накладным расходам и сложности отладки.** Не злоупотреблять.

### Возможные дополнительные вопросы интервьюера
*Как embed интерфейса помогает в прокси?* Позволяет не реализовывать все методы явно; автоматическое делегирование встроенному полю.
*Можно ли создать прокси, меняющий тип возвращаемого значения?* Только если новый тип также удовлетворяет интерфейсу; можно обернуть результат.

## Как протестировать код, зависящий от интерфейса, с помощью моков?

### Краткий ответ (30–60 секунд)
Для тестирования создаётся тип-заглушка (mock), реализующий нужный интерфейс, с методами, предоставляющими предопределённые ответы или проверяющими вызовы. Это позволяет изолировать тестируемый код от реальных зависимостей. В Go часто используют ручные моки или кодогенерацию (mockgen), но суть одна — удовлетворить контракт интерфейса.

### Развёрнутый ответ
Пример ручного мока для `UserRepository`:
```go
type mockRepo struct {
    findFunc func(id int) (User, error)
}
func (m *mockRepo) Find(id int) (User, error) { return m.findFunc(id) }
```
В тесте:
```go
repo := &mockRepo{ findFunc: func(id int) (User, error) { return User{ID: id}, nil } }
svc := NewService(repo)
...
```
Можно также создавать структуры с полями-каналами, счётчиками вызовов. Для сложных случаев используют `github.com/golang/mock` (mockgen), `github.com/stretchr/testify/mock` или `github.com/matryer/moq`. Тестирование через интерфейсы — одна из причин, почему Go-код хорошо тестируется.

### Под капотом (internals)
Ничего специфичного. Благодаря неявной реализации мок-типу не нужно объявлять, что он реализует интерфейс.

### Типичные ошибки кандидатов
1. **Создание моков с избыточной логикой, которая сама становится сложной и требует тестирования.** Мок должен быть простым.
2. **Использование моков там, где достаточно реальной легковесной реализации (например, in-memory repository).** Это уменьшает разрыв с реальностью.
3. **Забывание, что мок должен полностью реализовывать интерфейс; при изменении интерфейса моки ломаются.** Регулярное обновление.

### Возможные дополнительные вопросы интервьюера
*Что такое моки против стабов?* Стаб возвращает фиксированные ответы, мок — проверяет ожидания взаимодействия.
*Какие инструменты для генерации моков популярны?* `mockgen`, `moq`, `counterfeiter`.

## Как работает утверждение типа для non-interface значения?

### Краткий ответ (30–60 секунд)
Type assertion (`x.(T)`) требует, чтобы `x` был интерфейсного типа. Для не-интерфейсного значения применяется преобразование типа (`T(x)`), которое проверяется во время компиляции и допустимо только для совместимых типов. Однако есть понятие «non-interface type assertion»? Такого нет; это всегда преобразование.

### Развёрнутый ответ
Путаница возникает, когда значение имеет статический конкретный тип, а хочется «утверждать» его к интерфейсу. Делается это через присваивание: `var r io.Reader = myReader`. Если `myReader` уже реализует интерфейс, работает; иначе ошибка компиляции. Нельзя сделать `myReader.(io.Reader)` — синтаксис только для интерфейсных выражений. Для дженериков: если `x` имеет тип параметра `T`, а ограничение — `any`, то `x.(int)` не компилируется, потому что `x` не интерфейсного типа. Поэтому используют `interface{}(x).(int)` или type switch после приведения к `interface{}`.

### Под капотом (internals)
Компилятор различает синтаксис assertion только для интерфейсов. Преобразование типа `T(x)` генерирует инструкции конвертации, возможно, с изменением представления.

### Типичные ошибки кандидатов
1. **Попытка использовать утверждение типа на конкретном типе: `var s string; s.(int)`.** Ошибка компиляции. Решение: использовать `strconv` или `interface{}(s).(int)` с осторожностью.
2. **Использование приведения к интерфейсу для проверки типа, когда достаточно присвоения.**
3. **В дженериках:** попытка `t.(SomeInterface)` без предварительного преобразования в `interface{}`.

### Возможные дополнительные вопросы интервьюера
*Как проверить, реализует ли конкретный тип интерфейс во время выполнения без утверждения?* Через `reflect` или присвоение интерфейсу с проверкой `ok` паттерном (не применимо). Обычно это делается на этапе компиляции через and `var _ Iface = (*MyType)(nil)`.
*Можно ли преобразовать не-интерфейс в интерфейс во время выполнения?* Да, простым присваиванием.

## В чем отличие дженериков Go от шаблонов C++?

### Краткий ответ (30–60 секунд)
Дженерики Go используют ограничения на основе интерфейсов и компилируются через мономорфизацию без текстовой подстановки. Шаблоны C++ — это система макросов времени компиляции, дающая duck typing на этапе инстанцирования. Шаблоны мощнее, но сложнее, с неявными требованиями и раздуванием сообщений об ошибках. Дженерики Go спроектированы для простоты и явных контрактов.

### Развёрнутый ответ
| Аспект | Go Generics | C++ Templates |
|--------|-------------|---------------|
| Проверка типов | До инстанцирования по ограничениям | Во время инстанцирования (SFINAE, концепты с C++20) |
| Контракт | Явный интерфейс с методами/union | Неявный набор операций (duck typing) |
| Специализация | Нет | Полная и частичная специализация |
| Метапрограммирование | Нет (не Тьюринг-полное) | Тьюринг-полное |
| Размер кода | Мономорфизация с GCShape | Каждая инстанциация — новый код (может раздувать) |
| Сообщения об ошибках | Ясные, ссылаются на ограничение | Многословные, трудночитаемые (улучшены концептами) |
| Поддержка non-type параметров | Нет (только типы) | Да (значения, шаблоны шаблонов) |

Go сделал ставку на простоту и скорость компиляции, избегая «шаблонного метапрограммирования». Ограничения — это интерфейсы, которые проверяются до инстанцирования, что даёт чёткие ошибки.

### Под капотом (internals)
В Go: мономорфизация с словарём инстанцирования. В C++: код генерируется для каждого набора аргументов шаблона, возможно с встраиванием. Отсутствие специализации в Go упрощает компилятор и линковку.

### Типичные ошибки кандидатов
1. **Ожидание, что Go generics поддерживают специализацию.** Нет, нужно использовать разные функции.
2. **Попытка использовать шаблонные трюки (CRTP, expression templates).** Не применимы.
3. **Недопонимание, что ограничения в Go не duck typing: все операции должны быть разрешены ограничением.**

### Возможные дополнительные вопросы интервьюера
*Можно ли в Go сделать generic-функцию, разную для разных типов?* Только через type switch внутри, без статической специализации.
*Что общего у дженериков Go и концептов C++?* Оба задают формальные требования к типам, но в Go это часть языка с самого начала, а в C++ добавлено позже.

## Как эволюция интерфейсов в Go влияет на обратную совместимость в библиотеках?

### Краткий ответ (30–60 секунд)
Go гарантирует обратную совместимость на уровне языка. Добавление метода в интерфейс ломает все реализации за его пределами, поэтому в публичных API следует избегать расширения интерфейсов. Введение дженериков и новых ограничений совместимо, так как не меняет существующие интерфейсы. Расширение стандартных интерфейсов (например, `io.Reader`) невозможно без нарушения контракта, поэтому стандартная библиотека создаёт новые подинтерфейсы или отдельные интерфейсы.

### Развёрнутый ответ
Принципы:
- Изменение сигнатуры метода в интерфейсе — разрушительное изменение (breaking change).
- Добавление метода в интерфейс — ломает все существующие реализации.
- Удаление метода из интерфейса также ломает код, ожидающий этот метод.
- Добавление нового интерфейса безопасно.
- Добавление методов в конкретные типы безопасно.

Библиотеки решают это через выпуск новых версий (v2) с новыми именами или через композицию интерфейсов. Стандартная библиотека придерживается обещания совместимости: `io.Reader` не менялся с Go 1.0. Когда потребовалась функциональность `ReadByte`, добавили `io.ByteReader` с единственным методом, а не расширяли `Reader`.

Дженерики: создание generic-интерфейса `Set[T any]` безопасно; но если вы измените существующий не-generic интерфейс на generic — это breaking change.

### Под капотом (internals)
Компилятор не запрещает ломать обратную совместимость, это ответственность разработчика. `go mod` управляет версионированием, мажорные изменения требуют нового import path.

### Типичные ошибки кандидатов
1. **Добавление метода в публичный интерфейс при минорном обновлении.** Это ломает код клиентов. Исправление: публиковать новую мажорную версию или создавать новый интерфейс.
2. **Использование `interface{}` в публичном API, а затем переход на дженерики без сохранения старой сигнатуры.** Нарушает обратную совместимость. Лучше добавлять новую generic-функцию рядом.
3. **Предположение, что обратная совместимость автоматически гарантируется языком для всех конструкций.** Ответственность лежит на разработчиках библиотек.

### Возможные дополнительные вопросы интервьюера
*Как стандартная библиотека развивает интерфейсы без нарушения обратной совместимости?* Путем создания дополнительных интерфейсов, таких как `io.ReaderAt`, `io.WriterTo`.
*Что такое «Compatible changes» в Go модулях?* Изменения, не требующие смены мажорной версии.

## Что такое "interface pollution" и как его избежать?

### Краткий ответ (30–60 секунд)
Interface pollution — это бессмысленное создание интерфейсов, которые не несут полезной абстракции: дублируют сигнатуры конкретных типов, имеют только одну реализацию, или слишком велики и неудобны. Это усложняет код, не давая преимуществ. Избежать можно, следуя правилу: интерфейсы должны представлять поведение, а не данные; начинать с конкретных типов и вводить интерфейсы только при появлении реальной потребности в полиморфизме.

### Развёрнутый ответ
Признаки pollution:
- Интерфейс с единственным типом, который никогда не получит другие реализации.
- Интерфейс, зеркально повторяющий все методы конкретной структуры.
- Интерфейс, определённый в том же пакете, что и его единственная реализация, и экспортируемый наружу.
- Интерфейсы с огромным списком методов (например, 10+).

Правила избежания:
- Следуйте идиоме «принимайте интерфейсы, возвращайте структуры».
- Определяйте интерфейсы там, где они используются (пакет потребителя), а не там, где реализуются.
- Начинайте с конкретных типов, и только когда требуется несколько реализаций или моки, выделяйте интерфейс.
- Предпочитайте мелкие интерфейсы (1–3 метода), разделяйте большие.
- Используйте embedding для композиции без дублирования.

Пример pollution: `type MyServiceInterface interface { Do() }` с одной реализацией `myServiceImpl` в том же пакете — бесполезен.

### Под капотом (internals)
Интерфейсное загрязнение вредит производительности компиляции (увеличение количества типов, itab) и увеличивает бинарный размер незначительно. Основной ущерб — архитектурный: сложность поддержки и понимания кода.

### Типичные ошибки кандидатов
1. **Создание интерфейса для каждой структуры «на будущее».** YAGNI. Отложите до реальной необходимости.
2. **Экспорт интерфейса вместе с реализацией.** Потребитель должен сам определить нужный контракт.
3. **Добавление в интерфейс всех возможных методов, а не минимально нужных.** Это нарушает принцип разделения интерфейсов.

### Возможные дополнительные вопросы интервьюера
*Как отличить хороший интерфейс от плохого?* Хороший интерфейс маленький, определён потребителем, имеет несколько независимых реализаций, и его сигнатура отражает реальную потребность.
*Может ли interface pollution повлиять на производительность?* Минимально, но основное — усложнение кода и тестов.
