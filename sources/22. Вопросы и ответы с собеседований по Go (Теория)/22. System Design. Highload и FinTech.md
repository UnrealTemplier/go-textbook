## Как проектировать highload систему?

### Краткий ответ
Проектирование highload-системы начинается с определения целевых показателей: RPS, latency percentiles (p99.9), объем данных, допустимое время простоя. Далее применяются принципы горизонтального масштабирования, stateless-сервисов, шардирования БД, асинхронной обработки через очереди, кэширования и graceful degradation. Ключевое — строить систему на основе ограничений (backpressure, тайм-ауты, circuit breaker), тестировать нагрузкой и итеративно оптимизировать «узкие горлышки».

### Развёрнутый ответ
Проект начинают с нефункциональных требований: 100k RPS, p99 < 100ms, 99.99% доступности. Архитектура опирается на микросервисы, каждый из которых отвечает за ограниченный контекст (bounded context). Сервисы делаются **stateless**, чтобы любое количество реплик могло обрабатывать запросы. Состояние (сессии, балансы) выносится во внешние хранилища с поддержкой горизонтального масштабирования: Redis, Cassandra, CockroachDB, DynamoDB.

Основные паттерны:
- **Шардирование и партиционирование** данных по ключу (например, user_id), чтобы распределить нагрузку и избежать hot partitions.
- **Асинхронная развязка** через Apache Kafka, NATS, Redis Streams: запросы на запись отправляются в очередь, а клиенту возвращается немедленный подтверждение (eventual consistency).
- **Многоуровневое кэширование**: локальный in-memory кэш (ristretto, bigcache) + распределённый Redis, с инвалидацией через TTL или события БД.
- **Rate limiting и backpressure** на всех входящих точках: API-шлюз с алгоритмом token bucket/sliding window, внутренние сервисы с ограниченными каналами или семафорами.
- **Отказоустойчивость**: Circuit Breaker, тайм-ауты, автоматические retry с jitter, fallback-ответы, health checks.

В Go для высоконагруженного HTTP-сервера используют `fasthttp` или кастомный TCP-сервер с пулом горутин, ручным управлением памятью (arena, sync.Pool). Все аллокации на горячем пути минимизируют, escape analysis проверяется с помощью `go build -gcflags="-m"`. Применяется **rate limiter на основе слайсов** для скользящего окна за O(1).

### Под капотом (internals)
В Go runtime каждая горутина стоит ~2 КБ стека, планировщик work-stealing распределяет горутины по потокам ОС. Для highload критично избегать блокировок в epoll/kqueue: netpoller автоматически паркует горутины при ожидании I/O. При обработке сотен тысяч соединений используется асинхронный ввод-вывод с горутинами, но нужно контролировать количество одновременно активных горутин через семафоры (`make(chan struct{}, max)`).  

При использовании каналов (`chan`) важно помнить, что небуферизованный канал даёт синхронную backpressure, а буферизованный с большим capacity может привести к буферизации задержек и нарушению контроля потока. Внутренне канал — это структура `hchan`, хранящая кольцевой буфер и очереди ожидающих горутин. При переполнении буфера горутина-отправитель блокируется и помещается в очередь ожидания, что уже реализует естественный backpressure.

Для оптимизации сериализации/десериализации JSON на критическом пути используют кодогенераторы (easyjson, ffjson) или бинарные протоколы (protobuf + gRPC), которые снижают количество аллокаций за счёт `sync.Pool` для временных объектов.

### Типичные ошибки кандидатов
- **Игнорирование backpressure**: предполагают, что очередь Kafka бесконечна и не ограничивают продюсеров. Исправление: обернуть отправку в канал ограниченной ёмкости с тайм-аутом, использовать Context, чтобы отклонять запросы при перегрузке.
- **Stateless-сервис с локальным кэшем без стратегии инвалидации**: кэш расходится, и пользователи видят устаревшие данные. Исправление: TTL + broadcast-сообщения об инвалидации через pub/sub или использование распределённого кэша с версионированием.
- **Синхронное обновление нескольких сервисов в одной транзакции**: приводит к долгим цепочкам и снижению доступности. Исправление: применять паттерн «Сага» или Outbox для асинхронного выполнения с компенсирующими действиями.
- **Завязка на конкретное хранилище без абстракции**: замена БД или кэша невозможна без переписывания кода. Исправление: выделение интерфейсов хранилища, внедрение через DI, использование паттерна Repository.

### Возможные дополнительные вопросы интервьюера
- *«Как бы вы решали проблему горячей партиции в Cassandra при масштабировании?»* — Разбил бы партицию с помощью дополнительного ключа (compound partition key), например, добавив случайное число 0..N-1 к user_id, затем маршрутизировал запросы к нужному шарду на основе этого ключа, увеличивая пропускную способность в N раз.
- *«Где в highload системе допустима eventual consistency, а где нужна strong?»* — Профили пользователей, ленты новостей — eventual, баланс счёта или количество товара в наличии — strong (linearizable reads via Paxos/Raft). Всегда определяем, допускает ли бизнес-логика расхождения и насколько критична задержка.
- *«Как организовать тестирование нагрузки на этапе разработки?»* — Используем k6 или wrk2 с генерацией realistic traffic patterns, эмулируем пики, запуская в CI при каждом PR. Проверяем поведение при исчерпании ресурсов (chaos engineering) с помощью toxiproxy для network latency.

## Как делать rate limiter?

### Краткий ответ
Реализуется алгоритм фиксированного окна, скользящего окна (sliding window log/counter) или token bucket. В распределённой среде состояние хранится в Redis с атомарными операциями (Lua-скрипты), локальный rate limiter — в памяти с sync.Map. Ключом служит client_id, endpoint, IP. Go-реализация: пакет `golang.org/x/time/rate` (token bucket) или кастомный слайс для скользящего окна.

### Развёрнутый ответ
Rate limiter предотвращает перегрузку и гарантирует справедливость. Выделяют:
- **Token bucket**: пополняется с постоянной скоростью, позволяет краткосрочные всплески (burst). Подходит для ограничения среднего темпа.
- **Leaky bucket**: очередь постоянной длины, задерживает запросы до равномерного темпа — сглаживает трафик.
- **Fixed window counter**: простейший, но допускает удвоение нагрузки на границе окна.
- **Sliding window log**: хранит временные метки запросов и удаляет старые, даёт точное ограничение, но требует O(N) памяти.
- **Sliding window counter**: аппроксимирует нагрузку, комбинируя счётчики предыдущего и текущего окна с весом; компромисс точности и памяти.

В распределённом рейт-лимитере используется Redis с командой `INCR` и `EXPIRE`, либо Lua-скрипт для атомарного обновления скользящего окна. В Go удобно применять `redis_rate` или имплементировать Lua-скрипт самому:

```go
const slidingWindowScript = `
local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local count = redis.call('ZCARD', key)
if count < limit then
    redis.call('ZADD', key, now, now .. '-' .. math.random())
    redis.call('EXPIRE', key, window)
    return 1
else
    return 0
end
`
```

Для Go-сервиса на одном узле пишут lock-free версию: массив временных меток с атомарным индексом по модулю размера, или используют `xsync.Map` для хранения окна. Встроенный `rate.Limiter` — отличный выбор для локального ограничения; его можно использовать внутри middleware, проверяя `lim.Allow()`.

### Под капотом (internals)
`rate.Limiter` использует token bucket с расчётом времени последнего запроса и виртуального числа токенов. Внутри он блокирует мьютекс только при резервировании (метод `Reserve`), а `Allow` вызывает `AllowN(now, 1)`, который без блокировки делает быстрый путь через `float64`-арифметику с атомарным доступом к полю `lim.last` (через `atomic.LoadInt64`). 

Если реализовать скользящее окно локально, можно использовать кольцевой буфер `[]int64` размером window/accuracy и инкрементировать bucket с помощью `atomic.AddInt64`. Планировщик в Go сам позаботится о переключениях, но contention между горутинами минимален при использовании шардированных структур (например, `map[clientID]*bucket` с RW-мьютексом на шард).

### Типичные ошибки кандидатов
- **Использование глобального мьютекса на каждый запрос**: под высоким RPS возникает сильный contention. Исправление: шардировать счётчики по ключу (client_id) с помощью `sync.Map` или полосатого мьютекса (striped mutex), где хэш ключа выбирает один из N мьютексов.
- **Расчет rate limit только на gateway без учёта внутренних сервисов**: backpressure не передаётся, внутренние очереди переполняются. Исправление: каскадный rate limiting — каждый сервис имеет свой лимитер, а при отказе возвращает 429, шлюз ретраит с backoff.
- **Ручное управление expire без атомарности в Redis**: race condition между INCR и EXPIRE может сделать ключ вечным. Исправление: использовать `MULTI/EXEC` транзакцию или Lua-скрипт, где INCR и установка TTL атомарны.

### Возможные дополнительные вопросы интервьюера
- *«Как rate limiter поведёт себя при рестарте Redis?»* — При рестарте данные в оперативной памяти теряются, все счётчики обнулятся и может хлынуть лавина запросов. Решение: включить персистентность RDB/AOF, либо в коде приложения задать дефолтный “запасной” локальный лимитер, включаемый при недоступности Redis.
- *«Как реализовать rate limiter с приоритетами?»* — Использовать несколько bucket-ов или очередей с разными лимитами и весами; в Lua-скрипте проверять сначала приоритетный ключ, затем обычный, и распределять разрешения согласно приоритетам.
- *«Чем sliding window counter отличается от token bucket в отношении burst?»* — Sliding window counter задаёт жёсткое ограничение на скользящий период, не позволяя легальный burst больше определённого числа запросов за окно, в то время как token bucket может накопить токены до максимума и допустить большие пики. Выбирается по бизнес-требованиям: если допустимы краткие пики — token bucket.

## Как делать идемпотентность ключей (idempotency keys)?

### Краткий ответ
Клиент генерирует уникальный ключ для каждой новой операции и передаёт его в заголовке (Idempotency-Key). Сервер сохраняет ключ вместе с результатом выполнения в атомарном хранилище, проверяя его перед началом обработки. Если ключ уже существует, возвращается сохранённый ответ без повторного выполнения операции. Обязательно использовать уникальность ключа в рамках клиента (UUID v4) и TTL для очистки старых записей.

### Развёрнутый ответ
Идемпотентные API критичны в платёжных системах: повторный POST не должен привести к двойному списанию. Механизм:
1. Клиент создаёт UUID v4 и посылает запрос с `Idempotency-Key: <uuid>`.
2. Сервер в начале транзакции проверяет хранилище (Redis или БД) на наличие ключа. Обычно используется конструкция `SET key value NX EX 86400` в Redis — атомарное создание с TTL.
3. Если ключ создан успешно, выполняется бизнес-логика, результат (статус, тело ответа) сохраняется как значение ключа.
4. Если ключ уже существует, извлекается сохранённый ответ и немедленно возвращается клиенту.

В Go это оборачивается в middleware:

```go
func IdempotencyMiddleware(store IdempotencyStore) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            key := r.Header.Get("Idempotency-Key")
            if key == "" {
                // пропускаем без идемпотентности
                next.ServeHTTP(w, r)
                return
            }
            if resp, ok := store.Get(key); ok {
                w.WriteHeader(resp.StatusCode)
                w.Write(resp.Body)
                return
            }
            // устанавливаем маркер "processing", чтобы конкурентные запросы ожидали
            if !store.TryLock(key) {
                // ожидаем или возвращаем 409 Conflict
            }
            // захватываем ответ через кастомный ResponseWriter
            rec := httptest.NewRecorder()
            next.ServeHTTP(rec, r)
            store.Store(key, rec.Result())
        })
    }
}
```

Важно: ключ должен быть уникальным для конкретной операции, а не для всего запроса. Например, `payment_id` + сумма + получатель — хэш, чтобы идемпотентность действовала только для идентичных запросов. TTL обычно 24-48 часов, чтобы не хранить вечно.

### Под капотом (internals)
Redis `SET NX EX` атомарен, т.к. Redis исполняет одну команду за раз в одном потоке. В Go-коде используем библиотеку `go-redis`. Альтернативно, можно использовать PostgreSQL с `INSERT ... ON CONFLICT DO NOTHING`, где уникальный индекс на поле ключа обеспечивает идемпотентность на уровне БД. При использовании `sync.Map` в локальном кэше нужно гарантировать, что между проверкой и вставкой нет гонки: `LoadOrStore` идеально подходит, возвращая предыдущее значение, если оно было.

### Типичные ошибки кандидатов
- **Клиент генерирует ключ один раз и повторно использует его для разных операций**: приводит к тому, что все запросы клиента воспринимаются как повторы, и все, кроме первого, возвращают некорректный результат. Исправление: генерировать новый ключ на каждую уникальную бизнес-операцию, можно включать временную метку и инкремент.
- **Отсутствие конкурентного контроля**: два параллельных запроса с одним ключом могут оба увидеть отсутствие ключа и выполнить операцию дважды. Исправление: добавить lock (Redis `SETNX` с коротким TTL как lock) или использовать транзакцию БД с проверкой и вставкой ключа в одной транзакции.
- **Бесконечный TTL или отсутствие чистки**: хранилище растёт неограниченно. Исправление: всегда задавать TTL при создании ключа; при использовании БД — регулярный job для удаления старых записей.
- **Сохранение ответа без статуса выполнения**: если операция выполнилась, но ответ не сохранён из-за сбоя, повторный запрос приведёт к повторному выполнению. Исправление: хранить ключ в той же транзакции, что и бизнес-операция, используя БД с поддержкой атомарных записей (Redis Streams + persistence или PostgreSQL outbox).

### Возможные дополнительные вопросы интервьюера
- *«Как быть, если клиент не может сгенерировать ключ (IoT устройство)?»* — Лучше присваивать ключ на сервере в ответе на первый запрос (например, через `POST /operations` без ключа, сервер создаёт operation_id и возвращает его; дальнейшие запросы подтверждения идут с этим operation_id). Либо использовать детерминированный ключ на основе хэша тела запроса и временного окна.
- *«Что если повторный запрос приходит через 25 часов, а TTL истёк?»* — Возвращаем ошибку или выполняем операцию заново, но с особой проверкой дублирования на уровне бизнес-логики (например, проверка существования платежа с той же сделкой). Это компромисс: слишком большой TTL дорог по памяти, слишком маленький — риск дублирования.

## Saga vs 2PC?

### Краткий ответ
2PC (двухфазная фиксация) обеспечивает сильную консистентность за счёт координатора, блокирующего участников до завершения глобальной транзакции. Saga — последовательность локальных транзакций, каждая со своей компенсирующей операцией, дающая eventual consistency без блокировок. В highload-системах с долгими транзакциями и необходимостью масштабирования предпочтительнее Saga.

### Развёрнутый ответ
**2PC**: координатор запрашивает готовность участников (prepare), собирает голоса, затем принимает решение (commit/abort). Участники блокируют ресурсы на время всего процесса. Отказ координатора между фазами оставляет систему в неопределённом состоянии, поэтому применяют репликацию лога координатора и тайм-ауты с эвристическим решением. Хорошо подходит для коротких операций в пределах одного кластера БД (например, шардированный PostgreSQL с внешней транзакцией).

**Saga** — паттерн для распределённых транзакций с долгими бизнес-процессами, состоящий из шагов T1, T2, ..., Tn, и для каждого шага определена компенсирующая операция C1, C2, ..., Cn-1. Если на шаге T3 происходит ошибка, выполняются компенсации C2, C1 в обратном порядке, чтобы откатить систему в согласованное состояние. Два основных варианта: хореография (каждый сервис сам публикует события и реагирует на них) и оркестрация (центральный Saga-координатор управляет потоком).

На Go реализуют оркестрированную сагу через state machine и асинхронные каналы или очереди сообщений. Координатор хранит состояние саги в долговременном хранилище (MongoDB, Redis), чтобы пережить перезапуск. Шаги выполняются через вызовы gRPC/HTTP с таймаутами и ретраями.

Сравнение: Saga обеспечивает более высокую доступность и масштабируемость (нет блокировок), но требует компенсирующих операций, которые не всегда возможны (например, отправленное уведомление). 2PC даёт строгую изоляцию, но плохо переносит сетевые сбои и снижает пропускную способность.

### Под капотом (internals)
В распределённых БД 2PC реализован через протоколы с линейной консистентностью (Percolator в TiDB, Spanner использует TrueTime и 2PC). В коде на Go при использовании пакета `database/sql` с драйвером PostgreSQL 2PC доступен через `PREPARE TRANSACTION 'gid'` и `COMMIT PREPARED`. Saga чаще реализуется на основе фреймворков типа Temporal (Go SDK), которые предоставляют долгоживущие workflow, способные автоматически перезапускать шаги, обрабатывать тайм-ауты и сохранять состояние.

### Типичные ошибки кандидатов
- **Выбор 2PC для длительного (>1 сек) процесса**: блокировки исчерпывают пул соединений, приводят к тайм-аутам и каскадным отказам. Исправление: переходить на Saga, если бизнес-операция длится секунды/минуты.
- **Отсутствие компенсирующих операций в Saga или их неидемпотентность**: повторное выполнение компенсации при сбое координатора может привести к двойному возврату средств. Исправление: делать каждую компенсацию идемпотентной с уникальным ключом, проверять текущее состояние перед действием.
- **Хореография без контроля над зацикливанием событий**: событие A вызывает B, B вызывает C, C снова вызывает A, входя в бесконечный цикл. Исправление: вводить порядковый номер саги или монотонный счётчик, ограничивать глубину рекурсии.

### Возможные дополнительные вопросы интервьюера
- *«Можно ли комбинировать Saga и 2PC?»* — Да, например, каждый шаг саги может быть 2PC внутри небольшого кластера сервисов, при этом глобальная согласованность — саговая. Либо Saga для основного потока, а для критического шага перевода между двумя БД используется 2PC.
- *«Как откатить сагу, если одна из компенсаций тоже упала?»* — Компенсация обязана быть идемпотентной и в случае неудачи повторяться с backoff. Если недоступна критическая система, сага переходит в состояние ручного разрешения (manual intervention), используя сагу с транзакционным outbox и мониторингом.

## Как реализовать распределенную блокировку (distributed lock)?

### Краткий ответ
Используем внешнее координационное хранилище (Redis, etcd, Consul), предоставляющее атомарную операцию создания ключа с TTL. В Redis применяется команда `SET lock_key random_value NX PX TTL`, где random_value уникален для владельца. Для продления TTL используют Lua-скрипт, проверяющий принадлежность. В Go пакет `redislock` реализует этот паттерн. Надёжнее использовать etcd с Lease и сторожевым потоком.

### Развёрнутый ответ
Простейшая реализация на Redis:

```go
lock, err := redislock.Obtain(ctx, client, "lock:order:123", 10*time.Second, nil)
if err != nil {
    return ErrLockNotAcquired
}
defer lock.Release(ctx)
// критическая секция
```

Вручную:
```go
val := uuid.New().String()
ok, _ := client.SetNX(ctx, "lock_key", val, 15*time.Second).Result()
if !ok { /* не взяли */ }
```
Но при этом нужно гарантировать атомарное освобождение (проверка владельца и удаление) Lua-скриптом:
```lua
if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) else return 0 end
```

**Redlock** (рекомендован Redis) предполагает блокировку на нескольких независимых экземплярах Redis, чтобы пережить отказ одного. Клиент должен завладеть большинством узлов за короткий период, иначе снимает блокировку со всех. Важен clock drift: он может нарушить безопасность.

Более строгий вариант — etcd: через создание ключа с `Lease` и `KeepAlive`. Go-клиент `clientv3` автоматически продлевает lease, а если связь теряется, ключ удаляется. Это исключает ситуацию, когда процесс держит блокировку после зависания.

### Под капотом (internals)
В Redis `SETNX` с TTL полагается на однопоточность, атомарность гарантируется. Redlock-алгоритм страдает от проблемы неопределённой задержки GC в клиентском приложении: сборка мусора может приостановить горутину, и блокировка истечёт, пока процесс её ещё считает удерживаемой. В Go можно смягчить это, используя `runtime.GC` с осторожностью и обеспечивая продление с запасом. Лучше полагаться на etcd, где состояние блокировки активно поддерживается сервером и тайм-аутом.

### Типичные ошибки кандидатов
- **Освобождение блокировки без проверки владельца**: просто `DEL` может удалить чужую блокировку, если TTL у текущего владельца истёк, и ключ захвачен другим. Исправление: обязательно проверять значение перед удалением атомарным Lua-скриптом.
- **Использование блокировки для высококонкурентного доступа к счёту в БД**: это создаёт узкое горлышко и конфликт с транзакциями. Исправление: для операций над балансом лучше использовать оптимистическую блокировку (версия записи) или идемпотентные ключи с БД.
- **Зависимость от одной точки Redis без плана восстановления**: при потере Redis блокировки теряются, и возможны гонки. Исправление: Redlock с кворумом или etcd.

### Возможные дополнительные вопросы интервьюера
- *«Как продлить блокировку, если операция занимает больше, чем TTL?»* — Поток владельца должен периодически (на 20-30% периоде TTL) выполнять `KeepAlive` (etcd) или Lua-скрипт, проверяющий владельца и выполняющий `PEXPIRE`. Важно завершить продление до истечения, для чего используют буферизованный канал сигналов.
- *«Что такое fencing token и зачем он нужен?»* — Это монотонно возрастающий номер, присваиваемый при получении блокировки. Клиент передаёт его в запросы к ресурсу (например, записи в БД). Ресурс отвергает операции с меньшим номером, предотвращая конфликт, если предыдущий владелец «воскрес» после приостановки GC.

## Как работать с eventual consistency?

### Краткий ответ
Принимаем, что после фиксации записи реплики могут временно расходиться, но со временем сойдутся. В приложении это обрабатывают с помощью компенсирующих действий, явного управления ожиданиями (UI-паттерны), чтения с follower-реплик с пониманием возможной дельты, и, где критично, — strong read через linearizability (Raft, кворумы). В Go используют контексты с тайм-аутами, идемпотентные операции и версионирование.

### Развёрнутый ответ
Eventual consistency означает, что система гарантирует: если в данные не вносятся новые изменения, все реплики в итоге вернут одно и то же значение. Это широко применяется в NoSQL-базах (Cassandra, DynamoDB), системах репликации master-slave с асинхронным лагом.

Стратегии работы:
- **Согласованность на основе клиента**: клиент включает в запрос версию данных или токен, чтобы сервер мог определить, достаточно ли свежая реплика (session consistency).
- **Сильные чтения по требованию**: для критичных операций (проверка баланса до списания) используют чтение с кворумом (R + W > N) или от лидера.
- **Сага и компенсации**: при нарушении инварианта из-за несогласованности запускают откат.
- **UI-паттерн «Оптимистичное обновление + уведомление»**: после изменения клиент сразу показывает новое состояние, но в фоне опрашивает сервер для подтверждения; при конфликте показывает сообщение.
- **Conflict-free replicated data types (CRDT)**: структуры данных, сходящиеся без конфликтов.

Пример в Go: микросервис заказов создаёт запись в PostgreSQL, асинхронно отправляет событие в Kafka. Сервис уведомлений может получить событие позже, чем обновилась БД. Если сервис уведомлений, прежде чем отправить письмо, проверяет статус заказа в своём read-реплике, он должен учитывать возможную задержку и повторить проверку при необходимости.

### Под капотом (internals)
В основе лежит репликация: для Cassandra — hinted handoff, read repair, anti-entropy. В Go, при использовании CockroachDB (реализация Spanner-подобного консенсуса), чтение с follower возможно с точным stale-ness (опция `WITH FollowerReads`). При обращении к обычному PostgreSQL с read replica библиотечный код должен принимать параметр `read_concern` и при необходимости направлять запросы к primary.

### Типичные ошибки кандидатов
- **Прямое использование dirty reads для проверки бизнес-инвариантов**: данные ещё могут быть откачены или несогласованы, что приводит к двойному списанию. Исправление: для проверок использовать линейные или хотя бы monotonic reads.
- **Отсутствие механизма примирения конфликтов**: полагаемся на last-write-wins, теряя корректные обновления. Исправление: вводить версионирование, CRDT или domain-specific merge.
- **Считать, что eventual сойдётся «когда-нибудь», без тайм-аута**: клиент может бесконечно ждать. Исправление: задавать SLA на convergence, и для UI показывать альтернативные данные (stale) с индикатором.

### Возможные дополнительные вопросы интервьюера
- *«Как реализовать гарантию monotonic reads?»* — Клиент хранит максимальную увиденную версию (например, LSN или HLC), и в следующем запросе передаёт её. Сервер направляет запрос на реплику, которая уже догнала эту версию; если такой нет, ожидает или отказывает.
- *«Чем eventual consistency в Cassandra отличается от Apache Kafka?»* — В Cassandra реплики расходятся и сходятся через read repair; в Kafka сообщения гарантированно сохраняются в порядке смещения, но разные consumer группы могут быть на разных смещениях — eventual касается положения consumer’ов, а не самих данных. Архитектуры принципиально разные.

## Как проектировать matching engine (для биржи)?

### Краткий ответ
Сердце биржи — order book (стакан): две очереди заявок (bid/ask), обычно отсортированные по цене и времени (price-time priority). Операции: добавление, снятие, исполнение (match). Для низкой задержки используют lock-free структуры (Disruptor, ring buffers), работающие в одном потоке без блокировок. Аллокации минимизируются, сборка мусора контролируется. Данные хранятся в WAL для восстановления и реплицируются через Raft на несколько нод.

### Развёрнутый ответ
Основные компоненты:
- **Order Book**: хранит уровни цен. Для bid (покупка) — убывающая цена; ask — возрастающая. Внутри уровня — заявки в порядке FIFO.
- **Matching engine**: при новой рыночной заявке (market order) или лимитнике, который пересекается с противоположным лучшим предложением, происходит match: частичное или полное исполнение.
- **Потоковый ввод**: заявки поступают через FIX или проприетарный протокол, парсятся, валидируются.
- **Отказоустойчивость**: engine детерминированно обрабатывает входной поток событий, состояние периодически снапшотится. Репликация через Raft позволяет переключиться на follower в случае отказа лидера.

В Go реализация: единая горутина-движок, все операции через небуферизованный канал команд. Lock-free подход: использование кольцевого буфера (Disruptor) с единственным продюсером и множеством потребителей, но matching engine обычно один потребитель. Для order book — самописные коллекции без блокировок на основе `atomic` операций: skip list или массив уровней с CAS для обновления объёма.

```go
// упрощённо: структура движка в одной горутине
func (e *Engine) Run(commands <-chan Command) {
    for cmd := range commands {
        switch c := cmd.(type) {
        case *NewOrder:
            e.book.Insert(c)
            e.match()
        case *CancelOrder:
            e.book.Remove(c)
        }
    }
}
```

Для уменьшения latency — избегаем интерфейсов, используем value-типы на стеке, буферы из `sync.Pool`.

### Под капотом (internals)
В lock-free движке обычно используют memory ordering (atomic) с `atomic.Load/Store`, чтобы избежать мьютексов. Реальная high-perf система на Go может потребовать `unsafe` для управления памятью в кольцевом буфере, но чаще используют структуры вроде очереди LMAX Disruptor. В Go-порте `disruptor` использует CAS для координации курсоров. Также важна настройка GC: GOGC=off или периодический вызов `runtime.GC()` вне критического пути, либо использование Go 1.19+ с memory arena.

WAL: каждая команда перед применением записывается в файл с `O_SYNC` или в append-only лог на SSD. Для восстановления перечитывают лог и заново строят order book.

### Типичные ошибки кандидатов
- **Создание нескольких горутин для обработки заявок с общей блокировкой**: contention и непредсказуемые задержки из-за конкурентоспособности. Исправление: single-writer principle — вся обработка в одной горутине, параллелят только приём и валидацию заявок.
- **Использование динамических структур (срезы без предварительного выделения) в горячем пути**: приводит к частым аллокациям и GC-паузам. Исправление: фиксированные массивы, pool, ring buffer.
- **Отсутствие снапшотов и полагание только на WAL**: восстановление занимает часы. Исправление: периодически (например, каждые N ордеров) сохранять снимок order book, позволяющий быстро стартовать.

### Возможные дополнительные вопросы интервьюера
- *«Как обеспечить детерминизм при репликации на несколько движков?»* — Входной шлюз отправляет одинаковую последовательность сообщений всем репликам в одном порядке (RAFT + log), движки детерминированны (нет случайности, нет внешних вызовов), поэтому состояние идентично. Любой может стать лидером.
- *«Как справляться с пиками нагрузки без увеличения задержки?»* — Применять backpressure на gateway: ограничитель количества входящих заявок, сброс при превышении допустимой очереди. При этом критически важные заявки (например, cancel) могут иметь приоритетную очередь.

## Как проектировать платежный шлюз?

### Краткий ответ
Платёжный шлюз — прослойка между магазином и эквайерами/платёжными системами. Ключевые требования: идемпотентность, надёжность, безопасность (PCI DSS), маршрутизация между несколькими провайдерами с fallback, аудит всех операций. Используется асинхронная обработка с идемпотентным журналом и сагой для компенсации при отказе провайдера.

### Развёрнутый ответ
Архитектура обычно состоит из:
- **API Gateway**: принимает запросы от клиентов, валидирует, аутентифицирует.
- **Payment Service**: оркестрирует процесс: предварительная авторизация, выбор провайдера, выполнение списания, фиксация результата.
- **Router Service**: выбирает эквайера на основе правил (страна, сумма, валюта, текущая доступность и success rate). Использует circuit breaker для нестабильных провайдеров.
- **Transaction Ledger**: immutable лог всех транзакций, каждая имеет статус и журнал изменений.
- **Reconciliation**: сверка с отчетами провайдеров.

Поток обработки платежа:
1. `POST /pay` с уникальным ключом идемпотентности.
2. Сервис создаёт запись транзакции в состоянии `CREATED` в БД (вставка с ON CONFLICT по ключу).
3. Возвращает `202 Accepted` с transactionId.
4. Асинхронно отправляет команду `ExecutePayment` в очередь.
5. Worker выполняет: вызывает API провайдера; успех — обновляет статус `SUCCESS`, неудача — выбирает запасного провайдера или помечает `FAILED` и отправляет событие для саги.
6. Клиент может опросить `GET /payments/{id}`.

Go-реализация: worker’ы используют `rabbitmq` или `kafka` для гарантированной доставки команд, с ручным подтверждением после успешного обновления БД. Важно: обновление статуса транзакции и отправка события — атомарно через outbox-паттерн (в той же транзакции пишут в таблицу outbox, отдельный процесс публикует в очередь).

### Под капотом (internals)
Для PCI DSS чувствительные карточные данные не хранятся, а токенизируются: PAN заменяется токеном. В Go вся работа с картами — через `crypto/tls` и `crypto/aes` с принудительным использованием HSM через библиотеки PKCS#11. Outbox реализуется в PostgreSQL: `INSERT INTO outbox ...` в той же транзакции, что и смена статуса, затем Debezium или кастомный подписчик читает WAL (через replication сlot) и отправляет в Kafka.

### Типичные ошибки кандидатов
- **Синхронная обработка платежа в запросе HTTP**: приводит к таймаутам при медленном провайдере и отсутствию возможности ретрая. Исправление: немедленное создание транзакции и асинхронное выполнение; клиенту возвращается id для отслеживания.
- **Нет стратегии fallback провайдера**: при отказе провайдера платёж просто отклоняется. Исправление: реализовать приоритезированный список провайдеров, попытка списания через них до N раз.
- **Отсутствие проверки идемпотентности на уровне БД**: параллельные запросы с одним ключом создают дубликаты. Исправление: уникальное ограничение на поле idempotency_key, либо `INSERT ... ON CONFLICT DO NOTHING`.
- **Хранение PAN в логах**: нарушение PCI, риск утечки. Исправление: маскирование номера (первые 6, последние 4) на уровне логирования, использование `fmt.Sprintf` с маскировочной функцией.

### Возможные дополнительные вопросы интервьюера
- *«Как обрабатывать ситуацию, когда провайдер списал деньги, но ответ не пришёл?»* — Повторный запрос с тем же идемпотентным ключом, провайдер обязан вернуть тот же результат. Если он не поддерживает, необходим reconciliation: периодическая сверка с отчетами, запрос статуса операции через отдельный API. Это может привести к необходимости ручного разрешения.
- *«Как обеспечить порядок обработки команды ExecutePayment по конкретной транзакции?»* — Использовать партицию Kafka по transaction_id, тогда все события одной транзакции обрабатываются последовательно.

## Как обрабатывать ошибки в распределенных системах?

### Краткий ответ
Обработка ошибок строится на принципах: **retry с backoff и jitter**, **timeout**, **circuit breaker**, **bulkhead**, **fallback**. Ошибки классифицируются как временные (network blip) и перманентные (invalid input). Важно разграничивать бизнес-ошибки и системные. Go-паттерны: `context.Context` для дедлайнов, `errors.Is`/`As` для классификации, пакет `go-resiliency` для breaker/retrier.

### Развёрнутый ответ
При распределённых вызовах каждый запрос может упасть из-за сети, перегрузки, сбоя сервиса. Стратегия:
1. **Retry**: только для идемпотентных операций или операций с idempotency ключом. Используется экспоненциальный backoff с random jitter, чтобы избежать синхронизации клиентов.
2. **Timeout**: каждый вызов оборачивается в `context.WithTimeout`. Важно, чтобы сумма таймаутов по цепочке не превышала SLO.
3. **Circuit Breaker**: после N ошибок подряд переводит цепь в состояние Open, немедленно отклоняя запросы, давая сервису восстановиться. Half-Open пробует один запрос.
4. **Bulkhead**: изолирует ресурсы (пул соединений, горутины) для разных зависимостей, чтобы отказ одного не каскадировал.
5. **Fallback**: возврат кэшированных данных, дефолтного ответа или "sorry page".

В Go пакет `go-resiliency/breaker` позволяет легко реализовать Circuit Breaker. Важно, что таймауты должны распространяться через контекст: gRPC, HTTP, библиотеки работы с БД все уважают контекст.

Пример retrier с backoff:
```go
for attempt := 0; attempt < maxRetries; attempt++ {
    err := doCall(ctx)
    if err == nil {
        return nil
    }
    if !isRetryable(err) {
        return err
    }
    time.Sleep(backoff(attempt))
}
```

### Под капотом (internals)
В Go контекст реализован как дерево с каналом `Done()`. При истечении таймаута или вызове cancel закрывается канал, и все горутины, слушающие `ctx.Done()`, просыпаются. Net/http автоматически прерывает чтение тела при отмене контекста. Для Circuit Breaker библиотеки используют `atomic` для счетчиков и состояний, `time.Timer` для перехода в Half-Open.

### Типичные ошибки кандидатов
- **Бесконечный ретрай без задержки**: усугубляет перегрузку. Исправление: ограничить количество попыток и добавить backoff.
- **Retry для не идемпотентных POST**: приводит к двойному списанию. Исправление: либо сделать операцию идемпотентной (idempotency key), либо не ретраить мутирующие вызовы без токена.
- **Глобальный таймаут больше суммы таймаутов дочерних вызовов**: пользователь ждёт дольше SLO. Исправление: задавать таймауты на каждый вызов, общий дедлайн должен быть меньше внешнего SLO, использовать `context.Deadline` для контроля.
- **Отсутствие bulkhead: единый пул соединений для всех сервисов**: медленный бэкенд забирает все соединения, блокируя быстрые. Исправление: отдельные пулы (http.Transport с лимитами) на каждую зависимость.

### Возможные дополнительные вопросы интервьюера
- *«Как бы вы реализовали приоритетные retry без голодания?»* — Использовать приоритетную очередь (priority queue) для pending retry-задач: критические операции получают буст; backoff может снижать приоритет постепенно. В Go — `container/heap` с событиями.
- *«Как тестировать обработку ошибок в CI?»* — Внедряем toxiproxy для симуляции latency и ошибок, используем «chaos» middleware, проверяем, что breaker срабатывает и система восстанавливается.

## Как обеспечить «ровно один раз» (exactly once) доставку?

### Краткий ответ
Гарантировать exactly-once доставку сообщений в асинхронной системе невозможно без взаимодействия с получателем и идемпотентной обработки. На практике достигается через **идемпотентного потребителя** и транзакционный outbox у отправителя, а также использование Kafka с транзакциями (read-process-write) или уникальных ключей дедупликации на стороне получателя.

### Развёрнутый ответ
Термин «exactly once» обычно означает семантику «эффект ровно одного выполнения», а не доставку одного сообщения. Механизмы:
- **Idempotent Producer** (Kafka): продюсер присваивает каждому сообщению sequence number; брокер дедуплицирует сообщения с одинаковым producer id и sequence, так что внутри сессии обеспечивается idempotent send.
- **Transactional Messaging**: read-processing-write как единая транзакция (Kafka EOS). Потребитель читает сообщение, обрабатывает, записывает результат в другой топик и коммитит смещение атомарно с записью. Это гарантирует, что даже при перебалансировке сообщение не будет обработано дважды.
- **Idempotent Consumer**: потребитель хранит идентификатор уже обработанных сообщений в своей БД, и при получении повторного сообщения просто игнорирует его (проверка по ключу). Сочетание уникального идентификатора сообщения (UUID) и уникального ограничения в БД потребителя даёт семантику exactly once.

В Go consumer Kafka (sarama, confluent-kafka-go) может использовать `ReadOffset` и `CommitMessage` вручную. При использовании транзакций библиотека `franz-go` поддерживает EOS.

Пример реализации dedup-консьюмера:
```go
func process(msg *kafka.Message) error {
    tx, _ := db.Begin()
    id := extractID(msg.Value)
    _, err := tx.Exec("INSERT INTO processed (msg_id) VALUES ($1) ON CONFLICT DO NOTHING", id)
    if err != nil { /* обработать */ }
    if rowsAffected == 0 {
        // уже обработано, коммитим оффсет
        return tx.Commit()
    }
    // бизнес-логика, вставка данных
    // ...
    return tx.Commit()
}
```

### Под капотом (internals)
Kafka транзакции реализованы через transaction coordinator и внутренние топики `__transaction_state`. Продюсер отправляет сообщения, помечая их транзакционным идентификатором, а перед коммитом транзакции пишет в `__transaction_state`. Брокер гарантирует, что сообщения одной транзакции видны атомарно и дедуплицируются. В Go библиотеки используют низкоуровневые вызовы `initTransactions`, `beginTransaction`, `sendOffsetsToTransaction`, `commitTransaction`.

### Типичные ошибки кандидатов
- **Надеяться на идемпотентность сети**: полагать, что брокер доставит ровно один раз без применения описанных методов. Исправление: всегда писать идемпотентного потребителя.
- **Коммит смещения до завершения бизнес-логики**: при краше после коммита, но до записи результата, сообщение потеряно. Исправление: коммитить смещение после успешного сохранения результата (желательно в одной транзакции с outbox).
- **Забывать о дубликатах при ребалансировке**: consumer переподключается и получает сообщения заново. Исправление: dedup через уникальный message_key или idempotent handlers.

### Возможные дополнительные вопросы интервьюера
- *«Как бы вы реализовали exactly once при вызове внешнего сервиса без поддержки транзакций?»* — Используем idempotency key в запросе к внешнему сервису и записываем ключ в БД перед вызовом. Если вызов не дал ответа, повторяем с тем же ключом; внешний сервис должен быть идемпотентным. Это «эффект ровно одного раза».
- *«Какие ограничения у Kafka EOS?»* — Максимальная пропускная способность снижается из-за дополнительного обмена с транзакционным координатором, возможна потеря сообщений при неправильной конфигурации (transaction.timeout.ms, isolation.level).

## Как работает "double spending" проблема и как ее решить?

### Краткий ответ
Double spending — попытка потратить одну и ту же цифровую единицу более одного раза. В централизованных системах (банки) решается через авторизацию и атомарное обновление баланса с блокировкой или оптимистической проверкой. В децентрализованных (криптовалюты) — консенсус (PoW/PoS) и подтверждения сети. В высоконагруженном FinTech используют идемпотентные ключи и строгую сериализацию операций по счёту.

### Развёрнутый ответ
В традиционной банковской системе проблема предотвращается на уровне БД: операция списания включает проверку текущего баланса (`UPDATE accounts SET balance = balance - amount WHERE id = $1 AND balance >= amount`). Если строку не обновило, значит недостаточно средств — двойное списание невозможно при корректной изоляции. При конкурентном доступе используется блокировка строки (`SELECT ... FOR UPDATE`) или CAS с версией (optimistic locking).

В распределённой системе необходимо гарантировать, что два параллельных запроса на списание с одного счёта не пройдут одновременно. Для этого операции по конкретному счёту сериализуются (направляются в одну партицию, обрабатываются одной горутиной). Также применяют идемпотентные ключи: каждая операция несёт уникальный бизнес-ключ (paymentId), и сервер проверяет, не была ли выполнена.

В криптовалютах механизм иной: блокчейн хранит цепочку транзакций; двойная трата предотвращается майнерами, которые включают только одну из конфликтующих транзакций в блок. Консенсус решает, какая ветка каноническая. Это также форма eventual consistency с финальной гарантией.

### Под капотом (internals)
В PostgreSQL `SELECT FOR UPDATE` блокирует строку до конца транзакции, так что параллельные транзакции ждут на блокировке. В Go, используя `pgxpool`, важно ограничивать конкурентные горутины на один счёт: можно использовать структуру `sync.Cond` или channel per account для последовательной обработки. Lock-free подход: атомарный CAS на счётчике в памяти (например, `atomic.CompareAndSwapInt64`), но для персистентности нужен внешний store.

### Типичные ошибки кандидатов
- **Делать проверку баланса отдельно (SELECT) и потом UPDATE без блокировки**: между проверкой и обновлением другой запрос может потратить средства. Исправление: использовать `UPDATE ... WHERE balance >= amount` как атомарную проверку и списание.
- **Зависимость только от внешнего кэша (Redis) для баланса без синхронизации с источником истины**: при рассинхроне возможны списания с неверным состоянием. Исправление: источником истины должна быть реляционная БД с транзакциями; Redis — только кэш с механизмом инвалидации.
- **Обработка операций по одному счёту в разных параллельных потоках без упорядочения**: гонка может дать некорректный результат. Исправление: партиционировать по account_id, направлять все операции конкретного счёта в одну партицию (Kafka + consumer group с одним воркером на партицию) или использовать actor model.

### Возможные дополнительные вопросы интервьюера
- *«Как бы вы предотвратили двойное списание без блокировок и транзакций?»* — Использовать модель акторов: каждый счёт — актор, обрабатывающий запросы последовательно, храня баланс в своём состоянии. In-memory акторы могут реплицироваться через event sourcing для отказоустойчивости.
- *«Как влияет eventual consistency на double spending в крипто-платёжном шлюзе?»* — Пока транзакция не получила достаточно подтверждений, существует риск двойной траты в блокчейне. Шлюз должен дождаться необходимого количества блоков (например, 6 для Bitcoin) или использовать механизмы ускорения (off-chain, lightning network). Для микроплатежей можно рискнуть с 0 confirmations и смириться с небольшой вероятностью.

## Как проектировать anti-fraud систему?

### Краткий ответ
Anti-fraud система анализирует транзакции и действия пользователей в реальном времени, выставляя риск-скоры с помощью правил и ML-моделей. Архитектура включает event-driven ingestion данных, feature store для быстрых вычислений, движок правил с поддержкой сложной логики и low-latency ответа (<50 мс). Применяется паттерн CQRS/Event sourcing для аудита и совершенствования моделей.

### Развёрнутый ответ
Поток данных: транзакции через API публикуются в Kafka, стримовый процессор (Kafka Streams, Flink, или Go-сервисы на основе `franz-go` + групповых подписок) обогащает события признаками: геолокация, история пользователя, частота транзакций за последние N минут, сумма. Далее движок правил (можно написать на Go с использованием `expr` или `govaluate`) вычисляет score и принимает решение: approve, decline, review. Для низкой задержки критично, чтобы правила не обращались к медленным внешним сервисам; все данные должны быть предварительно загружены в in-memory хранилище (Redis, Apache Ignite), обновляемое через CDC из БД.

Компоненты:
- **Ingestion Service** (Go): принимает платежи, валидирует, отправляет в топик.
- **Feature Service**: поддерживает актуальные агрегаты (скользящие окна) по пользователю/карте, используя локальный state store (потоковая обработка RocksDB внутри процесса).
- **Rule Engine**: Go-библиотека `rulego` или свой DSL с компиляцией правил в Go-функции.
- **Model Inference**: ML-модель, экспортированная в ONNX, может быть загружена через `gorgonia` или CGo-привязки к TensorRT для ускорения.
- **Feedback Loop**: решения пишутся в лог, позже сверяются с реальными chargeback-ами для обучения модели офлайн.

### Под капотом (internals)
Низкая латентность достигается минимизацией аллокаций на пути обработки: объекты из `sync.Pool`, парсинг с помощью `easyjson` или `protobuf`, использование lock-free map (например, `mono` или `xsync.Map`) для feature store. Скользящие окна реализуются через кольцевые буферы с атомарными счётчиками.

### Типичные ошибки кандидатов
- **Синхронные вызовы внешних сервисов (AVS, KYC) во время проверки**: убивают latency (200-500 мс). Исправление: такие проверки выносить в асинхронный post-processing; если они обязательны, то с жёстким таймаутом и быстрым fallback (по умолчанию reject).
- **Недостаточная изоляция feature store**: правила начинают мутировать общее состояние без синхронизации, возникает гонка. Исправление: обновление признаков только через идемпотентные асинхронные события, подход "one writer principle" для каждого ключа.
- **Отсутствие feedback loop для моделей**: модель деградирует со временем из-за drift. Исправление: сохранять все входные данные и решения в data lake, регулярно переобучать модель, автоматизировать деплой новых версий через feature flag.

### Возможные дополнительные вопросы интервьюера
- *«Как обеспечить, чтобы anti-fraud сам не стал узким местом?»* — Горизонтально масштабировать сервис фрод-детекции по transaction_id, используя stateless обработку и локальный state store, который синхронизируется через changelog Kafka (KTable). Запросы распределяются равномерно.
- *«Как управлять порогами риска в реальном времени?»* — Хранить пороги в динамической конфигурации (Consul, etcd, Redis), которую сервис опрашивает или получает через watch. Изменения применяются без редеплоя. В Go — использование `fsnotify` для файла или потоковой подписки на etcd.

## Как работать с горячими партициями (hot partitions)?

### Краткий ответ
Горячая партиция — шард данных, получающий непропорционально много нагрузки (например, аккаунт популярного пользователя). Решают с помощью **дробления ключа** (добавление соли), **отдельного кэширования** таких ключей с более агрессивным TTL и выделенным ресурсом, **in-memory state** с репликацией, а также **реактивного перераспределения** при детекции hot spot. В системах на Go могут использовать шардирование с виртуальными секциями и переносом нагрузки.

### Развёрнутый ответ
Идея: заменить ключ `hot_user` на `hot_user_0`, `hot_user_1`, ..., `hot_user_N-1`, чтобы распределить операции по N партициям. Клиент/прокси знает, что для этого ключа нужно случайно выбирать суффикс. Это увеличивает пропускную способность в N раз ценой денормализации при чтении: для получения полной картины нужно опросить все N секций (scatter/gather).

В Go микросервисе можно обернуть доступ к хранилищу: при записи берётся `rand.Intn(N)`, ключ модифицируется. При чтении собираются данные со всех N ключей и агрегируются. Такой подход используется в Redis (key hashing) или Cassandra.

Другой метод — выделить горячий объект в отдельный in-memory кэш на каждом узле сервиса и обновлять через pub/sub. Например, счётчик лайков: инкремент накапливается локально в `atomic.Int64`, периодически сбрасывается в БД; чтение берётся из кэша, что убирает нагрузку с базы.

### Под капотом (internals)
В CockroachDB hot spot решается автоматическим split range когда нагрузка превышает порог, но если ключ один, то split не поможет. В Redis Cluster солирование ключей вручную — обычная практика. В Go lock-free map от `orcaman/concurrent-map` шардирована по внутренним бакетам и не даёт горячей области внутри процесса, но проблема hot partition в распределённом хранилище решается на уровне логики приложения.

### Типичные ошибки кандидатов
- **Применение случайной соли, но чтение только из одного шарда**: данные теряются. Исправление: либо на чтении делать запрос ко всем солёным ключам и агрегировать, либо использовать List/Set, где один ключ, но операции распределены (Write-back кэш).
- **Солирование с N=1000 без upper bound**: получаем много мелких запросов, ухудшаем latency. Исправление: подбирать N исходя из нагрузки и latency бюджета, обычно 2–10.
- **Игнорирование обратной совместимости при переходе на salted key**: старые данные недоступны. Исправление: постепенная миграция: некоторое время поддерживаем чтение по старому ключу (fallback) при отсутствии данных в новых, пишем только в новый.

### Возможные дополнительные вопросы интервьюера
- *«Как обнаружить горячую партицию в production?»* — Мониторинг метрик на уровне шарда: количество операций в секунду, задержка P99. Если один шард в разы превышает среднее, алертим. В Cassandra `nodetool tablehistograms` покажет per-partition latency.
- *«Можно ли использовать gossip протокол для балансировки горячих ключей?»* — Да, можно распределить ключи по узлам, используя consistent hashing с виртуальными узлами, и при обнаружении перегрузки узла перемещать виртуальный узел на менее загруженный сервер. Это реализовано в Dynamo-подобных системах.

## Как проектировать ledger (бухгалтерскую книгу)?

### Краткий ответ
Ledger — учётная система двойной записи, где каждая финансовая операция отражается по дебету одного счёта и кредиту другого в неизменяемых записях. Проектируется на базе immutable event log с полным аудитом и реконсиляцией. Используется event sourcing: все изменения — события, текущий баланс вычисляется агрегацией. В Go реализуется через хранение событий в БД, агрегаторы в памяти с периодическими снапшотами.

### Развёрнутый ответ
Основные принципы:
- **Immutable Entries**: запись транзакции не может быть изменена или удалена, возможна только компенсирующая запись.
- **Double-entry**: каждая транзакция состоит минимум из двух проводок (entries) с суммой дебета = сумме кредита.
- **Idempotency**: глобально уникальный ID транзакции гарантирует отсутствие дублей.
- **Reconciliation**: регулярная сверка итоговых балансов по всем счетам, сумма дебетов и кредитов всегда равна.

Архитектура:
1. `Ledger Service` Go: API `POST /transactions` с идемпотентным ключом. Сервис валидирует бизнес-правила, создаёт событие `TransactionCreated` с проводками и применяет его к in-memory проекциям (балансы счетов) или к таблице `current_balance` с оптимистической блокировкой.
2. События сохраняются в `events` таблице PostgreSQL (append-only) или в Cassandra (по time-series).
3. Чтение баланса счёта — либо из материализованной таблицы `balances`, обновляемой в той же транзакции, либо через агрегацию событий в реальном времени (снапшоты + чтение хвоста).

### Под капотом (internals)
При использовании PostgreSQL `SERIALIZABLE` изоляции или `SELECT FOR UPDATE` на строку счёта обеспечивается корректность одновременных проводок. Event sourcing в Go часто реализуют с помощью библиотеки `looplab/eventhorizon`, но для ledger можно написать специализированный агрегатор: горутина на каждый счёт, последовательно обрабатывающая команды и хранящая состояние в канале / actor.

Для производительности записи горячего счёта применяют партиционирование транзакций, как и с hot partitions, но при этом баланс счёта хранится как сумма всех партиций.

### Типичные ошибки кандидатов
- **Прямое обновление баланса без неизменяемого журнала**: невозможно восстановить историю, аудит не полный. Исправление: внедрить event sourcing, где баланс — проекция событий.
- **Использование floating-point для денег**: ошибки округления, потеря копеек. Исправление: использовать целые числа в минимальных единицах (минорная валюта) или `decimal` (сторонние библиотеки типа `shopspring/decimal`).
- **Отсутствие проверки на суммарное равенство дебита и кредита**: в результате данные могут разбалансироваться. Исправление: валидировать на уровне сервиса, а также добавлять constraint в БД (агрегатную проверку отсроченно через триггер или периодический job).

### Возможные дополнительные вопросы интервьюера
- *«Как поддерживать баланс при шардировании по account_id, если транзакция затрагивает два счёта из разных шардов?»* — Использовать двухфазную запись (2PC) или сагу: сначала резервируем сумму на дебетовом счёте, затем кредитуем второй счёт, при неудаче отменяем резерв (компенсация). Координатор управляет процессом.
- *«Как эффективно пересчитать баланс за период, если событий миллионы?»* — Хранить периодические снимки состояния (snapshot) и агрегировать только события после последнего снимка. Снимки можно создавать асинхронно (например, nightly batch).

## Как обрабатывать конкурентный доступ к счетам (account balance)?

### Краткий ответ
Конкурентное обновление баланса решается на уровне базы данных: пессимистическая блокировка (`SELECT ... FOR UPDATE`) или оптимистическая с проверкой версии (`UPDATE ... WHERE version = old_version`). В распределённой системе используется сериализация операций через actor model или очереди с партиционированием по счёту. Идемпотентные ключи предотвращают дублирование.

### Развёрнутый ответ
Пессимистичный подход:
```go
tx, _ := db.Begin(ctx)
row := tx.QueryRow("SELECT balance, version FROM accounts WHERE id=$1 FOR UPDATE", id)
// читаем баланс
_, err = tx.Exec("UPDATE accounts SET balance = $1, version = version+1 WHERE id=$2", newBalance, id)
tx.Commit()
```
Это гарантирует, что никто другой не обновит счёт до конца транзакции, но снижает параллелизм, т.к. все запросы к этому счёту встают в очередь на блокировке.

Оптимистическая блокировка: не блокирует, но ожидает, что конфликт редок. Применяем UPDATE с условием на старую версию; если `RowsAffected() == 0`, конфликт, повторяем транзакцию с чтением нового состояния.

В микросервисах лучший способ — сериализация запросов для одного счёта. В Go это удобно сделать через паттерн Actor: для каждого account ID создаётся горутина-актор, владеющая состоянием и обрабатывающая команды из dedicated канала. Входящие запросы маршрутизируются в нужный актор через map shard.

### Под капотом (internals)
В PostgreSQL `SELECT FOR UPDATE` блокирует строку, но не блокирует другие строки. При большом количестве операций по одному счёту может образоваться очередь из ожидающих транзакций, что повышает latency. В Go можно смягчить: использовать `context.WithTimeout` на транзакцию, чтобы быстро отказывать при длительном ожидании. Actor модель: каждый актор — отдельная горутина, взаимодействие через каналы. Так как горутина одна, состояние защищено от гонок без мьютексов. Это даёт высокую пропускную способность (lock-free внутри актора).

### Типичные ошибки кандидатов
- **Чтение баланса вне транзакции, затем отдельное обновление**: классическая гонка. Исправление: всегда читать с блокировкой или с версией внутри транзакции.
- **Использование Read Committed без повторного чтения**: при оптимистической блокировке без повторного получения версии не узнаем о конфликте. Исправление: перечитывать версию после неудачного UPDATE.
- **Обработка в одной горутине операций разных счетов, но с глобальным мьютексом**: последовательное выполнение, низкая пропускная способность. Исправление: шардированные блокировки или акторы.

### Возможные дополнительные вопросы интервьюера
- *«Как спроектировать систему, где суммарный баланс всех счетов должен оставаться константой при переводе?»* — Использовать две записи в ledger (дебет, кредит) в одной транзакции, которая атомарно изменяет оба счёта. При шардировании — двухфазная блокировка: сначала захватываем счёт с большим id, затем второй, чтобы избежать дедлоков.
- *«Что делать, если количество запросов к одному счёту настолько велико, что БД не справляется?»* — Вводить in-memory actor на уровне сервиса, который обрабатывает все операции в оперативной памяти, а периодически синхронизирует баланс с БД (write-behind). При крахе сервиса последнее состояние восстанавливается из WAL событий (event sourcing) или из последнего снапшота.

## Как проектировать систему для fiat/криптобиржи?

### Краткий ответ
Проектирование биржи включает торговый движок (matching engine), управление ордерами, кошельки/счета в фиате и крипте, аудит, комплаенс, real-time data feed (order book, свечи). Архитектура — событийно-ориентированная, с CQRS и event sourcing. Ключевой компонент — высокопроизводительный matching engine (см. выше). Фиатные шлюзы и крипто ноды интегрируются через адаптеры с сагами.

### Развёрнутый ответ
Основные модули:
- **Account Service**: управление балансами фиата и криптовалют. Для фиата — ledger с двойной записью; для крипты — холодные/горячие кошельки, адреса депозитов.
- **Trading Engine**: matching engine для каждой торговой пары. Для горизонтального масштабирования — по символам.
- **Market Data**: стриминг order book, цен, индексов через WebSocket.
- **Order Management**: создание, отмена ордеров с валидацией (наличие средств, лимиты).
- **Settlement**: клиринг и расчеты после матча. После исполнения ордера записываются транзакции перевода активов между участниками.
- **Risk Management**: контроль маржи, margin call, ликвидация позиций при торговле с плечом.

Event-driven: при создании ордера публикуется событие `OrderPlaced`, матчинговый движок его потребляет, генерирует `TradeExecuted`. Settlement сервис слушает `TradeExecuted` и обновляет балансы. В Go все эти сервисы могут общаться через Kafka, NATS или Redis Streams.

Для безопасности: 95% средств криптобирж хранятся в холодных кошельках, пополнения и выводы автоматизированы с многофакторной подписью.

### Под капотом (internals)
Matching engine обычно разделён по парам, каждая пара — отдельный процесс или горутина-актор. Порядок ордеров внутри пары сохраняется. State машина движка детерминирована, события логируются в WAL и могут воспроизводиться. Для фиата используют БД PostgreSQL с тщательным индексом на account+currency.

### Типичные ошибки кандидатов
- **Смешивание торговых движков с операциями баланса в одной БД**: при высокой нагрузке на ордера балансы должны быть отдельным сервисом, иначе contention. Исправление: разделение ответственности, асинхронное взаимодействие.
- **Отсутствие rate limiter на отправку ордеров**: пользователь может зафлудить движок. Исправление: rate limiter на API, также лимиты на открытое число ордеров.
- **Некорректная обработка частичного исполнения ордера в settlement**: при исполнении 50% объёма нужно списать/начислить пропорциональную сумму, остаток остаётся в стакане. Исправление: интеграция движка с учетом частичных fill.

### Возможные дополнительные вопросы интервьюера
- *«Как синхронизировать баланс между крипто-нодой и внутренним ledger?»* — Постоянно выполнять reconciliation: периодически проверять баланс на hot wallet, сравнивать с внутренним учётом, выявлять расхождения. Входящие транзакции должны обнаруживаться через scanning blockчейна (crontab + RPC), далее apply deposit.
- *«Как организовать обработку fork в блокчейне?»* — Служба мониторинга детектирует fork, приостанавливает операции депозита/вывода для affected chains до достижения консенсуса, затем перерабатывает блоки (требует careful state management). Лучше полагаться на подтверждения (например, 12 confirmations).

## Как масштабировать WebSocket соединения?

### Краткий ответ
Горизонтальное масштабирование WebSocket требует внешнего pub/sub механизма (Redis, NATS, Kafka) для обмена сообщениями между узлами. Клиенты подключаются к любому узлу через load balancer с поддержкой sticky sessions или session affinity (по IP или cookie). Каждый узел поддерживает локальные соединения, сообщения публикуются в общий канал, а подписчики на каждом узле рассылают своим подключённым клиентам. В Go используют библиотеки `gorilla/websocket` или `gobwas/ws`, а для координации — `redis.PubSub`.

### Развёрнутый ответ
Архитектура:
- **Ingress**: Layer 4 LB (HAProxy, Envoy) с `balance leastconn` и поддержкой WebSocket Upgrade. Sticky session гарантирует, что один клиент всегда попадает на один сервер (по IP, либо заголовку `X-Forwarded-For`).
- **WebSocket сервер Go**: горутина на каждое соединение, чтение в цикле, запись через канал. Для управления соединениями используется мапа `map[userID]*connection` с RWMutex.
- **Message Broker**: Redis PubSub или NATS. Когда сервис A хочет отправить сообщение пользователю, он публикует в топик `user:{userID}`. Все WebSocket узлы подписаны на этот топик; получив сообщение, ищут локальное соединение и отправляют.
- **Scale-out**: добавление новых узлов тривиально, они просто подписываются на Redis. Нет перекрестных соединений между узлами.

В Go реализация подписки:
```go
go func() {
    ch := redisClient.Subscribe(ctx, "user:123").Channel()
    for msg := range ch {
        mu.RLock()
        conn, ok := conns["user:123"]
        mu.RUnlock()
        if ok {
            conn.WriteMessage(websocket.TextMessage, []byte(msg.Payload))
        }
    }
}()
```

### Под капотом (internals)
`gorilla/websocket` использует буферизированные записи через `bufio.Writer`, отдельную горутину для записи и небуферизованный канал для контроля backpressure: `conn.SetWriteDeadline` управляет таймаутом на запись. При использовании `gobwas/ws` можно получить zero-copy upgrade и минимум аллокаций.

### Типичные ошибки кандидатов
- **Хранение всех соединений в одном слайсе с блокировкой Mutex на каждое сообщение**: contention на мьютексе под большим количеством горутин. Исправление: шардировать соединения (map с striped мьютексом) или использовать `sync.Map`, если подходит.
- **Отсутствие backpressure на запись**: при медленном клиенте горутина записи блокируется и накапливает буфер, что ведёт к OOM. Исправление: контролировать размер буфера канала записи, при переполнении отключать клиента с логированием.
- **Полагать, что LB автоматически терминирует WebSocket правильно**: многие L7 балансировщики требуют специальной конфигурации. Исправление: использовать L4 прокси или nginx с `proxy_set_header Upgrade $http_upgrade` и `Connection "upgrade"`.

### Возможные дополнительные вопросы интервьюера
- *«Как обеспечить order гарантии при доставке сообщений клиенту через несколько узлов?»* — Если клиент может быть подключён к разным узлам в течение сессии, необходимо добавить sequence number и дедупликацию на клиенте; либо использовать персистентные сессии, гарантирующие, что после переподключения сообщения с previous sequence будут пересланы (replay). Сервер должен хранить последние N сообщений для этого пользователя.
- *«Как масштабировать до миллионов соединений на одном сервере?»* — Оптимизировать настройки ОС (увеличить лимиты файловых дескрипторов, tcp buf), использовать epoll напрямую через `golang.org/x/sys/unix` с `Epoll`, горутины создавать только при фактической активности данных (событийно). Библиотека `gnet` или `evio` реализует event-loop модель.

## Как реализовать «скользящее окно» (sliding window) для rate limiting?

### Краткий ответ
Скользящее окно можно реализовать через **log** (хранение меток времени каждого запроса в отсортированном множестве Redis) или **counter** (аппроксимация — взвешивание счетчиков предыдущего и текущего фиксированного окна). В Go локально — кольцевой буфер с атомарными счётчиками на каждую секунду. Log даёт точное ограничение, counter — низкое потребление памяти и быстрый расчёт.

### Развёрнутый ответ
**Sliding Window Log** (Redis sorted set):
```lua
-- key: client_id, now: время, window: окно (сек), limit
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local count = redis.call('ZCARD', key)
if count < limit then
    redis.call('ZADD', key, now, now .. ':' .. math.random())
    redis.call('EXPIRE', key, window)
    return 1
else
    return 0
end
```
Точен, но требует `ZREMRANGEBYSCORE` при каждом запросе — O(log N + M), где M удаляемых элементов.

**Sliding Window Counter**: делим окно на N бакетов (например, 1 бакет = 1 секунда). Храним массив счётчиков в Redis (list или hash). Текущее окно — сумма значений всех бакетов в пределах window. При каждом запросе увеличиваем счётчик текущего бакета и считаем сумму; если превышен лимит — отказ. Это O(1) на запрос, память фиксирована.

Локальная Go-реализация с кольцевым буфером:
```go
type SlidingWindow struct {
    mu      sync.Mutex
    buckets []int64
    lastTime int64
    capacity int
    window   time.Duration
    slotLen  time.Duration
    cursor   int
}

func (sw *SlidingWindow) Allow() bool {
    now := time.Now().UnixNano()
    sw.mu.Lock()
    defer sw.mu.Unlock()
    slotsToAdvance := int((now - sw.lastTime) / int64(sw.slotLen))
    if slotsToAdvance > 0 {
        // очищаем пропущенные бакеты
        for i := 1; i <= slotsToAdvance && i <= len(sw.buckets); i++ {
            sw.buckets[(sw.cursor+i)%len(sw.buckets)] = 0
        }
        sw.cursor = (sw.cursor + slotsToAdvance) % len(sw.buckets)
        sw.lastTime = now
    }
    sum := atomic.SumInt64s(sw.buckets) // или пройтись
    if sum >= limit {
        return false
    }
    atomic.AddInt64(&sw.buckets[sw.cursor], 1)
    return true
}
```

### Под капотом (internals)
Redis sorted set — skiplist. Для sliding window log с большим количеством ключей может быть накладно. Альтернатива — использование `RedisTimeSeries` или Bloom-фильтры не подходят. В Go при использовании кастомной реализации с кольцевым буфером важно обеспечить атомарность операции получения среза: `sync.Mutex` или `atomic` для обновления суммы через CAS loop.

### Типичные ошибки кандидатов
- **Использование фиксированного окна (fixed window) и заявление, что это sliding window**: на границе окна возможно удвоение. Исправление: или sliding window log, или sliding counter с взвешиванием.
- **Счётчик реализован через инкремент без очистки старых данных**: память бесконечно растёт. Исправление: ротация бакетов с обнулением.
- **Глобальный мьютекс на весь слайс**: contention. Исправление: сегментировать по клиентам, использовать полосатые блокировки (striped locks) или шардированные структуры.

### Возможные дополнительные вопросы интервьюера
- *«Как быть с рассинхронизацией часов на машинах при распределённом rate limiter?»* — Использовать монотонные часы (monotonic clock) на сервере или время сервера Redis. В крайнем случае — принимать время от клиента, но с проверкой допустимого расхождения (до нескольких секунд). Большинство реализаций полагаются на серверное время.
- *«Как реализовать оконный лимит с burst?»* — Комбинировать token bucket и sliding window: token bucket для разрешения burst, sliding window для ограничения общего числа за окно. Можно внедрить два параллельных лимитера.

## Как реализовать "thundering herd" защиту?

### Краткий ответ
Thundering herd (эффект стада) — множество горутин/потоков одновременно пробуждаются по событию, создавая пиковую нагрузку. Защита: **singleflight** — все запросы к одному ключу объединяются, и реальное выполнение происходит только один раз, а остальные получают результат. В Go пакет `golang.org/x/sync/singleflight` делает это; для распределённых систем дополняется блокировкой в Redis.

### Развёрнутый ответ
В Go классический пример: кэш сервиса истёк, и множество горутин одновременно пытаются его обновить, вызывая внешний API или БД. Singleflight решает это:

```go
var g singleflight.Group
func getData(key string) (interface{}, error) {
    v, err, _ := g.Do(key, func() (interface{}, error) {
        return fetchFromDB(key)
    })
    return v, err
}
```
При нескольких одновременных вызовах `Do` с одним ключом, только одна горутина выполняет функцию, остальные ждут и получают тот же результат (или ошибку). Это эффективно предотвращает лавину запросов.

В распределённой среде, когда много подов, также может возникнуть thundering herd, но singleflight ограничен одним процессом. Решение: комбинация локального singleflight и распределённой блокировки (Redis `SETNX`) с коротким TTL для координации между подами. Первый захвативший блокировку выполняет запрос, остальные ждут и затем получают значение из кэша после его заполнения.

### Под капотом (internals)
Внутренне `singleflight.Group` хранит `map[string]*call` с мьютексом. `call` содержит канал, который закрывается, когда функция завершается, и `WaitGroup` для ожидания. При вызове `Do` создаётся `call`, горутина-исполнитель выполняет функцию и по завершении закрывает канал, пробуждая всех ожидающих.

### Типичные ошибки кандидатов
- **Использование singleflight для неидемпотентных операций**: если функция имеет побочные эффекты (например, создание заказа), все вызовы получат результат первого выполнения, но другие ожидают и не создают свой заказ, что, возможно, нежелательно. Исправление: применять singleflight только к идемпотентным операциям (например, загрузка данных).
- **Забыть про TTL результата**: если singleflight использован для обновления кэша, но результат не сохранён, после завершения другие горутины не получат обновлённый кэш (они ждали возврата значения, но не перезаписали кэш). Исправление: в функции обновления результат должен записываться в глобальный кэш.
- **Некорректное использование `DoChan` без контекста**: может привести к утечке горутин. Исправление: всегда передавать контекст с таймаутом.

### Возможные дополнительные вопросы интервьюера
- *«Как избежать проблем, когда singleflight приводит к задержке всех запросов из-за одного медленного?»* — Установить разумный таймаут на выполнение функции через контекст. Если таймаут истекает, `singleflight` возвращает ошибку, и ожидающие горутины могут попробовать выполнить отдельные вызовы или вернуть fallback.
- *«Можно ли применить singleflight для защиты от thundering herd на Kafka consumer?»* — Да, в обработчике сообщений, если партиция одна, но consumer группа имеет несколько воркеров, singleflight не поможет, т.к. они обрабатывают разные сообщения. Но если один и тот же ключ (например, user_id) обрабатывается конкурентно, можно использовать singleflight на уровне бизнес-логики для этого ключа.

## Как спроектировать "circuit breaker" с детектором состояний?

### Краткий ответ
Circuit Breaker автоматически переходит между состояниями Closed (пропускает запросы), Open (отклоняет) и Half-Open (пробный). Детектор на основе скользящего окна отслеживает соотношение ошибок/успехов. В Go можно использовать библиотеку `go-resiliency/breaker` или написать кастомный, используя `time.Timer` и кольцевой буфер счётчиков успехов/неудач. Ключевые параметры: порог ошибок, таймаут до перехода в Half-Open, количество пробных запросов.

### Развёрнутый ответ
Состояния:
- **Closed**: счётчик ошибок сбрасывается после окна. Если в пределах окна процент ошибок превышает порог, переход в Open.
- **Open**: все запросы немедленно фейлятся с ошибкой `ErrBreakerOpen`. По истечении `Timeout` (например, 30с) переходит в Half-Open.
- **Half-Open**: позволяет ограниченное количество пробных запросов (maxRequests). Если они успешны, сбрасывается в Closed, иначе обратно в Open.

Реализация в Go на кастоме:
```go
type CircuitBreaker struct {
    state         int32     // atomic
    failureCount  int64     // atomic
    successCount  int64     // atomic
    halfOpenMax   int32
    timeout       time.Duration
    nextTry       time.Time
    mu            sync.Mutex
}

func (cb *CircuitBreaker) Call(fn func() error) error {
    state := atomic.LoadInt32(&cb.state)
    if state == Open {
        if time.Now().Before(cb.nextTry) {
            return ErrBreakerOpen
        }
        cb.mu.Lock()
        if state == Open {
            atomic.StoreInt32(&cb.state, HalfOpen)
            cb.nextTry = time.Now().Add(cb.timeout)
        }
        cb.mu.Unlock()
    }
    err := fn()
    if err != nil {
        atomic.AddInt64(&cb.failureCount, 1)
    } else {
        atomic.AddInt64(&cb.successCount, 1)
    }
    // логика перехода состояний на основе счетчиков
}
```
Для точности часто используют скользящее окно с бакетами (как Hystrix).

### Под капотом (internals)
В `go-resiliency/breaker` используется синхронизация через мьютекс, но для высоконагруженного пути может быть узким местом. Улучшение — использовать атомарные указатели на состояния и lock-free кольцевой буфер (ring buffer) для хранения результатов последних N запросов.

### Типичные ошибки кандидатов
- **Не учитывать таймауты как ошибки**: если вызов завис на 5 секунд, это должно считаться за ошибку и увеличивать счётчик. Исправление: в функции fn использовать context, считать `context.DeadlineExceeded` как failure.
- **Переход в Half-Open без ограничения числа пробных запросов**: при восстановлении сервиса множество горутин одновременно отправляют пробные запросы и могут опять перегрузить его. Исправление: ограничить `maxRequestsInHalfOpen` (например, 1-5).
- **Сброс счетчиков успехов и ошибок только по времени, без скользящего окна**: может привести к резким перепадам. Исправление: скользящее окно с бакетами.
- **Не разделять типы ошибок**: считать все ошибки подряд, включая бизнес-ошибки, которые не связаны с отказом сервиса. Исправление: определить, какие ошибки считать «критичными» (5xx, timeout, connection refused), бизнес-ошибки не должны влиять на breaker.

### Возможные дополнительные вопросы интервьюера
- *«Как реализовать каскадный circuit breaker?»* — Каждый сервис имеет свой breaker, но при отказе зависимого сервиса сервис-клиент тоже может открыть свой breaker, чтобы быстро фейлиться и не занимать ресурсы. На высшем уровне можно возвращать fallback, например, кэш.
- *«Нужен ли circuit breaker для Kafka producer?»* — Если продюсер не может доставить сообщения (брокер недоступен), встроенный retry с backoff в клиенте обычно достаточен. Но если желаем избежать бесконечных попыток, можно обернуть продюсера в свой circuit breaker с таймаутом и после открытия помещать сообщения в dead letter.

## Как спроектировать систему для обработки сотен тысяч WebSocket соединений?

### Краткий ответ
Для поддержания 100k+ одновременных WebSocket-соединений на одном хосте необходимы: эффективная модель ввода-вывода (epoll/kqueue), минимизация горутин на бездействующее соединение, управление памятью (пулы буферов), и правильная настройка ОС. В Go используют библиотеки с event-loop подходом (`gnet`, `evio`) или кастомный epoll, а также шардирование соединений по нескольким worker горутинам с каналами.

### Развёрнутый ответ
Стандартная модель "одна горутина на соединение" с `gorilla/websocket` при 100k соединений создаёт 100k горутин, каждая потребляет минимум 2 КБ стека + буферы, что уже ~200 МБ только стеков, плюс нагрузка на планировщик при постоянном пробуждении большинства горутин, просто ожидающих данные. Это неэффективно.

Решение — использовать event-loop: одна или несколько горутин используют `epoll` для ожидания событий на множестве файловых дескрипторов. Библиотека `gnet` реализует эту модель. При поступлении данных вызывается callback, и только тогда создаётся временная горутина для обработки или выполняется в том же event-loop.

Альтернативный подход — пул горутин-обработчиков с каналами: каждое соединение не имеет своей горутины. Вместо этого используется epoll-горутина, которая при событиях ставит задачу в очередь к worker'ам. Worker'ы читают сообщение, обрабатывают и записывают ответ. Это похоже на стандартный netpoller, но даёт больше контроля.

Пример на Go с `gnet`:
```go
type wsServer struct {
    gnet.BuiltinEventEngine
    connections map[gnet.Conn]struct{}
}
func (s *wsServer) OnTraffic(c gnet.Conn) gnet.Action {
    msg, _ := c.Next(-1)
    // обработать сообщение
    c.AsyncWrite(frame)
    return gnet.None
}
```
Главное ограничение — gnet не поддерживает стандартную обработку HTTP upgrade на WebSocket «из коробки», нужен свой код для handshake.

### Под капотом (internals)
Netpoller в Go использует epoll/kqueue, но на каждое соединение есть горутина, которая вызывает `Read`/`Write`, и netpoller паркует/пробуждает её. При 100k соединений парковка и планирование горутин создаёт overhead. В `gnet` напрямую управляют epoll, избегая создания горутины на каждое соединение, что снижает потребление CPU и памяти.

### Типичные ошибки кандидатов
- **Использование небуферизированных каналов для записи в соединение**: при медленном клиенте пишущая горутина блокируется, занимая память и горутину. Исправление: канал с ограниченным буфером и сброс/дисконнект при переполнении.
- **Аллокация нового буфера на каждое сообщение**: GC под давлением. Исправление: sync.Pool для буферов, повторное использование.
- **Игнорирование TCP keep-alive**: со временем мёртвые соединения накапливаются. Исправление: установить `SetKeepAlive` и `SetReadDeadline` с таймаутом, периодическая проверка пингами.

### Возможные дополнительные вопросы интервьюера
- *«Как мониторить здоровье сотен тысяч соединений?»* — Экспорт метрик: количество активных соединений, throughput сообщений, latency. Использовать pprof для анализа числа горутин, GC пауз. Внедрять распределённую трассировку на уровне сообщений.
- *«Как обеспечить zero-downtime при деплое?»* — Кубить-под перезапускается, соединения обрываются. Решения: предварительное "drain" (новые соединения на другие поды, старые закрывать после grace period) и client reconnect с возобновлением стрима (смещение, sequence). Сервер может передать состояние сессии в Redis и новый под продолжит.

## Что такое "backpressure" на уровне всей системы?

### Краткий ответ
Backpressure — механизм регулирования потока данных, при котором потребитель сигнализирует производителю о своей занятости, замедляя или приостанавливая передачу. На уровне системы это охватывает все слои: от API-шлюза до БД, реализуется через тайм-ауты, ограниченные очереди, каналы, семафоры и отбрасывание запросов при перегрузке. В Go каналы и контексты — основные инструменты.

### Развёрнутый ответ
Без backpressure при превышении capacity очереди растут неограниченно, растёт latency, затем OOM и каскадный отказ. Backpressure начинается с самого конца: БД может принимать только N соединений, сервис-потребитель имеет ограниченный пул воркеров. Когда ресурс исчерпан, он должен отвергать новые запросы, заставляя вызывающий сервис замедлиться или вернуть ошибку.

Применяемые техники:
- **Rate limiting на входящем трафике**: API Gateway ограничивает rps, возвращая 429.
- **Ограниченные очереди**: Kafka broker ограничивает размер очереди на партицию, при превышении продюсер получает ошибку или блокируется. Go канал фиксированной ёмкости: при `ch <- msg` горутина блокируется, если буфер полон — естественный backpressure.
- **Семафоры**: `make(chan struct{}, maxWorkers)` ограничивают количество одновременных задач, вынуждая клиентов ждать.
- **Таймауты**: каждый запрос должен иметь дедлайн, чтобы не висеть бесконечно.

Пример: входящий HTTP запрос -> сервис A -> сервис B -> БД. Если БД перегружен, он медленно отвечает. Сервис B исчерпает свой пул воркеров и начнёт отклонять запросы или зависать в ожидании, что приведёт к исчерпанию ресурсов в A. Правильное решение: сервис B должен быстро возвращать ошибку при переполнении очереди (backpressure), а A — применять circuit breaker к B, отказывая клиенту раньше.

### Под капотом (internals)
В Go управлять backpressure можно через `select` с каналами и контекстом:
```go
select {
case sem <- struct{}{}:
    defer func() { <-sem }()
    // выполнить запрос
case <-ctx.Done():
    return ctx.Err()
}
```
`scheduler` при блокировке горутины на канале паркует её, не потребляя CPU, так что backpressure эффективен.

Клиентские библиотеки (gRPC, HTTP) имеют встроенные механизмы backpressure: gRPC flow control основан на HTTP/2 window update, ограничивая объём данных, отправляемых без подтверждения.

### Типичные ошибки кандидатов
- **Бесконечные очереди без предела**: использование небуферизованных каналов и затем создание горутин на каждый запрос без лимита — в итоге всё равно память кончится. Исправление: всегда ограничивать число горутин семафором, буферизованные каналы с разумным размером.
- **Ретраи без backoff при получении ошибки backpressure**: клиент в ответ на 429 ретраит немедленно, создавая ещё большую нагрузку. Исправление: уважать Retry-After заголовок и применять экспоненциальный backoff.
- **Не прокидывать контекст в вызовы**: операция без таймаута может блокироваться навсегда при перегрузке. Исправление: всегда передавать `ctx` с дедлайном во все операции ввода-вывода.

### Возможные дополнительные вопросы интервьюера
- *«Как реализовать backpressure между микросервисами через асинхронную очередь?»* — Использовать механизм подтверждений (ack/nack) с предварительным получением (QoS). Например, RabbitMQ задаёт `prefetch count`, ограничивая количество неподтверждённых сообщений, что естественно замедляет продюсера.
- *«Чем отличается backpressure от rate limiting?»* — Rate limiting — проактивное ограничение на входе, вне зависимости от реальной занятости системы. Backpressure — реактивный сигнал от перегруженного компонента к отправителю, который динамически замедляет поток.

## Как реализовать "graceful degradation" для критичных и некритичных сервисов?

### Краткий ответ
Graceful degradation — способность системы продолжать предоставлять основной функционал при отказе части зависимостей за счёт отключения некритичных функций или перехода на упрощённый режим (fallback). Реализуется через **приоритезацию вызовов**, **fallback-ы**, **stale-кэш**, и **статическое значение по умолчанию**. Критичные сервисы должны быть изолированы (bulkhead).

### Развёрнутый ответ
Пример: интернет-магазин. Главная страница показывает рекомендации (некритично) и информацию о товарах (критично). При сбое сервиса рекомендаций, магазин не должен падать. Рекомендационный сервис оборачивается в circuit breaker с fallback — возвращает пустой список или кэшированные ранее рекомендации.

Стратегии в Go:
- **Fallback функция**: при ошибке вызова сервиса возвращаем кэшированные данные или дефолтное значение.
- **Feature Flags**: возможность отключить некритичную функциональность без передеплоя (например, через конфиг в etcd).
- **Bulkhead**: разделение пулов горутин/соединений: критичные сервисы имеют свой пул, изолированный от некритичных.
- **Timeouts & Deadline**: некритичные вызовы делаются с жёстким таймаутом, если превышен — fallback немедленно.

Пример кода:
```go
func GetRecommendations(ctx context.Context, userID string) []Product {
    ctx, cancel := context.WithTimeout(ctx, 200*time.Millisecond)
    defer cancel()
    recs, err := recService.Get(ctx, userID)
    if err != nil {
        log.Warn("rec service failed", err)
        return fallbackCache.Get(userID) // stale cache
    }
    return recs
}
```

### Под капотом (internals)
В архитектурах с service mesh (Envoy) graceful degradation может выполняться на уровне прокси: envoy отключает маршрут к неисправному сервису и вставляет заранее заданный fallback ответ. В Go такая логика обычно в коде самого сервиса.

### Типичные ошибки кандидатов
- **Отсутствие различного таймаута для критичных и некритичных вызовов**: все ждут одинаково долго, некритичный сервис тормозит весь запрос. Исправление: устанавливать агрессивный таймаут для некритичных (например, 100мс), критичным давать 500мс+.
- **Паника при fallback из-за nil pointer**: fallback возвращает nil, а вызывающий код этого не ожидает. Исправление: тщательно проектировать fallback-значения, всегда возвращать не-nil слайс/структуру.
- **Не информировать клиентов о деградации**: клиент не понимает, почему нет рекомендаций. Исправление: в ответе добавить поле `degraded: true` или отправлять хедер, чтобы мониторинг мог отследить.

### Возможные дополнительные вопросы интервьюера
- *«Как определить, что пора включать degration на основе метрик?»* — Мониторинг latency и error rate. Если p99 некритичного сервиса превышает бюджет, можно автоматически перевести его в fallback (через feature flag или circuit breaker), об этом уведомляется команда.
- *«Как совместить graceful degradation и сильную консистентность?»* — Сильная консистентность обычно у критичных функций (платежи). Degradation для них может означать перевод в режим только чтения или использование штрафного кэша с риском устаревания. Нужно чётко определить, что допустимо для бизнеса.

## Как спроектировать "audit trail" для финансовых операций?

### Краткий ответ
Audit trail — неизменяемый журнал всех операций с сохранением контекста (кто, что, когда, источник). Реализуется как event log с append-only семантикой в отдельном хранилище (Cassandra, PostgreSQL с архивированием). Каждая операция пишет событие с уникальным ID, временем, идемпотентным ключом, деталями. Используется change data capture для репликации в аналитику.

### Развёрнутый ответ
Требования: записи не могут модифицироваться или удаляться, высокая долговечность, возможность воспроизведения всех изменений.

Архитектура:
- **Audit Log Service (Go)**: принимает события через gRPC/Kafka от всех сервисов.
- **Хранилище**: Cassandra с TTL записи (но юридически требуемое долгое хранение), или Amazon S3 с партиционированием по дате, или специализированные immutable ledger (Qldb). Cassandra подходит для высокой записи.
- **Схема записи**: `audit_id`, `timestamp`, `actor`, `action`, `entity_id`, `old_value`, `new_value`, `trace_id`, `idempotency_key`.
- **Idempotency**: уникальный ключ предотвращает дубликаты в журнале, проверка при вставке.
- **Шифрование**: чувствительные поля шифруются до попадания в лог (KMS).

В Go можно использовать `INSERT INTO ... IF NOT EXISTS` в Cassandra. Для PostgreSQL — `INSERT` с уникальным constraint по `audit_id`.

### Под капотом (internals)
Cassandra LWT (Lightweight Transactions) с `IF NOT EXISTS` использует Paxos, что замедляет запись, но гарантирует уникальность. Альтернатива — просто вставлять с тем же ключом и разрешить upsert, а дедупликацию делать при чтении.

Для высоких нагрузок (миллионы записей в сутки) используют асинхронную запись: из сервиса отправляется сообщение в Kafka, отдельный consumer пишет в БД пачками. При этом важно гарантировать доставку (retry+dedup).

### Типичные ошибки кандидатов
- **Запись аудита в той же транзакции, что и бизнес-операции**: замедляет основную операцию, усложняет транзакцию. Исправление: аудит отправлять асинхронно через очередь, либо использовать outbox pattern: запись в таблицу аудита в той же транзакции происходит синхронно, но быстро, а в фоне пересылается во внешнее хранилище.
- **Отсутствие обязательного поля trace_id**: невозможно связать события по цепочке вызовов. Исправление: всегда передавать `X-Trace-Id` или генерировать `trace.SpanContext`, записывать в аудит.
- **Хранение паролей или PAN в открытом виде**: нарушение комплаенса. Исправление: строгая политика маскирования и шифрования на уровне приложения.

### Возможные дополнительные вопросы интервьюера
- *«Как обеспечить, чтобы аудит не замедлял основной поток?»* — Использовать межпроцессное асинхронное взаимодействие с быстрой записью в локальный WAL или Kafka с подтверждением, и отдельный процесс для переноса данных в долговременное хранилище. Также можно применять буферизацию и запись батчами.
- *«Как подтвердить целостность аудиторского следа?»* — Периодически считать хеш цепочки (Merkle tree) и публиковать корневой хеш в открытом реестре или блокчейне, чтобы гарантировать неизменность. При аудите можно проверить любой отрезок цепочки.

## Как обеспечить целостность данных при асинхронном взаимодействии?

### Краткий ответ
Целостность обеспечивается через **транзакционный outbox**, **идемпотентность потребителя** и **Event sourcing**. Изменение данных и публикация события происходят атомарно в рамках одной БД-транзакции (outbox table), отдельный процесс доставляет событие. Потребитель обязан быть идемпотентным, проверяя уникальный event_id. Так достигается согласованность “в конечном счёте”.

### Развёрнутый ответ
Проблема: сервис изменяет свою БД и должен уведомить другие сервисы через очередь сообщений. Если сообщение публикуется после коммита, может случиться крах между коммитом и публикацией — событие потеряно. Если до коммита — событие отправлено, а транзакция откатилась — другие сервисы увидят несуществующее изменение.

**Outbox Pattern**: в той же транзакции, где изменяются бизнес-таблицы, добавляется запись в таблицу `outbox` (id, aggregate_id, event_type, payload). После коммита отдельный процесс (outbox relay) читает таблицу и публикует событие в брокер, после подтверждения удаляет запись. Таким образом, событие гарантированно публикуется ровно после успешной транзакции.

В Go relay может быть горутиной, периодически опрашивающей `SELECT ... ORDER BY id` и публикующей. Для масштабирования используют `SKIP LOCKED` в PostgreSQL, чтобы несколько relay-потоков не конфликтовали.

Идемпотентность потребителя: процесс получает сообщение с уникальным `event_id`, перед применением проверяет, не обработано ли уже это событие, вставляя в таблицу `processed_events`. Если уже есть, игнорирует.

Пример кода relay:
```go
rows, _ := db.QueryContext(ctx, `DELETE FROM outbox WHERE id IN (SELECT id FROM outbox ORDER BY id LIMIT 100) RETURNING *`)
// итерация по rows, публикация в Kafka
```

### Под капотом (internals)
CDC (Change Data Capture) подход: Debezium читает WAL PostgreSQL и отправляет изменения в Kafka напрямую, исключая необходимость outbox relay в приложении. Это нулевая задержка и надёжно. Однако в Go потребуется настройка коннектора.

Outbox с `SKIP LOCKED` обеспечивает конкурентную безопасность: несколько экземпляров сервиса могут одновременно обрабатывать outbox без дублирования.

### Типичные ошибки кандидатов
- **Публикация события в Kafka до коммита транзакции**: при откате событие всё равно доставлено, получатель может выполнить недействительное действие. Исправление: outbox после коммита.
- **Отсутствие idempotency key в потребителе**: повторная доставка того же сообщения приводит к двойной обработке. Исправление: вставка `event_id` в уникальный индекс.
- **Удаление из outbox сразу после успешной публикации в канал без гарантий**: если relay упадёт после публикации, но до удаления, сообщение будет отправлено повторно. Исправление: обработка outbox не должна удалять запись до тех пор, пока потребитель не обработает (сложно). Лучше полагаться на идемпотентность.

### Возможные дополнительные вопросы интервьюера
- *«Можно ли использовать outbox без релейной таблицы, напрямую в Kafka транзакциях?»* — Kafka транзакции могут гарантировать атомарность записи в топик и изменения данных, если БД и Kafka поддерживают двухфазную фиксацию (Debezium + Kafka Connect) или если используется Kafka Streams с EOS, но обычно всё равно нужен outbox.
- *«Как обработать ситуацию, когда outbox relay отстаёт и очередь событий растёт?»* — Добавить больше relay instances (scale out). Если причина — медленный consumer, наращивать потребителей. Также можно увеличить batch size для relay.

## Как спроектировать систему с "multi-tenancy"?

### Краткий ответ
Multi-tenancy позволяет обслуживать нескольких клиентов (тенантов) в одном инстансе приложения, изолируя их данные и конфигурации. Модели: разделение на уровне БД (database per tenant), схемы (schema per tenant) или дискриминатор-колонка (shared table). Выбор зависит от количества тенантов и требований к безопасности. В Go внедряются middleware, устанавливающие контекст тенанта и маршрутизирующие к нужному пулу БД.

### Развёрнутый ответ
Три основных подхода:
1. **Database per tenant**: отдельная БД для каждого клиента. Максимальная изоляция, простое резервное копирование. Подходит для небольшого числа крупных клиентов. Сложно делать cross-tenant агрегацию.
2. **Schema per tenant**: в рамках одного экземпляра PostgreSQL — отдельная схема для каждого тенанта. Хороший баланс изоляции и использования ресурсов, но количество схем может быть ограничено.
3. **Shared table with tenant_id**: все данные в одних таблицах, дискриминатор — столбец `tenant_id`. Наиболее эффективно по ресурсам, но требует строгой фильтрации каждого запроса, иначе возможна утечка данных. Подходит для огромного числа маленьких тенантов.

В Go обычно используют третий подход с middleware:
```go
func TenantMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        tenantID := r.Header.Get("X-Tenant-ID") // или из JWT
        ctx := context.WithValue(r.Context(), "tenant", tenantID)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}
```
Все репозитории при выполнении запросов добавляют `WHERE tenant_id = $1` из контекста. Для соединений с БД можно использовать один общий пул, а можно — пул на каждый тенант, но это дорого.

Безопасность: обязательно проверять, что пользователь имеет доступ к запрашиваемому тенанту. Фильтрация должна быть на уровне приложения и на уровне БД (Row-Level Security в PostgreSQL может автоматически добавлять `WHERE` политику).

### Под капотом (internals)
RLS (Row-Level Security) в PostgreSQL: `CREATE POLICY tenant_isolation ON orders USING (tenant_id = current_setting('app.current_tenant')::UUID);` затем в начале сессии `SET app.current_tenant = '...';`. Это защищает от багов в коде. В Go драйвер может устанавливать эту переменную в каждом контексте.

### Типичные ошибки кандидатов
- **Забывать добавить `tenant_id` в запросы**: данные одного тенанта попадают другому. Исправление: создать helper, который автоматически добавляет условие, и строгая политика RLS как дополнительный барьер.
- **Использование одного глобального кэша без tenant-ключей**: кэшированные данные могут быть отправлены другому клиенту. Исправление: инвалидация кэша с tenant-префиксом.
- **Создание нового пула соединений для каждого тенанта**: при большом количестве тенантов исчерпание ресурсов БД. Исправление: shared pool + RLS или сессионная переменная.

### Возможные дополнительные вопросы интервьюера
- *«Как масштабировать multi-tenant приложение, когда некоторые тенанты создают высокую нагрузку (noisy neighbor)?»* — Применить throttling на уровне тенанта (rate limiter per tenant), изолировать ресурсоёмких тенантов в собственные инстансы БД/пула (database per tenant), использовать весовые fair scheduling.
- *«Как обеспечить изоляцию между тенантами в Cassandra?»* — Использовать `tenant_id` как part of partition key. При создании keyspace на тенанта — сложно. Обычно выбирают shared table с tenant_id в партиции и role-based access control на уровне приложения.

## Как работает "reverse proxy" и "load balancer" на уровне layer 7?

### Краткий ответ
Layer 7 (Application) обратный прокси и балансировщик работают на уровне HTTP, анализируя заголовки, URL, cookies для маршрутизации. Могут выполнять SSL termination, сжатие, кэширование, аутентификацию. Балансировщик распределяет запросы по бэкендам на основе алгоритмов (round-robin, least connections, consistent hash). В Go можно реализовать с помощью `net/http/httputil.ReverseProxy` и кастомного `Director`.

### Развёрнутый ответ
Reverse proxy принимает запросы от клиентов и перенаправляет их на бэкенд-серверы, возвращая ответ. Это позволяет скрыть внутреннюю топологию, централизованно управлять политиками.

Балансировщик L7 использует информацию HTTP: по URL `/api/v1` направляет в один сервис, `/images` — в другой. Поддерживает sticky sessions на основе cookie или x-forwarded-for.

В Go базовая реализация:
```go
rp := &httputil.ReverseProxy{
    Director: func(req *http.Request) {
        req.URL.Scheme = "http"
        req.URL.Host = pickBackend() // из списка
        // модифицируем заголовки
    },
    Transport: &http.Transport{
        MaxIdleConns:    100,
        IdleConnTimeout: 90 * time.Second,
    },
}
http.ListenAndServe(":80", rp)
```
Для продвинутой балансировки с health-checkами пишут кастомный Director с внутренним пулом серверов, учитывающим их живучесть и текущую нагрузку (least connections).

### Под капотом (internals)
`ReverseProxy` в стандартной библиотеке обеспечивает буферизацию тела, обработку ошибок, поддержку WebSocket через `FlushInterval`. L7 балансировщик обычно использует epoll и пулы соединений. Envoy, HAProxy — мощные промышленные решения. На Go можно написать свой, используя `fasthttp` для большего RPS.

### Типичные ошибки кандидатов
- **Неправильная обработка потоков при использовании WebSocket**: обычный ReverseProxy может буферизовать ответы; для WebSocket нужно включить `FlushInterval=-1` и правильную обработку Upgrade заголовков.
- **Отсутствие health check'ов**: балансировщик продолжает слать запросы на мёртвый бэкенд. Исправление: реализовать активные проверки (HTTP /health) и пассивные (после N ошибок исключать сервер).
- **Некорректная обработка заголовков хоста и протокола**: бэкенд видит неправильный Host. Исправление: в Director обновлять `req.Host` и `req.URL.Host`, добавлять `X-Forwarded-For`, `X-Forwarded-Proto`.

### Возможные дополнительные вопросы интервьюера
- *«Как реализовать consistent hashing в L7 балансировщике?»* — Определить ключ (source IP, cookie), вычислить хэш, найти сервер в кольце. При изменении списка серверов перераспределится минимум ключей. В Go использовать готовое решение из `hashring` или реализовать кольцо отсортированных хэшей с бинарным поиском.
- *«В чём отличие L4 от L7 балансировки с точки зрения производительности?»* — L4 работает на уровне TCP, не парсит HTTP, потому быстрее и требует меньше ресурсов, но не может маршрутизировать по URL, не умеет SSL termination. L7 гибче, но добавляет задержку на разбор протокола.

## Как реализовать "health check" для сервисов с различными зависимостями?

### Краткий ответ
Health check должен проверять не только работоспособность самого процесса, но и критических зависимостей (БД, очереди, внешние сервисы). В Go используют endpoint `/health` с вариативной глубиной: liveness (жив ли процесс) и readiness (готов ли принимать трафик). Зависимости проверяются с учётом таймаутов, при их отказе сервис помечается как неготовый, чтобы оркестратор перестал слать запросы.

### Развёрнутый ответ
Kubernetes различает liveness и readiness probes. Liveness: простая проверка, что приложение не зависло — обычно `GET /healthz` возвращает 200. Readiness должен быть более умным: включает проверку подключения к БД, Redis, Kafka и т.д. Если БД недоступна, сервис может ещё какое-то время работать с кэшем, но новые запросы, требующие запись, обречены на провал; сервис должен сообщить о неготовности.

Реализация в Go:
```go
func readinessHandler(w http.ResponseWriter, r *http.Request) {
    checks := []struct{
        name string
        fn   func() error
    }{
        {"postgres", checkDB},
        {"redis", checkRedis},
        {"kafka", checkKafka},
    }
    healthy := true
    for _, c := range checks {
        if err := c.fn(); err != nil {
            log.Warn("readiness check failed", c.name)
            healthy = false
        }
    }
    if healthy {
        w.WriteHeader(http.StatusOK)
    } else {
        w.WriteHeader(http.StatusServiceUnavailable)
    }
}
```
Важно: проверки не должны блокироваться надолго; используют контекст с таймаутом (1–2 секунды). Результаты можно кэшировать на несколько секунд, чтобы избежать лишней нагрузки от частых опросов Kubernetes.

Для критических зависимостей — grace period: если БД кратковременно отвалилась, не стоит сразу выключать трафик; можно добавить деградацию и продолжать работу, но readiness должен всё равно сигнализировать.

### Под капотом (internals)
Go http сервер при проверке liveness может использовать канал `heartbeat`, который регулярно обновляется основной горутиной. Если горутина заблокирована, хендлер возвращает 500.

### Типичные ошибки кандидатов
- **Смешивание liveness и readiness в одном endpoint без дифференциации**: liveness проверяет БД, при зависании БД kubelet убивает все поды, усугубляя ситуацию. Исправление: разделить на `/live` (простая проверка) и `/ready` (с зависимостями).
- **Блокирование health handler’a из-за долгих проверок**: Kubernetes убивает под по таймауту. Исправление: давать health check-функциям короткий таймаут и возвращать ответ не дольше 1с.
- **Отсутствие кэширования результата readiness**: частые опросы каждую секунду перегружают БД кучей `SELECT 1`. Исправление: вычислять результат с интервалом и отдавать закэшированный.

### Возможные дополнительные вопросы интервьюера
- *«Как реализовать graduated health checks (разные уровни)?»* — Например, shallow (только локальный процесс), deep (все зависимости + синтетическая транзакция) — через опциональный query param `?depth=deep`. Оркестратор использует shallow для liveness, deep для readiness.
- *«Как тестировать, что health check правильно отражает отказ зависимости?»* — В интеграционных тестах временно останавливаем зависимость (testcontainers) и проверяем, что readiness возвращает 503, а liveness всё ещё 200. Убеждаемся, что трафик не идёт на неготовые поды.

## Как спроектировать "service mesh"?

### Краткий ответ
Service mesh выносит межсервисное взаимодействие из кода приложений в sidecar-прокси (Envoy), реализуя обнаружение, маршрутизацию, балансировку, безопасность (mTLS), трассировку и circuit breaking. Основа — контрольная плоскость (Istio, Linkerd) и data plane из прокси. Приложения Go общаются с localhost прокси, который берёт на себя все аспекты взаимодействия.

### Развёрнутый ответ
Mesh-архитектура решает проблемы микросервисной коммуникации без изменения кода:
- **Control Plane** (Istio Pilot, Mixer, Citadel): управляет конфигурацией маршрутов, политиками, сертификатами.
- **Data Plane**: sidecar (Envoy), встраиваемый рядом с каждым сервисом.
Все исходящие вызовы из сервиса идут через Envoy, который применяет правила: таймауты, ретраи, circuit breaker, трассировка. Входящие запросы также терминируются на Envoy, затем перенаправляются в приложение.

В Go-сервисе обычно не нужно менять код: он шлёт http-запросы на `localhost:80`, но реально работает через iptables/iptables перенаправление на Envoy. Envoy обеспечивает mTLS между собой, генерирует метрики и трейсы.

Преимущества: единообразие, наблюдаемость, безопасность. Недостатки: увеличение задержки (~1–2 мс на хоп), потребление ресурсов sidecar'ом. Для lightweight mesh можно использовать Linkerd, который написан на Rust и лёгок.

### Под капотом (internals)
Envoy реализован на C++, использует thread-per-core модель с non-blocking sockets. Sidecar инжектится через Kubernetes mutating webhook. На Go можно создать собственный data plane, используя библиотеки аналогичные `goproxy`, но это нецелесообразно.

### Типичные ошибки кандидатов
- **Попытка строить mesh без control plane**: ручная конфигурация каждого Envoy становится неуправляемой. Исправление: использовать Istio, Consul Connect.
- **Неправильная настройка mTLS без ротации сертификатов**: сертификаты истекают, сервисы ломаются. Исправление: автоматизированная ротация через CA (Citadel, cert-manager).
- **Добавление mesh в простую систему из 3 сервисов**: избыточно, добавляет сложность. Исправление: применять, когда количество сервисов превышает 10, и нужна наблюдаемость и гибкая маршрутизация.

### Возможные дополнительные вопросы интервьюера
- *«Как дебажить проблемы с задержками в service mesh?»* — Использовать распределённую трассировку (Jaeger), видеть hop-ы. В Envoy включить детальное логирование, метрики `upstream_rq_time`. Если задержка в sidecar, смотрим на CPU Envoy.
- *«Как сделать canary deployment через service mesh?»* — В Istio задаёте VirtualService с weight-based routing: 90% трафика на стабильную версию, 10% на канареечную, с отслеживанием ошибок.

## Как работать с "eventual consistency" в финансовом контексте?

### Краткий ответ
В финансах eventual consistency используется с осторожностью, дополняясь идемпотентностью, компенсирующими транзакциями и строгим аудитом. Где допустима слабая согласованность? В некритичных отчётах, расчётах бонусов, аналитике. Для платежей и балансов применяют strong consistency. Однако и для eventual операций нужна конечная гарантия: саги, реконсиляция, проверка инвариантов.

### Развёрнутый ответ
Например, начисление cashback: можно сделать асинхронно, использовать паттерн «Saga + outbox». После подтверждения покупки создаётся задача начислить кэшбек. В случае сбоя начисления, компенсация не нужна (можно повторить). Но чтобы избежать двойного начисления, используют идемпотентный ключ (transaction_id). Баланс кэшбека может быть слабо консистентным, показываться с небольшой задержкой, что приемлемо.

Другой пример: перевод между разными банками через систему SWIFT — это inherently eventual. Средства могут быть списаны в одном банке, но зачислены в другом с задержкой. Механизм реконсиляции и обратного платежа компенсирует ошибки.

Техники для финансы + eventual:
- **Outbox + CDC**: атомарная запись события о проводке гарантирует, что последующие потребители рано или поздно обновят свои проекции.
- **Идемпотентные операции**: позволяют безопасно повторять обработку.
- **Сага с компенсацией**: если перевод межбанковский не может быть завершён, выполняется обратный перевод.
- **Реконсиляция**: периодическое сравнение состояния с внешним источником истины.

### Под капотом (internals)
В финансовых ledgers (например, QLDB) используется immutable journal, который реплицируется по множеству нод, но предоставляет последовательное чтение? QLDB дает сильную консистентность. Для eventual систем на основе Kafka, потребитель должен использовать `KTable` с changelog, чтобы восстанавливать состояние.

### Типичные ошибки кандидатов
- **Применение eventual к критическим балансовым операциям без контроля**: двойное списание. Исправление: critical path всегда strong (linearizable).
- **Отсутствие консистентности при чтении после записи (read-your-writes)**: клиент сразу после совершения операции видит устаревшие данные и может подумать, что операция не прошла. Исправление: использовать sticky sessions к primary или read-after-write consistency.
- **Неточное понимание термина**: считать, что eventual consistency значит «данные могут быть некорректны всё время». Исправление: eventual гарантирует сходимость; нужно понимать окно конвергенции и его влияние на бизнес.

### Возможные дополнительные вопросы интервьюера
- *«В каких случаях в биржевой системе допустимо eventual?»* — Сводки рыночных данных (order book) могут приходить с небольшим лагом, это нормально. Выставление ордера требует сильной гарантии только в контексте баланса трейдера, но само размещение заявки может быть принято с eventual подтверждением, если используется система сообщений.
- *«Как обеспечить монотонные чтения при eventual?»* — Клиент передаёт маркер последней виденной версии (Log Sequence Number), и сервер направляет запрос к реплике, которая уже содержит эту версию.

## Что такое "margin call" система и как ее спроектировать?

### Краткий ответ
Margin call — требование брокера к клиенту внести дополнительные средства при падении стоимости залога ниже порога. Система должна мониторить позиции клиентов в реальном времени, вычислять equity и требуемый margin, и при нарушении инициировать уведомление и ликвидацию позиций. Проектируется как событийно-ориентированный пайплайн с низкой латентностью.

### Развёрнутый ответ
Компоненты:
- **Position Service**: хранит открытые позиции (лонг/шорт), цены входа, плечо.
- **Market Data Feed**: получает котировки для переоценки портфеля (mark-to-market).
- **Risk Engine**: при каждом обновлении цены пересчитывает для клиентов: Equity = Balance + PnL, Margin Requirement, Margin Level = Equity / Required Margin. Если Margin Level < порога, генерирует событие `MarginCall` (warning) или `Liquidation`.
- **Notification Service**: отправляет уведомления клиенту (email, push).
- **Liquidation Engine**: автоматически выставляет ордер на закрытие позиции по рынку для возврата к приемлемому уровню.

Архитектура: цена поступает в Kafka; consumer (Go) обновляет кэш цен, затем скользящим окном пересчитывает риски по всем позициям. Для большого числа клиентов пересчёт должен быть эффективным: можно использовать инкрементальный подход: пересчитывать только клиентов, затронутых изменением цены актива. Для этого держим мапу `asset -> list of client positions`.

Liquidation должна быть надёжной: ордер отправляется с высоким приоритетом, с таймаутом, и в случае неудачи — повтор.

### Под капотом (internals)
В Go risk engine может использовать несколько горутин, разделённых по asset. Каждая получает тики цен и обновляет позиции. Для ускорения можно использовать lock-free структуры данных и локальные счётчики.

### Типичные ошибки кандидатов
- **Пассивная стратегия: пересчёт только по запросу пользователя**: margin call может быть пропущен при быстром движении рынка. Исправление: активный мониторинг при каждом изменении цены.
- **Отсутствие механизма graceful handling при задержках маркет-даты**: система может не успеть среагировать на гэп. Исправление: иметь триггеры на основе `lastPrice` с таймаутом, и если данные старые, считать недействительными и использовать более консервативные лимиты.
- **Ликвидация ордером, который исполняется частично и не покрывает маржин-колл**: система снова генерирует новый ордер. Исправление: зациклить логику до тех пор, пока позиция не станет удовлетворительной, но с лимитом итераций.

### Возможные дополнительные вопросы интервьюера
- *«Как избежать каскадных ликвидаций на падающем рынке?»* — Использовать механизмы "auto-deleveraging" или страхование риска (insurance fund). На уровне архитектуры — задавать разумные уровни и мониторить системные риски, приостанавливать торговлю при экстремальной волатильности (цепной прерыватель).
- *«Как обеспечить атомарность списания маржи и закрытия позиции?»* — Использовать ledger с сагой: создать событие ликвидации, которое при успешном закрытии ордера уменьшает баланс и закрывает позицию; если ордер не исполнен, компенсировать.

## Как устроен процесс "клинга" (netting) транзакций?

### Краткий ответ
Netting (клиринг) — зачёт встречных обязательств между участниками для уменьшения количества операций и рисков. Бывает двусторонний (между двумя сторонами) и многосторонний (через центрального контрагента). В системе проектируется агрегация потоков платежей за период, вычисление чистых позиций и исполнение одной результирующей проводки. Реализуется через пакетную обработку с итоговыми расчётами.

### Развёрнутый ответ
Пример: брокер A и брокер B в течение дня совершают множество сделок друг с другом. Вместо того чтобы совершать денежный перевод по каждой сделке, в конце дня вычисляется нетто-позиция: кто кому должен доплатить. Это снижает нагрузку на платёжную систему и кредитный риск.

Процесс:
1. Сбор всех сделок за период (T+0, T+1).
2. Группировка по контрагенту и валюте.
3. Расчёт чистого обязательства: Sum(payables) - Sum(receivables).
4. Генерация единой проводки (settlement) для каждой пары.
5. Обновление ledger: дебет/кредит на чистую сумму.

В высоконагруженной системе можно делать непрерывный неттинг (real-time) для снижения пикового объёма расчётов. В Go это реализуется как потоковая агрегация: Kafka Streams, где входной топик — сделки, затем окно или сессия агрегирует, выдавая событие `NetPosition`. Затем сервис settlement выполняет финальный перевод.

Для финансовых бирж используется CCP (Central Counterparty), который становится стороной для каждой сделки и затем неттингом между участниками.

### Под капотом (internals)
Агрегация с использованием state store RocksDB в `kafka-streams` или свой in-memory map с периодической записью снапшотов. В Go можно написать consumer, который накапливает позиции в `sync.Map` (ключ participant+currency), а по таймеру записывает изменения в БД и публикует событие.

### Типичные ошибки кандидатов
- **Неправильный учёт валют при неттинге**: нельзя неттить разные валюты без пересчёта по курсу. Исправление: группировка по валюте, конверсия по фиксингу.
- **Не учитывать возможность отмены сделки**: после неттинга и расчёта приходит отмена — сложно развернуть. Исправление: делать неттинг только по финализированным сделкам, или иметь механизм реверсивного неттинга (корректировка).
- **Накопленная ошибка из-за округлений**: если округлять каждую сделку, сумма нетто может накопить ошибку. Исправление: округлять только на этапе итогового расчёта, следовать стандарту ISO 4217.

### Возможные дополнительные вопросы интервьюера
- *«Как реализовать многосторонний неттинг в распределённой системе?»* — Сначала группируем сделки по уникальному идентификатору участника, используя consistent hashing, чтобы все его сделки попадали в одну партицию. Затем воркер этой партиции считает нетто по отношению ко всем остальным, и результаты публикуются в топик расчётов. Центральный сервис затем агрегирует окончательные межконтрагентские позиции.
- *«Влияет ли неттинг на ликвидность?»* — Да, он снижает потребность в резервировании и ускоряет расчёты, что повышает ликвидность.

## Как спроектировать "real-time fraud detection" систему?

### Краткий ответ
Система реального времени для выявления мошенничества использует потоковую обработку событий, применяя правила и ML-модели с задержкой <50 мс. Компоненты: ingestion (Kafka), feature store с низкой латентностью (Redis, in-memory state), движок правил с поддержкой сложных временных окон и модель ML (ONNX runtime). Отказ может означать пропуск мошенничества, поэтому важна высокая доступность и точность.

### Развёрнутый ответ
Поток: транзакции публикуются в Kafka топик. Сервис fraud detection (Go) потребляет их, обогащает признаками из feature store (например, средняя сумма транзакций за последний час, количество попыток с этого устройства). Feature store обновляется из того же потока, обеспечивая актуальность.

Правила могут быть простыми: "если сумма > 10000 и страна != домашняя, то блокировать". Для сложных временных паттернов, например "более 5 транзакций за 10 минут с разных IP", реализуются через sliding windows с помощью Redis или in-memory.

ML-модель для скоринга риска: тренируется офлайн на исторических данных, экспортируется в ONNX. В Go можно загрузить модель через `onnxruntime-go` и выполнить инференс за доли миллисекунды. Результат — скоринговый балл; если выше порога, транзакция отклоняется.

### Под капотом (internals)
Feature store на Go: использование кольцевых буферов для окон по каждому ключу (card_id, user_id), синхронизация через горутину, которая обрабатывает события строго последовательно для каждого ключа (шардирование по ключу). lock-free структуры с атомарными указателями обеспечивают быстрый доступ при чтении. Инференс ONNX выполняется через C API, Go вызывает его через cgo, лучше использовать модель, оптимизированную под CPU.

### Типичные ошибки кандидатов
- **Блокирующие запросы к внешним сервисам во время принятия решения**: задержка, не укладываемся в бюджет 50 мс. Исправление: все данные должны быть предварительно загружены в локальный state, внешние сервисы вызывать асинхронно после решения (для обогащения аудита).
- **Использование глобальных мьютексов для обновления feature store**: contention замедляет обработку. Исправление: шардированный key-value store, каждый воркер владеет подмножеством ключей, либо lock-free map с CAS.
- **Отсутствие механизма быстрой адаптации правил**: мошенники меняют схемы, а обновление требует передеплоя. Исправление: хранить правила в динамической конфигурации (etcd, Consul), применять без рестарта.

### Возможные дополнительные вопросы интервьюера
- *«Как бороться с ложными срабатываниями?»* — Внедрить многоуровневую систему: при высоком скоре — challenge (запрос дополнительного подтверждения), при критическом — блокировка. Анализировать precision/recall, настраивать пороги.
- *«Как обрабатывать опоздавшие события при обновлении feature store?»* — Использовать событийный временной штамп, допускать окна с задержкой (allowed lateness), но поскольку это real-time fraud, сильно отставшие события могут быть отброшены или обработаны отдельно для корректировки статистики.

## Как обеспечить низкую латентность (< 1 мс) в Go-сервисе?

### Краткий ответ
Для достижения субмиллисекундной задержки в Go исключают блокировки (lock-free структуры), минимизируют аллокации (избегая GC-пауз), используют ручное управление памятью (arena/sync.Pool), настраивают GOGC, привязывают горутины к потокам ОС (LockOSThread) и используют быстрые сетевые библиотеки (gnet, evio) с прямым epoll. Каждый наносекундный шаг анализируется с помощью pprof и бенчмарков.

### Развёрнутый ответ
Ключевые техники:
- **No allocations on hot path**: все структуры создаются на стеке, escape analysis контролируется. Срезы и мапы предвыделяются, строки используются через `[]byte`. Использование `sync.Pool` для временных объектов.
- **Lock-free**: применение `atomic` операций, CAS для обновления счётчиков, ring buffers без мьютексов (Disruptor pattern).
- **GC Control**: `GOGC=off` или установка очень высокого значения, ручной вызов `runtime.GC()` в периоды низкой активности. В Go 1.19+ `arena` позволяет выделять большие регионы и быстро их освобождать без GC.
- **CPUs isolation**: закрепление критической горутины за выделенным CPU через `taskset` и `runtime.LockOSThread()` + `SchedSetaffinity`.
- **Networking**: использование `gnet` с epoll для сервера, обход блокировок stdlib net. На исходящих вызовах — connection pooling, keep-alive.
- **Batch processing**: обработка входящих сообщений пачками, использование SIMD (через ассемблерные вставки в Go 1.20+).

Пример ring buffer для intra-service communications:
```go
type RingBuffer struct {
    buf    []int64
    cursor uint64 // атомарный
    mask   uint64
}
func (r *RingBuffer) Offer(val int64) bool {
    curr := atomic.LoadUint64(&r.cursor)
    next := curr + 1
    if atomic.CompareAndSwapUint64(&r.cursor, curr, next) {
        r.buf[next&r.mask] = val
        return true
    }
    return false
}
```

### Под капотом (internals)
Go планировщик может прерывать горутину в любой safe-point (например, при вызове функций). Чтобы избежать неконтролируемых задержек от прерываний, в критическом цикле минимизируют вызовы, которые являются safe-points (планировщик вставляет их при переходе, но сложные циклы с арифметикой могут работать без прерываний). Однако на практике проще полагаться на LockOSThread и использовать изолированные ядра.

GC pause в Go сейчас суб-миллисекундные при грамотной настройке, но для <1мс сервиса даже 0.5 мс пауза критична. Поэтому используют `GOGC=off`, и вручную вызывают `runtime.GC()` каждые 10-30 секунд в фоне.

### Типичные ошибки кандидатов
- **Повсеместное использование `interface{}`**: boxing вызывает аллокации. Исправление: использовать конкретные типы, дженерики для обобщённых функций без боксинга.
- **Частое создание каналов**: каждый канал — структура с буфером, удаление требует GC. Исправление: переиспользование каналов из пула или использование кольцевых буферов без каналов.
- **Неправильная настройка GOMAXPROCS**: по умолчанию равно количеству воркеров, что может привести к излишней конкуренции за кэш. Исправление: устанавливать GOMAXPROCS равным количеству выделенных ядер, также можно задать `GOMAXPROCS=1` для single-threaded движка.

### Возможные дополнительные вопросы интервьюера
- *«Как измерять latency с микросекундной точностью?»* — Использовать `time.Now().UnixNano()`, который на современных платформах предоставляет наносекундное разрешение. Для снятия гистограмм — `hdrhistogram-go`. Важно измерять end-to-end: от приёма байтов из сокета до отправки ответа.
- *«Стоит ли использовать Go для действительно hard real-time (микросекунды)?»* — Go в общем случае не подходит для жёсткого реального времени из-за GC и планировщика. Но для soft real-time с задержкой в сотни микросекунд — да. Для мкс можно использовать C/ASM внутри cgo или избегать GC.

## Как работает "lock-free" движок для биржи?

### Краткий ответ
Lock-free движок построен на конкурентных структурах данных без мьютексов, использующих атомарные операции (CAS) для координации. Ключевой элемент — кольцевой буфер (Disruptor) для передачи команд между продюсерами и консьюмерами. Order book реализуется через lock-free списки/массивы с CAS-операциями для обновления уровней. В Go это достигается с помощью `atomic`, обхода pointer'ов и отсутствия аллокаций.

### Развёрнутый ответ
Disruptor pattern: pre-allocated ring buffer, где продюсеры претендуют на следующий слот через `atomic.AddUint64`, а консьюмеры отслеживают курсор завершения. Когда событие (новый ордер) помещено в слот, оно становится видимым для консьюмера (машинный барьер). Консьюмер (matching engine) обрабатывает события последовательно без блокировок.

Order book внутри движка может быть реализован как массив фиксированного размера для ценовых уровней, где каждый уровень защищён CAS для обновления объёма. Например, структура уровня:
```go
type PriceLevel struct {
    price   uint64
    volume  int64
    orders  []Order // list, но операции с ним реже
    next    *PriceLevel
}
var level *PriceLevel
// чтение и кастующие обновления: CAS на указатель level с новым объёмом
for {
    old := atomic.LoadPointer((*unsafe.Pointer)(unsafe.Pointer(&level)))
    newLevel := *(*Level)(old)
    // newLevel.volume += delta
    if atomic.CompareAndSwapPointer(...) { break }
}
```
На практике lock-free order book очень сложен и редко пишется вручную, чаще используют Disruptor и однопоточную обработку, которая внутри не имеет блокировок.

### Под капотом (internals)
В Go `atomic.CompareAndSwapPointer` генерирует инструкции LOCK CMPXCHG на x86, которые работают за ~50-100 циклов при отсутствии конкуренции. Модель памяти Go гарантирует sequential consistency для атомиков. Disruptor библиотека `disruptor` использует `atomic` для координации курсоров и memory barrier.

### Типичные ошибки кандидатов
- **Думать, что отсутствие мьютексов достаточно для lock-free**: lock-free алгоритмы должны гарантировать прогресс всей системы (не блокируют все потоки). Неправильная реализация CAS loop может привести к livelock. Исправление: изучать классические алгоритмы (Michael-Scott queue) и тщательно тестировать.
- **Использование указателей без учёта сборщика мусора**: в lock-free структурах указатели могут стать dangling из-за GC? В Go GC с барьерами записи, и он concurrency-safe, но memory ordering может нарушиться при неатомарных операциях. Исправление: все операции с разделяемыми указателями атомарные.
- **Пренебрежение false sharing**: две атомарные переменные на одной кэш-линии вызывают contention на линии. Исправление: разделять их отбивкой на 64-байта (`[64]byte`).

### Возможные дополнительные вопросы интервьюера
- *«Сравните lock-free с actor model для биржи.»* — Actor model (одна горутина-движок) проще, предсказуема, нет сложности lock-free, но требует асинхронного интерфейса и может иметь чуть большую задержку на взаимодействие между акторами. Lock-free позволяет параллельную обработку внутри движка, но сложен. Выбор зависит от требований пропускной способности.
- *«Как тестировать lock-free код?»* — Stress-тесты с race detector, но race detector не ловит все случаи. Использовать `sync/atomic` корректно, применять тесты на корректность порядка (serializability). Chaos-тестирование с задержками.

## Как спроектировать "распределенный планировщик задач"?

### Краткий ответ
Распределённый планировщик (distributed cron) гарантирует запуск задачи ровно один раз на одном из узлов кластера в заданное время. Реализуется через внешнее координационное хранилище (etcd, Consul, БД) с блокировками или лидерскими выборами (leader election). Планировщик может быть основан на паттерне «один сервис-лидер» или «партиционированные задачи с хэшем». В Go используется cron-библиотека с распределённым бэкендом.

### Развёрнутый ответ
Простейший вариант: leader election через etcd. Все поды соревнуются за создание key с lease. Только лидер запускает задачи по расписанию. Недостаток: все задачи выполняются на одном узле.

Более масштабируемый: партиционирование задач по имени или ID. Используется consistent hashing на списке живых узлов (обнаруживаются через etcd). Каждый узел отвечает за свой набор задач. При изменении кластера перераспределяются только затронутые.

Для обеспечения exactly-once выполнения каждая задача с unique execution_id записывается в хранилище с состоянием (claimed). Перед стартом узел пытается атомарно пометить задачу как выполняемую, обычно через `INSERT ... ON CONFLICT` или Redis `SETNX` с TTL.

В Go можно использовать `robfig/cron` и добавить middleware:
```go
c := cron.New()
c.AddFunc("* */1 * * *", func() {
    if !acquireLock("task:cleanup", 1*time.Hour) {
        return
    }
    doCleanup()
})
```
Lock реализован через Redis/etcd.

### Под капотом (internals)
etcd lease с keepalive: если узел умирает, ключ удаляется, и другой узел может занять блокировку. Для партиционирования можно использовать библиотеку `go-co-op/gocron` с распределённым locking через Redis.

### Типичные ошибки кандидатов
- **Запуск cron на всех узлах без координации**: задачи выполняются многократно. Исправление: внедрить распределённую блокировку с TTL.
- **Переиспользование одного lock для всех задач**: приводит к тому, что только один узел всё делает. Исправление: отдельные lock’и на каждую задачу либо шардирование.
- **Отсутствие мониторинга пропущенных или зависших задач**: нет алертов. Исправление: писать heartbeat задачи в БД, проверять, что задача выполнилась вовремя, иначе алерт.

### Возможные дополнительные вопросы интервьюера
- *«Как быть, если задача выполняется дольше, чем её интервал?»* — Использовать обнаружение overlapping: перед запуском проверять, не выполняется ли предыдущая итерация (по статусу в БД). Если да, можно пропустить или поставить в очередь. Важно не накапливать бесконечные горутины.
- *«Как реализовать задачу с зависимостями (DAG)?»* — Планировщик должен строить граф, при завершении задачи публиковать событие, триггерящее следующую. Можно использовать Temporal/Cadence для сложных workflow.

## Как обрабатывать "события с большим отставанием" (late events) в real-time пайплайнах?

### Краткий ответ
Late events — события, пришедшие с опозданием из-за сетевых задержек, сбоев продюсера. Обработка зависит от семантики: либо допустить запоздалые данные в окна (allowed lateness), обновив результаты, либо отбросить, либо направить в side output для специальной обработки. В Kafka Streams / Flink задают watermark и границу опоздания. В Go вручную реализуют окна с триггерами, используя таймеры и side channel.

### Развёрнутый ответ
При потоковой обработке окон (tumbling, sliding) события упорядочиваются по event time. Watermark — порог, показывающий, до какого времени система считает поток полным. События с временем меньше watermark — поздние. Стратегии:
1. **Отбросить**: простой подход, но теряем информацию.
2. **Разрешить латентность на некоторое смещение (allowed lateness)**: при поступлении позднего события окно перевычисляется и результат обновляется. Требует хранения состояния окна дольше.
3. **Side output**: запоздалые события направляются в отдельный топик для последующей оффлайн обработки или корректирующих действий.

В Go можно реализовать потоковый процессор с помощью горутин, слотов окон и таймеров. Например, слайдинговое окно размером 10 минут, смещение 1 минута. Входящие события пишутся в бакеты по event time. После прохождения watermark окно закрывается и эмитится результат. Если приходит late event, он добавляется в окно и результат немедленно обновляется, пока окно не удалено из памяти.

Для управления состоянием можно использовать embedded KV (bbolt, badger) или внешнее (Redis).

### Под капотом (internals)
Apache Flink использует чекпоинтинг состояний и распределённые соглашения о watermark. В самописном Go решении координация watermark между нодами сложна; обычно окна делают локально или используют агрегацию на основе Kafka Streams через библиотеку `kafka-go` и `franz-go` с ручным управлением оффсетами.

### Типичные ошибки кандидатов
- **Игнорирование временных зон и часов event time**: сравнение по system time сервера приводит к неправильным окнам. Исправление: строго использовать event time метку из сообщения.
- **Удаление состояния окна сразу после первого срабатывания**: late events теряются. Исправление: держать окно открытым ещё `allowedLateness` времени, затем удалять.
- **Обновление downstream результатов без идемпотентности**: если отправить пересчитанный результат, получатель может дважды применить изменение. Исправление: отправлять корректирующее событие (delta) или результат с окном/версией, получатель дедуплицирует.

### Возможные дополнительные вопросы интервьюера
- *«Как определить watermark в многопартиционном Kafka топике?»* — Нужен глобальный watermark: минимум из watermark каждой партиции. Это можно делать в потребителе, собирая максимальные обработанные event times от всех партиций и беря минимум. Более сложные схемы с tolerance.
- *«Что делать, если late events составляют 50% трафика?»* — Значит, проблема с задержками в источнике, нужно исправлять корень: буферизация на продюсере, переезд на синхронную отправку. Временное решение — увеличить allowed lateness и ресурсы для хранения.

## Как спроектировать "глобально распределенную базу данных" для FinTech?

### Краткий ответ
Глобально распределённая БД должна обеспечивать низкую задержку чтения/записи в разных регионах, соблюдая нормативные требования (data residency) и обеспечивая strong consistency где нужно. Обычно используют CockroachDB, Google Spanner, YugabyteDB — NewSQL системы с автоматическим шардированием, multi-region support, транзакциями с ACID. Архитектурно приложение должно понимать местоположение данных и использовать региональные инстансы для записи, минимизируя cross-region latency.

### Развёрнутый ответ
FinTech часто требует, чтобы данные клиентов хранились и обрабатывались в определённой юрисдикции. Поэтому БД должна поддерживать региональные политики размещения данных.

Ключевые свойства:
- **Geo-partitioning**: возможность привязать строки таблицы к конкретному региону на основе ключа (например, customer country). CockroachDB позволяет `ALTER TABLE ... LOCALITY REGIONAL BY ROW`.
- **Глобальные транзакции**: при необходимости перевода между разными регионами применяется двухфазная фиксация с координатором в одном из регионов, что добавляет задержку в 100-200 мс. В FinTech такие переводы обычно не требуют интерактивного выполнения, допустима асинхронность.
- **Multi-active**: запись может выполняться в любом регионе, но лидерство диапазона ключей должно быть размещено рядом с клиентом, чтобы минимизировать задержку.
- **Disaster recovery**: асинхронная репликация в другие регионы для DR, переключение с помощью admin tool.

Архитектура приложения: сервисы деплоятся в каждом регионе, подключаясь к локальному инстансу БД. Запросы, которым нужны данные из другого региона, выполняются через кросс-региональный вызов сервиса или через специальный API с маршрутизацией. Используется CQRS: записи идут в региональный primary, чтения из локальной read replica (stale reads разрешены).

### Под капотом (internals)
CockroachDB использует Raft для репликации внутри региона, но для multi-region может использовать follower reads в других регионах. Спецификация таблицы с `REGIONAL BY ROW` обеспечивает, что строки партицированы по регионам, а глобальные индексы доступны для чтения везде. Для реализации в Go используется драйвер `pgx` с поддержкой multi-region через DSN с указанием региона.

### Типичные ошибки кандидатов
- **Использование глобальных сильных транзакций для каждого запроса**: latency >100 мс убивает UX. Исправление: асинхронная репликация где возможно, строгие только для финансовых проводок внутри региона или оффлайн.
- **Игнорирование GDPR/CCPA при перемещении данных между регионами**: может быть незаконно. Исправление: настроить политику размещения данных с помощью `LOCALITY` и ограничить cross-region запись правилами.
- **Полагать, что автоматический шардинг решит все проблемы бесконтрольно**: hot spots всё равно возможны. Исправление: тщательно выбирать ключ шардирования, тестировать.

### Возможные дополнительные вопросы интервьюера
- *«Как реализовать read-your-writes в глобальной системе?»* — Если запись и чтение происходят в одном регионе, лидерство этого ключа должно быть локальным, и клиент читает с этого же узла (консистентность гарантирована). Если клиент переехал, нужен либо sticky routing на предыдущий регион, либо глобальная транзакция с linearizability, что дорого.
- *«Какие альтернативы CockroachDB для глобального FinTech?»* — Spanner (Google Cloud), YugabyteDB, FoundationDB. Для небольших компаний можно использовать PostgreSQL с декларативным партиционированием и Citus для шардирования, но без полной автоматической геопривязки.

## Какие метрики (latency percentiles) критичны для трейдинговой системы?

### Краткий ответ
Для трейдинга критичны tail latency: **p99.9**, **p99.99**, а также максимальная задержка (max). Ориентируются на p50 как на обычную, но инвестируют в оптимизацию «хвоста», чтобы минимизировать задержки для самых медленных запросов. Метрики собираются с гистограммами (HdrHistogram), визуализируются в Grafana. Целевые значения: p99.9 < 1 мс для HFT, < 5 мс для обычного трейдинга.

### Развёрнутый ответ
В трейдинговой системе самое медленное выполнение ордера определяет worst-case price slippage. Поэтому важно измерять распределение задержек от получения заявки до ответа. Помимо средних и медиан, необходимы:
- **p99**: 99% запросов быстрее этого значения. Показывает «типичный хвост».
- **p99.9**: один из 1000 запросов хуже. Критично для большого потока.
- **p99.99**: один из 10000, для систем с огромным RPS.
- **Max**: наихудший случай, часто вызван GC или сетевыми вспышками.

В Go для сбора используют `github.com/HdrHistogram/hdrhistogram-go`, который с высокой точностью фиксирует распределение, в отличие от Summary в Prometheus, где ошибка на высоких перцентилях значительна. Агрегацию гистограмм выполняют на стороне приложения, экспортируя уже готовые квантили.

Важно измерять не только время обработки движка, но и сквозное (end-to-end), включая время в очереди на входе. Поэтому ставят таймеры от момента получения байтов до отправки ответа.

### Под капотом (internals)
HdrHistogram использует логарифмическую шкалу бакетов, потребляя фиксированный объём памяти и гарантируя определённую ошибку (обычно 1-2%). В Go `hdrhistogram` эффективен, так как не требует аллокаций при записи значений. Приложение периодически сбрасывает гистограмму в Prometheus через экспортер или напрямую.

### Типичные ошибки кандидатов
- **Смотреть только на среднее (avg)**: скрывает пиковые задержки, которые убивают трейдинг. Исправление: обязательно выводить p99 и выше.
- **Использовать Prometheus Summary без понимания ошибок**: большие ошибки на p99.9. Исправление: использовать HdrHistogram и агрегировать серверной стороной или через клиентские библиотеки с поддержкой.
- **Не различать типы ордеров в метриках**: смешивают cancel и new order, у них разные профили. Исправление: добавлять лейбл `order_type` в гистограмму.

### Возможные дополнительные вопросы интервьюера
- *«Почему p99.9 может быть выше, чем p99?»* — Потому что tail latency обусловлена GC паузами, планировщиком, contention, что затрагивает малую долю запросов. Анализируют причины с помощью CPU profiling в момент высокой задержки.
- *«Как настроить алерты на основе перцентилей?»* — Скользящее окно: если p99 за 5 минут превышает SLO, алерт. Важно исключить флуктуации, использовать многократное срабатывание.

## Как реализовать "риск-менеджмент" на уровне API?

### Краткий ответ
Риск-менеджмент на API включает проверки лимитов позиций, плеча, максимальной суммы ордера, частоты транзакций и KYC статуса до принятия заявки. Реализуется middleware, проверяющим параметры запроса против правил из кэша, и быстро блокирующим нарушения. Может применяться с использованием Redis для хранения текущих риск-показателей по пользователю.

### Развёрнутый ответ
Проверки выполняются синхронно в рамках запроса, до отправки в trading engine, чтобы быстро отвергнуть рискованные действия, не нагружая ядро. Этапы:
1. Из JWT/API-ключа извлекаем идентификатор пользователя и его роли.
2. Middleware загружает из кэша (Redis) профиль риска: max order amount, max position per instrument, daily turnover limit, KYC level.
3. Проверяет: лимиты на сумму ордера, не превышает ли позиция с учётом нового ордера риск.
4. При необходимости делает быстрый запрос к сервису позиций для получения текущего объёма.
5. Если какая-то проверка не пройдена — возвращаем 403 Forbidden с описанием.

Кэш должен обновляться быстро при изменении лимитов, например, через pub/sub. Для обеспечения низкой задержки проверка должна занимать < 1 мс. Поэтому избегают запросов к БД; используют Redis pipelining.

Также сюда относится и circuit breaker на уровне API: если много ошибок, можно временно снижать лимиты.

### Под капотом (internals)
Используем `sync.Map` для локального кэша риск-профилей с периодической синхронизацией или инвалидацией через Redis pub/sub. Для ускорения чтения профили хранятся в сжатом виде, например, Protobuf.

### Типичные ошибки кандидатов
- **Делать все проверки в синхронном запросе к БД**: медленно, нарушает latency. Исправление: кэшировать профиль риска, обновлять через события.
- **Не учитывать возможность race condition при расчёте позиции на уровне API**: два одновременных ордера могут оба пройти лимит. Исправление: API может быть быстрым, но окончательное решение за matching engine, который точно знает состояние. API — предфильтр.
- **Забывать проверять IP/геолокацию для anti-fraud**: ордер с необычного места должен быть либо заблокирован, либо помечен на дополнительную проверку. Исправление: интегрировать geo-IP сервис с кэшем.

### Возможные дополнительные вопросы интервьюера
- *«Как обрабатывать изменение лимитов в реальном времени без перезапуска сервиса?»* — Использовать dynamic config (Consul, etcd) с watcher. В Go `fsnotify` или подписка на события изменения конфигурации, после чего атомарно обновить глобальную переменную с рисками.
- *«Можно ли риск-менеджмент вынести на API шлюз (Kong, Envoy)?»* — Частично можно: rate limit, проверка API-ключа, грубая валидация тела. Но бизнес-логика с позициями требует доступа к состоянию, лучше делать в самом сервисе на уровне middleware.

## Как работает "двухфазная фиксация" (2PC) и "трехфазная фиксация" (3PC)?

### Краткий ответ
2PC — протокол атомарного коммита распределённой транзакции: координатор запрашивает prepare у участников, при всех голосах «да» отправляет commit. Участники блокируют ресурсы до подтверждения. 3PC добавляет фазу pre-commit, чтобы избежать блокировок при отказе координатора, но ценой дополнительных сообщений и не решает проблему сетевых разделений полностью. На практике в Go 2PC реализуется через менеджера распределённых транзакций.

### Развёрнутый ответ
**2PC фазы**:
1. **Prepare** (Voting): Координатор отправляет `prepare` каждому участнику. Участник выполняет операцию, записывает её в local redo-лог, но не коммитит, и отвечает `Yes` (готов) или `No` (отказ). Во время этого участник держит локальные блокировки.
2. **Commit/Abort** (Decision): Если все `Yes`, координатор отправляет глобальный `commit`. Если хотя бы один `No` или таймаут, координатор рассылает `abort`. Участники фиксируют или откатывают.

Проблемы: блокировки на время ожидания решения, неопределённое состояние при отказе координатора после фазы prepare (участники не знают, коммитить или нет). Решение: журналирование координатора и использование heuristic commit по таймауту.

**3PC** (Three-Phase Commit) добавляет фазу `pre-commit`:
1. CanCommit (опционально).
2. PreCommit: координатор сообщает всем, что готово к коммиту, но пока не коммитить. Участники знают, что коммит близок.
3. DoCommit: завершающий коммит.
Идея: если координатор упал, таймаут позволяет участникам выбрать нового координатора и восстановить состояние. Однако при сетевом разделении всё равно возможны конфликты. 3PC не получил широкого распространения из-за сложности и неспособности полностью гарантировать атомарность в асинхронной сети.

### Под капотом (internals)
Реализация 2PC в Go может быть построена на основе gRPC с сохранением лога транзакции в etcd. Координатор использует state machine: сообщения и таймауты. Участники регистрируют prepare в локальной БД и ждут.

### Типичные ошибки кандидатов
- **Не хранить лог координатора**: при рестарте теряется состояние, и другие участники остаются с блокировками навсегда. Исправление: координатор пишет решение в персистентный лог до отправки commit.
- **Использовать 2PC для долгих операций, удерживая блокировки**: исчерпание ресурсов. Исправление: выбирать Saga, если длительность велика.
- **Полагать, что 3PC решает все проблемы**: не решает проблему разбиения сети, только некоторые случаи отказа координатора. Исправление: понимать ограничения, предпочесть Paxos/Raft для современных систем.

### Возможные дополнительные вопросы интервьюера
- *«Как реализовать 2PC без блокировок?»* — Вариант с оптимистическим подходом: участники в фазе prepare не блокируются, а записывают намерение, и при конфликте во время коммита проверяются условия. Но это сложнее.
- *«Где реально применяется 2PC в современных системах?»* — В PostgreSQL distributed foreign data wrappers, в некоторых шардированных БД (Citus), в менеджерах сообщений (Kafka транзакции – внутренне похожи на 2PC с координатором транзакций и стабильным хранилищем).

## Как обеспечивается "линейная консистентность" (linearizability) в распределенных системах?

### Краткий ответ
Линейная консистентность гарантирует, что операции выглядят так, будто выполняются мгновенно в некоторый момент между их началом и завершением, и этот порядок соблюдается глобально. Обеспечивается через алгоритмы консенсуса (Paxos, Raft), которые линеаризуют запись, и чтение с линейной гарантией (через чтение лидера или lease/read index). В Go, используя etcd или CockroachDB, получаем линейные операции.

### Развёрнутый ответ
Линейная консистентность строже, чем sequential: она учитывает реальное время. Если операция A завершилась до начала B, то в линейном порядке A должна быть перед B. Это то, что ожидают от банковских транзакций.

Для достижения:
- Raft: все операции проходят через лидера, который записывает их в лог и после репликации на большинство узлов подтверждает клиенту. Это даёт линейную запись.
- Чтение: простое чтение из лидера не всегда линейное, так как лидер может быть изолирован. Используют `ReadIndex` (лидер удостоверяется, что он всё ещё лидер, запросив подтверждение у большинства) или `Lease` (лидер получает временную аренду, пока он считается лидером, и обслуживает чтение). Также вариант — чтение с кворума (R + W > N), но с witness нодами.
- В etcd: `clientv3` поддерживает `WithSerializable=false` для линейного чтения.

### Под капотом (internals)
Алгоритм Raft в etcd: когда клиент делает запрос сериализации, лидер отправляет `MsgReadIndex` и ждёт подтверждения от большинства followers, что они не признали другого лидера. Это добавляет network round trip.

### Типичные ошибки кандидатов
- **Путать линейную консистентность с сериализуемостью (serializability)**: последняя — про изоляцию транзакций без учёта реального времени, линейная — про порядок операций. Исправление: чётко различать эти понятия.
- **Считать, что кворумное чтение автоматически линейное**: в Cassandra с `QUORUM` чтение даёт сильную консистентность только при R+W>N и только для последней записи, но без учета глобального порядка операций, конфликтующих на разных репликах. Линейность требует дополнительных механизмов (lightweight transactions с Paxos).
- **Использовать линейное чтение для всех запросов без необходимости**: замедляет систему. Исправление: применять только к операциям, требующим свежайших данных.

### Возможные дополнительные вопросы интервьюера
- *«Как измерить линейную консистентность?»* — С помощью Jepsen тестов: записываем историю операций, проверяем, можно ли построить линейный порядок, удовлетворяющий ограничениям времени.
- *«Реализуйте линейное чтение в распределённом хранилище на Go без Raft?»* — Можно использовать ZooKeeper: запись и чтение с синхронизацией (sync перед чтением) обеспечивают линейность, так как ZAB протокол.

## Как работает "WAL" в распределенных базах данных?

### Краткий ответ
Write-Ahead Log (WAL) — журнал упреждающей записи: все изменения сначала атомарно записываются в append-only лог на диск, а затем применяются к основным структурам данных. В распределённых БД WAL используется для восстановления после сбоя и репликации: записи WAL пересылаются на реплики. В Go при реализации БД (например, etcd) WAL — ключевой компонент надёжности.

### Развёрнутый ответ
В традиционных БД (PostgreSQL) WAL позволяет при сбое проиграть лог и вернуть базу в согласованное состояние (REDO). В распределённых системах также служит для репликации: лидер пишет в WAL, followers получают поток WAL записей и применяют их.

Структура WAL в простейшем виде: последовательность записей фиксированного размера с контрольными суммами. В etcd WAL хранится в отдельных файлах по сегментам (wal-00001, wal-00002). При достижении определённого размера создаётся снапшот состояния, а старые сегменты WAL могут удаляться.

Go библиотека для WAL: можно писать свой с помощью `os.File.Write` с `f.Sync()` для fsync. В etcd используется `wal` пакет внутри.

Для обеспечения долговечности важно вызывать fsync, но это дорого; используют групповой коммит (group commit) — накопление нескольких записей и один fsync.

### Под капотом (internals)
В etcd wal реализован с CRC32 для целостности, с использованием `bufio.Writer` и блочного выравнивания. При рестарте проигрывается весь лог с последним снапшотом.

### Типичные ошибки кандидатов
- **Запись WAL без fsync или с задержкой**: при крахе теряются последние записи, нарушая durability. Исправление: fsync после каждой логической транзакции или группы.
- **Монотонный рост WAL без ротации**: в конце концов заканчивается место на диске. Исправление: периодически делать снапшот и усекать старые записи.
- **Неправильное восстановление при повреждении записи**: нет проверки CRC. Исправление: добавить контрольную сумму к каждой записи, при повреждении использовать последний валидный снапшот + оставшийся валидный хвост.

### Возможные дополнительные вопросы интервьюера
- *«Почему в распределённых системах WAL часто хранят на локальном SSD?»* — Потому что низкая задержка fsync критична для производительности. Для восстановления после отказа узла используются репликация WAL на другие узлы, а не сетевое хранилище.
- *«Как обрабатывается запись WAL в мульти-лидерной конфигурации?»* — Обычно используется Paxos/Raft для консенсуса на записи в WAL: предлагается запись, кворум подтверждает, запись включается в лог. Это делает её общей.

## Как спроектировать "event-driven архитектуру" для highload?

### Краткий ответ
Event-driven архитектура основана на событиях как основных единицах обмена: сервисы публикуют события при изменении состояния, и другие сервисы асинхронно реагируют. Для highload используется брокер событий с высокой пропускной способностью (Kafka), гарантии доставки at-least-once, идемпотентные потребители, и паттерны Event sourcing, CQRS. В Go это реализуется с помощью Kafka клиентов, NATS, или Redis Streams.

### Развёрнутый ответ
Компоненты:
- **Event Bus**: Kafka топики с партиционированием по aggregate ID для сохранения порядка.
- **Продюсеры**: публикуют события после изменения состояния. Используется outbox pattern для атомарности.
- **Потребители**: группа консьюмеров, каждая обрабатывает свой топик, выполняя действия: обновление проекций, отправка уведомлений, запуск саг.
- **Хранилище событий (Event Store)**: журнал всех событий для возможности повтора и аудита (может быть Kafka + долговременное хранилище).

Проект highload сервиса обработки заказов:
1. Order Service принимает `CreateOrder`, сохраняет в БД, отправляет событие `OrderCreated` в outbox → Kafka.
2. Payment Service подписан на `OrderCreated`, выполняет списание, публикует `PaymentConfirmed`.
3. Order Service обрабатывает `PaymentConfirmed`, меняет статус на `Paid`.

Такой подход развязывает сервисы и позволяет горизонтальное масштабирование потребителей.

В Go для Kafka можно использовать `segmentio/kafka-go` с батчевой записью и чтением, с ручным управлением коммитами смещений для гарантий.

### Под капотом (internals)
Kafka партиция гарантирует порядок сообщений с одним ключом. Если нужно обрабатывать события в порядке для агрегата, используют ключ партиции = aggregate ID. В Go consumer должен быть написан с учётом того, что обработка одного сообщения должна быть идемпотентной.

### Типичные ошибки кандидатов
- **Отсутствие обработки дубликатов событий**: полагаются на «exactly once» Kafka, но не реализуют dedup. Исправление: уникальный event_id и проверка в БД.
- **Публикация события до коммита транзакции**: событие видно, а данных ещё нет. Исправление: outbox.
- **Создание топика на каждое событие без группировки**: плодятся сотни топиков, управление сложное. Исправление: группировать события по бизнес-домену (Topic per aggregate type).

### Возможные дополнительные вопросы интервьюера
- *«Как версионировать события в event-driven архитектуре?»* — Добавлять в заголовок версию схемы. Потребители должны уметь обрабатывать несколько версий или использовать schema registry (Avro). В Go можно использовать `protobuf` с эволюцией.
- *«Как отладить цепочку событий в production?»* — Использовать распределённую трассировку с trace_id в заголовках, централизованное логирование.

## Как обрабатывать "отказы" (failures) в долгоиграющих процессах?

### Краткий ответ
Долгоиграющие процессы (workflows) разбиваются на шаги с сохранением состояния в долговременном хранилище. При отказе процесс возобновляется с последнего успешного шага. Используются саги с компенсацией, таймауты, повторные попытки с backoff, и мониторинг. В Go применяют Temporal/Cadence для надёжных workflow, либо реализуют state machine с персистентностью.

### Развёрнутый ответ
Пример: onboarding клиента длится несколько дней (проверка KYC, активация счета). Нельзя держать HTTP соединение. Вместо этого при старте создаётся процесс с уникальным ID и состоянием в БД (MongoDB, PostgreSQL). Каждый шаг выполняется отдельным воркером или сервисом, который получает задачу из очереди.

Процесс:
1. Сервис получает событие `UserRegistered`.
2. Запускает workflow, записывая начальное состояние.
3. Планировщик задач или orchestrator (на базе Temporal) выполняет шаг `verifyDocuments`. При ошибке — retry policy. Если документы не загружены за 24ч, таймаут завершает процесс с ошибкой.
4. Успех — переходит к следующему шагу `createAccount`.
5. На каждом шаге фиксируется результат и переход в следующее состояние.

Temporal Go SDK позволяет писать workflow как обычный код:
```go
func OnboardingWorkflow(ctx workflow.Context, userID string) error {
    var result string
    err := workflow.ExecuteActivity(ctx, VerifyDocumentsActivity, userID).Get(ctx, &result)
    if err != nil { return err }
    err = workflow.ExecuteActivity(ctx, CreateAccountActivity, userID).Get(ctx, &result)
    return err
}
```
Temporal гарантирует перезапуск activity при отказе, повторную доставку, таймауты.

### Под капотом (internals)
Temporal использует event sourcing: все команды workflow записываются в лог, и при перезапуске worker-а состояние восстанавливается проигрыванием истории. В Go серверная часть общается с persistence (Cassandra/PostgreSQL) и очередью задач.

### Типичные ошибки кандидатов
- **Хранение состояния процесса только в памяти**: при рестарте теряется. Исправление: персистентное хранилище.
- **Отсутствие таймаута на шаг workflow**: процесс может зависнуть навсегда. Исправление: задавать `ActivityOptions.StartToCloseTimeout`.
- **Некорректная обработка идемпотентности в activity**: повторное выполнение после таймаута должна не дублировать эффект. Исправление: использовать идемпотентный ключ (например, `activityID` + `attempt`), Temporal сам обеспечивает хотя бы одно выполнение, но бизнес-логика должна быть идемпотентной.

### Возможные дополнительные вопросы интервьюера
- *«Чем Temporal лучше самописного workflow engine на базе очередей?»* — Temporal предоставляет встроенные retry, таймауты, visibility, управление версиями кода workflow при развёртывании, что сложно реализовать самостоятельно без ошибок.
- *«Как отменять workflow, если поступило событие отмены?»* — Использовать `workflow.Go` и `workflow.Selector` для ожидания сигнала отмены, внутри вызывать компенсирующие activity. Temporal поддерживает отмену.

## Как реализовать "leader-follower" репликацию с автоматическим переключением?

### Краткий ответ
Leader-follower: все записи идут на лидера, он реплицирует WAL на follower’ов. Автоматическое переключение (failover) достигается через мониторинг живости лидера и выборы нового лидера с использованием алгоритма консенсуса (Raft) или внешнего координатора (etcd). В Go можно реализовать на основе HashiCorp Raft или ZooKeeper.

### Развёрнутый ответ
Сценарий: кластер PostgreSQL с Patroni (использует etcd для выборов лидера). Но мы можем создать кастомный Go-сервис с встроенной репликацией, например, с помощью `hashicorp/raft`. Raft автоматически управляет лидерством и репликацией лога.

Упрощённая схема:
- Каждый узел запускает Raft instance.
- Raft через голосование выбирает лидера.
- Клиенты обращаются к лидеру (адрес лидера можно получить через etcd или специальный API).
- При отказе лидера запускаются новые выборы, лидером становится один из follower’ов.
- Приложение должно перенаправлять клиентов или использовать proxy (например, Consul Connect).

Go-реализация: библиотека `hashicorp/raft` предоставляет `raft.Raft`, который требует `LogStore`, `StableStore`, `SnapshotStore`. FSM (Finite State Machine) обрабатывает команды. Примеры есть в `raft-boltdb`. 

### Под капотом (internals)
Raft в `hashicorp/raft` реализован через горутины, таймеры, каналы. Лидер отправляет AppendEntries RPC последователям, используя gRPC или TCP.

### Типичные ошибки кандидатов
- **Забыть про split-brain**: при сетевом разрыве могут появиться два лидера, если нет кворума. Исправление: Raft гарантирует, что лидером становится только тот, кто получил большинство голосов. Важно не обрабатывать запросы в режиме minority.
- **Неправильная настройка таймаутов**: слишком частые выборы вызывают нестабильность. Исправление: настраивать heartbeat interval и election timeout в зависимости от сети.
- **Использовать лидера для всех чтений без масштабирования**: лидер становится узким местом. Исправление: разрешить follower reads со stale гарантией или через ReadIndex.

### Возможные дополнительные вопросы интервьюера
- *«Как клиент узнает, кто лидер после переключения?»* — Сервис-дискавери (Consul, etcd) обновляет адрес лидера. Клиенты могут использовать retry с обновлением адреса. Или использовать proxy, который знает лидера и маршрутизирует.
- *«Можно ли использовать обычный PostgreSQL с потоковой репликацией и Patroni?»* — Да, это готовая реализация, написанная на Python, но управляющая PostgreSQL и etcd, обеспечивая автоматическое переключение. В Go-микросервис интегрируется через подключение к floating VIP или через PgBouncer.

## Что такое "Raft consensus algorithm" и как он применяется в распределенных системах на Go?

### Краткий ответ
Raft — алгоритм консенсуса для управления реплицированным логом. Состоит из выборов лидера, репликации лога и безопасности. В Go широко применяется через библиотеку `hashicorp/raft` для реализации распределённых хранилищ ключ-значение, сервисов обнаружения или встраиваемых БД. Обеспечивает strong consistency и fault tolerance.

### Развёрнутый ответ
Raft разделяет ответственность:
- **Leader election**: выделяется таймаут выборов, при истечении кандидат запрашивает голоса, побеждает получивший большинство.
- **Log replication**: лидер принимает команды клиента, добавляет в лог и реплицирует на последователей через AppendEntries. Когда большинство подтвердило, запись считается закоммиченной.
- **Safety**: гарантируется, что новый лидер содержит все закоммиченные записи предыдущих термов.

Применение в Go:
- Создание распределённого KV-хранилища: `hashicorp/raft` + boltdb для лога и FSM для применения команд к `map`.
- Использование в etcd (написан на Go) — именно Raft лежит в основе etcd.
- В CockroachDB — тоже Raft.
- В собственных сервисах для координации блокировок или выбора лидера.

Пример интеграции Raft в Go-сервис: определяем FSM, которая обрабатывает `Apply`:
```go
type MyFSM struct { data map[string]string }
func (f *MyFSM) Apply(log *raft.Log) interface{} {
    var cmd Command
    json.Unmarshal(log.Data, &cmd)
    // изменить состояние
    return nil
}
```
Запускаем Raft с транспортом TCP, присоединяемся к кластеру.

### Под капотом (internals)
Библиотека `hashicorp/raft` запускает горутины для обработки RPC, таймеров, снапшотов. Внутреннее состояние — структура `raftState` с текущим термом, голосом и т.д. Использует каналы и блокировки.

### Типичные ошибки кандидатов
- **Неправильная реализация снапшотов**: лог бесконечно растёт. Исправление: периодически делать снапшот FSM и вызывать `raft.Snapshot()`, удалять старые записи лога.
- **Игнорирование производительности снапшотов**: блокирует обработку новых команд. Исправление: делать инкрементальные или асинхронные снапшоты, используя `Snapshot()` с записью в фоне.
- **Не обрабатывать случай, когда узел отстаёт и ему нужен снапшот**: лидер передаёт снапшот через `InstallSnapshot`. Нужно корректно реализовать интерфейс.

### Возможные дополнительные вопросы интервьюера
- *«Можно ли использовать Raft для репликации миллионного состояния?»* — Да, но с осторожностью. Лог большого размера приводит к задержкам. Используют сегментирование и параллельную репликацию. В CockroachDB миллиарды ключей реплицируются через Raft, так как данные разбиты на ranges, каждый со своим Raft-группой.
- *«Как Raft справляется с нестабильной сетью?»* — Election timeout должен быть значительно больше, чем RTT в сети, чтобы избежать частых выборов. Heartbeat интервал маленький. Если связь потеряна, узел не может стать лидером без кворума, и кластер становится недоступным для записи, но сохраняет консистентность.

## Как спроектировать систему "real-time аналитики"?

### Краткий ответ
Система real-time аналитики должна обрабатывать поток событий и предоставлять агрегированные результаты с задержкой в секунды. Строится на основе потоковой обработки (Kafka Streams, Apache Flink) с материализованными представлениями в быстром OLAP-хранилище (ClickHouse, Apache Druid) или через serving layer (Redis). В Go используется потребитель Kafka, агрегация в памяти или RocksDB, и выдача через API с кэшем.

### Развёрнутый ответ
Компоненты:
- **Ingestion**: сбор событий через Kafka.
- **Stream Processor**: Go-приложение, использующее `kafka.Reader` с group и индивидуальной обработкой. Агрегирует метрики в окнах (слайдинг/тамблинг) и записывает результаты в time-series БД или in-memory cache.
- **Storage**: ClickHouse для долговременного хранения и быстрых аналитических запросов с демографическими колонками; Redis для serving текущих показателей (например, количество заказов за последний час).
- **Query API**: Go-сервис, принимающий запросы от дашбордов, читает из ClickHouse/Redis и отдаёт агрегаты.

Альтернатива: использовать Kafka + ksqlDB (написан на Java), но для Go-экосистемы можно написать custom stream processor, который управляет состоянием в RocksDB (используя `grocksdb` или `pebble`).

### Под капотом (internals)
Для stateful обработки в Go используют библиотеку `watermill` с Kafka pub/sub, но для сложной аналитики проще применить Apache Flink SQL. Однако если нужно всё на Go, то реализуют операторы окон вручную, сохраняя состояние в встраиваемой БД и выдавая результаты по таймеру.

### Типичные ошибки кандидатов
- **Прямая запись сырых событий в ClickHouse на каждый запрос**: высокая нагрузка на вставку. Исправление: пакетная запись с накоплением (buffer).
- **Вычисление всех агрегатов в реальном времени без предварительной агрегации**: запросы к API выполняются медленно при большом объёме. Исправление: предварительно вычислять и материализовать популярные окна (pre-aggregation).
- **Игнорирование late events**: искажает результаты. Исправление: использовать watermark и разрешённое опоздание, как обсуждено ранее.

### Возможные дополнительные вопросы интервьюера
- *«Как обеспечить консистентность между real-time аналитикой и batch-отчётами?»* — Батч-система (Hadoop, Spark) может читать тот же лог событий, что и стрим, и пересчитывать точно. Стрим даёт приближённый быстрый результат (lambda architecture). При расхождении предпочтение отдаётся batch-версии, если не требуется мгновенность.
- *«Как масштабировать запросы к ClickHouse под высоким RPS?»* — Использовать реплицированные таблицы, распределённые запросы, кэширование часто запрашиваемых данных в Redis с TTL 1-5 секунд.

## Как работать с "feed handlers" для биржевых данных (FIX protocol)?

### Краткий ответ
Feed handler — сервис для приёма и обработки биржевых данных по протоколу FIX (Financial Information eXchange). Включает управление сессиями (логин, heartbeat, восстановление), парсинг FIX-сообщений в реальном времени, нормализацию и публикацию во внутреннюю шину. В Go реализуется с помощью библиотеки `quickfixgo` или с нуля для максимальной производительности.

### Развёрнутый ответ
FIX — TCP-based протокол с сообщениями в виде тегов и значений, разделённых `\001`. Сессии требуют Logon сообщений с exchange, поддержки sequence numbers и gap fill при разрывах.

Компоненты handler:
- **Session Layer**: управляет несколькими соединениями к разным биржам. Поддерживает логин, heartbeat, resend request для восстановления пропущенных сообщений.
- **Parser**: преобразует байтовый поток FIX в структуры (быстрый парсер без аллокаций). В Go используют `quickfix` или кастомный FSM-парсер, который накапливает поля.
- **Normalizer**: приводит разные версии FIX к единому внутреннему формату (например, OrderBookSnapshot).
- **Publisher**: отправляет нормализованные сообщения в Kafka/Redis для downstream сервисов.

Пример настройки `quickfix` в Go:
```go
func (s *MyApp) OnLogon(sessionID quickfix.SessionID) {
    log.Println("Logon")
}
func (s *MyApp) OnMessage(msg *quickfix.Message, sessionID quickfix.SessionID) quickfix.MessageRejectError {
    // process market data
    return nil
}
```

Для низкой задержки часто пишут кастомный обработчик без `quickfix`, чтобы контролировать аллокации и парсинг.

### Под капотом (internals)
`quickfix-go` использует горутину чтения и записи, буферы, таймеры для heartbeat. При больших объёмах (сотни тысяч сообщений в секунду) может стать узким местом. Альтернатива — `go-fix` или in-house парсер с использованием finite state machine и `sync.Pool` для сообщений.

### Типичные ошибки кандидатов
- **Не обрабатывать Sequence Reset и Gap Fill**: при разрыве соединения пропущенные сообщения не запрашиваются, поток данных становится с пропусками, нарушается целостность. Исправление: реализовать полную логику восстановления (resend request).
- **Парсить FIX с помощью `strings.Split`**: аллокации на каждое поле убивают производительность. Исправление: парсить байтовый поток in-place, используя срезы на исходный буфер.
- **Игнорирование heartbeat слишком долго**: биржа отключает. Исправление: отправлять Heartbeat сообщения вовремя, слушать TestRequest.

### Возможные дополнительные вопросы интервьюера
- *«Как обеспечить надёжный failover при сбое handler?»* — Журналирование входящих сообщений (raw FIX) в persistent лог перед обработкой, как WAL. При переключении на резервный handler он догоняет из лога. Либо использовать первичный/вторичный сессионный подход с синхронизацией sequence numbers.
- *«Как справиться с быстрым изменением биржевых данных без потерь?»* — Увеличить размер буфера чтения TCP, использовать epoll, разнести чтение и обработку в разные горутины с каналом/ринг буфером фиксированной ёмкости, с backpressure.
