## Что такое latency?

### Краткий ответ (30–60 секунд)
Latency (задержка) — это время от начала запроса до получения первого байта ответа (или до полного завершения операции). В контексте распределённых систем это сумма сетевых задержек, времени обработки и ожидания в очередях. Ключевая метрика для интерактивных сервисов, где важна отзывчивость.

### Развёрнутый ответ
Latency измеряется в миллисекундах/микросекундах и описывает «как долго ждать». Различают:
- **Network latency** — время передачи пакета (RTT).
- **Processing latency** — время работы процессора над запросом.
- **Queueing latency** — ожидание в очередях горутин, сетевых буферах, на мьютексе.
В Go latency критична для gRPC/REST сервисов. Например, вызов удалённого метода может иметь latency 5ms, но если внутри вызывается map с блокировкой и GC паузой 10ms, общая latency взлетает до 15ms. Инструментирование через `prometheus` и `net/http/pprof` даёт разбивку по стадиям.

Важно различать latency и throughput. Можно иметь низкую пропускную способность при низкой задержке (один поток быстро обрабатывает запросы по одному), и наоборот. Amdahl’s law: оптимизация latency узкого места даёт наибольший прирост.

В Go на latency влияют:
- Блокировки (`sync.Mutex`, каналы).
- Остановки мира (STW) в GC.
- Выделение памяти (аллокации), вызывающие частые сборки.
- Сетевые системные вызовы в неблокирующем режиме (netpoller).

### Под капотом (internals)
Планировщик Go ставит горутину в очередь P. Если горутина делает системный вызов (например, `read()`), она передаётся netpoller (epoll/kqueue) — это добавляет latency, но освобождает P. Пробуждение горутины после сетевого события даёт задержку планирования ~несколько микросекунд. Внутри runtime используется `futex` для парковки/пробуждения потоков — это тоже задержка. Профилировщик latency через `runtime/pprof` с метками `profile` по времени блокировок (`block`, `mutex`) показывает где горутины ждут.

Измерение latency в наносекундах: `time.Now()` идёт через VDSO (Virtual Dynamic Shared Object) без syscall на Linux, уменьшая оверхед. `runtime.nanotime` реализован на ассемблере с `RDTSC` или через VDSO.

### Типичные ошибки кандидатов
1. **Путают latency и throughput**  
   Утверждают, что оптимизация пропускной способности автоматически снижает задержку. На деле добавление буферизации (batching) для throughput увеличивает latency отдельного элемента, так как надо ждать накопления батча.  
   *Исправление:* Всегда чётко разграничивать метрики и оптимизировать ту, что важнее для бизнес-требований.

2. **Игнорирование хвостовой латентности (p99)**  
   Среднее (avg) маскирует выбросы из-за GC пауз или блокировок. Пользователь чувствует именно p95/p99.  
   *Исправление:* измерять перцентили (`quantile`) и внедрять тайм-ауты, circuit breaker.

3. **Создание излишних горутин**  
   Наивный код `go func()` на каждый запрос без контроля пула. Переключения контекста горутин добавляют latency при раздутом количестве.  
   *Исправление:* применять воркер-пулы с фиксированным числом горутин или семафоры.

### Возможные дополнительные вопросы интервьюера
- *Чем latency отличается от response time?*  
  Response time включает полное время выполнения, latency — только задержка до начала обработки. Часто оба термина взаимозаменяемы, но строго: latency + processing time = response time.
- *Как влияет GC на хвостовую латентность?*  
  Mark termination фазы GC (STW) прямо добавляют задержку всем горутинам; оптимизация через уменьшение числа объектов, `sync.Pool`, `GOGC`.
- *Как измерить latency в Go сервисе с микрометрами?*  
  Использовать `go.opentelemetry.io/otel` или `prometheus.NewHistogram` для записи длительности операций, настроить бакеты.

## Что такое throughput?

### Краткий ответ (30–60 секунд)
Throughput (пропускная способность) — количество операций, выполненных системой в единицу времени (например, запросов в секунду, RPS). Он показывает производительность системы под нагрузкой и особенно важен для систем пакетной обработки, потоков данных.

### Развёрнутый ответ
Throughput можно измерять на разных уровнях:
- **Application throughput**: запросы/с.
- **Network throughput**: мегабиты/с.
- **CPU throughput**: инструкций/с, полезная работа/такт.
В Go throughput увеличивают параллелизмом, конкурентностью (concurrency) и асинхронным IO. Например, HTTP сервер обрабатывает тысячи соединений благодаря неблокирующему netpoller и горутинам — это повышает throughput без блокировки потоков ОС на каждый запрос.

Закон Литтла: \( \text{concurrency} = \text{throughput} \times \text{latency} \). Значит, при фиксированной пропускной способности рост задержки требует больше горутин.

Метрики throughput критичны для балансировщиков нагрузки, очередей сообщений. В Go профилировщик `pprof` с `-top` по CPU показывает функции, на которые тратится больше всего времени — их оптимизация непосредственно поднимает throughput. Также важен `GOMAXPROCS` — количество параллельно работающих ядер определяет максимальный CPU throughput.

### Под капотом (internals)
Планировщик Go распределяет горутины по P (логическим процессорам). Если все P заняты полезной работой (CPU-bound), достигается пиковый throughput. Но если появляется много блокировок (сетевые вызовы), планировщик открепляет горутину от P и захватывает другой поток через `needm`/`dropm` — механизмы для поддержания throughput, когда реальных потоков недостаточно.

Профиль через `runtime.metrics`: `/sched/latencies:seconds` показывает время, проведённое горутинами в очереди исполнимых (`runqueue`). Длинные очереди снижают throughput каждой горутины. Использование work-stealing между P’s помогает выравнивать throughput.

Измерение: бенчмарк `testing.B` запускает функцию в цикле, измеряя ns/op — это обратно throughput. Также `go test -benchmem` показывает выделения памяти, что косвенно — больше аллокаций → чаще GC → падение throughput.

### Типичные ошибки кандидатов
1. **Отождествление увеличения горутин с ростом throughput**  
   Слишком много горутин создаёт конкуренцию за планировщик и кэш CPU, реальный throughput может упасть.  
   *Исправление:* подбирать количество воркеров эмпирически, использовать пулы горутин.

2. **Игнорирование пропускной способности памяти**  
   CPU может работать вхолостую из-за cache misses, throughput падает. Кандидаты редко упоминают memory bandwidth.  
   *Исправление:* профилировать cache misses через `perf` и применять структуры данных, дружественные к кэшу.

3. **Неправильная оценка throughput при бенчмарках**  
   Запуск `testing.B` с 1 итерацией (N=1) даёт неверные цифры из-за оптимизаций компилятора.  
   *Исправление:* позволить бенчмарк-фреймворку самому определить N, проверять `go test -bench . -count 10`.

### Возможные дополнительные вопросы интервьюера
- *Как связаны throughput и закон Амдала?*  
  Максимальный прирост throughput ограничен долей последовательного кода. Если она 10%, даже бесконечное количество ядер даст ускорение не более 10x.
- *Почему при росте числа потоков throughput иногда падает?*  
  Эффекты contention на блокировках, когерентность кэша, false sharing, насыщение шины памяти.
- *Как измерить throughput базы данных из Go приложения?*  
  Использовать `database/sql` с пулом соединений, запустить воркеры, измерять успешные транзакции в секунду, отслеживать время ожидания соединения.

## Как измерять производительность?

### Краткий ответ (30–60 секунд)
Производительность измеряется через бенчмаркинг (`testing.B`) и профилирование (`pprof`, трассировка). Сначала формулируется цель (latency, throughput, потребление памяти), затем собираются метрики до и после изменений. Ключевой принцип — измерять на реалистичной нагрузке, изолируя влияние внешних факторов.

### Развёрнутый ответ
Методология:
1. **Микробенчмаркинг**: `func BenchmarkXxx(b *testing.B)` — для небольших функций, алгоритмов.
2. **Макробенчмаркинг**: профилирование целого сервиса под нагрузкой (например, `wrk`, `hey`), анализ pprof.
3. Сбор метрик в проде: экспорт в Prometheus/OpenTelemetry.

Инструменты:
- `go test -bench . -benchmem -cpuprofile=cpu.out -memprofile=mem.out`
- `go tool pprof -http=:8080 cpu.out`
- `runtime/pprof` — профили кучи, горутин, мьютексов, блокировок.
- `runtime/trace` — запись событий планировщика, GC.

Важно: измерять на стабильной машине, не на ноутбуке с троттлингом. Использовать `-count=10` для усреднения и расчёта статистической значимости через `benchstat`.

### Под капотом (internals)
Системы профилирования в Go:
- **CPU profiler**: по сигналу `SIGPROF` (на Linux) с частотой 100Hz останавливает горутину, записывает стек. При обработке сигнала используется механизм `sigprof`, который собирает traceback через `gentraceback`. Это минимально инвазивно, но добавляет ~2-5% оверхеда.
- **Memory profiler**: вставляет инструментацию в аллокатор `runtime.mallocgc` для записи стектрейса выделений. При включении `MemProfileRate=1` может сильно замедлить.
- **Block/Mutex profiler**: использует плюсовые счётчики в `semacquire`, `sync.Mutex.lockSlow`.

Бенчмарки `testing.B`: рантайм динамически увеличивает N, пока функция не стабилизируется по времени (обычно 1 секунда). Используется `runtime/benchmark.go` с поддержкой монадного поведения. `b.ResetTimer()` сбрасывает накопленное время на setup.

### Типичные ошибки кандидатов
1. **Запуск бенчмарков на девелоперской машине с нагрузкой**  
   Другие процессы искажают результаты, добавляя шум.  
   *Исправление:* выделенная CI-машина, отключение Turbo Boost, изоляция ЦПУ (taskset).

2. **Неправильная интерпретация `ns/op` при разных размерах входных данных**  
   Бенчмарк может быть линеен, но если измерять только на одном размере, можно пропустить квадратичный рост.  
   *Исправление:* бенчмарк с разными размерами через параметр `b.Run(size)`.

3. **Игнорирование прогрева JIT/кэшей (в Go нет JIT, но есть прогрев страниц)**  
   Первые итерации могут включать page faults. Используйте `b.ResetTimer()` после прогревочных итераций.

4. **Компилятор оптимизирует измеряемый код (inlining, dead code elimination)**  
   Результаты занижены вплоть до 0ns.  
   *Исправление:* присваивать результат глобальной переменной, использовать `//go:noinline`.

### Возможные дополнительные вопросы интервьюера
- *Чем отличается профилирование от трейсинга в Go?*  
  Профилирование показывает агрегированную картину по функциям, трейсинг — временную диаграмму событий планировщика, горутин, GC.
- *Как оценить, что бенчмарк статистически значим?*  
  `benchstat` вычисляет p-value, сравнивает выборки, сигнализирует о незначительном изменении.
- *Зачем добавлять `//go:noinline` в бенчмарках?*  
  Чтобы предотвратить встраивание функции в тело цикла, которое искажает действительные затраты вызова.

## Как уменьшить аллокации?

### Краткий ответ (30–60 секунд)
Аллокации в Go — выделения памяти в куче, за которыми следит GC. Уменьшение достигается размещением объектов на стеке (escape analysis), переиспользованием памяти через пулы, использованием значений вместо указателей, аллокацией слайсами с запасом ёмкости, применением `strings.Builder` и `copy` вместо конкатенации строк.

### Развёрнутый ответ
Каждая аллокация из кучи запускает вставку в кучу, нагружая GC и кэш. Методы снижения:
- **Escape analysis**: не возвращать указатели на локальные переменные вверх по стеку, передавать значения маленьких структур по значению.
- **Стековая аллокация**: если размер известен и переменная не «убегает», компилятор разместит её на стеке — ноль накладных расходов.
- **Переиспользование буферов**: `sync.Pool`, слайсы с заготовленной ёмкостью.
- **Конкатенация**: `strings.Builder` вместо `+` в цикле — Builder внутри использует `[]byte` с ростом без постоянных аллокаций маленьких строк.
- **Сериализация**: использовать `enc.Encode` на предварительно выделенный `bytes.Buffer`, применять библиотеки-кодеки с нулевыми аллокациями (easyjson, jsoniter).
- **Уменьшение boxing**: избегать интерфейсов для примитивов, не использовать `interface{}` без надобности.

Пример: до аллокаций
```go
func concat(ss []string) string {
    var r string
    for _, s := range ss {
        r += s   // каждая итерация создает новый string
    }
    return r
}
```
После:
```go
func concat(ss []string) string {
    var b strings.Builder
    b.Grow(estimated)  // одна аллокация
    for _, s := range ss {
        b.WriteString(s)
    }
    return b.String()
}
```

### Под капотом (internals)
Escape analysis реализован в пакете `cmd/compile/internal/escape`. Решение принимается на этапе SSA, основываясь на том, видна ли переменная после возврата функции. Переменные, чей адрес взят, но не «убежал», могут всё ещё аллоцироваться на стеке — это локальная убегаемость (local escape), но она не требует кучи.

Аллокатор: `runtime.mallocgc(size, typ, needzero)`. Если объект маленький (<=32KB), выделяется из кэша размера (mcache), привязанного к P, без блокировок. При большом — напрямую из кучи через mheap. Использование `sync.Pool` позволяет вернуть объект в локальный пул P, миную GC.

Профилировщик `-benchmem` показывает allocs/op. Найти убегающие переменные: `go build -gcflags="-m" 2>&1 | grep escapes`. Исправить можно, переписав API так, чтобы не возвращать указатели, а значения.

### Типичные ошибки кандидатов
1. **Преждевременная борьба с аллокациями без профилирования**  
   Могут усложнить код ради сомнительной выгоды.  
   *Исправление:* сначала профилировать, убедиться, что аллокации на hot path, затем действовать.

2. **Возврат по указателю ради «производительности»**  
   Часто приводит к убеганию на кучу, когда можно вернуть значение.  
   *Исправление:* следовать правилу: маленькие структуры (~до 64-128 байт) возвращать по значению.

3. **Игнорирование выделений от интерфейсов**  
   Присваиваем `var x interface{} = 42` — упаковка значения в `iface` требует выделение копии в куче, если значение не указатель.  
   *Исправление:* использовать типизированные поля, дженерики.

### Возможные дополнительные вопросы интервьюера
- *Как проанализировать что именно убегает в кучу?*  
  `go build -gcflags="-m -m"` показывает решение компилятора и причины.
- *Почему слайс с запасом уменьшает аллокации?*  
  `append` при нехватке ёмкости вызывает `growslice`, которая выделяет новый массив. Задавая cap, избегаем повторных ростов.
- *Что такое arena allocation и когда применима?*  
  Экспериментальная фича (с Go 1.20) для массового выделения объектов с последующим освобождением арены разом; хороша для серверов с чёткими жизненными циклами запросов.

## Что такое пулинг (pooling)?

### Краткий ответ (30–60 секунд)
Пулинг — техника переиспользования объектов вместо создания новых, чтобы избежать аллокаций и снизить нагрузку на GC. Объекты берутся из пула, используются, затем возвращаются (сбрасывая состояние). В Go основная реализация — `sync.Pool`.

### Развёрнутый ответ
Проблема: частые выделения короткоживущих объектов (буферы, структуры запросов) заставляют GC сканировать их и освобождать, вызывая паузы. Пулинг сокращает количество аллокаций, поскольку объект уже выделен и просто очищается.

Но пулинг не бесплатный: требует ручного управления жизненным циклом, может привести к утечке объектов (если не возвращать), добавляет накладные расходы на синхронизацию (хотя `sync.Pool` работает локально для горутины). Важно, чтобы объекты были потокобезопасными или использовались эксклюзивно.

В Go часто пулят: `[]byte` буферы (для чтения из сети), `Context` обёртки, `Request` структуры, `json.Encoder`.

Шаблон:
```go
var bufPool = sync.Pool{
    New: func() any { return make([]byte, 4096) },
}
buf := bufPool.Get().([]byte)
defer bufPool.Put(buf[:0]) // сброс длины
```

### Под капотом (internals)
`sync.Pool` реализован как цепочка локальных пулов (`poolLocal`), прикреплённых к каждому P. Получение (Get) без блокировок обращается к локальному пулу текущего P. Если там пусто, забирает у случайного соседа (work stealing). Возврат (Put) кладёт в локальный пул, при его заполнении объект может быть удалён сборщиком мусора при следующем цикле — `sync.Pool` не гарантирует сохранность между GC.

Важный нюанс: при GC все объекты в пулах могут быть удалены. Это и хорошо (не удерживаются мёртвые ссылки), и плохо (неподходяще для объектов с дорогим созданием).

### Типичные ошибки кандидатов
1. **Не очищают объект перед возвратом**  
   Если в пуле остались старые данные (слайс с грязными элементами), это может привести к багам.  
   *Исправление:* явно сбрасывать состояние: обнулять слайс (`buf = buf[:0]`), карты чистить.

2. **Используют пулы для долгоживущих объектов**  
   `sync.Pool` автоматически очищается GC, поэтому для объектов, которые нужны долго, он не подходит.  
   *Исправление:* для долгоживущих — кастомные пулы с `chan` или `sync.Cond`.

3. **Не учитывают contention на общем пуле**  
   Одна блокировка на весь пул может стать узким местом.  
   *Исправление:* использовать `sync.Pool`, который минимизирует contention; либо шардировать пул самостоятельно.

### Возможные дополнительные вопросы интервьюера
- *Можно ли пулить горутины?*  
  Напрямую нет, но можно контролировать количество (семафор, worker pool). Существуют библиотеки вроде `ants`, реализующие пул горутин с переиспользованием.
- *Почему `sync.Pool` не гарантирует сохранность объектов после GC?*  
  Философия: борьба с давлением GC, а не вечное хранение. Если объект не используется, он удаляется, чтобы уменьшить метрику heap in use.

## Что такое `sync.Pool`?

### Краткий ответ (30–60 секунд)
`sync.Pool` — готовый пул временных объектов с горутино-локальными кэшами и автоматической очисткой при сборке мусора. Он подходит для выделения буферов и других объектов с коротким временем жизни, снижая количество аллокаций и нагрузку на GC.

### Развёрнутый ответ
Типичный сценарий: HTTP сервер каждый запрос обрабатывает в своей горутине, создаёт временный буфер для чтения тела. Вместо `make([]byte, 4096)` при каждом запросе, буфер запрашивается из `sync.Pool` и после обработки возвращается. Экономия огромная.

API:
- `Get() any` — извлекает объект (если пул пуст, вызывает `New`).
- `Put(x any)` — возвращает объект.

Важно: после `Get` нужно всегда быть готовым к `nil` (если `New` не определён), но обычно `New` обязательно.

Устройство: пул шардирован. Каждый P имеет свой приватный кэш `private` и разделяемый `shared`. `Get` проверяет `private` → `shared` головы → проходится по спискам других P. `Put` кладёт в `private`, если тот пуст, иначе — в `shared`.

Сборщик мусора в фазе mark termination принудительно очищает все пулы, чтобы объекты не задерживались навечно. Это поведение нужно учитывать: нельзя хранить в `sync.Pool` данные, которые должны жить дольше одного цикла GC.

### Под капотом (internals)
Файл `sync/pool.go`. Структура:
```go
type poolLocal struct {
    poolLocalInternal
    pad [128 - unsafe.Sizeof(poolLocalInternal{})%128]byte // false sharing prevention
}
```
`poolLocalInternal` содержит `private any` и `shared poolChain` — двунаправленную очередь lock-free (Michael-Scott). При GC runtime вызывает `poolCleanup`, которая пробегает по всем P, сдвигает указатель, по сути удаляя объекты.

Критически: `Get` использует `runtime_procPin`/`runtime_procUnpin`, чтобы привязаться к P во избежание миграции между взятием и возвратом. Из-за этого пул эффективен только при краткосрочном удерживании объектов.

### Типичные ошибки кандидатов
1. **Рассчитывают на сохранность между GC**  
   Полагают, что объект в пуле останется надолго. При следующей сборке он исчезнет.  
   *Исправление:* трактовать пул как кэш на один GC-цикл, не хранить состояние вне области запроса.

2. **Забывают про `New` и получают `nil`**  
   При первом обращении или после GC `Get` может вернуть `nil`, если `New` не задан.  
   *Исправление:* всегда задавать `New`, либо проверять `nil`.

3. **Кладут объекты разного типа**  
   Пул типизирован слабо, поэтому можно случайно положить не тот тип, что вызовет панику при type assertion.  
   *Исправление:* создавать обёртки с конкретным типом или использовать дженерики `sync.Pool` в Go 1.23+ (пока нет) и кастомные.

### Возможные дополнительные вопросы интервьюера
- *Чем `sync.Pool` отличается от свободного списка (free list) на каналах?*  
  Free list на каналах чреват блокировками и отсутствием автоматической очистки GC. `sync.Pool` гораздо производительнее в многопоточной среде.
- *Можно ли ускорить `sync.Pool` добавлением шардирования вручную?*  
  Не нужно, внутри уже шардирован по P. Дополнительное шардирование только усложнит код без выгоды.

## Когда использовать `sync.Pool`?

### Краткий ответ (30–60 секунд)
Использовать для временных объектов с высоким темпом создания и коротким временем жизни, когда их аллокация существенно влияет на пропускную способность или GC-паузы. Идеально для буферов чтения, временных структур парсинга, временных слайсов в hot path.

### Развёрнутый ответ
Критерии:
- **Высокая частота выделений**: тысячи/сек на горутину.
- **Короткий жизненный цикл**: объект нужен лишь на время обработки запроса/итерации.
- **Не содержит указателей на долгоживущие данные** (или легко обнуляется), иначе мешает GC.
- **Стоимость создания выше, чем извлечение из пула + сброс**.

Примеры:
- `[]byte` для чтения запроса `io.ReadAll`.
- `strings.Builder` для сборки ответа.
- `encoding/json` `Decoder` / `Encoder` с переиспользованием буфера.
- Временные слайсы в алгоритмах слияния.

Не подходит:
- Объекты, которые должны жить дольше одного GC (GC очистит пул).
- Объекты, чьё состояние сложно очистить.
- Потокобезопасные структуры с мьютексами (их состояние после использования неопределённое).

### Под капотом (internals)
Между циклами GC пул может пережить одну сборку? Нет, при mark termination вызывается `sync.Pool.poolCleanup`, которая пробегает по всем `poolLocal` и перемещает указатель поколения, фактически «отсекая» все имеющиеся объекты. Поэтому любые ссылки на объекты, оставшиеся в пуле, теряются. Это диктует паттерн: забирай-используй-возвращай в одной горутине и не храни после возврата.

Есть нюанс с `runtime.SetFinalizer`: объект может быть финализирован до очистки пула? Нет, финализаторы помечают объект как достижимый для одного цикла GC, поэтому они хуже совместимы с пулом.

### Типичные ошибки кандидатов
1. **Помещение в пул объектов, содержащих указатели на «живые» данные**  
   Например, слайс, ссылающийся на подмассив глобального буфера. Такой объект помешает сборке мусора и приведёт к удержанию лишней памяти.  
   *Исправление:* копировать данные, использовать `make` для нового куска.

2. **Использование пула для дешёвых объектов**  
   Стоимость `Get`/`Put` может превысить выгоду, если создание объекта дешевле (маленький `int`).  
   *Исправление:* бенчмаркинг подтверждает улучшение.

3. **Не учитывают, что после GC пул опустеет**  
   Это может вызвать лавинообразную аллокацию новых объектов в начале следующего цикла.  
   *Исправление:* `New`-функция должна быть дёшева, либо использовать прогрессивный прогрев.

### Возможные дополнительные вопросы интервьюера
- *Как оценить эффективность пула?*  
  Сравнить `allocs/op` с включённым и выключенным пулом через `testing.B`, также профилировать сборщик мусора.
- *Какую альтернативу использовать для долгоживущих объектов вместо `sync.Pool`?*  
  Свободный список на мьютексе или канале, где вы сами контролируете удаление.

## Что такое zero-copy?

### Краткий ответ (30–60 секунд)
Zero-copy — техника передачи данных между операциями или слоями без промежуточного копирования в пользовательском пространстве. В Go это использование `io.ReaderFrom`/`io.WriterTo`, sendfile, splice, и манипуляции слайсами/строками через `unsafe` там, где это безопасно.

### Развёрнутый ответ
Копирование больших объёмов данных съедает CPU и пропускную способность памяти. Zero-copy избегает этого, передавая указатели (или используя системные вызовы). Примеры в Go:
- **HTTP**: `http.ServeContent` может использовать `sendfile` для статики — напрямую из файлового дескриптора в сокет, минуя пользовательский буфер.
- **Перекодирование строк/слайсов**: `unsafe.Slice(unsafe.StringData(s), len(s))` даёт `[]byte` без копирования.
- **Слияние буферов**: `io.Copy` с типами, реализующими `ReadFrom`/`WriteTo`, например, `net.TCPConn.ReadFrom` применяет splice.
- **Работа с bytes.Buffer**: `Buffer.Bytes()` возвращает ссылку на внутренний массив — ноль копий.

Ограничения: менять данные без копии опасно, если исходная строка или слайс могут быть изменены. Для неизменяемого интерфейса это критично: строка иммутабельна, поэтому преобразование через unsafe в `[]byte` и модификация приведёт к неопределённому поведению (исключение: если конструируем `[]byte` из string только на чтение).

### Под капотом (internals)
Системный вызов `sendfile(2)` (Linux) передаёт данные напрямую из файлового дескриптора в сокет в ядре, без копий в user space. В Go его использует `(*os.File).ReadFrom()` и `net.TCPConn` при вызове `io.Copy` между файлом и соединением. Реализация в `src/internal/poll/sendfile_linux.go`. Аналогично `splice` — передача данных между двумя дескрипторами без пользовательских копий.

`unsafe.StringData` и `unsafe.SliceData` просто возвращают указатель на данные, позволяя создать структуру заголовка без копирования. Внутреннее представление строки и слайса:
```go
type StringHeader struct { Data uintptr; Len int }
type SliceHeader struct { Data uintptr; Len int; Cap int }
```
При unsafe-преобразовании создаётся новый заголовок, ссылающийся на тот же Data.

### Типичные ошибки кандидатов
1. **Модификация []byte, полученного из unsafe string**  
   Это нарушает иммутабельность строк и может испортить интернированные строки, привести к краху.  
   *Исправление:* использовать только для чтения, или делать `string(clone)` при необходимости изменений.

2. **Держать ссылку на bytes.Buffer.Bytes() после возврата буфера в пул**  
   Slice указывает на массив пула, который может быть передан другому потоку и перезаписан.  
   *Исправление:* копировать данные, если нужна долгосрочная ссылка.

3. **Думать, что `io.Copy` всегда даёт zero-copy**  
   Ускорение происходит только если оба участника реализуют `ReadFrom`/`WriteTo` с поддержкой sendfile/splice; иначе это обычный цикл копирования.  
   *Исправление:* проверять типы, при необходимости явно передавать `*os.File` на TCP-соединение.

### Возможные дополнительные вопросы интервьюера
- *Какие риски имеет zero-copy при работе с сетью?*  
  Если пакет изменится до отправки, это может привести к повреждению данных; нужно гарантировать, что исходный буфер не модифицируется.
- *Как реализован `io.Copy` в части sendfile?*  
  В `io.copyBuffer` проверяет, реализует ли `dst` интерфейс `ReadFrom`, а `src` — `*os.File`; тогда вызывает `dst.ReadFrom(src)`, который под капотом использует syscall sendfile.

## Как уменьшить влияние GC?

### Краткий ответ (30–60 секунд)
Для уменьшения влияния GC (пауз и CPU) необходимо сократить количество аллокаций и размер кучи. Достигается через пулы объектов, размещение на стеке (escape analysis), уменьшение числа указателей, увеличение `GOGC`, а также пакетную обработку для минимизации выделений.

### Развёрнутый ответ
Сборщик мусора Go — конкурентный mark-sweep, но фазы mark (особенно mark termination) всё ещё вызывают паузы ~микросекунды, а главное — накладные расходы CPU (back-pressure) и memory overhead. Чтобы минимизировать негативные эффекты:
- **Сократить темп аллокаций** — меньше мусора → меньше работы GC.
- **Использовать дженерики/стек** — избегайте указателей для мелких структур, возвращайте значения.
- **Предварительно выделять память** для слайсов, карт (указать `make(map, hint)`).
- **Переиспользовать буферы** через `sync.Pool`, `strings.Builder`.
- **Увеличить `GOGC`** — повысить порог запуска GC (по умолчанию 100, т.е. при +100% живого размера кучи). Можно установить `GOGC=200`, чтобы реже запускать сборщик, но за счёт большего пика памяти.
- **Memory ballast** (устаревший трюк) — выделить большой массив в начале, чтобы поднять порог срабатывания GC. Сейчас лучше использовать `debug.SetMemoryLimit` (Go 1.19+), который задаёт мягкий лимит и управляет GC более точно.

### Под капотом (internals)
GC запускается когда размер кучи достигает `GOGC`% от размера живых объектов после предыдущего цикла, либо когда сборщик простаивал 2 минуты. Фазы:
1. **Sweep termination** (кратковременная STW) — завершение незаконченных sweep.
2. **Mark** (конкурентный) — идёт параллельная разметка, стартует с корневых объектов.
3. **Mark termination** (STW) — финализация.

В Go 1.22 улучшена конкуретность: больше работа по mark делается без STW. Оптимизация через `packages ascii` и внутренние вызовы `mallocgc`. Использование `debug.SetMemoryLimit(max)` включает регулирование по мягкому лимиту, GC стремится удерживать кучу в лимите.

### Типичные ошибки кандидатов
1. **Слепое повышение GOGC до 1000**  
   Это может отложить GC, но пиковый размер кучи вырастет и приложение свалится по OOM.  
   *Исправление:* мониторить реальное потребление памяти, устанавливать memory limit.

2. **Игнорирование влияния указателей на mark**  
   На сканирование кучи уходит время пропорционально количеству указателей. Большая карта с ключами-указателями требует дорогого сканирования.  
   *Исправление:* использовать значения или непрозрачные ключи (unsafe.Pointer не всегда), по возможности переходить на map со сканируемым значением.

3. **Надеяться на то, что GC не будет мешать с latency SLO**  
   Даже с конкурентным mark, он потребляет CPU и может влиять на хвостовую задержку.  
   *Исправление:* профилировать GC (GODEBUG=gctrace=1, prometheus `go_gc_duration_seconds`), настраивать под нагрузку.

### Возможные дополнительные вопросы интервьюера
- *Что такое `debug.SetMemoryLimit` и как он взаимодействует с GOGC?*  
  Лимит — мягкий, GC стремится удержать кучу ниже лимита, уменьшая GOGC если превышение близко. Двойной контроль: GOGC задаёт базовый порог, лимит — абсолютный.
- *Как измерить долю времени на GC?*  
  Метрика `go_gc_cpu_fraction` из `runtime/metrics`, либо профилирование `pprof` с фильтром `runtime.gcBgMarkWorker`.

## Как писать бенчмарки (`testing.B`)?

### Краткий ответ (30–60 секунд)
Бенчмарк — функция с сигнатурой `func BenchmarkXxx(b *testing.B)`, которая запускает тестируемый код в цикле `b.N`. Важно не включать setup в замер (`b.ResetTimer`), избегать dead-code elimination (присваивать результат глобальной переменной), запускать с `-benchmem` для видимости аллокаций.

### Развёрнутый ответ
Пример:
```go
var result int

func BenchmarkSum(b *testing.B) {
    data := make([]int, 1000) // setup вне замера или с ResetTimer
    b.ResetTimer()
    for i := 0; i < b.N; i++ {
        result = sum(data) // присваиваем внешней, чтобы не вырезали
    }
}
```
Запуск: `go test -bench=. -benchmem -count=5`

Ключевые практики:
- `b.ReportAllocs()` — вывод allocs/op.
- `b.Run(name, func(b *testing.B))` — подбенчмарки для разных вариантов.
- `b.StopTimer()` / `StartTimer()` — исключение дорогой подготовки/очистки.
- Использовать `//go:noinline` на тестируемой функции, чтобы избежать инлайнинга, если надо измерить именно вызов.
- Пакет `benchstat` для статистического сравнения результатов.

### Под капотом (internals)
Стандартный фреймворк бенчмарков в `testing` использует корректировку количества итераций до тех пор, пока общее время не стабилизируется (обычно 1 секунда). Внутри `b.N` — счётчик, цикл `for i:=0; i<b.N; i++` — пользовательский. Процессорное время измеряется функцией `runtime.ReadMemStats`? Нет, измерение времени через `time.Now()` до и после цикла.

Оптимизации компилятора: константное распространение и инлайнинг могут сделать цикл пустым. Обход: использовать `bson.E` или `Sink`. В Go 1.18+ можно использовать `testing.B.Loop()` (новый API) для эргономики, но суть та же.

### Типичные ошибки кандидатов
1. **Забывают `b.ResetTimer()` после выделения ресурсов**  
   Аллокация setup в тестовом буфере увеличивает `allocs/op` и `ns/op`.  
   *Исправление:* вызвать Reset перед циклом.

2. **Результат вычислений не используется**  
   Компилятор удалит весь код как dead code, бенчмарк покажет 0 ns/op.  
   *Исправление:* сохранять результат в переменную уровня пакета (sink).

3. **Запускают бенчмарк на 1 итерацию**  
   Не доверяют автоматическому подбору N, задают `-benchtime=1x`, что даёт нестабильный результат.  
   *Исправление:* дать бенчмарку прогреться, использовать `-benchtime=10s` или несколько повторов.

4. **Не отключают CPU frequency scaling**  
   На ноутбуках частота меняется динамически, искажая замеры.  
   *Исправление:* фиксировать частоту или использовать CI-сервер.

### Возможные дополнительные вопросы интервьюера
- *Как заставить бенчмарк выполниться фиксированное количество раз?*  
  `-benchtime=1000x` — ровно 1000 итераций.
- *Как сравнивать бенчмарки «до» и «после»?*  
  `benchstat old.txt new.txt` — выдаст дельту, p-значение, проценты.

## Как интерпретировать результаты бенчмарков?

### Краткий ответ (30–60 секунд)
Результаты содержат `ns/op` (время на операцию), `B/op` (байт на операцию) и `allocs/op`. Меньшие значения лучше. Но требуют статистической проверки через многократный запуск и `benchstat` для оценки значимости изменений. Игнорировать выбросы, смотреть на медиану.

### Развёрнутый ответ
Пример вывода:
```
BenchmarkConcat-8    1234 ns/op    248 B/op    5 allocs/op
```
- `-8` — количество используемых потоков (GOMAXPROCS).
- `ns/op` — наносекунды на операцию.
- `B/op` — выделенные байты памяти за операцию.
- `allocs/op` — количество выделений в куче.

Интерпретация:
- Уменьшение `ns/op` на 20% может быть в пределах шума, если дисперсия высокая (`benchstat` покажет p-value).
- Смотрим на `allocs/op` — даже если время упало, но аллокаций стало больше, возможно, выигрыш временный из-за кэширования и в долгосроке GC ухудшит ситуацию.
- Сравнивать бенчмарки нужно на одинаковом железе и версии Go.

### Под капотом (internals)
Значения вычисляются суммарно: общее время / общее количество операций, общие выделенные байты / N. Метрики собираются через `runtime.MemStats`. `allocs/op` считается через `MemStats.Mallocs - Mallocs_prev`.

Важно: ОС может влиять на `ns/op` из-за page faults, планирования нитей. Бенчмарк нагружает один P? Нет, `testing.B.Run` по умолчанию запускает в одной горутине, но профилировщик может создавать дополнительные горутины (незначительно). Чтобы исключить параллелизм, используют `-cpu=1` и `GOMAXPROCS=1`.

### Типичные ошибки кандидатов
1. **Смотреть только на `ns/op`**  
   Игнорирование `allocs/op` может дать ложное чувство оптимизации, тогда как на самом деле увеличилась нагрузка на GC.  
   *Исправление:* всегда учитывать метрики памяти.

2. **Принимать единичный запуск за истину**  
   Без статистической проверки (benchstat) делают выводы, в то время как разница может быть случайной.  
   *Исправление:* минимум 5-10 прогонов, benchstat.

3. **Сравнивать бенчмарки разных бенчмарк-функций**  
   `ns/op` несопоставимы, если отличаются входные данные; необходимо нормировать.  
   *Исправление:* бенчмарк с одинаковым payload и окружением.

### Возможные дополнительные вопросы интервьюера
- *Что означает `p=0.23` в benchstat?*  
  Вероятность, что разница случайна; обычно порог 0.05, значит разница статистически незначима.
- *Почему `allocs/op` может быть не целым числом?*  
  Усреднение по множеству операций; может быть дробным как среднее.

## Что значит "allocs/op" и "B/op"?

### Краткий ответ (30–60 секунд)
`allocs/op` — среднее количество выделений в куче за одну итерацию бенчмарка. `B/op` — среднее количество байт, выделенных в куче за операцию. Оба показателя отражают нагрузку на аллокатор и GC.

### Развёрнутый ответ
Каждое выделение вызывает `runtime.mallocgc`. `allocs/op` показывает, сколько раз вызывался аллокатор. Снижение этой метрики напрямую улучшает производительность, потому что каждое выделение не бесплатно: затрагивает кэш процессора, увеличивает работу GC, вызывает системные вызовы при необходимости роста кучи.

`B/op` — суммарный размер выделенной памяти в куче (без учёта стека). Чем больше байт, тем быстрее заполняется куча и чаще запускается GC. Оптимизация может уменьшить `B/op` даже без изменения числа аллокаций через выделение меньших объектов или переиспользование.

Пример: `append` в слайс: если слайс имеет capacity, аллокации нет, `allocs/op = 0`. Если превышает capacity, вызывается `growslice`, давая +1 alloc и соответствующие байты.

### Под капотом (internals)
При старте бенчмарка (метод `StartTimer`) запоминается текущее состояние `runtime.MemStats`. После цикла снова снимаются значения. Разница `NumMallocs` делится на `b.N`, даёт `allocs/op`. Аналогично для `TotalAlloc`. Значения не включают стековую память, только динамическую.

Точность учёта: если между итерациями происходит выделение другими горутинами (например, GC), оно будет записано в дельту? Нет, `testing.B` изолирует подсчёт только по текущей горутине через `memstats.record`/ `ReadMemStats` — но они снимают глобальную статистику, поэтому фоновые горутины могут вносить искажения. На практике при небольших аллокациях это не страшно, но рекомендуется запускать с минимальным фоновым шумом.

### Типичные ошибки кандидатов
1. **Не учитывают выделения в setup**  
   Если `b.ResetTimer()` не вызван, первоначальные выделения включаются в метрики.  
   *Исправление:* правильное позиционирование Reset.

2. **Считают, что `allocs/op = 0` означает ноль работы GC**  
   Даже без аллокаций может быть работа по разметке уже существующей кучи. Но метрика влияет на скорость наполнения.  
   *Исправление:* понимать разницу.

3. **Неправильно сравнивают `B/op` между разными бенчмарками**  
   Размер данных на входе разный, среднее несопоставимо.  
   *Исправление:* нормализовать по размеру входа.

### Возможные дополнительные вопросы интервьюера
- *В каком модуле runtime считается `MemStats.Mallocs`?*  
  В `runtime/mstats.go`, атомарно увеличивается при каждом вызове `mallocgc`.
- *Может ли `allocs/op` быть больше числа вызовов `new/make`?*  
  Да, например, операции со строками дают неявные выделения.

## Как избежать инлайнинга в бенчмарках?

### Краткий ответ (30–60 секунд)
Чтобы не допустить инлайнинг (встраивание) тестируемой функции в цикл бенчмарка, используют `//go:noinline` перед функцией, либо сохраняют результат в глобальную переменную (sink), усложняя анализ компилятора; также можно отключить оптимизации флагом `-gcflags="-l"`, но это влияет на всё.

### Развёрнутый ответ
Инлайнинг убирает overhead вызова функции и может позволить компилятору ещё сильнее упростить код, вплоть до превращения цикла в пустышку. Чтобы измерить реальную стоимость функции как отдельного вызова, инлайнинг нужно предотвратить.

Способы:
1. Директива `//go:noinline` над функцией — надёжный запрет.
2. Использование вызова через интерфейс (неявный запрет инлайнинга для конкретного типа), но добавляет свой оверхед.
3. Присвоение результата глобальной переменной `sink` не блокирует инлайнинг, но не даёт компилятору отбросить код (dead code elimination). Но функция всё ещё может быть встроена.

Пример:
```go
//go:noinline
func f(n int) int { return n * n }

var Sink int

func BenchmarkF(b *testing.B) {
    for i := 0; i < b.N; i++ {
        Sink = f(i)
    }
}
```
Для бенчмарков, где важна не только работа функции, но и оверхед вызова, инлайнинг надо отключить.

### Под капотом (internals)
Компилятор принимает решение об инлайнинге на этапе SSA на основе бюджета «inlining cost» (размер AST, количество операций). Функции с большим количеством выражений не встраиваются автоматически. Флаг `-gcflags="-l"` отключает инлайнинг полностью, но вместе с ним выключаются и другие оптимизации. Директива `//go:noinline` работает как аннотация для компилятора: в процессе построения SSA метка учитывается и функция пропускается.

Проверить принятое решение: `go build -gcflags="-m"`. Вывод `can inline X` означает, что инлайнинг возможен; отсутствие — нет.

### Типичные ошибки кандидатов
1. **Ставят `//go:noinline` на слишком маленькую функцию и удивляются медленному результату**  
   Это нормально — они измеряют реальный оверхед вызова. Важно понимать, что в реальном коде функция могла бы быть встроена.  
   *Исправление:* явно указывать, что бенчмарк измеряет стоимость вызова, либо для оптимизационного бенчмарка не использовать noinline.

2. **Используют `-gcflags="-l"` глобально и получают искажённую картину**  
   Отключаются и другие полезные инлайнинги, меняя поведение.  
   *Исправление:* предпочесть точечную директиву.

3. **Думают, что sink предотвращает инлайнинг**  
   Sink предотвращает удаление кода, но не инлайнинг функции — она всё ещё может быть встроена, просто результат не отбрасывается.

### Возможные дополнительные вопросы интервьюера
- *Как узнать, была ли функция встроена в моём коде?*  
  `go build -gcflags="-m" ./...` и grep по выводу.
- *Есть ли способ запретить инлайнинг только в бенчмарке, не трогая исходную функцию?*  
  Можно создать обёртку-заглушку с `//go:noinline`, которая вызывает оригинал.

## Как использовать `pprof` для поиска мест с аллокациями?

### Краткий ответ (30–60 секунд)
Записываем профиль кучи (`memprofile`) или аллокаций (`allocs`) через `runtime/pprof` или `net/http/pprof` во время работы. Затем `go tool pprof --alloc_space` или `--inuse_space` показывает горячие точки. Интерактивные команды `top`, `list`, `web` открывают путь к оптимизации.

### Развёрнутый ответ
Сбор данных:
```go
import _ "net/http/pprof"
// ...
go func() { http.ListenAndServe(":6060", nil) }()
```
Затем `go tool pprof http://localhost:6060/debug/pprof/allocs` — показывает аллокации с начала работы; `heap` — текущее состояние кучи. Команда `top` выводит функции с наибольшим числом выделенных байт. `list FuncName` показывает строки с аннотациями аллокаций.

Можно собрать офлайн: `curl -o allocs.out http://localhost:6060/debug/pprof/allocs?seconds=30`. `seconds` ограничивает дельту за 30 секунд (полезно для живой системы).

Для бенчмарков: `go test -bench . -memprofile=mem.out`, потом `go tool pprof -http=:8080 mem.out`.

График flame graph (через pprof веб-интерфейс) показывает иерархию вызовов и их вклад.

### Под капотом (internals)
Профиль allocations работает на основе того же механизма, что и `runtime.MemProfile`. Когда включено профилирование, аллокатор по `MemProfileRate` (по умолчанию 512 КБ) записывает стек вызовов. Каждый вызов `mallocgc` проверяет, превышен ли лимит, и если да, добавляет запись в профиль. Переполнение профиля обрабатывается через сэмплирование. Профиль `allocs` инкрементно считает все выделения (сброс при получении). `heap` профиль отражает живые объекты.

### Типичные ошибки кандидатов
1. **Смотрят `heap` вместо `allocs` для поиска источников давления**  
   `heap` показывает текущие живые объекты, которые могут уже не выделяться активно. `allocs` за всё время даёт кумулятивную картину, что нужно для оптимизации throughput.  
   *Исправление:* использовать оба профиля в зависимости от цели.

2. **Не фильтруют по времени при длительном профилировании**  
   Профиль `allocs` может быть раздут ранними инициализациями.  
   *Исправление:* задавать `seconds` для дельты, либо снимать diff между двумя точками.

3. **Не включают `alloc_objects` для счётчика**  
   По умолчанию pprof показывает `alloc_space`; чтобы увидеть количество аллокаций, нужно `--alloc_objects`.  
   *Исправление:* `go tool pprof --alloc_objects`.

### Возможные дополнительные вопросы интервьюера
- *Как найти точное место аллокации в функции?*  
  Команда `list` в pprof покажет построчно.
- *Что такое `MemProfileRate` и как его настроить?*  
  Частота сэмплирования выделений; уменьшение (1) даёт больше деталей, но замедляет. Меняется: `runtime.MemProfileRate = 1`.

## Как работает CPU profiler (`runtime/pprof`)?

### Краткий ответ (30–60 секунд)
CPU profiler останавливает процесс (SIGPROF) с частотой 100 Гц, записывает стек текущей горутины, суммируя время, проведённое в функциях. Данные передаются в кольцевой буфер и анализируются `go tool pprof`. Позволяет выявить горячие CPU-bound функции.

### Развёрнутый ответ
Включение: `pprof.StartCPUProfile(f)` записывает в `io.Writer`. По сигналу (на Linux — `SIGPROF` от `setitimer`) ОС прерывает поток, runtime вызывает обработчик `sighandler`, который:
1. Атомарно проверяет, не находится ли поток в критической секции.
2. Собирает traceback текущей горутины (`gentraceback`).
3. Сохраняет стек в буфер профайлера.

Данные потом в формате pprof могут быть визуализированы как flame graph, где ширина полосы пропорциональна времени.

Оверхед: в основном 2-5% при 100 Гц. Возможно увеличение частоты через `runtime.SetCPUProfileRate(hz)`, но повышается накладной расход.

### Под капотом (internals)
Основные структуры в `runtime/cpuprof.go`. Буфер состоит из записей `cpuprofEntry` с PC (program counter) и временем. Профайлер работает на уровне ОС-нитей (M), не на P. Каждый M может получить сигнал. Обработчик использует `sigprof` для получения стека и сохраняет его в хэш-таблицу. При превышении буфера данные сбрасываются в выходной файл.

Важно: во время profiler может включаться STW, но это не ломает профиль — просто записывается метка.

### Типичные ошибки кандидатов
1. **Включают CPU профилирование и забывают остановить**  
   Утечка ресурсов, бесконечный рост файла.  
   *Исправление:* всегда `defer pprof.StopCPUProfile()`.

2. **Думают, что CPU profiler меряет wall-clock время**  
   Он измеряет процессорное время, затраченное горутинами в состоянии выполнения. Ожидание I/O сюда не входит.  
   *Исправление:* для анализа ожиданий использовать block profiler.

3. **Выключают фрейм-указатели (`-fno-omit-frame-pointer` забывают)**  
   На некоторых платформах без frame pointer стек не может быть развёрнут, профиль будет неполным. В Go по умолчанию с 1.7 frame pointer включён на amd64, но можно проверить.

### Возможные дополнительные вопросы интервьюера
- *Почему не видно времени системных вызовов?*  
  Горутина в состоянии syscall не получает процессорного времени; для этого нужен отдельный профиль.
- *Как профилировать горутины отдельно?*  
  Можно использовать runtime/pprof с метками `Do` и `ForLabels`.

## Как оптимизировать сериализацию/десериализацию JSON?

### Краткий ответ (30–60 секунд)
Использовать быстрые библиотеки (`easyjson`, `jsoniter`, `goccy/go-json`) с кодогенерацией; переиспользовать `bytes.Buffer`, `*json.Decoder`/`Encoder`; минимизировать рефлексию за счёт кодогенерации; избегать ненужных аллокаций через `RawMessage`, стриминг; задавать структуру данных, удобную для парсинга без излишних промежуточных представлений.

### Развёрнутый ответ
Стандартный `encoding/json` основан на рефлексии, что вызывает много аллокаций и накладных расходов. Оптимизации:
1. **Кодогенерация**: `easyjson` генерирует маршалинг/анмаршалинг без рефлексии; сериализация String ускоряется в разы.
2. **Переиспользование encoder/decoder**:
   ```go
   var buf bytes.Buffer
   enc := json.NewEncoder(&buf)
   for _, v := range items {
       enc.Encode(v)
   }
   ```
   буфер сбрасывается через `buf.Reset()`.
3. **Стриминг для больших данных**: `json.Decoder` читает потоком, не загружая всё в память.
4. **Использование `json.RawMessage`** для отложенной обработки частей без полного парсинга.
5. **Снижение аллокаций**: предварительное выделение слайсов через `Decode` с `DisallowUnknownFields`.
6. **Структурные оптимизации**: предпочитать `int` вместо `string` для числовых полей в JSON (избегать преобразований), использовать `omitempty` осмотрительно, так как нулевые значения не сериализуются, но само сравнение дёшево.

### Под капотом (internals)
Стандартный `json` пакет внутри использует `reflect` для итерации по полям структуры, создания map, слайсов. `easyjson` генерирует прямые вызовы методов `MarshalEasyJSON`/`UnmarshalEasyJSON` без рефлексии. `json-iterator/go` предлагает API, совместимое с `encoding/json`, но с фреймворком итераторов (Iterator/Stream) и возможностью замены адаптеров.

Последний тренд — `goccy/go-json` использует JIT-компиляцию (генерация машинного кода для конкретной структуры) и показывает лучшие результаты.

### Типичные ошибки кандидатов
1. **Создают новый `Encoder`/`Decoder` для каждой операции**  
   Это приводит к лишним аллокациям внутренних буферов.  
   *Исправление:* кэшировать в `sync.Pool` или переиспользовать.

2. **Парсят весь JSON в `map[string]any` для извлечения одного поля**  
   Колоссальный расход памяти и процессора.  
   *Исправление:* использовать частичный парсинг с `RawMessage` или `gjson`.

3. **Используют `json.Marshal` на больших структурах в горячем цикле**  
   Каждый вызов выделяет результирующий слайс.  
   *Исправление:* предоставить `Buffer`, использовать пул.

4. **Не отключают escape HTML**  
   По умолчанию `Encoder` экранирует `<`, `>`, `&`, что лишний расход CPU. `enc.SetEscapeHTML(false)`.

### Возможные дополнительные вопросы интервьюера
- *Что быстрее: easyjson или goccy/go-json?*  
  Зависит от нагрузки; goccy/go-json показывает высокую скорость при повторных вызовах благодаря JIT, но easyjson даёт стабильный результат кодогенерации.
- *Как устроен `json.RawMessage` zero-copy?*  
  Это `[]byte`, указывающий на участок исходного входного буфера, без копирования.

## Когда использовать `strings.Builder`?

### Краткий ответ (30–60 секунд)
Используется, когда нужно сконструировать длинную строку путём множества конкатенаций (особенно в цикле). Он избегает создания промежуточных строк, минимизируя аллокации и копирования. Идеален для горячих участков кода, где идёт сборка ответа или форматирование.

### Развёрнутый ответ
Наивный `+=` в цикле создаёт новую строку на каждой итерации, потому что строки в Go неизменяемы. `Builder` внутри держит `[]byte`, растущий по необходимости, и при вызове `String()` возвращает строку без копии (через unsafe, но безопасно, т.к. больше не изменяется). Использовать:
```go
var b strings.Builder
for _, s := range ss {
    b.WriteString(s)
}
result := b.String()
```
Также можно `b.Grow(n)` для предварительного выделения памяти, что исключает дальнейшие росты.

Применяется везде: формирование URL, SQL, текстовых отчётов, сериализация шаблонов.

### Под капотом (internals)
Структура `strings.Builder`:
```go
type Builder struct {
    addr *Builder // detector of copies
    buf  []byte
}
```
Метод `String()` использует `unsafe.Slice(unsafe.StringData(string(b.buf)), len(b.buf))` для нуль-копии. Но как только `String` вызван, если потом продолжают писать в Builder, он копирует буфер (copy-on-write), чтобы не нарушить иммутабельность уже полученной строки, которая может использоваться. `Grow` вызывает `growslice` внутренне.

### Типичные ошибки кандидатов
1. **Копирование `Builder` после записи**  
   При копировании внутренний `addr` больше не совпадает с адресом нового экземпляра, что приводит к панике при вызове методов.  
   *Исправление:* передавать по указателю, либо не копировать.

2. **Использование `Builder` для однократной конкатенации двух строк**  
   Оверхед создания Builder’а может превысить выигрыш; проще `+` или `fmt.Sprintf`.  
   *Исправление:* профилировать, использовать Builder при 3+ конкатенациях.

3. **Забывают про `Grow` при известном размере**  
   Излишние переаллокации буфера.  
   *Исправление:* вызывать `Grow` с оценкой.

### Возможные дополнительные вопросы интервьюера
- *Почему `String()` возвращает копию после продолжения записи?*  
  Для гарантии того, что ранее возвращённая строка остаётся валидной и неизменяемой; буфер копируется при следующем Write.
- *Можно ли использовать `strings.Builder` параллельно?*  
  Нет, он не потокобезопасен.

## Как `copy` может быть эффективнее `append`?

### Краткий ответ (30–60 секунд)
`copy(dst, src)` копирует элементы в уже существующий слайс без выделения нового массива, если ёмкость достаточна. `append` при нехватке capacity вызывает `growslice` и выделяет новый массив, копируя старые данные. При слиянии слайсов с известной суммарной длиной `copy` позволяет избежать лишних аллокаций, задействуя предварительно выделенный буфер.

### Развёрнутый ответ
Шаблон с предварительным выделением и `copy`:
```go
func merge(a, b []int) []int {
    c := make([]int, len(a)+len(b))
    copy(c, a)
    copy(c[len(a):], b)
    return c
}
```
Если использовать `append` несколько раз, могут произойти промежуточные выделения. Даже `append(append([]int(nil), a...), b...)` может вызвать рост при первом append, если `a` не nil. С предварительным make избегаем лишних операций.

`copy` также может быть эффективнее для «урезания» слайса без удержания старого массива: `newSlice := make([]int, n); copy(newSlice, old)` гарантирует новый независимый массив; `newSlice = old[:n]` оставляет ссылку на большой подлежащий массив, что может мешать GC.

### Под капотом (internals)
`copy` в рантайме реализован как `runtime.memmove` (ассемблерная функция), копирующая блок памяти. Компилятор может заменить `copy` на вызов `memmove` напрямую, если размер известен, либо вставить REP MOVSB для маленьких размеров. Он не вызывает аллокатор. `append` с недостаточной ёмкостью идёт через `runtime.growslice`, которая выделяет новый массив, что значительно дороже.

### Типичные ошибки кандидатов
1. **Использование `append` для копирования элементов из одного слайса в другой**  
   `dst = append(dst, src...)` может выделить новый массив, даже если dst имеет свободное место (если src длиннее остатка capacity).  
   *Исправление:* проверить capacity, применить `copy`.

2. **Игнорирование проблемы удержания массива при срезке**  
   `new := old[:needed]` оставляет старый большой массив в памяти.  
   *Исправление:* `copy` в новый слайс нужной длины.

3. **Не использование `copy` для перестановок внутри слайса**  
   Часто пишут цикл с `for`, хотя `copy` с пересекающимися участками работает (не в Go из-за запрета overlapping, нужно использовать `copy` с осторожностью: если области перекрываются, `copy` помечена как undefined, но в реальности использует memmove, поэтому для неперекрывающихся).

### Возможные дополнительные вопросы интервьюера
- *Можно ли `copy` с перекрывающимися слайсами?*  
  Спецификация говорит, что результат не определён, если источник и назначение пересекаются. На практике внутренний memmove обрабатывает, но полагаться не стоит — использовать `copy` с смещением.
- *Как `copy` связан с `memmove` в ассемблере?*  
  Компилятор генерирует вызов `runtime.memmove`, который оптимизирован под архитектуру (AVX на amd64).

## Как избежать boxing overhead при использовании интерфейсов?

### Краткий ответ (30–60 секунд)
Boxing overhead — упаковка конкретного значения в интерфейс (iface/eface) с возможным размещением в куче (escape). Избежать можно через использование дженериков, где компилятор генерирует специализированный код без интерфейсов. Если интерфейсы необходимы, использовать указатели на большие структуры, чтобы не копировать и не аллоцировать.

### Развёрнутый ответ
При присваивании `var w io.Writer = &buf` создаётся интерфейсная структура (itab + data pointer). Для типов значений, превышающих размер указателя, значение копируется и может убежать в кучу. Это добавляет:
- Аллокацию при escape.
- Косвенный вызов метода (dynamic dispatch) — невозможно инлайнинг.

Оптимизации:
- **Generics (Go 1.18+)**: функции `func Print[T Stringer](v T)` — компилятор создаёт отдельную реализацию для каждого типа, избегая интерфейсного вызова.
- **Передача по указателю**: `var w io.Writer = &MyLargeStruct{}` — интерфейс хранит только указатель, копирования большого объекта нет.
- **Ограничение интерфейсов** — использовать конкретные типы насколько возможно, но в высокоуровневом коде полиморфизм неизбежен. Тогда платить только за необходимое.

Пример дженерика без интерфейса:
```go
func Print[T interface{ String() string }](v T) {
    fmt.Println(v.String()) // прямой вызов
}
```

### Под капотом (internals)
Интерфейсное значение представлено:
```go
type iface struct {
    tab  *itab          // указатель на таблицу методов тип
    data unsafe.Pointer // указатель на значение
}
```
Для пустого интерфейса — `eface` (просто тип + data). При присваивании значения копируется в data, если его размер > слова, то копия размещается динамически и присваивается указатель. Это вызывает `mallocgc`. Дженерики устраняют интерфейсное представление: в сгенерированной функции сигнатура использует конкретный тип, поэтому прямой доступ к полям и методам без таблиц.

### Типичные ошибки кандидатов
1. **Помещают большие структуры по значению в интерфейс**  
   Вызывает копирование и возможный escape, нагружая GC.  
   *Исправление:* использовать указатели.

2. **Используют `interface{}` / `any` для передачи чисел**  
   Упаковка простого int в интерфейс идёт через побег в кучу.  
   *Исправление:* заменить на дженерики или конкретные функции.

3. **Пишут библиотеки с интерфейсами без необходимости, принуждая пользователей к boxing**  
   *Исправление:* проектировать API с дженериками, где возможно.

### Возможные дополнительные вопросы интервьюера
- *Что такое itab и как он влияет на производительность?*  
  Таблица методов, динамически разрешающая вызовы; для каждой пары (тип, интерфейс) создаётся один itab, что глобально добавляет память и небольшой оверхед вызова.
- *Может ли компилятор девиртуализировать интерфейсный вызов?*  
  Да, в некоторых случаях (когда тип известен на этапе компиляции) может быть прямой вызов, но это ограничено escape анализом.

## Как использование указателей влияет на производительность?

### Краткий ответ (30–60 секунд)
Указатели добавляют косвенность (разыменование) и часто провоцируют аллокации в куче (escape analysis). Они увеличивают нагрузку на GC, так как нужно прослеживать ссылки. Однако для больших структур указатели снижают копирование. Баланс: маленькие структуры передавать по значению; большие или требующие мутабельности — по указателю.

### Развёрнутый ответ
Плюсы указателей:
- Изменяемость исходного объекта.
- Избегание копирования тяжёлых объектов.

Минусы:
- Каждый указатель создаёт ссылку в куче, которую GC должен сканировать.
- Разыменование может привести к cache miss.
- Escape analysis может перенести объект в кучу только потому, что его адрес возвращается или присваивается интерфейсу.
- Код с указателями имеет меньше возможностей для оптимизации компилятором (bound check, инлайнинг).

Правило большого пальца: структуры размером до 64–128 байт лучше копировать. Для неизменяемых данных указатели излишни.

### Под капотом (internals)
Анализатор убегания (`cmd/compile/internal/escape`) отслеживает, утекает ли адрес. Если да — объект перемещается в кучу. Компилятор SSA преобразует доступ к полям указателя в `MOV` с регистром, что дёшево, но если указатель далеко от кэша, стоимость возрастает. GC сканирует все указатели, начиная от корней, проходя по графу. Чем больше указателей, тем длиннее mark фаза.

### Типичные ошибки кандидатов
1. **Возвращают указатель на локальную переменную "для микрооптимизации"**  
   Это приводит к её размещению в куче, а не на стеке, хотя простое копирование значения было бы быстрее.  
   *Исправление:* возвращать значение.

2. **Используют `*int` для поля флага**  
   Значение int занимает 8 байт, указатель на него — тоже 8, но добавляет нагрузку на GC и дополнительную индирекцию.  
   *Исправление:* использовать значение.

3. **Держат указатели в map ключах без необходимости**  
   Ключи-указатели усложняют сканирование GC и могут вызывать промахи кэша.  
   *Исправление:* если указатель идентифицирует сущность, можно обернуть в структуру с хэшем.

### Возможные дополнительные вопросы интервьюера
- *Когда указатель не ведёт к размещению в куче?*  
  Если объект не убегает (адрес не выходит за пределы функции) — он может остаться на стеке, имея адрес.
- *Как профилировать излишние обращения по указателю?*  
  `perf stat -e cache-misses` или `cachegrind`, но проще — уменьшать количество указателей в горячих структурах.

## Как кэш-миссы (cache misses) влияют на скорость?

### Краткий ответ (30–60 секунд)
Кэш-мисс происходит, когда CPU не находит данные в L1/L2/L3 кэше и вынужден идти в RAM (десятки-сотни тактов). Это создаёт задержки, снижает throughput, особенно в многопоточном коде. В Go влияние проявляется при обходе больших разреженных структур (связные списки, map с объектами не подряд), false sharing.

### Развёрнутый ответ
Иерархия памяти: регистры (0 циклов), L1 (4-5), L2 (~12), L3 (~40), DRAM (~200-300 циклов). Код с последовательным доступом к памяти (массивы/слайсы) выигрывает от prefetch и cache line (64 байта). Непоследовательные доступы (прыжки по указателям) генерируют много промахов.

В Go большое количество указателей ведёт к разбросу данных по куче, ухудшая локальность. Оптимизация: плоские структуры (слайс значений, а не слайс указателей), использование `array` вместо `slice` маленьких размеров при известном количестве, упаковка часто используемых полей в начало структуры (первые поля с большей вероятностью в кэш-линии).

Измерение: `perf stat -e cache-references,cache-misses ./myapp`.

### Под капотом (internals)
Процессор загружает данные линиями по 64 байта. Если два потока изменяют разные переменные в одной кэш-линии, происходит false sharing — постоянные промахи L1/L2 при записи. В runtime Go структура `p` (P) в `runtime/runtime2.go` содержит padding для предотвращения false sharing: `_ [cpu.CacheLinePadSize]byte`.

Компилятор не переупорядочивает поля структуры (в отличие от C), поэтому ответственность на программисте.

### Типичные ошибки кандидатов
1. **Используют `[]*Struct` вместо `[]Struct`**  
   Последовательный доступ к слайсу значений идёт по сплошному участку памяти, а к слайсу указателей — прыжки по указателям с промахами.  
   *Исправление:* хранить значения, если размер элемента приемлем.

2. **Не используют padding для защиты от false sharing**  
   В конкурентном доступе разные горутины пишут в поля структуры, затирая кэш-линии.  
   *Исправление:* добавить заполнитель `_ [64]byte` между часто обновляемыми полями.

3. **Игнорирование порядка полей**  
   Если в начале структуры лежит редко используемое поле, оно занимает первую кэш-линию, а частое — уже следующую.  
   *Исправление:* расположить горячие поля первыми.

### Возможные дополнительные вопросы интервьюера
- *Как проверить эффективность использования кэша в Go программе?*  
  `perf stat`, `pprof` с `cache-misses` сэмплированием; инструменты вроде `valgrind --tool=cachegrind`.
- *Какую стратегию выбрать для мапа с частыми обновлениями?*  
  Применять шардированную карту, распределяя записи по разным кэш-линиям.

## Как false sharing влияет на многопоточную производительность?

### Краткий ответ (30–60 секунд)
False sharing возникает, когда две горутины на разных ядрах модифицируют разные переменные, попавшие в одну кэш-линию (64 байта). Это вызывает постоянную инвалидацию кэш-линий и промахи, радикально замедляя параллельный код, даже если синхронизация не требуется.

### Развёрнутый ответ
Проблема: каждое ядро кэширует линию кэша. Когда одно ядро пишет в переменную, протокол когерентности (MESI) помечает копию линии на другом ядре как инвалидную. Если другое ядро читает/пишет соседнюю переменную из той же линии, оно ждёт, пока первое ядро сбросит линию и загрузит актуальное состояние. Это вызывает сильное падение производительности, даже без явных блокировок.

В Go типичный случай — глобальный счётчик с другими полями в той же структуре:
```go
type Counters struct {
    counter1 int64
    counter2 int64 // попадают в одну линию
}
```
Решение — padding:
```go
type Counters struct {
    counter1 int64
    _ [56]byte // padding до 64 байт
    counter2 int64
}
```
`sync.Pool` и планировщик внутри себя используют такие паддинги.

### Под капотом (internals)
Размер кэш-линии на x86-64 — 64 байта. В исходниках Go `cpu.CacheLinePadSize` равен 64 для соответствующих архитектур. Структура `p` содержит `_ [cpu.CacheLinePadSize]byte`, чтобы защитить горячие поля от false sharing. Компилятор не переупорядочивает поля, поэтому без padding они остаются рядом. Выявить false sharing можно через `perf c2c` или внутри Go через `go run -race`? Нет, race detector не покажет, т.к. доступа к одной переменной нет. Но видно как деградацию параллельного масштабирования.

### Типичные ошибки кандидатов
1. **Добавляют padding неправильного размера**  
   Используют `[64]byte`, где размер структуры до padding уже 8 байт, 64 байта переполнят линию и не помогут.  
   *Исправление:* рассчитать размер до границы 64: `_ [64 - (unsafe.Sizeof(field) % 64)]byte`.

2. **Игнорируют false sharing в слайсах**  
   Если горутины обрабатывают элементы слайса больших структур, где смежные элементы могут оказаться в одной линии, но обычно слайс элементов по 8 байт не вызывает false sharing при параллельном доступе к разным индексам, если структура больше 64 байт, то индексы могут перекрываться линиями.  
   *Исправление:* добавлять padding в конец структуры, чтобы её размер был кратен 64.

3. **Не используют инструменты для проверки**  
   *Исправление:* `perf c2c` — профилировщик проблем с кэш-линиями.

### Возможные дополнительные вопросы интервьюера
- *Работает ли race detector для false sharing?*  
  Нет, потому что гонки именно по данным — обращения к разным адресам. Но счётчик perf покажет.
- *Как false sharing может появиться в каналах?*  
  Внутренняя структура `hchan` содержит поля, изменяемые разными горутинами; разработчики runtime добавили паддинги.

## Как оптимизировать `map`?

### Краткий ответ (30–60 секунд)
Оптимизация map: предварительное выделение размера (`make(map[K]V, hint)`) для уменьшения перехеширований; использование ключей-значений без указателей для снижения нагрузки на GC; шардирование для уменьшения contention при параллельном доступе; переход на `sync.Map` в специфичных сценариях.

### Развёрнутый ответ
Основные стратегии:
1. **Hint в make**: когда известно примерное количество элементов, `make(map[string]int, 10000)` выделяет достаточный начальный размер, избегая дорогих эвакуаций (evacuation) бакетов.
2. **Типы ключей**: предпочтительны ключи-значения (int, string) или структуры без указателей, так как указатели в ключах добавляют работы GC.
3. **Шардирование**: создать `numShards` отдельных `map` с мьютексом (или `sync.RWMutex`) и распределять ключи по шардам через хэш. Уменьшает блокировки, особенно при записях.
4. **Итерация**: при итерации по большой map с удалением старше — использовать очистку через повторное выделение (assign to map variable) или метод `delete` накопленных ключей пачками.
5. **Структуры значений**: хранить значения-указатели, если они большие и часто копируются при реорганизации map? Нет, лучше указатель, чтобы map хранила только 8-байтовый указатель; иначе при эвакуации бакетов значения копируются целиком. Но это увеличивает нагрузку на GC.
6. **Использовать `sync.Map`**, когда есть много чтений с редкими записями и ключи стабильны (см. следующий вопрос).

### Под капотом (internals)
Map в Go — хэш-таблица с цепочками бакетов. Каждый бакет хранит 8 пар ключ-значение и ссылку на overflow бакет. При росте (load factor > 6.5 или overflow-фактор) запускается эвакуация — данные постепенно переносятся в новый массив бакетов. Это вызывает задержки. Структура `hmap` содержит B (логарифм числа бакетов), `buckets`, `oldbuckets` (при эвакуации). Доступ без блокировки (не потокобезопасный) детектирует конкурентную запись и вызывает фатальную ошибку.

Хранение ключей и значений: если тип не содержит указателей, GC может пропускать сканирование таких сегментов, что ускоряет mark.

### Типичные ошибки кандидатов
1. **Создание map без hint при известном размере**  
   Множественные перераспределения и эвакуации.  
   *Исправление:* `make(map[K]V, size)`.

2. **Использование map для хранения большого количества мелких объектов с указателями**  
   GC будет сканировать весь объём, увеличивая паузы.  
   *Исправление:* сериализовать в плоский массив или сменить дизайн.

3. **Шардирование без умного выбора функции хэша**  
   Если ключи не распределяются равномерно, шарды не сбалансированы.  
   *Исправление:* использовать `hash/fnv` или `crc32`, затем `mod`.

### Возможные дополнительные вопросы интервьюера
- *Почему при добавлении в map нагрузка может внезапно возрасти?*  
  Запуск эвакуации — постепенное перемещение данных, но отдельная операция может вызвать двойной доступ (к старому и новому бакету).
- *Как map проверяет конкурентные записи?*  
  В hmap есть флаг `flags`, при записи устанавливается бит `hashWriting`, при чтении проверяется; если гонка — паника.

## Когда `sync.Map` быстрее обычной `map`?

### Краткий ответ (30–60 секунд)
`sync.Map` быстрее, когда есть интенсивное чтение стабильного набора ключей с редкими записями (вставка/обновление), или когда множество горутин читают и записывают непересекающиеся ключи (read-heavy / write-rare). Встроена двухуровневая стратегия: read-only копия (lock-free) и dirty.

### Развёрнутый ответ
Стандартный `map` + `sync.RWMutex` даёт хорошую производительность при сбалансированных чтениях/записях, но блокировка на запись сериализует все операции. `sync.Map` оптимизирован под:
- **Стабильные ключи**: после достижения стационарного состояния большинство обращений обслуживаются из read-only структуры без атомарных операций? Нет, read map использует атомарные указатели, но без блокировок (lock-free).
- **Кэш записей**: при записи модифицируется `dirty` map, защищённая мьютексом; если ключ часто меняется, выгода теряется.
- **Мигрирующие ключи**: при частом чтении после долгого периода без изменений read-часть почти не меняется, dirty продвигается в read (промоушн) при определённых условиях.

Поведение: `Load` сначала ищет в read (атомарно). Если пропуск (miss), блокирует mutex и ищет в dirty, также увеличивая счётчик misses. Когда misses достигают длины dirty, dirty замещает read (read = dirty, dirty = nil). Поэтому если read покрывает почти все ключи, Load очень быстрый. Если же ключи постоянно меняются, постоянные misses приводят к частым промоушнам и блокировкам, становясь медленнее обычной map+Mutex.

### Под капотом (internals)
Структура `sync.Map`:
```go
type Map struct {
    mu sync.Mutex
    read atomic.Pointer[readOnly]
    dirty map[any]*entry
    misses int
}
```
`readOnly` содержит `map[any]*entry` и флаг `amended` (true, если в dirty есть ключи, отсутствующие в read). Каждая `entry` содержит указатель на значение и позволяет lock-free Store/Load через атомарные CAS. При `Store`, если ключ есть в read, CAS обновляет значение; если нет, блокирует mu, добавляет в dirty. При `Load`, если read не содержит и `amended`, блокируется mu и ищет в dirty. Misses после превышения порога вызывают замену read на dirty.

### Типичные ошибки кандидатов
1. **Использование `sync.Map` для структуры с частыми вставками/удалениями**  
   Приводит к постоянным блокировкам и промоушнам, производительность падает.  
   *Исправление:* применять `sync.RWMutex` + обычный map, либо шардированный map.

2. **Утверждение, что `sync.Map` использует lock-free операции**  
   Только read-части; записи новых ключей требуют мьютекс. Не стоит ожидать полной свободы от блокировок.  
   *Исправление:* понимать гибридную модель.

3. **Неправильное применение в кэшах с истечением срока**  
   `sync.Map` не предоставляет механизм очистки старых записей, что ведёт к утечкам.  
   *Исправление:* реализовывать TTL самостоятельно поверх или использовать другой подход.

### Возможные дополнительные вопросы интервьюера
- *Что произойдёт при удалении ключа из `sync.Map`?*  
  `Delete` устанавливает значение в `nil` через CAS; ключ остаётся в read, но с nil-значением. Позже может быть физически удалён при промоушне.
- *Как `sync.Map` ведёт себя при частых Range?*  
  `Range` требует блокировки, если dirty не nil, что может быть дорого.

## Как работает функция `growslice` и почему это может быть медленно?

### Краткий ответ (30–60 секунд)
`growslice` вызывается, когда `append` превышает capacity слайса. Она выделяет новый, больший массив, копирует старые элементы (через `memmove`), обновляет заголовок. Это медленно из-за аллокации и копирования. Частые вызовы создают нагрузку на аллокатор и GC.

### Развёрнутый ответ
Алгоритм роста (в `runtime/slice.go`):
- Если capacity < 1024, новый cap = oldcap * 2.
- Если >= 1024, новый cap = oldcap + oldcap/4 (прирост 25%).
- Далее округление с учётом выравнивания по размеру элемента.

Результат: новый массив выделяется через `mallocgc`, старые данные копируются. Поэтому в циклах с `append` при неизвестной финальной длине производительность страдает от множественных ростов. Предварительное выделение (`make([]T, 0, capacity)`) решает проблему.

Также `growslice` может быть вызван при полном заполнении слайса, что в высоконагруженном коде создаёт джиттер латентности.

### Под капотом (internals)
`growslice` принимает старый слайс и минимальную требуемую capacity. Возвращает новый слайс с тем же указателем, если capacity уже достаточна (не вызывается). Копирование реализовано `runtime.memmove`. В ранних версиях при росте большого слайса использовался коэффициент 1.25, что могло привести к значительному перерасходу памяти; теперь округление помогает подобрать размер, близкий к странице.

Стоимость включает не только копирование, но и обнуление новой памяти (если добавляемые элементы не сразу покрывают весь массив, что происходит когда делается `append` меньше чем новый cap). Это вызывает `memclr`.

### Типичные ошибки кандидатов
1. **Забывают указывать capacity при make**  
   `make([]int, 0)` — приводит к множественным `growslice`.  
   *Исправление:* `make([]int, 0, expectedLen)`.

2. **Используют `append` в цикле с множеством итераций без ограничения**  
   Даже с начальным capacity может не хватить при превышении.  
   *Исправление:* заранее вычислить общую длину, если возможно.

3. **Держат ссылку на подлежащий массив после добавления**  
   Старый слайс становится невалидным (указывает на старый массив, который может быть использован другими или очищен GC).  
   *Исправление:* всегда использовать возвращаемый слайс.

### Возможные дополнительные вопросы интервьюера
- *Как избежать копирования при росте, если данные уже в новом месте?*  
  Никак; можно только планировать размер.
- *Почему коэффициент роста 25% для больших слайсов, а не удвоение?*  
  Компромисс между памятью и скоростью, чтобы не выделять слишком много.

## Как оптимизировать код для CPU-bound задач?

### Краткий ответ (30–60 секунд)
CPU-bound задачи ограничены производительностью процессора. Ожидаемые действия: профайлинг CPU (`pprof`), улучшение алгоритмической сложности, минимизация аллокаций, использование параллелизма через горутины/каналы с `GOMAXPROCS`, оптимизация горячего кода (ассемблерные вставки, SIMD через assembler), увеличение локальности данных.

### Развёрнутый ответ
Шаги оптимизации:
1. **Найти горячую точку**: `go tool pprof`, flame graph.
2. **Алгоритмическая оптимизация**: заменить O(n²) на O(n log n), применять кэши.
3. **Избегать лишних операций**: убрать bounds check (см. BCE), сократить вызовы функций.
4. **Параллелизация**: разбить данные на независимые части, обработать горутинами (worker pool, fan-out/fan-in).
5. **Использовать SIMD** через низкоуровневый ассемблер (планетарный пакет `avo`) для математики.
6. **Управление памятью**: выделить массивы на стеке, избегать указателей.
7. **Инлайнинг**: убедиться, что критический код встраивается (`-gcflags="-m"`).
8. **Бенчмаркинг** с разными размерами и профилирование кэш-промахов.

Пример параллельной обработки слайса:
```go
func parallelProcess(data []int) {
    nCPU := runtime.NumCPU()
    chunk := len(data) / nCPU
    var wg sync.WaitGroup
    for i := 0; i < nCPU; i++ {
        wg.Add(1)
        go func(part []int) {
            defer wg.Done()
            for _, v := range part { /* heavy math */ }
        }(data[i*chunk : (i+1)*chunk])
    }
    wg.Wait()
}
```
Но остерегайтесь false sharing при параллельной записи результатов.

### Под капотом (internals)
Планировщик равномерно распределяет горутины по P. При CPU-bound максимальная утилизация достигается при `GOMAXPROCS = NumCPU`. Если горутин больше чем P*потоков, они делят время, добавляя накладные расходы. Для критических математических вычислений можно применять ассемблерные функции, написанные на инструменте `avo` и вызываемые из Go. Пакет `math/big` и `crypto/...` использует ассемблер для ускорения.

### Типичные ошибки кандидатов
1. **Создают слишком много горутин для CPU-bound задач без пула**  
   Излишние переключения контекста (тысячи горутин) снижают полезную работу.  
   *Исправление:* ограничить количество воркеров числом P.

2. **Используют каналы для передачи большого объёма данных между горутинами**  
   Это добавляет синхронизацию и копирование; лучше разделить слайс без коммуникации.  
   *Исправление:* доступ к disjoint частям массива.

3. **Пренебрегают аллокациями, думая, что CPU-bound не чувствителен к GC**  
   Частые аллокации вызывают GC, который крадёт CPU у полезной нагрузки.  
   *Исправление:* минимизировать выделения в горячих циклах.

### Возможные дополнительные вопросы интервьюера
- *Как использовать `sync/atomic` для параллельного накопления результата?*  
  Для суммирования `atomic.AddInt64` в каждом воркере, но это может стать узким местом; лучше локальное накопление и слияние.
- *Что такое SIMD в Go?*  
  Непосредственно Go не предоставляет SIMD, но через assembler можно использовать SSE/AVX инструкции.

## Как оптимизировать код для IO-bound задач?

### Краткий ответ (30–60 секунд)
IO-bound задачи простаивают в ожидании сети/диска. Оптимизация заключается в асинхронной обработке, использовании событийного цикла (netpoller), конкурентных горутинах, уменьшении блокировок и копий данных, конвейерной обработке (pipeline), применении zero-copy и `bufio`.

### Развёрнутый ответ
Главное — не блокировать потоки ОС. Горутины идеальны: при системном вызове ввода-вывода горутина паркуется, netpoller отслеживает готовность, поток высвобождается для других горутин. Рекомендации:
- **Увеличить конкурентность**: больше горутин для обработки запросов (но не бесконечно, настраивать лимиты).
- **Буферизация**: `bufio.Reader/Writer` снижают количество системных вызовов.
- **Пакетная обработка (batching)**: агрегировать несколько запросов в один системный вызов, если возможно.
- **Zero-copy**: `sendfile`, `splice`, `io.Copy`.
- **Connection pooling**: переиспользовать соединения (HTTP keep-alive, redis pool).
- **Асинхронные операции с контекстами**: отмена запросов, тайм-ауты предотвращают удержание ресурсов.

Пример: чтение большого файла и обработка:
```go
func processFile(path string) error {
    f, _ := os.Open(path)
    defer f.Close()
    r := bufio.NewReader(f)
    for {
        line, err := r.ReadBytes('\n')
        if err != nil { break }
        // обработать line
    }
}
```
Здесь `bufio` минимизирует read syscall’ы.

### Под капотом (internals)
Netpoller: интегрирован в планировщик. Горутина, выполняющая `conn.Read()`, в конечном счёте вызывает `runtime.netpollblock`, который регистрирует файловый дескриптор в epoll/kqueue и переводит горутину в ожидание. Поток M освобождается, чтобы взять другую горутину из очереди P. Когда данные готовы, netpoller пробуждает горутину и ставит в очередь готовых.

Для ускорения io используется `io.Copy`, которая при поддержке обеими сторонами `ReadFrom`/`WriteTo` вызывает `sendfile`.

### Типичные ошибки кандидатов
1. **Создание нового соединения на каждый запрос**  
   Дорого: TCP handshake, TLS; разруливается пулом соединений.  
   *Исправление:* `http.Client` с `Transport` и keep-alive.

2. **Игнорирование буферизации ввода-вывода**  
   Чтение по байту через `Read(b[0:1])` вызывает системный вызов на каждый байт.  
   *Исправление:* `bufio.Reader`.

3. **Блокирующие операции в обработчиках**  
   Запись в файл без асинхронной обработки может снизить пропускную способность.  
   *Исправление:* вынести в очередь и отдельную горутину-райтера.

### Возможные дополнительные вопросы интервьюера
- *Как netpoller обрабатывает тысячи соединений в одной горутине?*  
  Он не в одной; множество горутин, каждая на своё соединение. Netpoller просто сообщает об готовности.
- *Что такое `syscall.RawConn` для zero-copy?*  
  Доступ к файловому дескриптору для вызова специализированных syscall’ов.

## Как работает `sync.Pool` с цепочками объектов?

### Краткий ответ (30–60 секунд)
Под цепочкой понимается, что `sync.Pool` может хранить не только простые объекты, но и сложные структуры с внутренними буферами, которые, возвращаясь в пул, сохраняют ссылки на другие объекты, потенциально препятствуя GC. Это требует тщательной очистки и иногда выделения дополнительного пула для вложенных объектов.

### Развёрнутый ответ
Пример: HTTP-запрос обрабатывает тело через `bytes.Buffer`, который внутри содержит `[]byte`. Если пулить весь объект запроса, то вместе с ним сохраняется и буфер. Если буфер большой, он удерживает память. При частой смене размера тела пулы могут стать причиной удержания памяти. Решение: очищать буфер (`buf.Reset()`) или пулить отдельно буферы.

Цепочка также возникает при пуле, который содержит другие пулы (вложенные) — распространено в сложной обработке. Важно гарантировать, что все вложенные reference сброшены до возврата родителя, иначе GC не освободит ссылающиеся объекты.

`sync.Pool` автоматически очищает все объекты после GC, поэтому даже если остались ссылки на крупные дочерние объекты, при следующем GC они будут удалены. Но до этого момента они занимают место и увеличивают метрику кучи.

### Под капотом (internals)
При GC `poolCleanup` обнуляет локальные хранилища всех P, что удаляет все объекты из пула, включая цепочки. Поэтому «утечка» временна. Однако в период между GC, особенно при большом GOGC, куча может расти, вызывая ложное увеличение потребления памяти.

Рекомендация: если объекты цепочки могут быть переиспользованы отдельно, создать несколько пулов с разной гранулярностью, чтобы избежать удержания лишнего.

### Типичные ошибки кандидатов
1. **Помещение в пул структуры с ссылками на другие неочищенные объекты**  
   Это удерживает эти объекты в куче, увеличивая пиковый memory footprint.  
   *Исправление:* обнулять указатели перед возвратом.

2. **Создание «матрешки» пулов, где один Get порождает вызов других Get**  
   Усложняет освобождение, легко забыть вернуть внутренний объект.  
   *Исправление:* упрощать дизайн, использовать единый пул контекста запроса.

3. **Не учитывают очистку слайсов**  
   Слайс, подлежащий массив которого имеет большую ёмкость, сохранит память.  
   *Исправление:* `buf = buf[:0]`, при необходимости nil.

### Возможные дополнительные вопросы интервьюера
- *Что будет, если я положу в пул объект, внутри которого есть указатель на другую структуру из пула?*  
  Двойное возвращение может привести к повторному использованию обеих частей, что в целом ОК, если правильно управлять.
- *Как контролировать, чтобы пул не разрастался?*  
  `sync.Pool` сам ограничен механизмом GC; кастомный можно сделать с лимитом размера через семафор.

## Что такое "escape analysis" и как он влияет на оптимизацию?

### Краткий ответ (30–60 секунд)
Escape analysis — статический анализ компилятора, определяющий, может ли переменная быть размещена на стеке или должна уйти в кучу. Если переменная не «убегает» (её адрес не сохраняется после возврата, не попадает в интерфейс, глобальные переменные), она выделяется на стеке — это дёшево, не влияет на GC. Оптимизация кода с учётом escape analysis гораздо снижает количество аллокаций.

### Развёрнутый ответ
Ключевые правила:
- Переменная убегает, если её адрес возвращается из функции, сохраняется в глобальном состоянии, передаётся в интерфейс (содержащий значение, а не указатель), захватывается замыканием и т.п.
- Анализ работает на уровне пакета, но может учитывать межпроцедурную информацию.

Оптимизационные паттерны:
- Передавать структуры по значению, если не нужна мутация.
- Возвращать значения, а не указатели.
- Использовать малые буферы на стеке (массив фиксированного размера) вместо динамических слайсов, если размер известен.
- Избегать сохранения ссылок на локальные переменные во внешних структурах.

Просмотр решений компилятора: `go build -gcflags="-m"`. Сообщения `escapes to heap` или `does not escape`.

### Под капотом (internals)
Анализатор расположен в `cmd/compile/internal/escape`. Работает на основе SSA (раньше на AST). Анализирует каждую операцию взятия адреса, присваивания, вызовы встроенных функций (например, `make` может убегать при возврате). Алгоритм быстрое вычисление замыканий: переменная может быть распределена на стеке, если время её жизни ограничено её функцией. Итог влияет на генерацию кода: если стек, генерируются инструкции с регистром SP; если куча — вызов `runtime.newobject`.

### Типичные ошибки кандидатов
1. **Стремление всё возвращать по указателю для «производительности»**  
   Заставляет компилятор размещать объект в куче, добавляет аллокации.  
   *Исправление:* ориентироваться на escape analysis отчёт.

2. **Использование `interface{}` для малых значений**  
   Приводит к их упаковке и убеганию.  
   *Исправление:* применять дженерики.

3. **Создание замыканий в цикле, захватывающих переменные**  
   Может вызвать неожиданные утечки.  
   *Исправление:* передавать переменную как параметр замыкания.

### Возможные дополнительные вопросы интервьюера
- *Как заставить переменную не убегать, если интерфейс требует указатель?*  
  Если интерфейс принимает указатель, то значение само по себе не убегает, только указатель.
- *Может ли инлайнинг помочь escape analysis?*  
  Да, инлайнинг функции позволяет анализатору увидеть больше контекста и возможно оставить переменную на стеке.

## Как использовать `unsafe` для оптимизации (string to []byte)?

### Краткий ответ (30–60 секунд)
Пакет `unsafe` позволяет выполнить zero-copy преобразование `string` в `[]byte` и обратно без копирования данных. Используется `unsafe.Slice` + `unsafe.StringData` (Go 1.20+) или манипуляции с заголовками через `reflect.SliceHeader`. Даёт выигрыш при передаче больших строк в функции, ожидающие `[]byte`, но требует осторожности: полученный слайс нельзя модифицировать.

### Развёрнутый ответ
Стандартное `[]byte(s)` копирует строку. В критических участках это замедляет. Zero-copy конверсия:
```go
import "unsafe"

func stringToBytes(s string) []byte {
    return unsafe.Slice(unsafe.StringData(s), len(s))
}
```
И наоборот:
```go
func bytesToString(b []byte) string {
    return unsafe.String(unsafe.SliceData(b), len(b))
}
```
Эти функции не аллоцируют. Но модификация полученного `[]byte` приведёт к изменению строковых данных, что нарушает иммутабельность строк и может вызвать неопределённое поведение (например, если строка интернирована или используется в других местах). Поэтому применять только при уверенности, что слайс не будет изменён, или когда строка создаётся как владелец данных и немедленно освобождается (например, передача во временный буфер).

Также `bytesToString` позволяет избежать копирования при передаче данных из `[]byte` в функции, требующие `string`.

### Под капотом (internals)
`unsafe.StringData` возвращает `*byte`, указывающий на первый байт строки. `unsafe.Slice` конструирует слайс с этим указателем и длиной. Внутреннее представление совпадает: строка и слайс имеют одинаковый базовый указатель. Но у слайса есть capacity, которая здесь устанавливается равной длине, поэтому при `append` произойдёт выделение нового массива, что безопасно в смысле изоляции от строки. Однако если кто-то изменит элемент `b[0] = 'x'`, он запишет в память строки.

Использование `reflect.SliceHeader` устарело и не рекомендуется; `unsafe.Slice` — современный идиоматичный способ.

### Типичные ошибки кандидатов
1. **Модификация слайса, полученного из строки**  
   Вызов `b[0] = 'a'` на `string2bytes("hello")` вызовет segmentation fault или повреждение констант.  
   *Исправление:* никогда не менять; заводить копию при необходимости модификации.

2. **Использование `bytesToString` на слайсе, который позже изменяется**  
   Полученная строка будет показывать новые данные, что может нарушить ожидания (строка стала неиммутабельной на практике).  
   *Исправление:* делать копию перед конверсией, если слайс может измениться.

3. **Попытка применить unsafe-конверсию к пустой строке**  
   Работает, но `StringData` может вернуть nil для `""`; `unsafe.Slice(nil, 0)` допустимо.

### Возможные дополнительные вопросы интервьюера
- *Безопасно ли использовать `bytesToString` для ключа map?*  
  Если базовый слайс изменялся после вставки в map, это сломает хэш-таблицу. Категорически нельзя.
- *Как насчёт производительности?*  
  Выигрыш может быть значительным при больших размерах, но всегда измерять.

## Что такое "function call overhead" и как `inline` его уменьшает?

### Краткий ответ (30–60 секунд)
Function call overhead — затраты на вызов функции: сохранение регистров, передача параметров, вызов команды CALL, пролог/эпилог, возврат. Инлайнинг (встраивание) подставляет тело функции в точку вызова, устраняя эти затраты и открывая возможности для дальнейших оптимизаций (постоянное распространение, удаление мёртвого кода).

### Развёрнутый ответ
Оверхед особенно заметен для маленьких функций (геттеры, простые вычисления). Компилятор Go автоматически инлайнит функции, если их стоимость не превышает бюджет (примерно 80 узлов AST). Разработчик может подсказать компилятору, сделав функцию маленькой и простой.

Пример:
```go
func add(a, b int) int { return a + b } // будет встроен
```
Инлайнинг улучшает не только скорость вызова, но и контекст для escape analysis, позволяя переменным оставаться на стеке.

Ограничения: функции с циклами, рекурсией, большим телом не инлайнятся.

### Под капотом (internals)
В процессе компиляции SSA-оптимизатор выполняет инлайнинг. Маленькие функции, не содержащие сложных конструкций, помечаются `inline`. При вызове их SSA-граф копируется в точку вызова. После этого следуют оптимизации: сокращение констант, упрощение выражений. Принудительный запрет через `//go:noinline` используется для отладки или бенчмарков.

Результат виден в `go build -gcflags="-m"`: `inlining call to func`.

### Типичные ошибки кандидатов
1. **Искусственное раздувание функции, чтобы избежать инлайнинга**  
   Не нужно, если вы не пишете бенчмарк.  
   *Исправление:* дать компилятору делать свою работу.

2. **Полагаться на инлайнинг сложной функции**  
   Если функция большая, она не будет встроена; ожидание нулевого оверхеда неоправданно.  
   *Исправление:* разбить на мелкие, профилировать.

3. **Путать инлайнинг с макросами**  
   В Go нет препроцессора, инлайнинг — решение компилятора.

### Возможные дополнительные вопросы интервьюера
- *Можно ли форсировать инлайнинг?*  
  Нет, Go не даёт такой возможности; только косвенно через уменьшение сложности.
- *Как узнать, была ли функция встроена?*  
  `go build -gcflags="-m"`.

## Как `pprof` flame graph помогает в оптимизации?

### Краткий ответ (30–60 секунд)
Flame graph визуализирует стек вызовов профилировщика, где ширина прямоугольника пропорциональна времени в функции. Позволяет быстро найти узкое место («башню»), понять иерархию вызовов и количественно оценить вклад каждой функции, включая затраты подвызовов.

### Развёрнутый ответ
Интерактивный `go tool pprof -http=:8080` показывает flame graph (вкладка Graph, затем Flame Graph). От корня (вход в приложение) идут столбцы вызовов. Ширина по горизонтали — количество сэмплов, в которых функция присутствовала на стеке. Клик на блоке приближает его, показывая детали.

Использование: ищем широкий блок наверху стека — это горячая функция, в которой процессор проводит много времени. Смотрим, какие её дети занимают время, рекурсивно спускаемся. Оптимизируем либо саму функцию, либо уменьшаем количество вызовов.

Пример: обнаружено, что 30% времени тратится на `json.Unmarshal`, видно его внутренние вызовы рефлексии. Принимаем решение перейти на кодогенерацию.

### Под капотом (internals)
CPU профиль собирает сэмплы, каждому сэмплу соответствует стек вызовов. Pprof агрегирует одинаковые стеки и строит дерево. Flame graph — это представление этого дерева снизу вверх (или сверху вниз, зависит от ориентации). При клике обрезаются не вошедшие сэмплы.

### Типичные ошибки кандидатов
1. **Исследуют только «верхушку» flame graph**  
   Нижние широкие полосы указывают на функции, которые проводят много времени из-за детей, но сами они дешёвые; их оптимизация не поможет.  
   *Исправление:* искать широкие блоки наверху (leaf functions).

2. **Игнорируют маленькие, но многочисленные горутины**  
   При многопоточном профиле несколько горутин могут складываться в широкую полосу суммарно, давая неверное представление.  
   *Исправление:* использовать фильтр по горутинам или thread.

3. **Не сравнивают «до» и «после»**  
   Flame graph быстро меняется после оптимизаций; нужно делать diff.

### Возможные дополнительные вопросы интервьюера
- *Можно ли экспортировать flame graph в SVG?*  
  Да, pprof может выгрузить в формате, понятном для Brendan Gregg’s скрипта.
- *Как убрать системные вызовы из графика?*  
  Фильтр `--focus` / `--ignore` в pprof.

## Что такое "memory bandwidth" и как его измерить?

### Краткий ответ (30–60 секунд)
Memory bandwidth — максимальный объём данных, который процессор может считать или записать в RAM за секунду. В Go важен при обработке больших массивов данных (streams, сжатие). Когда пропускная способность памяти исчерпана, ядра простаивают. Измеряется с помощью `mbw`, `stream`, `lmbench` или `perf stat -e memory-bound`.

### Развёрнутый ответ
Bandwidth = (частота памяти × ширина шины × количество каналов) / 8 (для перевода в байты). Современные сервера имеют 50-200 ГБ/с. Приложение может упираться в память, если много копирований, чтений больших кусков. Пример: обработка видео, машинное обучение.

Измерение в Go: написать бенчмарк, который последовательно читает/пишет большой слайс, засечь время и вычислить объём / время. Более точно: `perf stat -e LLC-stores,LLC-store-misses` и т.д., или `perf mem record`.

Оптимизации: сократить количество операций чтения/записи (объединение проходов), использовать кэш-дружественные шаблоны (unit stride), избегать ненужного копирования, применять SIMD для уменьшения числа инструкций на байт.

### Под капотом (internals)
Процессор имеет контроллер памяти, несколько каналов. Когда CPU запрашивает данные, не попавшие в кэш, транзакция идёт к DRAM. Если несколько ядер одновременно нагружают память, они делят bandwidth. `runtime` сам не контролирует bandwidth, но использование `memmove` и `memclr` оптимизировано под использование non-temporal хранилищ (movnti) для избежания загрязнения кэша.

### Типичные ошибки кандидатов
1. **Считают, что оптимизация CPU всегда даёт прирост, игнорируя память**  
   Ускорение вычислений бесполезно, если данные не успевают подвозиться.  
   *Исправление:* профилировать пропускную способность памяти.

2. **Слишком агрессивное распараллеливание без учёта bandwidth**  
   Четыре горутины на четырёх ядрах могут упереться в один канал памяти и не дать ускорения.  
   *Исправление:* бенчмарк и мониторинг `perf`.

3. **Ненужное копирование данных между горутинами**  
   Каждая копия расходует bandwidth.  
   *Исправление:* работать с одним экземпляром, передавать по указателю.

### Возможные дополнительные вопросы интервьюера
- *Как узнать, достигнут ли предел bandwidth в Go сервисе?*  
  `perf stat -e instructions,cycles,LLC-misses`; если много промахов последнего уровня и низкая утилизация ядер, возможно.
- *Что такое non-temporal stores?*  
  Запись в обход кэша, чтобы не вытеснять полезные данные. Используется в memclr.

## Как `GOMAXPROCS` влияет на производительность на многоядерных системах?

### Краткий ответ (30–60 секунд)
`GOMAXPROCS` задаёт количество P (логических процессоров), которые могут одновременно исполнять горутины. На многоядерных системах увеличение GOMAXPROCS до числа ядер повышает параллелизм и throughput для CPU-bound задач, но может увеличить contention на блокировках и затраты на планировщик для IO-bound.

### Развёрнутый ответ
По умолчанию равно `runtime.NumCPU()`. Ручная настройка может быть полезна:
- **Уменьшение** для снижения конкуренции за shared ресурсы (mutex, кэш) в высококонкурентных программах.
- **Увеличение** (больше числа физических ядер) иногда помогает, если много блокирующих системных вызовов, потому что заблокированный поток не занимает P, и ОС может выделить другой. Но обычно избыток не даёт преимуществ.
- В виртуализированных средах `NumCPU()` может вернуть число ядер хоста, но контейнер ограничен; Go 1.5+ учитывает cgroups? Начиная с версии 1.5, `NumCPU` возвращает количество ядер, доступных процессу, но могут быть проблемы с cgroups v1, решено в 1.18+ автоматически.

Оптимальный выбор: провести бенчмарки под нагрузкой.

### Под капотом (internals)
Структура `sched` в runtime содержит массив `allp []*p`. Количество P задаётся при старте и может быть изменено через `runtime.GOMAXPROCS()`. При любом изменении происходит остановка мира (STW) для перераспределения P. Каждый P имеет локальную очередь горутин. Если P заблокирован в системном вызове, он может быть откреплён от M, но M уходит в ожидание, а P перехватывается другим M или idle-потоком.

### Типичные ошибки кандидатов
1. **Установка GOMAXPROCS=1 на многоядерном сервере для IO-bound**  
   Ограничивает параллелизм, netpoller не сможет использовать мультиплексирование эффективно? Он работает и с одним P, но throughput будет ограничен одним ядром.  
   *Исправление:* использовать как минимум число физических ядер.

2. **Установка GOMAXPROCS >> NumCPU без причины**  
  Больше потоков ОС, больше планирования, не улучшает производительность.  
   *Исправление:* оставить по умолчанию.

3. **Изменение GOMAXPROCS во время высокой нагрузки без остановки**  
   Вызов STW может добавить задержку. Лучше задавать при старте через переменную окружения.

### Возможные дополнительные вопросы интервьюера
- *Как GOMAXPROCS влияет на GC?*  
  GC-воркеры также запускаются на P; больше P — быстрее mark фаза, но больше остановка.
- *Следует ли менять GOMAXPROCS в go-роутинах с cgo?*  
  Блокировки в cgo могут занимать M; увеличение GOMAXPROCS может помочь, но управлять сложно.

## Как работает `GOMAXPROCS` и почему его не всегда нужно выкручивать на максимум?

### Краткий ответ (30–60 секунд)
`GOMAXPROCS` управляет только количеством P (виртуальных CPU), но ОС всё равно выделяет реальные потоки. Увеличение сверх числа физических ядер повышает overhead переключений контекста ОС и contention, не увеличивая параллелизм по-настоящему. Кроме того, в средах с ограничениями ресурсов (контейнеры) следует задавать его по реально доступным ядрам.

### Развёрнутый ответ
Причины не ставить максимум:
- **Совместное использование ядер с другими процессами**: если на машине работают ещё процессы, излишние P приведут к overcommit потоков и ухудшению отклика.
- **Нагрузка на планировщик ОС**: M потоков больше, чем ядер, вызывают частые переключения, что увеличивает latency и снижает cache affinity.
- **Конкуренция за общие структуры данных** — больше параллелизма может усилить блокировки и false sharing.
- **Экономия ресурсов**: меньше P — меньше структур планировщика, меньше кэш-промахов.

Рекомендация: для CPU-bound — GOMAXPROCS = NumCPU; для IO-bound с большим количеством блокировок — можно поставить немного больше, но профилировать. В контейнерах использовать `GOMAXPROCS` считывание из cgroups (автоматически с Go 1.18+ через `automaxprocs`).

### Под капотом (internals)
При увеличении GOMAXPROCS вызывается `procresize`, который реаллоцирует массив `allp`. Новые P инициализируются с пустыми очередями. Потоки M могут быть созданы при необходимости до `MaxThreads` (10000 по умолчанию). Когда горутина делает syscall и блокируется, P освобождается, и если есть другой M в ожидании, он может подхватить P. Однако слишком много P при ограниченных ядрах приводят к тому, что больше горутин находятся в состоянии «выполняется» и быстро вытесняются, снижая эффективность кэша.

### Типичные ошибки кандидатов
1. **Установка `GOMAXPROCS` равным количеству контейнерных «виртуальных» CPU, взятому из /proc/cpuinfo**  
   Может быть больше реальной квоты; перегрузка.  
   *Исправление:* довериться автоматическому определению через `automaxprocs` или `runtime.NumCPU()` (Go 1.18+ учитывает cgroups).

2. **Изменение GOMAXPROCS в рантайме без веской причины**  
   Каждое изменение приводит к stop-the-world, что добавляет latency.  
   *Исправление:* задавать при старте через env.

3. **Снижение GOMAXPROCS до 1 для «уменьшения задержек» на многоядерном сервере**  
   Потеря параллелизма, запросы копятся.  
   *Исправление:* балансировать на основе бенчмарков.

### Возможные дополнительные вопросы интервьюера
- *Какой механизм использует Go для удержания потоков M в ожидании при большем количестве P?*  
  Потоки паркуются в `futex` при нехватке работы, пробуждаются при появлении.
- *Как `GOMAXPROCS` влияет на работу netpoller?*  
  У каждого P есть свой netpoller? Нет, netpoller один на весь рантайм, но горутины опрашиваются по готовности и распределяются по P.

## Как написать эффективный код с дженериками без потерь в производительности?

### Краткий ответ (30–60 секунд)
Дженерики в Go (типы-параметры) при правильном использовании не добавляют boxing overhead, так как компилятор создаёт специализированные экземпляры (мономорфизация). Главное — избегать излишней косвенности через интерфейсы внутри дженерик-функций, использовать `constraints.Ordered` и другие для выбора эффективных операций, не создавать интерфейсы без необходимости.

### Развёрнутый ответ
Механизм работы Go generics (в Go 1.18+): при вызове дженерик-функции с конкретными типами создаётся отдельная версия функции (shape-based или специализированная). Это позволяет избежать боксинга. Однако некоторые аспекты могут замедлить:
- **Теневые интерфейсы**: если в дженерик-функции вызывается метод из ограничения (interface), компилятор генерирует косвенный вызов, который не инлайнится.
- **Конструирование новых значений**: `new(T)` или `make([]T, n)` работает через `typedmemclr` и т.д., что эффективно.
- **Использование `any` ограничения с приведением типов**: это эквивалентно `interface{}` и всё равно приводит к боксингу.

Советы:
- Использовать конкретные ограничения (`int`, `float64`).
- Принимать компаратор как параметр, если нужен custom compare, чтобы не заворачивать в интерфейс.
- Избегать создания интерфейсных переменных из generic-типа.
- Профилировать сборочный код: `go build -gcflags="-S"`.

Пример эффективной обобщённой суммы слайса:
```go
func Sum[T constraints.Integer](s []T) T {
    var total T
    for _, v := range s {
        total += v
    }
    return total
}
```
Компилятор генерирует отдельные версии для int, int64 и т.д. с прямыми инструкциями ADD.

### Под капотом (internals)
Компилятор использует технику «GC shape stenciling» (начиная с Go 1.19+). Для каждого уникального GC shape (размер, выравнивание) генерируется один экземпляр, который параметризуется. Если типы имеют одинаковую форму, они могут разделять код. Например, `int` и `int64` на 64-битной платформе имеют одинаковую форму, поэтому разделяют код, но доступ к значению через регистры. Это даёт почти нулевые накладные расходы.

### Типичные ошибки кандидатов
1. **Использование дженериков там, где можно обойтись конкретным типом**  
   Добавляет сложность без выигрыша. Дженерики хороши для библиотечных функций (контейнеры, алгоритмы).  
   *Исправление:* применять, когда реально нужна абстракция.

2. **Передача интерфейсных ограничений в hot path**  
   Например, `func Sort[T Sortable](s []T)`, где `Sortable` — интерфейс. Каждый вызов метода Less будет динамическим.  
   *Исправление:* передавать компаратор как функцию `func(a, b T) bool`, которая может быть встроена.

3. **Думать, что дженерики = zero-cost абстракция**  
   Хотя боксинга нет, есть стоимость создания специализированных версий в бинарнике, а косвенные вызовы методов могут блокировать инлайнинг.

### Возможные дополнительные вопросы интервьюера
- *Что такое shape-based stenciling?*  
  Компилятор группирует типы по GC shape и создаёт одну реализацию на группу, используя словарь типов для операций, специфичных для типа.
- *Можно ли через дженерики уйти от аллокаций при работе с интерфейсами?*  
  Да, ведь переменная типа T размещается прямо на стеке, если не убегает.

## Что такое "boundary check elimination" и как компилятор Go это делает?

### Краткий ответ (30–60 секунд)
Boundary check elimination (BCE) — оптимизация компилятора, удаляющая проверки выхода за границы слайса/массива, когда можно доказать, что индекс всегда в допустимом диапазоне. Это ускоряет код в циклах. Go компилятор умеет выводить такие доказательства из условий цикла или контекста.

### Развёрнутый ответ
Пример: в цикле `for i := 0; i < len(s); i++ { s[i]++ }` компилятор видит, что `i < len(s)`, и убирает проверку `i < len` и `i >= 0` внутри тела цикла. Но в сложных случаях (индекс в другой переменной) проверка остаётся. Можно подсказать компилятору, добавив проверку `_ = s[i]` до цикла? Иногда помогает.

Проверить, где остались проверки: `go build -gcflags="-d ssa/check_bce"` выводит строки с оставшимися проверками.

Оптимизация: переформулировать цикл так, чтобы компилятор мог доказать безопасность; идти от длины.

### Под капотом (internals)
Пасс BCE в SSA backend: он анализирует отношения между переменными, видит constraints из условий ветвления. Если индекс сравнивается с длиной, он помечает, что граница не нужна. Использует технику доказательства неравенств в пределах блока/цикла.

В ранних версиях Go граничные проверки были значительным источником оверхеда в крипто-коде, поэтому многие писали ассемблерные вставки. Сейчас BCE существенно улучшен.

### Типичные ошибки кандидатов
1. **Надеяться, что BCE уберёт проверку в `for _, v := range s`**  
   Range и так гарантирует отсутствие выхода за границы, проверки нет. Но копирование значения может добавить оверхед.  
   *Исправление:* понимать разницу.

2. **Усложнение кода для «помощи» BCE без бенчмарков**  
   Может ухудшить читаемость без измеримой выгоды.  
   *Исправление:* профилировать, сравнивать.

3. **Использование `unsafe` для обхода проверок**  
   Опасно, ведёт к повреждению памяти.  
   *Исправление:* полагаться на BCE, а если не хватает — профилировать и искать причину.

### Возможные дополнительные вопросы интервьюера
- *Может ли BCE убрать проверку в map доступе?*  
  Нет, map доступ включает поиск, а не границу. Это другая операция.
- *Что делает `-d ssa/check_bce` помимо вывода?*  
  Если есть `check_bce/debug=1`, он паникует при обнаружении проверок, используемых разработчиками для выявления узких мест.

## Как использовать `go build -gcflags="-d ssa/check_bce"`?

### Краткий ответ (30–60 секунд)
Флаг `-gcflags="-d ssa/check_bce"` заставляет компилятор выводить в stderr позиции исходного кода, где были вставлены boundary checks. Это позволяет найти места, где проверки границ не оптимизированы, и скорректировать код для улучшения производительности.

### Развёрнутый ответ
Пример вывода:
```
./main.go:12: Found IsInBounds
```
Значит, в строке 12 присутствует проверка выхода за границы. Оптимизатор BCE не смог её удалить. Проанализировав контекст, можно попытаться переписать код, чтобы доказать безопасность индекса.

Например:
```go
for i := 0; i < len(s); i++ {
    s[i] = s[i] * 2 // BCE удалит
}
```
Если заменить условие на `for i := 0; i < len(s); i += step`, и step > 1 выражение `s[i]` всё ещё будет иметь проверку? Не всегда, компилятор может доказать, если step положителен и начало безопасно. Но сложные выражения могут помешать.

Совместно с бенчмарком можно оценить эффект от устранения проверки.

### Под капотом (internals)
Флаг активирует вывод в функции `ssa.checkBounds`. Во время компиляции каждая операция индексирования слайса порождает инструкцию `IsInBounds`. BCE пытается доказать её избыточность. Если не удалось, инструкция остаётся, и `check_bce` печатает информацию.

### Типичные ошибки кандидатов
1. **Фанатично устранять все проверки, жертвуя читаемостью**  
   В большинстве кода накладные расходы несущественны.  
   *Исправление:* фокусироваться на горячих циклах, подтверждённых профилем.

2. **Забывать, что `range` не имеет проверок индекса**  
   Тратить время на анализ кода с range.  
   *Исправление:* использовать range, если нужно обойти все элементы.

3. **Использование `unsafe` для обхода проверки**  
   См. ошибки выше.

### Возможные дополнительные вопросы интервьюера
- *Как отключить BCE для тестирования?*  
  `-gcflags="-d ssa/check_bce/debug=1"` — останавливает компиляцию при обнаружении проверки (для CI).
- *Можно ли увидеть ассемблерный код проверок?*  
  `go tool compile -S` покажет инструкции CMP и JAE.

## Как работает `bufio` и почему он ускоряет IO?

### Краткий ответ (30–60 секунд)
`bufio` оборачивает `io.Reader`/`io.Writer`, добавляя пользовательский буфер в памяти. Вместо частых системных вызовов `read`/`write` по мелким порциям, данные копятся и передаются в ОС большими блоками, сокращая количество переключений в ядро и повышая пропускную способность.

### Развёрнутый ответ
Без буферизации `conn.Read(b)` с коротким `b` (например, 8 байт) вызывает `read()` системный вызов на каждые 8 байт. Это добавляет overhead context switch. `bufio.Reader` внутренне выделяет буфер (по умолчанию 4096 байт) и при первом `Read` заполняет его через один системный вызов, затем обслуживает мелкие запросы из буфера, пока он не опустеет.

Аналогично `bufio.Writer` накапливает данные и сбрасывает по заполнению или явному `Flush()`. Это особенно эффективно при записи в сеть — объединение маленьких сообщений в один TCP-сегмент снижает накладные расходы.

Размер буфера можно подобрать под характер нагрузки: например, 64 КБ для потоковой передачи.

### Под капотом (internals)
`bufio.NewReader` создаёт структуру `Reader` с полем `buf []byte`. Метод `Read` проверяет наличие данных в буфере; если недостаточно, выполняется `rd.Read(buf[:cap(buf)])`, считывающий напрямую из источника. Системный вызов `Read` на уровне ОС обходится дороже, чем копирование памяти из буфера. `io.Copy` использует `bufio`-подобную логику через `copyBuffer`.

Для `Writer`: аналогичный принцип, при заполнении вызывает `wr.Write(buf)`. Есть метод `WriteString`, который может принимать строку без преобразования.

### Типичные ошибки кандидатов
1. **Обёртывание уже буферизованного источника в `bufio`**  
   Например, `os.File` сам по себе не буферизован? `os.File` имеет небольшой буфер? В Go `os.File` напрямую делает syscall, поэтому `bufio` полезен. Но если обернуть TCP-conn в несколько слоёв `bufio`, лишняя копия.  
   *Исправление:* избегать двойной буферизации.

2. **Забыть `Flush` у `bufio.Writer`**  
   При завершении работы данные могут остаться в буфере и потеряться.  
   *Исправление:* всегда `defer w.Flush()`, либо после записи вызывать.

3. **Размер буфера по умолчанию не согласован с нагрузкой**  
   Для высоконагруженной системы 4 КБ может быть мало, ведёт к частым сбросам.  
   *Исправление:* задавать `bufio.NewWriterSize(w, 65536)`.

### Возможные дополнительные вопросы интервьюера
- *Когда `bufio` вреден?*  
  Если программа уже пишет большие блоки, лишний слой буфера добавляет копирование без выигрыша.
- *Как `bufio.Scanner` управляет буфером?*  
  Он также использует внутренний буфер, наращивая динамически при длинных строках.

## Как `io.Copy` и `io.CopyBuffer` помогают избежать лишних аллокаций?

### Краткий ответ (30–60 секунд)
`io.Copy` использует внутренний буфер фиксированного размера (32 КБ) для копирования данных из `Reader` в `Writer` без выделения нового буфера при каждом вызове. `io.CopyBuffer` позволяет передать собственный буфер, избегая аллокации внутреннего. Это уменьшает количество временных объектов и нагрузку GC при интенсивном обмене.

### Развёрнутый ответ
Стандартный код:
```go
n, err := io.Copy(dst, src)
```
Внутри выделяет буфер 32KB один раз (аллокация на стек?) Раньше выделялся в куче. Сейчас `io.Copy` оптимизирован: если передаётся тип, реализующий `WriterTo` или `ReaderFrom`, аллокация не происходит вовсе. Если не реализует, `copyBuffer` с буфером `make([]byte, 32*1024)`. Эту аллокацию можно избежать, предоставив буфер через `io.CopyBuffer`:
```go
buf := make([]byte, 64*1024)
n, err := io.CopyBuffer(dst, src, buf)
```
Это позволяет переиспользовать один и тот же массив в цикле, например, из пула (`sync.Pool`). Очень полезно в прокси-серверах и передаче данных между соединениями.

### Под капотом (internals)
`io.Copy` вызывает `copyBuffer` с `nil`-буфером. Если буфер `nil`, создаётся `make([]byte, 32*1024)`. Версия `io.CopyBuffer` позволяет избежать этого. Если `src` реализует `WriterTo`, вызывается напрямую без пользовательского буфера (например, `*os.File` -> `*net.TCPConn` sendfile). В `io.CopyN` логика аналогична.

Важно: используя `io.CopyBuffer`, программист отвечает за то, чтобы буфер не изменялся конкурентно.

### Типичные ошибки кандидатов
1. **Использование `io.Copy` в горячем цикле с небольшими объёмами данных**  
   Постоянно выделяются 32KB буферы, нагрузка на GC.  
   *Исправление:* `io.CopyBuffer` + `sync.Pool`.

2. **Неправильная очистка переиспользуемого буфера**  
   Данные от прошлой операции могут протечь. `io.CopyBuffer` обрабатывает только во время копирования; буфер чист неявно перезаписью.

3. **Предоставление буфера нулевой длины в `CopyBuffer`**  
   Тогда будет создан новый 32KB буфер, аллокация не избегнута.  
   *Исправление:* передавать ненулевой слайс нужной ёмкости.

### Возможные дополнительные вопросы интервьюера
- *Что произойдёт, если буфер в `io.CopyBuffer` меньше 32 КБ?*  
  Будет использоваться предоставленный; если он мал, возрастёт число системных вызовов.
- *Есть ли гарантия, что `io.CopyBuffer` не изменит длину буфера?*  
  Длина не меняется, только содержимое.

## Как работает `net/http` транспорт и пул соединений?

### Краткий ответ (30–60 секунд)
`http.Transport` управляет пулом TCP-соединений (keep-alive). При запросе берётся свободное соединение к целевому хосту, после завершения ответа оно возвращается в пул для переиспользования. Это уменьшает задержки на установку соединения и TLS handshake. Параметры `MaxIdleConns`, `IdleConnTimeout` и др. управляют пулом.

### Развёрнутый ответ
Основные поля:
- `MaxIdleConns` — общее максимальное количество простаивающих соединений (по умолч. 100).
- `MaxIdleConnsPerHost` — на конкретный хост (по умолч. 2).
- `MaxConnsPerHost` — максимальное количество соединений одновременно (0 — не ограничено).
- `IdleConnTimeout` — время бездействия, после которого соединение закрывается.

Алгоритм: при новом запросе `Transport` ищет свободное idle-соединение к нужному адресу. Если находит — использует; в противном случае открывает новое (ограничивая `MaxConnsPerHost`). При завершении запроса, если ответ содержит `Connection: close` или достигнут лимит idle на хост, соединение закрывается; иначе — кладётся в idle-пул.

Пул ускоряет отправку множества запросов к одному сервису (микросервисная архитектура), снижая latency и нагрузку на CPU (TCP/TLS).

### Под капотом (internals)
`Transport` реализован в `net/http/transport.go`. Внутри используется `connectMethod` для идентификации хоста. Соединения хранятся в `idleConn` map по ключу `connectMethodKey`. При извлечении проверяется `IdleConnTimeout`. Если простаивающие соединения закрываются сервером, они помечаются и не возвращаются в пул.

TLS-соединения также кэшируются пулом; но для каждого нового клиентского сертификата может создаваться новое.

### Типичные ошибки кандидатов
1. **Создают новый `http.Client` на каждый запрос**  
   Каждый клиент по умолчанию имеет свой `Transport`, поэтому теряется пул.  
   *Исправление:* переиспользовать глобальный клиент или custom transport.

2. **Не вычитывают тело ответа до конца**  
   Если `resp.Body` не закрыто и не прочитано до EOF, соединение не может быть возвращено в пул и утекает.  
   *Исправление:* всегда `defer resp.Body.Close()`, читать до конца или `io.Copy(io.Discard, resp.Body)`.

3. **Задают слишком маленький `MaxIdleConnsPerHost` при высоком RPS**  
   Это ограничивает параллелизм на хост, создавая узкое место.  
   *Исправление:* настраивать под нагрузку, мониторить.

### Возможные дополнительные вопросы интервьюера
- *Как `Transport` обрабатывает DNS изменения?*  
  По умолчанию кэширует IP и не перезапрашивает; это может быть проблемой в динамическом окружении. Нужно настраивать `DialContext` с устареванием.
- *Что делает `DisableKeepAlives`?*  
  Запрещает переиспользование соединений, каждый запрос создаёт новое TCP.

## Как оптимизировать `tls.Handshake` в высоконагруженных сервисах?

### Краткий ответ (30–60 секунд)
TLS handshake дорог (асимметричная криптография, обмен ключами). Оптимизируется через кэширование сессий (`tls.SessionCache`, `SessionTicket`), возобновление сеансов, `TLS 1.3` 0-RTT, переиспользование соединений (keep-alive), и аппаратное ускорение криптографии (AES-NI, специализированные CPU).

### Развёрнутый ответ
Методы:
- **Session resumption**: используя session IDs или session tickets, клиент и сервер могут пропустить полный handshake, восстанавливая предыдущий сессионный ключ. На сервере включается `Config.SessionTicketsDisabled = false`, на клиенте `ClientSessionCache`. Пример: `tls.NewLRUClientSessionCache(maxEntries)`.
- **TLS 1.3 0-RTT**: позволяет отправлять данные вместе с ClientHello, если сессия возобновлена. Требует осторожности из-за возможной повторной отправки запроса (replay).
- **Reducing certificate chain**: использовать ECDSA-сертификаты (меньше вычислений, чем RSA).
- **Hardware acceleration**: современные процессоры имеют инструкции для AES-GCM. Go использует ассемблерные реализации в `crypto/aes`.
- **Connection pooling**: HTTP/2 мультиплексирует запросы в одном TLS-соединении, амортизируя стоимость рукопожатия.
- **Оптимальный порядок cipher suites**: `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256`.

### Под капотом (internals)
В `crypto/tls` пакете рукопожатие реализовано в `handshake_client.go` и `handshake_server.go`. Для клиента `ClientSessionCache` хранит `ClientSessionState`, содержащую `sessionTicket`. При возобновлении клиент отправляет ticket, сервер расшифровывает его и восстанавливает мастер-секрет. Используется `ticketKey` для шифрования сессионных ticket’ов на сервере — её ротация может прервать старые сессии.

### Типичные ошибки кандидатов
1. **Забывают настроить `ClientSessionCache` у клиента**  
   Без этого каждое новое соединение делает полный handshake, даже при повторных запросах.  
   *Исправление:* установить `tls.NewLRUClientSessionCache(0)` (0 — размер по умолчанию).

2. **Пренебрегают ротацией `tls.Config.SessionTicketKey` на сервере**  
   Компрометация ключа позволяет расшифровать прошлые сессии (forward secrecy теряется).  
   *Исправление:* регулярно сменять ключ и хранить старые для расшифровки валидных ticket’ов.

3. **Использование только RSA-сертификатов**  
   RSA handshake медленнее, ECDSA предпочтительнее.  
   *Исправление:* выпускать ECDSA-сертификаты.

### Возможные дополнительные вопросы интервьюера
- *Что такое 0-RTT и какие риски?*  
  Данные могут быть воспроизведены злоумышленником (replay attack); для идемпотентных запросов допустимо.
- *Как Go выбирает между AES-NI и программной реализацией?*  
  Автоматически: если процессор поддерживает, используется ассемблерная версия с AES-NI.

## Что такое "slow path" в `sync.Mutex` и как его избежать?

### Краткий ответ (30–60 секунд)
`sync.Mutex` реализует двухфазную стратегию: быстрый путь — атомарное захват через `atomic.CompareAndSwapInt32`, если мьютекс свободен. Если не удаётся, горутина переходит в медленный путь — добавляется в очередь ожидания, паркуется (futex), пробуждается при освобождении. Избежать медленного пути можно, уменьшая contention, делая критические секции короткими, используя `sync.RWMutex` или lock-free структуры.

### Развёрнутый ответ
Fast path — это `Lock()` без ожидания: одна атомарная операция. Slow path включает:
- Спиннинг (активное ожидание) на некоторых архитектурах.
- Постановку в очередь ожидания (связанный список).
- Парковку & пробуждение через `runtime.Semacquire`/`Semrelease`.

Медленный путь значительно дороже, особенно когда много горутин конкурируют за мьютекс.

Как избежать:
- **Уменьшить время удержания**: выносить подготовку данных за критическую секцию, минимизировать код под локом.
- **Снизить частоту захвата**: агрегировать операции, использовать локальные кэши на горутину, собирать результаты пакетно.
- **Заменить на `sync.RWMutex`**, если основная масса операций — чтение.
- **Применять lock-free алгоритмы** (`sync/atomic`, `atomic.Pointer`, каналы).
- **Шардирование данных** — несколько мьютексов на части данных.

### Под капотом (internals)
Структура `sync.Mutex` содержит `state int32` и `sema uint32`. Пакет `sync/mutex.go` содержит функцию `lockSlow`, которая вызывается, когда fast path (CAS с 0 на 1) провалился. В `lockSlow` есть попытка спин-блокировки (`do_spin`), если количество занятых P больше 1. Затем горутина устанавливает флаг ожидания и вызывает `runtime_SemacquireMutex`, который увеличивает счётчик и переводит горутину в ожидание. При разблокировке, если есть ожидающие, `unlockSlow` пробуждает одну через `runtime_Semrelease`.

### Типичные ошибки кандидатов
1. **Выполнение тяжёлых вычислений под мьютексом**  
   Это не только вызывает медленный путь у ждущих, но и увеличивает вероятность ожидания.  
   *Исправление:* выносить за критическую секцию.

2. **Забывают, что `defer mu.Unlock()` продлевает удержание**  
   Если после defer идёт долгая логика до фактического возврата, мьютекс держится.  
   *Исправление:* явно вызывать `Unlock()` как можно раньше.

3. **Чрезмерное использование `sync.Mutex` вместо каналов или атомиков**  
   Иногда коммуникация проще и эффективнее.  
   *Исправление:* анализировать паттерн.

### Возможные дополнительные вопросы интервьюера
- *Что такое спин-блокировка в `sync.Mutex`?*  
  Короткое активное ожидание перед парковкой, уменьшает задержку, если мьютекс быстро освободится.
- *Может ли `sync.Mutex` вызвать приоритетную инверсию?*  
  В Go нет приоритетов горутин, поэтому инверсия в классическом смысле не проблема, но длительное удержание снижает пропускную способность.

## Как `memclr` и `memmove` оптимизированы в Go ассемблере?

### Краткий ответ (30–60 секунд)
`memclr` (обнуление памяти) и `memmove` (копирование) реализованы на ассемблере под конкретную архитектуру с использованием векторных инструкций (MOVDQA, REP STOSB, MOVNT) и оптимизаций под размер блоков, включая non-temporal хранилища для `memclr`. Это даёт высокую скорость базовых операций, используемых runtime и встроенными функциями.

### Развёрнутый ответ
`memmove` используется при копировании слайсов (`copy`), `growslice`, перемещении объектов GC. `memclr` — для обнуления выделенной памяти, инициализации структур, очистки слайсов.

Ассемблерные файлы: `runtime/memmove_amd64.s`, `runtime/memclr_amd64.s`. Для amd64:
- При малых размерах (до 8/16 байт) — обычные MOV.
- Для средних — используются SSE-регистры (XMM) для 16-байтовых операций.
- Для больших блоков (>2 КБ) применяются non-temporal store инструкции (MOVNTDQ), которые не загрязняют кэш.
- Используется развёрнутый цикл (unrolling) для уменьшения накладных расходов перехода.
- Для `memclr` может использоваться `REP STOSB` с оптимизацией Enhanced REP MOVSB (ERMS) на процессорах Intel.

Эти функции вызываются ядром runtime и доступны через `//go:noescape` объявления для быстрого вызова.

### Под капотом (internals)
Объявление в Go: `func memmove(to, from unsafe.Pointer, n uintptr)` определена в `runtime/stubs.go`. Реальная реализация в ассемблере. Компилятор иногда встраивает вызовы `memmove`, если размер известен на этапе компиляции.

Для `memclr` аналогично.

### Типичные ошибки кандидатов
1. **Предположение, что `copy` между слайсами всегда вызовет `memmove`**  
   Если слайсы перекрываются, поведение не определено; на практике `memmove` не безопасен для перекрытия, поэтому компилятор может не использовать его напрямую. Спецификация запрещает перекрытие в `copy`.

2. **Самописные циклы для копирования вместо `copy`**  
   Они не используют SIMD и медленнее.  
   *Исправление:* использовать `copy`.

3. **Игнорирование выравнивания данных**  
   `memmove` обрабатывает выравнивание, но лучше, когда данные выровнены, чтобы избежать штрафов.

### Возможные дополнительные вопросы интервьюера
- *Что такое non-temporal stores и зачем они в `memclr`?*  
  Запись в обход кэша, чтобы не вытеснять полезные данные; полезно при обнулении больших массивов, которые не будут сразу прочитаны.
- *Используется ли `REP MOVSB` в Go?*  
  На некоторых процессорах с ERMS да, рантайм проверяет поддержку.

## Как работает `fast path` в каналах и как он ускоряет операции?

### Краткий ответ (30–60 секунд)
Fast path — оптимистичные проверки при отправке/приёме в канал без блокировок: если канал не буферизован и есть ожидающая горутина — прямая передача данных между стеками (без промежуточного буфера). В буферизованном случае, если буфер не полон/не пуст, данные просто кладутся/забираются с помощью атомарных операций. Это минимизирует блокировки и контекстные переключения.

### Развёрнутый ответ
Операции с каналом (`ch <- v`, `v = <-ch`) сначала выполняют быстрый путь:
- **Небуферизованный**: проверяется, есть ли горутина, ожидающая в очереди `recvq` или `sendq`. Если да, данные копируются напрямую из стека отправителя в стек получателя (или наоборот) без копирования через буфер канала. Это zero-copy.
- **Буферизованный**: проверяется заполненность буфера. Если буфер не полон/не пуст, значение атомарно помещается/извлекается из буфера, индексы обновляются. Блокировки не требуется, только CAS на индексах? На самом деле используется одна блокировка `lock` поля канала, но оптимизировано.

Когда fast path невозможен (буфер полон или пуст, или нет готового партнёра), горутина переходит в slow path: добавляется в очередь ожидания и паркуется.

Эффект: при минимальной нагрузке или синхронизированных передачах overhead очень низкий.

### Под капотом (internals)
Структура `hchan` в `runtime/chan.go` содержит:
```go
type hchan struct {
    qcount   uint           // total data elements in queue
    dataqsiz uint           // size of the circular queue
    buf      unsafe.Pointer // points to an array of dataqsiz elements
    closed   uint32
    lock     mutex
    recvq    waitq
    sendq    waitq
}
```
Быстрый путь реализован в функциях `chansend` и `chanrecv`. Сначала `lock(&c.lock)` — блокировка на быструю операцию? Фактически блокировка всё же берётся, но для небуферизованной прямой передачи используется сложный механизм с разблокировкой сразу после проверки очередей, копирования данных, разблокировки и ready горутины. В буферизованном случае блокировка удерживается короткое время для изменения указателей, поэтому contention мал. Детали описаны в `runtime/chan.go`.

### Типичные ошибки кандидатов
1. **Утверждение, что каналы полностью lock-free**  
   Быстрый путь использует мьютекс `lock`, хотя и очень коротко. Поэтому при высокой конкуренции каналы могут стать узким местом.  
   *Исправление:* шардирование каналов, использование семафоров.

2. **Посыл данных в полный буферизованный канал без обработки ожидания**  
   Переход в slow path и блокировка горутины.  
   *Исправление:* применять `select` с default для неблокирующей отправки, если это допустимо.

3. **Непонимание прямой передачи данных**  
   Думают, что данные всегда проходят через буфер, что неверно для небуферизованных каналов.

### Возможные дополнительные вопросы интервьюера
- *Как работает прямая передача между стеками?*  
  Во время операции горутина-партнёр помечается как `g.waiting`; копирование осуществляется с использованием `memmove` напрямую из стека отправителя в стек получателя.
- *Что будет, если попытаться читать из закрытого канала?*  
  Быстрый путь вернёт zero value и флаг false.

## Как `sched affinity` (привязка горутины к P) влияет на производительность?

### Краткий ответ (30–60 секунд)
Аффинность горутины к P (логическому процессору) означает, что горутина стремится выполняться на том же P для лучшего использования локальных кэшей CPU. Планировщик Go поддерживает work-stealing, но старается сохранить аффинность, чтобы минимизировать кэш-промахи. Это повышает производительность за счёт локальности данных.

### Развёрнутый ответ
Планировщик Go: каждый P имеет локальную очередь горутин. G выполняется на M (поток ОС), привязанном к P. Если G блокируется, P может переключиться на другой M, но G возобновится на том же P? Не гарантируется. После разблокировки горутина помещается в очередь того P, где она ожидала? Или нет. В ранних версиях Go был affinity, сейчас горутина ставится в очередь своего P или глобальную. Но есть механизм `p->runnext` (специальный слот для следующей горутины), который помогает сохранить локальность.

Эффект affinity: если горутина длительное время работает на одном ядре, её данные остаются в L1/L2 кэше, повышая скорость. Однако слишком жёсткая привязка может привести к дисбалансу нагрузки.

### Под капотом (internals)
Структура P в `runtime2.go` содержит `runq [256]guintptr` — кольцевой буфер локальных горутин; `runnext guintptr` — слот для одной горутины, которая будет запущена следующей. При разблокировке горутины (`goready`) она помещается в очередь P (локальную) и попадает в `runnext`, если тот пуст, обеспечивая быстрый repeat. При занятом runnext старая горутина перемещается в локальную очередь. Это даёт шанс сохранить кэш.

Work stealing: если P простаивает, он пытается украсть половину очереди другого P, что нарушает affinity, но балансирует нагрузку.

### Типичные ошибки кандидатов
1. **Пытаются вручную привязать горутину к ядру через `runtime.LockOSThread`**  
   Это фиксирует M на поток, что может мешать планировщику и вызывать потерю производительности.  
   *Исправление:* не использовать без крайней нужды (cgo, графические библиотеки).

2. **Создание горутин, работающих с одними данными, но разбросанных по разным P**  
   Увеличивает кэш-промахи.  
   *Исправление:* если данные связаны, лучше обрабатывать их последовательно или в малом количестве воркеров.

3. **Игнорирование `runtime.Gosched()` в долгих CPU-bound циклах**  
   Лишает другие горутины на том же P возможности работать.  
   *Исправление:* иногда добавлять `Gosched` или разбивать на части.

### Возможные дополнительные вопросы интервьюера
- *Что такое `runnext` и как он помогает аффинности?*  
  Позволяет сразу запустить горутину, которая только что была в работе (если она, например, ждала канала), сохраняя кэш.
- *Как отключить work stealing?*  
  Нельзя; это фундаментально для Go.

## Как оптимизировать код, который интенсивно работает с `reflect`?

### Краткий ответ (30–60 секунд)
Рефлексия в Go медленная из-за анализа типов в рантайме и множества аллокаций. Оптимизация: кэшировать результаты `reflect.TypeOf`/`ValueOf`, использовать `unsafe.Pointer` для обхода рефлексивных вызовов, сократить количество `FieldByName` (строить карту полей один раз), в горячих путях заменить на кодогенерацию или дженерики.

### Развёрнутый ответ
Типичное узкое место: `v.FieldByName("Name")` каждый раз ищет поле по строке (O(n)). Вместо этого один раз получить индекс поля через `reflect.Type.FieldByName` и сохранить индекс для последующего `v.FieldByIndex`.

Кэширование `reflect.Value` не всегда возможно, но можно кэшировать `reflect.Type` и методы.

Если нужно установить значение, избегайте `v.Set(reflect.ValueOf(x))` с созданием нового Value, используйте `v.SetInt`, `v.SetString`.

Самый радикальный способ — отказаться от рефлексии: кодогенерация (`easyjson`, `msgp`) или дженерики. Но иногда рефлексия неизбежна (работа с произвольными структурами в ORM, сериализация). Тогда применяйте библиотеки, которые уже оптимизированы (`jsoniter`, `goccy/go-json`).

### Под капотом (internals)
`reflect.Value` содержит указатель на данные и `reflect.Type`. Операции извлечения/установки полей выполняются через небезопасные указатели с проверками. `FieldByName` обходит массив полей типа и сравнивает строки. `v.Interface()` часто вызывает аллокацию (побег в кучу). Компилятор не может инлайнить рефлексивные вызовы.

### Типичные ошибки кандидатов
1. **`reflect.ValueOf` в горячем цикле**  
   Создаёт новый `reflect.Value`, что ведёт к аллокациям.  
   *Исправление:* передавать `reflect.Value` явно, вызывать `ValueOf` вне цикла.

2. **Использование `FieldByName` в цикле**  
   Каждый вызов парсит поля заново.  
   *Исправление:* получить `index` заранее и применять `FieldByIndex`.

3. **Вызов `v.Interface()` для каждого элемента слайса**  
   Преобразование в `interface{}` дорого.  
   *Исправление:* работать напрямую с `v.Int()`, `v.Index()`.

### Возможные дополнительные вопросы интервьюера
- *Можно ли избежать рефлексии в универсальной сериализации?*  
  Кодогенерация генерирует статический код для каждого типа, полностью исключая рефлексию.
- *Что такое `reflect.StructOf`?*  
  Позволяет динамически создавать типы структур; очень дорого, только для крайних случаев.

## Как работает `batch processing` и как он увеличивает `throughput`?

### Краткий ответ (30–60 секунд)
Batch processing — обработка нескольких элементов за одну операцию вместо поодиночке. Снижает оверхед на единицу работы (блокировки, системные вызовы, сетевые передачи) и увеличивает пропускную способность за счёт амортизации фиксированных затрат.

### Развёрнутый ответ
Примеры:
- **Запись в БД**: вставка 1000 строк одной командой вместо 1000 отдельных `INSERT` уменьшает количество сетевых round-trip, парсинга SQL, транзакций.
- **Сетевые пакеты**: отложенная отправка через `bufio.Writer` с автоматическим flush по заполнению буфера.
- **Обработка очередей**: worker забирает пачку событий из канала, обрабатывает их скопом.
- **Файловые операции**: собирать несколько логов в один `Write`.

Go способствует батчингу каналами: отправляем задачи в канал, воркер накапливает N задач или ждёт таймаут, затем обрабатывает пачку. Важно выбрать размер пачки: слишком большой — увеличивает latency, слишком маленький — мало экономии.

### Под капотом (internals)
Батчинг использует тот факт, что стоимость выполнения одной операции = фиксированная часть (syscall, mutex) + переменная. Собирая M элементов в один вызов, фиксированная часть делится на M. В Go уменьшение количества вызовов `Write` системного вызова через `bufio` яркий пример: буферизованный writer вызывает `syscall.Write` только при заполнении буфера, а не на каждый байт.

В `growslice` тоже своего рода батчинг: выделяется память с запасом, чтобы не вызывать аллокатор постоянно.

### Типичные ошибки кандидатов
1. **Бесконечное ожидание формирования полного батча**  
   При низком трафике latency становится неприемлемой.  
   *Исправление:* установить таймаут (time-based flushing).

2. **Копирование данных в батч без необходимости**  
   Например, собирают слайс из указателей, а потом проходят ещё раз; можно сразу обрабатывать.  
   *Исправление:* использовать кольцевой буфер или писать непосредственно в приёмник.

3. **Неправильный размер батча**  
   Слишком большой батч может вызвать пиковое потребление памяти.  
   *Исправление:* подбирать размер экспериментально.

### Возможные дополнительные вопросы интервьюера
- *Как батчинг согласуется с контекстами и таймаутами?*  
  Контекст должен проверяться для каждого элемента в батче, чтобы отменять частично обработанные.
- *Что даёт буферизация каналов для батчинга?*  
  Буферизованный канал с размером, равным батчу, позволяет продюсеру не блокироваться до заполнения всего батча.

## Как найти и устранить "hot path" в коде с помощью трейсинга?

### Краткий ответ (30–60 секунд)
Hot path — часто выполняемый участок кода. Трассировка (`runtime/trace`) записывает события (старт/стоп горутин, системные вызовы, GC) на временной шкале. Инструмент `go tool trace` показывает загруженность P, длительность функций, позволяет идентифицировать участки, где горутины проводят больше всего времени, и причины ожиданий.

### Развёрнутый ответ
Включение: `f, _ := os.Create("trace.out"); trace.Start(f); defer trace.Stop()`. Анализ: `go tool trace trace.out`. Открываются вкладки:
- **Goroutine analysis**: показывает, сколько времени горутины проводили в выполнении, ожидании (sync, network, syscall).
- **View trace**: временная диаграмма событий, можно приблизить регион и увидеть длительность вызовов.
- **Network/Sync blocking profile**: похоже на pprof.

Hot path выявляется как функция, где суммарное время выполнения велико. Увидев это, можно копнуть профилировщиком CPU для детализации. Затем оптимизировать алгоритмически или микрооптимизациями.

Трассировка особенно полезна для понимания взаимодействия горутин, поиска неожиданных блокировок и простоев.

### Под капотом (internals)
`runtime/trace` работает через запись событий в буфер, используя `runtime.traceEvent`. События включают `GoCreate`, `GoStart`, `GoStop`, `GoBlock`, `GoSysCall`, и специальные аннотации пользователя (`trace.Log`). Включение добавляет оверхед (~10-20%), но даёт детальнейшую картину. Для прода он, как правило, не предназначен, только для отладки/профилирования.

### Типичные ошибки кандидатов
1. **Пытаться найти hot path только по CPU профилю, игнорируя ожидания**  
   Иногда горутина долго висит на блокировке, это тоже hot path, но не CPU.  
   *Исправление:* комбинировать CPU и trace.

2. **Слишком долгая трассировка, гигантский файл**  
   Анализ становится невозможным.  
   *Исправление:* ограничить время (5-10 секунд) и фокусироваться на типичной нагрузке.

3. **Неправильная интерпретация «простоя»**  
   Простой горутины в ожидании сети — нормально, hot path — это когда много времени уходит на синхронизацию или обработку.

### Возможные дополнительные вопросы интервьюера
- *Как пометить интересующий регион в трейсе?*  
  `ctx, task := trace.NewTask(ctx, "process")` и `defer task.End()`; в трейсе появится полоса задачи.
- *Что делать, если не удаётся воспроизвести проблему в трейсе?*  
  Использовать `pprof` в production с низким оверхедом, или непрерывный трейсинг с семплированием.
