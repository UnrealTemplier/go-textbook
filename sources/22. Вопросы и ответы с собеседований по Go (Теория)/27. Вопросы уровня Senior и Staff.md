## Как проектировать систему под 1M RPS?

### Краткий ответ
Система на 1M RPS требует горизонтального масштабирования, асинхронной обработки везде, где возможна потеря синхронности, и минимизации длины критического пути. Используем шардирование на всех уровнях (L7-балансировщики, сервисы, базы данных), многоуровневое кэширование, неблокирующий I/O, реактивные паттерны и событийную архитектуру. Ключевые метрики — tail latency (p99.9) и пропускная способность на ядро.

### Развёрнутый ответ
Проектирование начинается с декомпозиции лимитирующих факторов: CPU, память, сеть, диск. Для 1M RPS средний запрос не может превышать 1 мкс на одном ядре, но реальная работа с I/O требует асинхронности. Основные паттерны:
- **Многоуровневый L7-балансировщик**: Envoy/nginx на входе + внутренний service mesh с client-side балансировкой.
- **Backpressure и контроль очередей**: неблокирующие очереди; лимит запросов в обработке (shedding load) при приближении к порогу насыщения.
- **Шардирование по request id (равномерное)**: stateless-сервисы горизонтально масштабируются, состояние — в шардированных хранилищах.
- **Кэширование на всех уровнях**: локальный in-memory кэш (с TTL и инвалидацией через Pub/Sub), распределённый кэш (Redis/Dragonfly), CDN для статики.
- **Предварительная обработка и агрегация**: слияние аналитических данных в фоне, вместо вычислений на лету.
- **Go-специфичные оптимизации**: sync.Pool для переиспользования объектов, минимизация аллокаций (reuse buffers, zero-copy IO), использование goroutine pool (ants и т.п.) для фиксированного параллелизма, когда слишком много соединений.
- **Аппаратное обеспечение**: использование DPDK, eBPF (XDP) для супергорячих путей, kernel bypass в C с привязкой к Go через cgo (но осторожно, с batching).

Пример кода shed load с каналом и быстрым возвратом 429:

```go
var sem = make(chan struct{}, maxConcurrent)

func handler(w http.ResponseWriter, r *http.Request) {
    select {
    case sem <- struct{}{}:
        defer func() { <-sem }()
        // обработка
    default:
        http.Error(w, "Too Many Requests", http.StatusTooManyRequests)
    }
}
```

### Под капотом (internals)
В Go высокая производительность достигается за счёт трёх столпов: горутины (M:N планировщик), неблокирующий сетевой poller (epoll/kqueue), escape analysis. Для 1M RPS важно:
- **Планировщик Go (runtime/proc.go)**: при огромном количестве горутин переключения стоят дёшево (~десятки нс), но пропускная способность ограничена числом P (GOMAXPROCS). Правильный баланс — держать число активных горутин близко к числу P для CPU-bound задач.
- **netpoller**: все сетевые вызовы асинхронны: горутина не блокирует поток ОС. Это позволяет держать миллионы открытых соединений.
- **Аллокации**: каждый запрос должен генерировать минимум мусора. Использование `sync.Pool` для буферов, избегание `[]byte` -> `string` преобразований, которые влекут копирование (либо unsafe, но аккуратно). Go 1.22+ улучшил escape analysis, всё равно профилирование с `-gcflags="-m"` обязательно.
- **Балансировка горутин**: work stealing между P. source: `runtime/proc.go: findrunnable()`.

### Типичные ошибки кандидатов
1. **Запуск горутины на каждый запрос без пула**
   Неправильно: `go process(req)`. Для 1M RPS это создаст миллионы горутин в секунду, что вызовет огромное потребление памяти (минимум 2KB стек на горутину + аллокации каналов). Правильно: использовать фиксированный пул воркеров или семафоры, чтобы ограничить конкурентность.
2. **Синхронные операции внутри цепочки обработки**
   Вызов БД или HTTP-запроса без таймаутов и context propagation приведёт к каскадному отказу. Всегда wrap в `context.WithTimeout` и обрабатывай `ctx.Err()`.
3. **Использование глобальных мьютексов в горячем пути**
   `sync.Mutex` в handler на запись разделяемой структуры убьёт производительность. Используй шардированные структуры (например, `[]sync.Mutex` с выбором по хэшу) или lock-free алгоритмы (atomic).
4. **Игнорирование хвостовой задержки (tail latency)**
   Усреднённые цифры скрывают p99.9, который может быть на порядки выше из-за GC пауз или блокировок. Необходимо таргетироваться на процентили и выделять бюджет на оптимизацию именно хвостов.

### Возможные дополнительные вопросы интервьюера
*Как обеспечить согласованность данных при шардировании?*
Используем двухфазную фиксацию (2PC) или саги для распределённых транзакций; для согласованности в конечном счёте — событийно-ориентированную архитектуру с идемпотентными обработчиками.
*Как бороться с перегрузкой GC в системе с 1M RPS?*
Тюнинг GOGC (или GOMEMLIMIT), использование value-типов вместо указателей, предварительное выделение памяти (арены в Go 1.22+), минимизация числа объектов.
*Как изменится дизайн при переходе от REST к gRPC?*
gRPC поверх HTTP/2 даёт мультиплексирование, потоковую передачу, Protobuf сериализацию (значительно меньше CPU), что позволяет уменьшить количество соединений и нагрузку на балансировщики.

## Как уменьшить latency с 100ms до 10ms?

### Краткий ответ
Сокращение латентности на порядок требует устранения всех синхронных блокировок, оптимизации сериализации/десериализации, локализации данных (in-memory), сокращения холостых проходов и использования предварительно вычисленных результатов. Надо профилировать каждый этап запроса flamegraph’ами.

### Развёрнутый ответ
Начинаем с разложения энд-ту-энд пути:
1. **Сеть**: минимизировать число хопов, использовать keep-alive соединения (HTTP/2), уменьшить MTU overhead. Переход на UDP/QUIC для внутренних вызовов.
2. **Сериализация**: заменить JSON на Protobuf с zero-allocation кодогенерацией (vtprotobuf, gogoproto) или вообще избегать сериализации через shared memory (если процесс локальный).
3. **Бизнес-логика**: предварительный расчёт (материализованные представления), кэширование с упреждающей загрузкой (cache warming). Любое чтение с диска — приговор; замена на NVMe/RAM диски.
4. **База данных**: перейти от B-tree индексов к LSM (RocksDB) для write-heavy или in-memory SQLite для read-heavy локальных данных. Использовать client-side кэш с optimistic locking.
5. **Go-специфика**: убрать интерфейсы в горячем пути (dynamic dispatch дороже), использовать массивы вместо слайсов (bounds check elimination), макросы inline (компилятор сам инлайнит маленькие функции). Использовать `fasthttp` для HTTP-сервера с минимальным оверхедом (но жертвуя совместимостью).
6. **Параллелизм**: конкурентные вызовы к нескольким источникам с merge результатов (`errgroup`), но с осторожностью: плата за координацию.

Пример оптимизированного gRPC unary-обработчика с пулом:

```go
var respPool = sync.Pool{New: func() any { return &pb.Response{} }}

func (s *server) GetInfo(ctx context.Context, req *pb.Request) (*pb.Response, error) {
    resp := respPool.Get().(*pb.Response)
    defer respPool.Put(resp)
    resp.Reset()
    // заполнение ответа без аллокаций
    return resp, nil
}
```

### Под капотом (internals)
Задержку в Go создают: reflection, boxing в interface{}, выделение памяти, ожидание GC. Конкретные механизмы:
- **Escape analysis**: если переменная не убегает в кучу, она на стеке — ноль накладных расходов на GC. Проверяем `-gcflags="-m -l"`. Стек растёт динамически (копирование), поэтому избегаем больших стековых фреймов (>1KB).
- **System calls**: переход в kernel стоит ~100ns на современном железе. syscall.Read() блокирует горутину и P, пока netpoller не вернёт управление. Поэтому лучше использовать ring buffer (io_uring) с асинхронным I/O (но в Go пока через cgo/asm). Для сетевого I/O netpoller и так эффективен, главное — не делать синхронные syscall’ы.
- **Таймеры**: `time.After` создаёт таймер в куче; лучше `time.NewTimer` и переиспользование.
- **Приоритет планировщика**: если latency критична, можно использовать `runtime.LockOSThread` для привязки сетевого потока к ядру и обхода планировщика (жертвуя масштабируемостью).

### Типичные ошибки кандидатов
1. **Использование `encoding/json` в горячем пути**
   Он делает много аллокаций и работает через reflection. Даже easyjson не даст нулевых аллокаций. Правильно перейти на Protobuf + vtprotobuf или на ручную сериализацию в []byte.
2. **Забывают про время разогрева JIT/Go runtime**
   Go — AOT, но кэши CPU (cold cache) на старте могут увеличить первые запросы. Нужно прогревать кэши и инструкции перед запуском трафика.
3. **Синхронный вызов logging/metrics**
   Запись лога на диск или отправка метрик по сети синхронно в обработчике — прямая дорога к деградации. Используйте асинхронные ring buffer (zap с async core).
4. **Игнорирование NUMA-топологии**
   Обращения к памяти с удалённого NUMA-узла добавляют десятки наносекунд. Привязка процессов через `numactl` и `taskset` в купе с `GOMAXPROCS` может дать ощутимый прирост.

### Возможные дополнительные вопросы интервьюера
*Что делать, если оставшиеся 5ms — это GC паузы?*
Применить `GOGC=off` с ручным вызовом `runtime.GC()` в фоне, либо использовать `GOMEMLIMIT` для мягкого ограничения, чтобы GC запускался чаще, но паузы были короче. В крайнем случае — memory pooling и ручное управление памятью через арены (arena в Go 1.20, но осторожно).
*Как уменьшить latency до sub-millisecond?*
Исключить сетевой стек: использовать shared memory IPC между процессами, eBPF для обработки пакетов прямо в ядре с пробросом в userspace через perf buffer.
*Как измерить реальную задержку в production?*
Использовать high-resolution таймеры (`runtime.nanotime`), инструментировать код с помощью `otel` и выводить гистограммы с микросекундными бакетами.

## Как оптимизировать GC в огромном монолите?

### Краткий ответ
Цель — сократить GC паузы и общее время работы GC. Основные рычаги: уменьшить количество живых объектов в куче (value types, pooling), снизить аллокации (escape analysis), настроить параметры GOGC/GOMEMLIMIT, использовать арены для временных объектов, выделять память под крупные структуры через `make` с capacity.

### Развёрнутый ответ
В огромном монолите GC — частая причина хвостовых задержек. Системный подход:
1. **Профилирование**: `pprof` heap и allocs. Найти top-5 аллокаторов. Использовать `go tool trace` для визуализации GC циклов.
2. **Уменьшение аллокаций**: замена указателей на значения там, где структура маленькая (до 2-3 машинных слов). Переход от `[]byte` к массивам фиксированной длины для избегания побега в кучу. 
3. **Object pooling**: `sync.Pool` для часто используемых объектов (bytes.Buffer, структур запросов/ответов). Важно: пул привязан к P, поэтому не подходит для объектов, которые должны пересекать горутины.
4. **Настройка GC**: `GOGC=100` (по умолчанию) может приводить к большим паузам, если куча велика. Увеличение `GOGC` (например, до 200) снижает частоту GC, но увеличивает пиковую память. `GOMEMLIMIT` (1.19+) мягко запускает GC при приближении к лимиту, что эффективнее нативных параметров. В Kubernetes часто ставят `GOMEMLIMIT=0.8 * resource.limit.memory`.
5. **Арены (Go 1.20, экспериментальные; Go 1.22 улучшения)**: позволяют выделять группу объектов в contiguous памяти и освобождать разом, не затрагивая глобальный GC. Полезно для временных структур в обработчиках.
6. **Code patterns**: избегание `string([]byte)` в цикле (копия), использование `strings.Builder` с предварительным Grow.

Пример перехода от указателей к значениям:

```go
type Node struct {
    Value int
    Next  *Node // указатель -> в кучу, если Node убежал
}

// Если дерево неглубокое, можно:
type FlatTree struct {
    nodes [maxNodes]node // все на стеке/внутри структуры
}
```

### Под капотом (internals)
GC в Go — tricolor concurrent mark-sweep. Основные структуры: mark bits, work buffers (wbuf), GC assist.
- **Mark assist**: если горутина активно аллоцирует, а GC не успевает, она помогает маркировке, что добавляет задержку. Поэтому важно ограничивать аллокации.
- **Write barrier**: включён всегда (диктуется конкурентностью). Каждое присвоение указателя в куче добавляет несколько инструкций. При частых обновлениях (например, обход связного списка) overhead ощутим. Если перейти на value-типы и слайсы, write barrier не задействуется или уменьшается.
- **Heap spans**: аллокации < 32KB идут из thread-local cache (mcache), что быстро, но способствует фрагментации. Крупные объекты напрямую из mheap. Знание этого позволяет размер объекта подбирать так, чтобы избежать лишней работы GC по сканированию большого числа мелких объектов.
- **Pacer (gcController)**: вычисляет целевой размер кучи и соотношение времени GC к прикладному времени. Настройки GOGC/ GOMEMLIMIT меняют целевой множитель. Исходники `src/runtime/mgcpacer.go`.

### Типичные ошибки кандидатов
1. **Установка GOGC=off без плана**
   Отключение GC приведёт к неограниченному росту кучи и OOM убийце. Вместо этого используют мягкие лимиты и мониторинг.
2. **Неправильное использование sync.Pool: утечка памяти**
   Пул хранит объекты между GC, но если объект содержит ссылки на другие (например, слайс с capacity), может возникнуть эффект удерживания. Всегда обнуляйте объекты (`obj.Field = nil`) перед сбросом в пул.
3. **Игнорирование внутренних аллокаций стандартной библиотеки**
   `fmt.Sprintf`, `json.Marshal`, `http.ReadRequest` порождают много временных объектов. Заменяйте на zero-alloc аналоги (jsoniter с config, `strconv`).
4. **Массовое использование `time.Tick` и `context.WithTimeout`**
   Каждый таймер — куча объектов (heap allocated timer). В Go 1.14+ таймеры переиспользуются лучше, но всё равно надо следить. Лучше использовать `time.NewTicker` и останавливать явно.

### Возможные дополнительные вопросы интервьюера
*Как выбрать между GOGC и GOMEMLIMIT?*
GOGC задаёт процентный рост кучи между сборками, подходит для стабильных нагрузок. GOMEMLIMIT приоритетнее, если память ограничена контейнером: GC будет чаще, но предотвратит OOM.
*Что делать с фрагментацией кучи?*
Использовать арены или ручное размещение через cgo (нежелательно). В Go 1.22 появились экспериментальные возможности сжатия/дефрагментации через `debug.SetMemoryLimit` и новые аллокаторы. Пока основное — минимизировать разнообразие размеров объектов и переиспользовать.
*Как мониторить латентность GC?*
Метрики `go_gc_duration_seconds` по квантам, а также trace-события `runtime.GC` в `go tool trace`. Надо следить за STW-фазами (mark termination).

## Как дебажить прод (production debugging)?

### Краткий ответ
Отладка на проде без остановки сервиса строится на observability (логи, метрики, трейсы), динамическом изменении уровня логирования, conditional breakpoints через eBPF/DTrace, дампах профилей по требованию (pprof через HTTP), core dump анализ в extreme случаях. Никаких дебаггеров, останавливающих процесс.

### Развёрнутый ответ
Подходы делятся на пассивные и активные. Пассивные включают распределённую трассировку (OpenTelemetry), которая даёт полную картину запроса. Для активной отладки:
- **pprof endpoint**: включаем `import _ "net/http/pprof"` на отдельном порту с авторизацией; профили cpu, heap, goroutine, mutex, block. В прод-среде снимаем 30-секундный CPU профиль — выявляем горячие точки.
- **Динамическое логирование**: feature flags, позволяющие включить debug логи для конкретного пользователя (by userID или traceID) без перезагрузки; используем atomic-переключатели или etcd/consul live config.
- **eBPF-based инструментация (с Go 1.18+ с осторожностью)**: bpftrace скрипты для трассировки конкретных функций, аргументов, задержек без изменения кода. Необходимо наличие символов DWARF.
- **core dump**: при панике — `GOTRACEBACK=crash` + дамп ядра. Затем восстанавливаем состояние горутин через `delve core` или `gops`. Позволяет найти deadlock или коррапт данных.
- **gops агент**: позволяет интерактивно увидеть stack trace, статистику GC, текущие горутины (https://github.com/google/gops).
- **Отказоустойчивость при отладке**: Всегда делаем профилирование с осторожностью: CPU профилирование увеличивает задержку на ~5-10%, heap профиль может спровоцировать GC. Используем sampling.

Пример обработчика включения pprof по HTTP:

```go
import _ "net/http/pprof"

go func() {
    http.ListenAndServe(":6060", nil) // отдельный порт, не доступный публично
}()
```

### Под капотом (internals)
Go runtime предоставляет богатую инфраструктуру:
- **SIGPROF**: ppوف CPU профилирование использует сигнал SIGPROF, который срабатывает по тайм-ауту (100 Гц), при этом снимается стек вызовов текущей горутины (через `runtime.sigprof`). Это относительно безопасно.
- **Trace**: инструмент `runtime/trace` записывает события планировщика, системных вызовов, GC; может показать причину задержек (например, горутина ждёт сети или мьютекса). Включается на короткий промежуток.
- **Goroutine profiles**: снятие дампа всех горутин (`debug.Stack()`, `pprof.Lookup("goroutine")`) работает блокировками, но без остановки мира полностью — только остановка отдельных P для чтения стека (в Go 1.19+ значительно быстрее).
- **Lock**: block profile включает в себя замер времени ожидания мьютексов; требует сборки с `-race` не обязательно, но для точности нужен runtime установка параметров блокировки (`runtime.SetBlockProfileRate`).

### Типичные ошибки кандидатов
1. **Оставляют pprof endpoint открытым без защиты**
   Публичный доступ к `/debug/pprof/` позволяет вызвать `debug=2` и получить стек всех горутин с чувствительными данными. Использовать TLS + mutual auth или пробрасывать через kubectl port-forward.
2. **Снимают heap профиль без учёта GC**
   Из-за GC объекты могут быть уже собраны, искажая картину. Перед снятием нужно запустить `runtime.GC()` (через `curl ...?gc=1`).
3. **Запускают CPU профилирование на продолжительное время в высоконагруженной системе**
   Это замедляет все запросы. Ограничивать 10-15 секундами и делать это на канареечном инстансе.
4. **Предполагают, что отладка в дебаггере (delve) эквивалентна прод-поведению**
   Delve изменяет тайминги, может скрывать гонки. Анализируйте прод через пассивные инструменты.

### Возможные дополнительные вопросы интервьюера
*Как узнать из-за чего упал прод-сервис, если логи пустые?*
Использовать core dump и `delve core <binary> <core>`, затем `goroutines` и `stack` для осмотра. Если паника — `bt`; если OOM — в dmesg ядро напишет.
*Можно ли включить трассировку (trace) на лету без перекомпиляции?*
Да, через `GODEBUG=trace=1` перед запуском бинарника, либо через `http://.../debug/pprof/trace?seconds=5` активное снятие. Требует, чтобы HTTP-обработчик был.
*Как поймать утечку горутин?*
Периодический дамп `pprof.Lookup("goroutine")` и сравнение количества по стекам; смотреть на подозрительные блокировки (chan receive, mutex). Сигнализировать при росте.

## Как оценить емкость системы (capacity planning)?

### Краткий ответ
Оценка основывается на пиковой нагрузке (QPS), профиле запросов (resource per request), ограничениях ресурсов (CPU, память, сеть, I/O) и коэффициентах запаса. Используем линейное масштабирование как первое приближение, но обязательно проверяем насыщение (Knee point) через нагрузочное тестирование и модель очередей (Little’s law).

### Развёрнутый ответ
Этапы:
1. **Сбор метрик текущей системы**: Prometheus/Grafana — CPU usage, memory, goroutines, задержки, длинна очередей. Для Go-сервисов критичны `go_goroutines`, `go_memstats_alloc_bytes`.
2. **Анализ unit cost**: измеряем CPU/память на один типичный запрос (с учётом фоновых процессов). Для этого на изолированном инстансе подаём фиксированную нагрузку и замеряем потребление. Учитываем тип запроса (лёгкий/тяжёлый).
3. **Построение модели масштабирования**: если 1 CPU потребляет 10% на 100 QPS, то на 1 CPU лимит около 1000 QPS (при линейном росте). Но необходимо учесть нелинейность из-за contention (блокировки, GC). Поэтому строим кривую "throughput vs concurrency" и ищем точку перегиба.
4. **Планирование под пиковые события**: применяем коэффициент запаса 1.5x-2x и проверяем способность горизонтального масштабирования до нужного числа реплик. Автоскейлинг должен успеть развернуть поды до пика (с учётом времени запуска).
5. **Финансовая рамка**: переводим ресурсы в стоимость инстансов/подов, считаем общий бюджет.
6. **Go-специфика**: учитываем ограничения GOMAXPROCS, влияние GOMEMLIMIT. Например, установка GOMEMLIMIT слишком низко заставит GC работать чаще и снизит пропускную способность.

### Под капотом (internals)
В Go планирование ёмкости тесно связано с моделью потоков:
- **GOMAXPROCS**: каждый P может выполнять горутину одновременно. Эффективная ёмкость CPU-bound задач: `GOMAXPROCS * эффективность_использования`. Если горутины блокируются на I/O, планировщик добавляет дополнительные потоки (M), но ограничение по P сохраняется. Значит, для I/O-bound увеличение GOMAXPROCS сверх числа ядер может помочь или навредить (оверхед планировщика).
- **Сетевые лимиты**: файловые дескрипторы (ulimit), количество сокетов. Мониторим `process_open_fds`.
- **Пределы GC**: pacer GC стремится удерживать использование CPU GC в районе 25% от прикладного времени (по умолчанию). Поэтому ёмкость CPU для бизнес-логики примерно 75% от общего. Это надо закладывать в модель.

### Типичные ошибки кандидатов
1. **Экстраполяция по среднему значению**
   Использование среднего QPS и среднего CPU ведёт к недооценке ресурсов, так как пики и хвостовые задержки требуют гораздо больше. Всегда используйте процентили (p95, p99) потребления CPU/памяти.
2. **Забывают про burst-трафик**
   Автоскейлинг по CPU запаздывает; нужно предусматривать burst credits или overprovisioning с буфером.
3. **Не учитывают вертикальные лимиты языка**
   Например, `map` в Go при большом количестве элементов (миллионы) может вызвать большой GC overhead, и добавление CPU не поможет линейно. Стоит использовать специализированные структуры (off-heap БД).
4. **Игнорирование пропускной способности сети**
   При больших объёмах данных (стриминг) сетевая карта может стать узким местом раньше CPU. Считайте Mbps.

### Возможные дополнительные вопросы интервьюера
*Как смоделировать ёмкость нового сервиса без исторических данных?*
Создать прототип критического пути, провести нагрузочное тестирование с realistic трафиком (синтетические сценарии), измерить unit cost, экстраполировать с запасом. Добавить фактор неизвестности (+30%).
*Как учесть стоимость GC в планировании?*
Через GOGC и профили GC циклов определяем процент времени на GC. Затем из доступных CPU-ядер выделяем только долю (1 - GC_процент) для приложения. При планировании реплик считаем эффективное число CPU.
*Как спланировать ёмкость для мультитенантной системы?*
Расчитать изоляцию по ресурсам (на tenant), сделать шардирование с отдельными пулами, мониторить «noisy neighbour» и предусмотреть hard limits.

## Как проводить профилирование и оптимизацию в продакшен-среде без даунтайма?

### Краткий ответ
Профилирование в проде выполняется с помощью встроенных HTTP-ендпоинтов pprof, снятия профилей по требованию, eBPF-трассировки и динамического управления уровнем детализации (feature flags). Всё это не требует остановки сервиса, только кратковременное снижение производительности.

### Развёрнутый ответ
Процесс безопасного профилирования:
- **Инфраструктура**: сервис должен слушать отдельный порт или unix-сокет с авторизацией для pprof. Kubernetes проброс через `kubectl port-forward`.
- **Типы профилей и их влияние**: 
  - CPU профиль (30 сек): замедляет сервис ~5%, безопасно на канареечном экземпляре. 
  - Heap профиль: перед снятием вызвать GC через параметр `?gc=1`, чтобы видеть только живые объекты.
  - Goroutine/block/mutex профили: быстро, практически без нагрузки.
- **Continuous Profiling**: используйте агентов вроде Parca или Pyroscope, которые периодически снимают CPU профили (каждые 60 сек) и агрегируют. Это позволяет видеть изменения во времени.
- **Динамическая оптимизация без перезагрузки**: через HTTP-интерфейс менять значения переменных (например, размер кэша, пороги), используя `sync/atomic` и admin handlers.
- **Трассировка (execution trace)**: крайне полезна для поиска задержек, но генерирует большой объём данных; включается на 5-10 секунд, влияет умеренно.
- **Изоляция**: все профилировочные действия проводим на одном экземпляре (канареечном), либо используем rate limiting на профилирующие запросы.

Пример защищённого pprof:

```go
mux := http.NewServeMux()
mux.Handle("/debug/pprof/", http.HandlerFunc(pprof.Index))
// оборачиваем в basic auth или mTLS
```

### Под капотом (internals)
- **CPU профилирование (runtime/pprof)**: использует сигнал SIGPROF, который посылается таймером. Обработчик сигнала `sigtramp` в runtime фиксирует текущий PC/SP горутины. Риск: если сигнал пришёлся на критическую секцию (например, во время GC mark), профиль может исказиться, но это редкость.
- **Heap профилирование**: опирается на аллокатор (mcache/mcentral). `runtime.MemProfile` отмечает аллокации. Поскольку аллокатор lock-free в большинстве случаев, профилирование добавляет немного contention.
- **Execution trace (runtime/trace)**: записывает события в per-P буфер, буферы сливаются в общий ring buffer. В Go 1.22 улучшили производительность; трэйс не требует остановки мира.
- **GOEXPERIMENT=profinline** (с Go 1.22) позволяет профилировать инлайнинг-решения компилятора, что помогает в микрооптимизациях.

### Типичные ошибки кандидатов
1. **Снимают профиль на прод-сервисе в момент пиковой нагрузки**
   Замедление может вызвать таймауты у клиентов. Профилируйте в период низкой нагрузки или на отдельном инстансе.
2. **Неправильно интерпретируют heap профиль**
   Видят большое потребление памяти на `runtime.mallocgc` и думают, что это утечка, хотя это просто точка аллокации. Надо смотреть на inuse_space и inuse_objects после GC.
3. **Используют `pprof.StartCPUProfile` без установки runtime.SetCPUProfileRate**
   По умолчанию 100Hz; изменение перед стартом позволяет гибкость, но многие не знают.
4. **Забывают отключать профилировщик после использования**
   Оставляют CPU профилирование включённым, что перманентно снижает производительность.

### Возможные дополнительные вопросы интервьюера
*Как профилировать latency внутри отдельной функции в проде?*
Вставляем в код измерения (timer + atomic record) с feature flag. Или используем eBPF uprobe для замера времени выполнения функции без изменения кода.
*Можно ли профилировать без pprof, используя только логи?*
Можно агрегировать логи с временными метками, но точность низкая. Лучше использовать трассировку.
*Что такое continuous profiling и зачем он нужен?*
Позволяет видеть регрессии производительности во времени (после деплоя), находить периодические пики, анализировать долгосрочное ухудшение производительности.

## Как построить self-healing систему с автоматическим восстановлением?

### Краткий ответ
Self-healing основывается на 4-х столпах: обнаружение аномалий (health checks, метрики), автоматическая эскалация (рестарт, деградация, failover), переключение на резервные компоненты (circuit breaker, retry, fallback), восстановление состояния после сбоя (rehydration из лога/снапшотов). В Go реализуется с помощью паттернов отказоустойчивости и оркестрации (Kubernetes/собственные контроллеры).

### Развёрнутый ответ
Компоненты самовосстановления:
- **Health probes**: liveness (восстановление через перезапуск пода), readiness (исключение из балансировки), startup (долгий старт). В Go используем `net/http` обработчики, которые проверяют зависимости (DB, каналы).
- **Контроллеры репликации и автоскейлинга**: K8s deployment rollback при неудачном обновлении; HPA на основе кастомных метрик (Prometheus Adapter).
- **Логика приложения**:
  - Circuit Breaker: при превышении порога ошибок разрываем цепь, через некоторое время пробуем half-open.
  - Retry с exponential backoff и jitter, идемпотентность.
  - Graceful degradation: если сервис зависимость недоступна, возвращаем устаревшие данные из локального кэша.
  - Shedding load: при заполнении очереди отбрасываем запросы с низким приоритетом.
- **Автоматическое восстановление данных**: если обработка прервалась, перечитываем сообщение из журнала (WAL) или очереди (Kafka) и восстанавливаем состояние через Event Sourcing.
- **Chaos testing**: регулярно убиваем сервисы/сеть, чтобы убедиться в работоспособности self-healing.

Пример Circuit Breaker с использованием `gobreaker`:

```go
cb := gobreaker.NewCircuitBreaker(gobreaker.Settings{
    Name:        "db",
    MaxRequests: 5,
    Interval:    time.Minute,
    Timeout:     time.Second * 30,
    ReadyToTrip: func(counts gobreaker.Counts) bool {
        return counts.ConsecutiveFailures > 3
    },
})
result, err := cb.Execute(func() (interface{}, error) {
    return db.Query(query)
})
```

### Под капотом (internals)
В Go нет магии — всё строится на паттернах:
- **Горутины как легковесные потоки**: при панике в горутине без recover, весь процесс падает (по умолчанию). Чтобы сервис мог самовосстановиться после паники, необходимо использовать `recover` в корневой горутине каждого воркера, либо внешний оркестратор перезапускает контейнер.
- **Shutdown gracefully**: `http.Server.Shutdown` с контекстом; перед остановкой перестаём принимать новые запросы, ждём завершения текущих.
- **Health checkers**: можем реализовать проверку зависимостей с фоновой горутиной, результаты хранить в atomic переменной, и отдавать статус readiness. Это быстрее, чем проверка на каждый запрос.
- **Pooling соединений**: автоматическое переподключение при ошибке с помощью `database/sql` и `db.SetConnMaxLifetime`.

### Типичные ошибки кандидатов
1. **Бесконечные ретраи без backoff и jitter**
   Приводят к "thundering herd" — одновременные повторные запросы кладут сервис-зависимость. Всегда экспоненциальная задержка и случайный коэффициент.
2. **Отсутствие идемпотентности для ретраев**
   Если операцию можно выполнить дважды, повторная попытка может дублировать платёж. Генерируем idempotency key и проверяем его на стороне получателя.
3. **Зацикленные восстановления**
   Если crash вызван persistent data corruption, рестарт контейнера приведёт к бесконечному циклу. Нужен limit на перезапуски (K8s `backoffLimit`), после которого инцидент эскалируется.
4. **Использование только синхронных health checks**
   Зависимость может тормозить; проверка должна быть асинхронной с кэшированием результата, чтобы не замедлять readiness пробу.

### Возможные дополнительные вопросы интервьюера
*Как обработать частичный сбой внутри распределённой транзакции?*
Использовать Saga pattern: компенсирующие действия при откате, асинхронные сообщения.
*Как понять, что самовосстановление работает, но сервис уже упал?*
Мониторинг метрик уровня платформы (blackbox), внешние проверки (Pingdom), алертинг при снижении success rate ниже порога независимо от health эндпоинта.
*Как реализовать self-healing для stateful сервиса в Go?*
Реализовать Raft-консенсус с автоматическим failover лидера; в Go есть Hashicorp Raft.

## Как управлять асинхронным межсервисным взаимодействием и избегать "распределенного монолита"?

### Краткий ответ
Управление через чётко определённые контракты событий (Schema Registry), владение данными (Data Ownership), асинхронные шины (Kafka/NATS), идемпотентные обработчики и ограничения на цепочки синхронных вызовов. Распределённый монолит возникает, когда сервисы сильно связаны синхронными запросами или разделяют базы данных.

### Развёрнутый ответ
Ключевые практики:
1. **Событийно-ориентированная архитектура**: сервисы публикуют доменные события в топики, другие сервисы подписываются и обрабатывают асинхронно. Важна гарантия порядка в рамках одного ключа (ключ шардирования).
2. **Контракты**: используем Protobuf/Avro со Schema Registry для эволюции без breaking changes.
3. **Владение данными**: каждый микросервис владеет своим хранилищем, другие сервисы могут читать только через API или через read-only реплику (CQRS). Никаких прямых join’ов между БД разных сервисов.
4. **Борьба с синхронным спагетти**: задаём лимит на глубину синхронного стека (например, не более 2). Все остальные взаимодействия — через события.
5. **Транзакционные outbox**: для гарантированной публикации события атомарно с изменением состояния используем outbox-паттерн + Debezium/специальный воркер.
6. **Мониторинг**: распределённая трассировка (OpenTelemetry) связывает асинхронные цепочки по correlation id.

Пример публикации события с outbox в Go:

```go
func PlaceOrder(db *sql.DB, order Order) error {
    tx, _ := db.BeginTx(ctx, nil)
    // вставка заказа
    tx.Exec("INSERT INTO orders ...")
    // вставка в outbox
    tx.Exec("INSERT INTO outbox (event_type, payload) ...", "OrderPlaced", msg)
    tx.Commit()
}
// Фоновый процесс читает outbox и отправляет в Kafka.
```

### Под капотом (internals)
Go хорошо подходит для асинхронной обработки благодаря горутинам и каналам, но это не панацея:
- **Гарантии доставки**: Kafka consumer group в Go (segmentio/kafka-go или sarama) управляет смещениями. Ручной commit после успешной обработки и идемпотентность (проверка duplicate key) обеспечивает exactly-once семантику.
- **Контроль потока**: каналы с буфером ограничивают входящий трафик. При переполнении — backpressure через паузу consumer’а.
- **State machines**: для сложных рабочих процессов используем lightweight state machine на основе каналов или библиотек типа `stateless`. Надо не допустить «сверхразумного» сервиса-оркестратора, который знает всё о всех.
- **Идемпотентность**: храним множество обработанных идентификаторов (с TTL) в локальном bloom-фильтре или в Redis.

### Типичные ошибки кандидатов
1. **Оркестрация через синхронные вызовы без компенсаций**
   Сервис A дёргает B, B дёргает C синхронно — получаем хрупкую цепь. Правильно: A публикует событие, B и C реагируют независимо.
2. **Общая база данных как «быстрый способ обмена данными»**
   Мгновенно создаёт сильную связанность; изменение схемы одним сервисом ломает другие. Каждый сервис должен иметь свою БД.
3. **Игнорирование проблем порядка событий**
   Если бизнес-логика требует строгого порядка, но используется топик с несколькими партициями, порядок не гарантирован. Решение: маршрутизация по ключу (order_id) в одну партицию.
4. **Не обрабатывают дубликаты**
   Семантика at-least-once означает, что обработчик может быть вызван повторно. Дедупликация обязательна.

### Возможные дополнительные вопросы интервьюера
*Как обеспечить консистентность чтения собственных записей (read-your-writes) в асинхронной системе?*
Использовать механизм блокировки на стороне клиента: после записи ожидать события об успешной обработке, либо читать из primary БД сервиса-владельца (синхронный API).
*Что делать с запоздалыми событиями (late events)?*
Проверять временные метки, отбрасывать слишком старые или запускать пересчёт оконных агрегатов.
*Как избежать блокировки consumer’а при обработке одного медленного события?*
Разделять обработку на быструю часть и долгую (отправка в отдельную очередь для CPU-тяжёлых задач), не блокируя polling цикл.

## Как внедрить культуру performance engineering в команде?

### Краткий ответ
Культура перформанса — это непрерывный процесс, включающий метрики (SLI/SLO), автоматизированное нагрузочное тестирование в CI/CD, профилирование в прод-среде (continuous profiling), постмортемы по производительности и общие цели (error budget). Начинается с обучения и демонстрации ценности через конкретные кейсы.

### Развёрнутый ответ
Шаги построения:
1. **Определите SLO и error budget**: например, p95 latency < 200ms. Когда бюджет исчерпан, блокируем фиче-релизы, фокусируемся на перформансе.
2. **Внедрите инструменты observability**: распределённая трассировка, детальные гистограммы задержек, непрерывное профилирование (Pyroscope). Они должны быть доступны каждому разработчику.
3. **Добавьте в CI/CD performance gates**: запуск сценариев с ожидаемой нагрузкой и проверка, что latency/profiling метрики не ухудшились против baseline.
4. **Проводите "Performance Review" встреч**: аналогично code review, но для архитектурных решений, влияющих на производительность.
5. **Обучайте команду**: внутренние воркшопы по профайлингу в Go, GC-тюнингу, паттернам эффективного кода (sync.Pool, zero allocation). Покажите на примере, как оптимизация сократила счёт за облако.
6. **Геймификация и признание**: соревнования "кто снизит latency сервиса", доска почёта лучших оптимизаторов.
7. **Лидерство**: Staff/Principal инженеры должны инициировать дискуссии и устанавливать стандарты (coding guidelines for performance).

Пример добавления performance gate в GitHub Actions:

```yaml
- name: Run load test
  run: go test -run=^$ -bench=. -benchtime=10s ./...
- name: Compare with baseline
  run: benchstat baseline.txt current.txt
```

### Под капотом (internals)
С точки зрения Go, внедрение культуры поддерживается экосистемой:
- **Benchmark в стандартной библиотеке**: `testing.B` позволяет получить воспроизводимые замеры с подсчётом аллокаций. Используем `b.ReportAllocs()`.
- **Perf-росты через компилятор**: PGO (Profile-Guided Optimization) в Go 1.21+ позволяет собирать профиль из продакшена и перекомпилировать сервис с улучшением производительности. Это отличный способ объединить культуру перформанса с CI/CD: профили автоматически подаются в компиляцию нового билда.
- **Метрики runtime**: экспорт `go_*` метрик в Prometheus; визуализация GC пауз, числа горутин — первый шаг к прозрачности.

### Типичные ошибки кандидатов
1. **Оптимизация без предварительного замера (premature optimization)**
   Без бенчмарков и профилировщика пытаются «улучшить» код, часто делая его сложнее без выигрыша. Культура должна требовать data-driven подход: профиль -> гипотеза -> эксперимент.
2. **Фокус только на CPU, забывая о памяти и GC**
   В Go важно метрики `alloc/op` и `allocs/op`. Высокая аллокация порождает GC нагрузку, которая съедает CPU.
3. **Отсутствие performance SLO для внутренних сервисов**
   Если нет целевых показателей для библиотек или общих модулей, каждый сервис будет иметь разные уровни — это приводит к непредсказуемости. Общий стандарт: максимальное количество аллокаций на вызов.
4. **Сопротивление изменениям из-за отсутствия видимых стимулов**
   Инженеры не видят связи между оптимизацией и бизнес-результатом. Решение: показывать стоимость ресурсов в деньгах («этот сервис стоит $10k/мес, снизив CPU на 20%, мы экономим $2k»).

### Возможные дополнительные вопросы интервьюера
*Как убедить бизнес потратить две недели на оптимизацию вместо новых фич?*
Привести данные: медленный UX уменьшает конверсию, замедление Amazon на 100ms стоило 1% продаж. Показать ROI.
*Как масштабировать культуру на десятки команд?*
Создать центральную команду performance advocates (подобно SRE), которая консультирует, разрабатывает инструменты и проводит тренинги.
*Как предотвратить регресс производительности при быстром росте кодовой базы?*
Автоматизированные бенчмарки в CI на каждый PR, дашборд исторических трендов производительности, лимит на регресс (например, не более 5%).

## Как построить "канареечные" деплои и систему автоматического отката?

### Краткий ответ
Канареечное развёртывание — это постепенное направление доли трафика на новую версию с автоматическим сравнением метрик (ошибки, задержки, насыщение) с baseline и откатом при отклонении. Реализуется на уровне ingress/сервис-меша (Envoy, Istio) с правилами маршрутизации и контроллером принятия решений.

### Развёрнутый ответ
Компоненты системы:
- **Ingress/Service Mesh**: поддерживает взвешенную маршрутизацию (напр., 5% -> canary, 95% -> stable). В Istio это DestinationRule с subset.
- **Контроллер канареечного анализа (Flagger, Argo Rollouts)**: автоматически увеличивает долю трафика, считывая метрики из Prometheus/Datadog, выполняет проверки.
- **Метрики для сравнения**: error rate, p95/p99 latency, saturation (CPU, goroutines). Должны быть идентифицированы до деплоя как baseline.
- **Интеграция с Go-сервисом**: сервис должен экспортировать метрики, поддерживать health/ready эндпоинты и корректно обрабатывать shutdown (graceful), чтобы откат был незаметен.
- **Автоматический откат**: если метрики выходят за порог (статистический тест Манна-Уитни), откат происходит уменьшением веса до 0. В экстремальных случаях — инициируется rollback deployment в Kubernetes.
- **Feature Flags**: могут служить дополнением для условного включения нового кода без развёртывания.

Пример конфигурации Flagger:

```yaml
canary:
  service: myservice
  analysis:
    interval: 30s
    threshold: 5
    maxWeight: 50
    stepWeight: 10
    metrics:
    - name: request-success-rate
      thresholdRange:
        min: 99
    - name: request-duration
      thresholdRange:
        max: 200
```

### Под капотом (internals)
- **Go shutdown hook**: `http.Server.RegisterOnShutdown` выполняет действия перед остановкой, чтобы не терять in-flight запросы. Важно, чтобы readiness проба начинала возвращать false до shutdown, чтобы балансировщик перестал слать трафик.
- **Метрики**: с помощью `expvar` или Prometheus клиента. Используем `promhttp` для экспорта. Для точного сравнения нужны гистограммы.
- **Flagger использует Prometheus запросы**: важно, чтобы метрики канареечного пода были отличимы по pod label. Тогда собираем агрегаты.
- **Проблема холодного старта**: при старте пода может быть высокий latency из-за JIT (отсутствует) и прогрева кэша процессора — это ложно спровоцирует откат. Решение: давать «прогревочное окно» без анализа.

### Типичные ошибки кандидатов
1. **Анализ метрик на слишком коротком окне**
   Случайный всплеск задержки на одном поде вызывает ложный откат. Нужно использовать статистические тесты и окно не менее 2-3 минут.
2. **Игнорирование идемпотентности при маршрутизации**
   Если пользователь во время сессии попадает на разные версии, и API не обратно совместим, он получит ошибки. Нужно привязывать сессию к версии (sticky session) или гарантировать backward compatibility.
3. **Не обрабатывают graceful shutdown для долгих соединений (WebSocket)**
   Просто `Shutdown(context.Timeout)` оборвёт соединения. Надо предупредить клиента о переподключении через close code.
4. **Не тестируют откат в CI**
   Система отката может не сработать из-за неправильных RBAC или сетевых политик. Проверять дрилл-тестами.

### Возможные дополнительные вопросы интервьюера
*Как минимизировать impact при откате stateful-сервиса?*
Использовать шаблон «State Snapshot»: перед включением канарейки делать снепшот состояния, в случае отката восстанавливать. Либо канарейка должна работать с отдельным шардом данных.
*Как автоматически определить baseline метрик?*
Можно усреднить последние 5 минут стабильной версии с доверительным интервалом. Flagger делает это автоматически.
*Что делать, если метрики не успевают отреагировать из-за низкого трафика?*
Продлить интервал анализа или использовать искусственную генерацию трафика (shadow traffic).

## Как организовать "Zero Downtime Migrations" для критичных сервисов?

### Краткий ответ
Миграция без даунтайма требует совместимости схем на время перехода, phased rollout, обратной совместимости API, использования промежуточных состояний (двойная запись, чтение из новой БД с fallback), и флагов для быстрого отката. Инфраструктура и клиенты согласованно переключаются.

### Развёрнутый ответ
Процесс миграции:
1. **Совместимость данных**: расширяем схему — только добавляем nullable столбцы/новая таблица, не удаляем старые. Код должен корректно обрабатывать отсутствие новых полей.
2. **Двойная запись (dual write)**: пишем и в старую БД, и в новую (асинхронно, с гарантией записи в старую как primary). Используем транзакцию с outbox для согласованности.
3. **Обработка чтений**: сервис читает из новой БД, если данные не найдены — fallback на старую (или наоборот). Постепенно переносим трафик чтения.
4. **Сверка и очистка**: запускаем фоновый процесс сверки данных; переключаем все чтения на новую БД; отключаем запись в старую; удаляем старый код и схему.
5. **API версионирование**: если меняется контракт, публикуем новую версию API, поддерживая старую в течение депрекационного периода.
6. **Координация с клиентами**: SDK/библиотеки с поддержкой нескольких endpoint’ов и фолбеком.

Пример двойной записи с идемпотентностью:

```go
func storeOrder(order *Order) error {
    // primary DB commit
    if err := primaryDB.Insert(order); err != nil {
        return err
    }
    // async write to new DB with retry
    go func() {
        _ = newDB.Upsert(order)
    }()
    return nil
}
```

### Под капотом (internals)
- **Миграции схемы в Go-сервисах**: при старте приложения используется `migrate` (golang-migrate) с транзакционными изменениями. Для zero-downtime нужно применять расширение схемы до деплоя кода, который использует новую схему. Kubernetes rolling update не поможет, если схема несовместима.
- **Балансировщики нагрузки и graceful shutdown**: во время rolling update старые поды завершаются с ожиданием завершения запросов. Это позволяет избегать ошибок при обработке изменённых схем.
- **Использование интерфейсов**: абстрагируем хранение за интерфейсом `Repository`, что позволяет поэтапно подменять реализацию. Старая и новая реализации работают параллельно через композитный репозиторий с логикой роутинга.

### Типичные ошибки кандидатов
1. **Удаление старого столбца на первом шаге миграции**
   Сразу ломает читающий код старой версии. Правильная последовательность: добавить -> деплой кода, использующего новый столбец -> удалить старый после полного перехода.
2. **Отсутствие тестирования отката**
   План отката должен быть проверен: если что-то пошло не так, как быстро вернуться к старой БД/API без потерь данных.
3. **Двойная запись без идемпотентности**
   При сбое и повторе старой записи в новой БД может возникнуть дубликат. Используем `INSERT ... ON CONFLICT DO NOTHING`.
4. **Игнорирование timeouts при миграции больших таблиц**
   `ALTER TABLE` может заблокировать таблицу; используем pt-online-schema-change или миграции через shadow table с триггерами, либо делаем это в окно низкой нагрузки, поэтапно.

### Возможные дополнительные вопросы интервьюера
*Как мигрировать данные с изменением структуры (ETL)?*
Запустить двойную запись в старой и новой схеме, затем асинхронно преобразовывать существующие данные с помощью batch-процессов, с контролем прогресса.
*Что делать с очередями сообщений во время миграции?*
Если формат сообщений меняется, сначала добавляем новое поле опционально, постепенно переводя producers, потом consumers. Можно использовать schema registry с поддержкой эволюции.
*Как обеспечить отказоустойчивость миграции distributed транзакций?*
Использовать SAGA или 2PC с компенсацией, тщательно тестировать.

## Как спроектировать систему, устойчивую к региональным сбоям (Disaster Recovery)?

### Краткий ответ
Система должна работать в multi-region active-active или active-passive конфигурации с репликацией данных, автоматическим переключением DNS/балансировщика, отказоустойчивостью на уровне приложения (retry на другой регион, circuit breaker) и регулярным тестированием восстановления. Целевое RTO/RPO определяет архитектуру.

### Развёрнутый ответ
Ключевые элементы:
- **Multi-region deployment**: каждый регион — полностью независимый стек (K8s кластеры, базы данных). Используется инфраструктура как код (Terraform) для идентичности.
- **Репликация данных**: для stateful — cross-region replication (Cassandra, CockroachDB, YugabyteDB). Для асинхронной — Kafka MirrorMaker, NATS leaf nodes. RPO зависит от задержки репликации.
- **Маршрутизация трафика**: GeoDNS (Route53, Cloudflare) с health check региона. В случае сбоя — переключение на здоровый. Для актив-актив: пользователи маршрутизируются к ближайшему региону, сессии sticky (но это сложно).
- **Статическая устойчивость (static stability)**: система должна работать в деградированном режиме без зависимости от внешних сервисов; локальные кэши, fallback конфигурации.
- **Chaos Engineering**: регулярное отключение целого региона (GameDays) для проверки DR.
- **Go-специфика**: HTTP-клиент должен поддерживать retry с учётом переключения endpoint’ов на другой регион через резолвер с несколькими адресами. Используем `gRPC` с клиентским балансировщиком и fail-fast при ошибках.

Пример клиента с многорегиональной поддержкой:

```go
resolver.SetDefaultScheme("dns")
conn, _ := grpc.Dial("service.example.com:443", grpc.WithDefaultServiceConfig(`{"loadBalancingPolicy":"round_robin"}`))
// DNS резолвит A записи разных регионов, gRPC балансирует.
```

### Под капотом (internals)
Go net.Resolver позволяет кастомное разрешение имён. Можно при ошибке пробовать другой адрес. `gRPC` health checking автоматически исключает недоступные поды.
- **Keepalive и connection draining**: важно быстро обнаружить отказ. gRPC параметры `GRPC_ARG_KEEPALIVE_TIME_MS` и `KEEPALIVE_TIMEOUT` должны быть агрессивными (<10s).
- **Circuit breaker per region**: реализация на уровне `gobreaker` или `sony/gobreaker` с разбивкой по регионам, чтобы при отказе region1 запросы сразу отправлялись в region2 без попыток.
- **Распределённая блокировка**: если требуется глобальная координация, используем консенсусный алгоритм с большинством регионов (невозможно при только двух: лучше 3).

### Типичные ошибки кандидатов
1. **Бесконечные ретраи без учета регионального переключения**
   Если клиент ретраит на тот же регион, он не восстанавливается. Нужен механизм смены адресата после нескольких ошибок.
2. **Использование синхронной репликации БД между регионами**
   Добавляет большие задержки; лучше асинхронная с eventual consistency, а для критических данных — multi-master с конфликтным разрешением (CRDT).
3. **Отсутствие backoff при массовом переключении**
   Когда весь трафик резко уходит в уцелевший регион, его может затопить. Нужен controlled ramp-up и shedding.
4. **Игнорирование проверки данных после восстановления**
   Просто переключить трафик недостаточно; нужно убедиться, что данные консистентны (например, проверка чексуммами).

### Возможные дополнительные вопросы интервьюера
*Как выбрать между active-active и active-passive?*
Active-active обеспечивает низкую задержку для пользователей повсюду, но сложнее в обеспечении консистентности. Active-passive проще, но RTO выше (минуты на активацию). Для финансовых систем часто active-passive с горячим резервом.
*Как обрабатывать двойные записи в multi-master?*
Конфликты разрешаются через LWW (Last Write Wins) или CRDT; в идеале избегать конфликтов, направляя запросы пользователя всегда в один регион (session affinity).
*Как тестировать DR, не влияя на пользователей?*
Запустить параллельную копию системы (shadow environment) и переключить туда синтетический трафик, убивая регионы.

## Какие метрики и SLO выбрать для комплексного мониторинга бизнес-логики?

### Краткий ответ
Четыре золотых сигнала (Latency, Traffic, Errors, Saturation) плюс бизнес-ориентированные SLI (например, conversion rate, payment success). SLO определяются для критических пользовательских путей (user journeys) с учётом процентиля и окон измерения.

### Развёрнутый ответ
1. **латентность**: гистограммы с разбивкой по кодам возврата и эндпоинтам, p95/p99 за 5-минутное окно. Для Go используем `go-metrics` или Prometheus.
2. **Трафик**: QPS на каждый сервис, сегментированный по типам запросов.
3. **Ошибки**: доля запросов с 5xx или таймаутами. Важно исключить из ошибок штатные 4xx (например, 404 на несуществующий ресурс, если это ожидаемо).
4. **Насыщение**: utilisation CPU, memory, goroutines, длина очереди, сетевые лимиты.
5. **Бизнес SLI**: например, "успешная оплата" — количество успешных транзакций / общее число попыток. Эти метрики напрямую связаны с доходами, их мониторинг критичен.
- **SLO**: устанавливаем для каждого SLI: p95 latency < 300ms, error rate < 0.5% и т.д. Error budget позволяет балансировать стабильность и скорость разработки.
- **Инструментация в Go**: middleware для HTTP/gRPC автоматически записывает задержки и коды; кастомные метрики через `prometheus` client.

Пример middleware для сбора RED метрик:

```go
var reqDuration = prometheus.NewHistogramVec(prometheus.HistogramOpts{...}, []string{"method", "path", "status"})
func MetricsMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        rw := &responseWriter{ResponseWriter: w}
        next.ServeHTTP(rw, r)
        reqDuration.WithLabelValues(r.Method, r.URL.Path, strconv.Itoa(rw.status)).Observe(time.Since(start).Seconds())
    })
}
```

### Под капотом (internals)
- **Go runtime метрики экспортируются автоматически через `promhttp`**: включают GC, память, горутины. Важно отслеживать `go_goroutines` — всплеск может говорить об утечке.
- **Гистограммы и bucketing**: для правильного расчёта процентилей надо настроить бакеты под свои ожидаемые значения. Go клиент Prometheus позволяет задать кастомные бакеты.
- **Overhead**: инкремент счётчика или гистограммы через `sync/atomic` очень дёшев, но лейблы высокой кардинальности могут создать нагрузку. Используем их только для агрегации.

### Типичные ошибки кандидатов
1. **Слишком много SLO, потеря фокуса**
   Отслеживать всё подряд невозможно. Нужно выбрать 2-3 ключевых user journeys (например, оформление заказа) и сконцентрироваться на них.
2. **Смешивание 4xx и 5xx ошибок в одном SLI**
   Ошибки клиента не должны расходовать error budget, потому что сервис не может их контролировать. Исключайте 400, 401, 404 из бюджетных метрик.
3. **Использование среднего вместо процентилей**
   Средняя задержка скрывает хвостовые выбросы. Только процентили гарантируют качество для большинства.
4. **Не привязывают SLO к бизнес-целям**
   SLO "latency < 100ms" может быть избыточен и дорог, если пользователи не ощущают разницы. Определяйте пороги на основе пользовательских ожиданий и конверсии.

### Возможные дополнительные вопросы интервьюера
*Как определить SLO для нового сервиса?*
Наблюдать за метриками в staging/проду с реалистичной нагрузкой, взять p95 + запас 20%. Со временем ужесточить на основе обратной связи.
*Что такое error budget и как его считать?*
Error budget = 1 – target. Например, 99.9% uptime даёт бюджет 0.1% отказов. За месяц это 43 минуты. Когда бюджет исчерпан, фиче-фриз.
*Как обрабатывать длинные хвосты, вызванные GC?*
Настроить алертинг на увеличение GC пауз и добавить их в SLO (латентность с учётом GC). При превышении бюджета — фокус на оптимизацию GC.

## Как оценить стоимость и окупаемость (ROI) архитектурных изменений?

### Краткий ответ
ROI рассчитывается как разница между затратами (инженерные часы, инфраструктура) и полученными выгодами (снижение стоимости ресурсов, увеличение дохода, снижение рисков). Для архитектурных изменений необходимо построить модель «как есть» и «как будет», оценить количественно ключевые метрики и учесть стоимость задержки (cost of delay).

### Развёрнутый ответ
Методология:
1. **Идентифицировать драйверы изменений**: снижение хостинг-затрат (на 20%), повышение пропускной способности (нужно для Black Friday), сокращение time-to-market.
2. **Оценить затраты**: человеко-часы * ставка, стоимость новых сервисов/лицензий, время на миграцию и тестирование. Учитываем риски (непредвиденные сложности).
3. **Измерить выгоды**: 
   - Прямые: экономия на инфраструктуре (например, переход с управляемой БД на self-hosted с арендой памяти), снижение CPU/памяти за счёт оптимизации Go.
   - Косвенные: увеличение конверсии от снижения latency (были исследования: 100ms = +1% продаж), уменьшение оттока.
4. **Посчитать денежный поток и NPV**: если экономия ежегодная, NPV = Sum(Savings / (1+r)^t). Обычно горизонт 2-3 года.
5. **Оценка через "cost of delay"**: если мы не сделаем изменение сейчас, сколько мы потеряем за квартал в конкурентной борьбе.
6. **Пример Go**: переход на Go 1.22 с PGO может дать 5-10% прирост CPU бесплатно, затраты — только тестирование и деплой, ROI огромен.

Формула простого ROI: `ROI = (Выгода - Затраты) / Затраты * 100%`.

### Под капотом (internals)
Здесь скорее экономика инженерии, но можно упомянуть внутренние инструменты:
- **`benchstat`**: для сравнения производительности до и после оптимизации, переводит CPU время в деньги через стоимость ядра/час.
- **Профилирование затрат в облаке**: Go-сервисы метриками CPU/memory можно напрямую сопоставить с стоимостью Kubernetes нод; следовательно, снижение CPU на 100m на под даёт экономию на нодах.
- **Моделирование**: можно написать симулятор на Go, который рассчитывает потребление ресурсов при изменении архитектуры.

### Типичные ошибки кандидатов
1. **Игнорирование стоимости внедрения и поддержки**
   Новая архитектура может требовать новых навыков, найма, переписывания тулов. Эти затраты надо честно посчитать.
2. **Оценка только снижения инфраструктурных затрат без учёта доходов**
   Иногда главная выгода — скорость доставки фич, которая приносит больше денег, чем экономия на серверах.
3. **Недооценка "soft" выгод**
   Улучшение поддерживаемости снижает баги в проде, что уменьшает потери из-за инцидентов. Это можно оценить через стоимость инцидента.
4. **Сравнение с идеальным будущим без учёта переходного периода**
   Во время миграции система может потреблять больше ресурсов (дуальная работа), что на время ухудшит показатели.

### Возможные дополнительные вопросы интервьюера
*Как презентовать ROI руководству, которое не понимает технических деталей?*
Переведи в язык бизнеса: "Этот проект сэкономит $X/мес, что составляет Y% от нашего облачного бюджета, и окупится через Z месяцев".
*Как учесть риск технологической неудачи?*
Вероятность умножить на стоимость провала, вычесть из ожидаемой выгоды. Если риск высок, предложить PoC для снижения неопределённости.
*Что делать, если ROI отрицательный, но изменение необходимо по compliance?*
Compliance риск потенциальных штрафов и потери репутации оценивается как выгода избежания этих штрафов.

## Как спроектировать "rate limiting" для всех сервисов экосистемы?

### Краткий ответ
Rate limiting проектируется как многоуровневая система: глобальный rate limit на уровне gateway (по tenant/API ключу), локальный per-service rate limit для защиты от внутреннего всплеска, и алгоритмический выбор (token bucket, sliding window). Используем распределённый счётчик (Redis/Memcached) с локальным кэшом, а также децентрализованные алгоритмы типа адаптивного ограничения на основе задержек.

### Развёрнутый ответ
Архитектура:
- **API Gateway**: первый эшелон, делает rate limit по ключу клиента с помощью алгоритма скользящего окна или обобщённого лимита. Для высокой пропускной способности применяем фиксированное окно с локальными счётчиками и синхронизацией.
- **Сервисный уровень**: каждый сервис реализует rate limiter для своих эндпоинтов, используя middleware. Может использовать локальный алгоритм с выделенной памятью без внешних зависимостей (если лимит глобальный нельзя гарантировать, то локально ограничиваем насыщение).
- **Алгоритмы**: 
  - Token Bucket: допускает burst, подходит для пропускной способности.
  - Sliding Window Log/Counters: точнее, но требует больше памяти.
  - Leaky Bucket: сглаживает, но отбрасывает burst.
  - Adaptive Limiter: как в Netflix, на основе p95 latency и concurrency, динамически отклоняет запросы при перегрузке.
- **Хранение состояния**: Redis с Lua-скриптом для атомарного обновления счётчика окна. Для уменьшения задержки: локальный bucket с асинхронной синхронизацией (RAF).
- **Заголовки**: RateLimit-Limit, RateLimit-Remaining, Retry-After для клиентов.
- **Go-реализация**: `golang.org/x/time/rate` для локального; для распределённого — кастомная обёртка над Redis.

Пример middleware с x/time/rate:

```go
limiter := rate.NewLimiter(rate.Limit(100), 50) // 100 RPS, burst 50
func Middleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if !limiter.Allow() {
            http.Error(w, "Too Many Requests", http.StatusTooManyRequests)
            return
        }
        next.ServeHTTP(w, r)
    })
}
```

### Под капотом (internals)
- `rate.Limiter` использует под капотом `time.Timer` и атомарные операции, что очень эффективно. Планировщик таймеров в Go 1.14+ использует хеширование по P, поэтому при большом количестве limiter’ов (на каждого пользователя) это может стать дорогим. Тогда лучше самодельный sliding window с `sync.Map`.
- **Redis счётчик**: Lua скрипт `INCR` + `EXPIRE` для фиксированного окна. Для точности используем упорядоченные множества (sorted sets) для sliding window, но это дороже.
- **Backpressure через context**: `golang.org/x/net/context/ctxhttp` и transport с ограничением числа соединений.

### Типичные ошибки кандидатов
1. **Только глобальный, распределённый rate limit без локальной защиты**
   Сеть до Redis может замедлить или отказать, тогда сервис останется без защиты. Всегда должен быть локальный предохранитель.
2. **Фиксированное окно без учёта burst на границе окна**
   В начале окна может пройти двойной burst. Используйте перекрывающиеся окна или token bucket.
3. **Хранение состояния rate limit на уровне пода без репликации**
   Если под упал, состояние лимитов теряется. Для stateless нужно внешнее хранилище.
4. **Игнорирование "Retry-After" на клиентской стороне**
   Если клиент не знает, когда можно повторить, он будет слать повторные запросы, усугубляя нагрузку.

### Возможные дополнительные вопросы интервьюера
*Как реализовать rate limit с разной стоимостью запросов?*
Использовать весовые токены: один запрос может стоить N токенов (см. следующий вопрос).
*Как бороться с обходом лимита через распределение по множеству мелких клиентов?*
Ввести иерархический лимит на уровне tenant/account, агрегирующий лимиты всех ключей.
*Как обеспечить согласованность лимитов при multi-region?*
Либо глобальный Redis с синхронной репликацией, либо CRDT счётчики, либо деление общего лимита между регионами статически с координацией.

## Как внедрить модель безопасности "BeyondCorp" или "Zero Trust" в инфраструктуру, написанную на Go?

### Краткий ответ
Zero Trust означает отказ от доверия по расположению в сети; каждый запрос аутентифицируется и авторизуется. Реализация через mutual TLS (mTLS) между всеми сервисами, проверку JWT/токенов на каждом входящем запросе (даже внутри кластера), политики на основе атрибутов (ABAC) и контекста, централизованное управление доступом (IAM).

### Развёрнутый ответ
Ключевые компоненты:
- **Идентификация сервисов**: каждый Go-сервис получает идентификатор (SPIFFE ID) через X.509 сертификаты, выдаваемые платформой (cert-manager, Vault, Istio).
- **mTLS везде**: все межсервисные взаимодействия шифруются и аутентифицируются. Настраиваем `tls.Config` с `ClientAuth: tls.RequireAndVerifyClientCert`, загружаем сертификаты из файлов, обновляемых без перезагрузки (atomic fsnotify).
- **JWT/OAuth2 для внешних запросов**: проверяем подпись и claims через JWKS endpoint, извлекаем user/roles. Middleware выполняет авторизацию на основе RBAC.
- **Policy engine**: интеграция с OPA (Open Policy Agent) или встроенная библиотека `go-ladon`. Политика проверяется на каждый API call.
- **Сетевые политики**: Kubernetes NetworkPolicies ограничивают egress/ingress на уровне IP, добавляя дополнительный слой (defense in depth).
- **Аудит**: все запросы логируются с атрибутами безопасности для SIEM.

Пример TLS конфигурации для сервера:

```go
cert, _ := tls.LoadX509KeyPair("svc.crt", "svc.key")
clientCAs, _ := x509.SystemCertPool() // или собственный CA
cfg := &tls.Config{
    Certificates: []tls.Certificate{cert},
    ClientAuth:   tls.RequireAndVerifyClientCert,
    ClientCAs:    clientCAs,
}
server := &http.Server{TLSConfig: cfg}
```

### Под капотом (internals)
- **crypto/tls**: в Go 1.22 улучшена производительность TLS 1.3, поддерживается 0-RTT. Для high-performance нужно управлять сессиями и переиспользовать `tls.Config` с `SessionTicketKeys`.
- **Автоматическая ротация сертификатов**: через `fsnotify` или `cert-manager` CSI driver, обновляем `tls.Config` атомарно через `GetCertificate` callback, который перезагружает сертификат при изменении файла.
- **Проверка JWT**: библиотека `golang-jwt/jwt` с кэшированием JWKS. Избегаем аллокаций при парсинге через `jwt.Parser` без замыканий.
- **SPIFFE/SPIRE**: агент SPIRE выдаёт сертификаты на основе attestation узла. Go сервис получает их через Unix Domain Socket API и использует для gRPC.

### Типичные ошибки кандидатов
1. **Доверие к внутреннему трафику (No TLS внутри кластера)**
   Компрометация одного пода позволяет атакующему перехватывать трафик. В Zero Trust каждый хоп защищён.
2. **Проверка только подписи JWT без проверки issuer или audience**
   Можно подставить токен, выпущенный для другого сервиса. Всегда проверяем `iss`, `aud`, срок действия.
3. **Отсутствие rate limiting на аутентификацию**
   Злоумышленник может исчерпать ресурсы сервера проверкой токенов. Rate limit на эндпоинты логина и валидации.
4. **Хранение секретов в коде или конфигах без шифрования**
   Использовать Vault, Secrets Store CSI Driver. В Go используем `os.Getenv` или библиотеки для vault.

### Возможные дополнительные вопросы интервьюера
*Как внедрить Zero Trust без переписывания всех сервисов?*
Использовать sidecar proxy (Envoy) с automatic mTLS, offloading’ом аутентификации и авторизации в mesh.
*Как обрабатывать авторизацию с учётом контекста устройства пользователя?*
Передавать контекст в claims токена (device posture) через аутентификационный прокси, затем в Go проверять через OPA.
*Как обновлять политики безопасности без перезапуска?*
OPA agent встраивается в Go приложение через библиотеку `opa/rego`, политики загружаются из внешнего бандла периодически.

## Как организовать "feature lifecycle" от идеи до продакшена и последующего вывода из эксплуатации?

### Краткий ответ
Жизненный цикл фичи включает фазы: предложение (RFC) → эксперимент (feature flag) → разработка → тестирование → канареечный деплой → общий rollout → мониторинг успеха → депрекация и удаление. Ключевой инструмент — система feature flags, позволяющая изолированно включать/отключать функциональность.

### Развёрнутый ответ
Процесс:
- **Идея и RFC**: шаблон с описанием бизнес-цели, метрик успеха, design doc (включая архитектурные решения в Go, влияние на перформанс).
- **Реализация за feature flag**: флаг в конфигурационной системе (LaunchDarkly, встроенный конфиг с динамическим обновлением). Код оборачивается в `if featureFlag.IsEnabled(ctx, "new_feature")`. Это позволяет мержить в main раньше, не включая на проде.
- **Тестирование**: unit/integration тесты с разными значениями флага; нагрузочное тестирование под флагом.
- **Канареечный деплой и эксперимент**: сначала включается на 1% пользователей (A/B тест), сравниваются метрики успеха (конверсия, latency, ошибки).
- **Полный rollout**: постепенное увеличение до 100%. Флаг остаётся какое-то время для аварийного отключения.
- **Оценка и зачистка**: после подтверждения стабильности и достижения целей, флаг удаляется из кода (death of a flag). Иначе технический долг.
- **Депрекация**: если фича не прижилась, выводится из эксплуатации с уведомлением пользователей перед окончательным удалением.

Пример feature flag:

```go
if flags.Bool("new_algo", false) {
    return newAlgo(input)
}
return oldAlgo(input)
```

### Под капотом (internals)
- **Feature flag библиотеки**: могут использовать `context.Context` для передачи значений на протяжении запроса. Важно, чтобы проверка флага была быстрой (кеширование в памяти). Реализация на `sync.Map` и atomic-обновление при изменении конфига.
- **Безопасность типов**: использование кодогенерации (`go generate`) для строгой типизации флагов, чтобы избежать строковых ошибок.
- **Метрики**: для каждого флага экспортируем `feature_flag_evaluation_total` с лейблом имени флага и результатом. Это помогает отслеживать, кто использует флаг.

### Типичные ошибки кандидатов
1. **Отсутствие процесса удаления старых флагов**
   Флаги накапливаются, усложняя код и создавая непреднамеренные комбинации. Заводим задачу в бэклоге на удаление сразу после полного rollout.
2. **Долгоживущие флаги, которые становятся "постоянной конфигурацией"**
   Флаг должен жить не более нескольких месяцев; если настройка нужна постоянно, это конфигурация, а не флаг фичи — управлять через конфиг сервиса.
3. **Не тестируют все комбинации флагов**
   Если флаги зависимы, их сочетание может быть не протестировано. Используем комбинаторное тестирование.
4. **Включение флага на основе случайного выбора в горячем пути с высокими накладными расходами**
   Случайная выборка для A/B должна быть дешёвой (hash userID % 100 < percent). Иначе latency растёт.

### Возможные дополнительные вопросы интервьюера
*Как гарантировать, что выключенный флаг работает корректно после длительного времени?*
Регулярно запускать тесты с переключением флагов в CI; периодически проводить chaos testing с отключением флагов в production-подобной среде.
*Как управлять флагами в moblie/клиентских приложениях, использующих Go на бэкенде?*
Бэкенд должен предоставлять конфигурацию через API, клиент кэширует и применяет без задержек.
*Как избежать утечек данных при A/B тестировании?*
Изолировать данные экспериментов, гарантировать, что при выключении флага пользовательские данные в новом формате доступны старым кодом.

## Как управлять версионированием в микросервисной среде (API версии, версии данных)?

### Краткий ответ
Версионирование API осуществляется через URL/заголовки (v1/v2), либо через content negotiation, с гарантией обратной совместимости не менее одного мажорного цикла. Версионирование данных (схемы БД, сообщений) — через эволюцию схем с добавлением полей, использованием schema registry и версионных endpoints.

### Развёрнутый ответ
Стратегии:
- **API**: используем семантическое версионирование, но в URL только мажорную версию (`/api/v2/`). Внутреннее взаимодействие через gRPC — версионирование через пакет (`service.v2`). Обратная совместимость по правилам Protobuf.
- **Депрекация**: старые версии помечаются `deprecated` в proto/документации, устанавливается срок отключения (3-6 месяцев). Мониторим использование.
- **Версионирование данных**:
  - Схема БД: миграции с добавлением nullable столбцов, использование представлений для обратной совместимости.
  - События: Avro/Protobuf с schema registry; поля добавляются с default значениями. Консюмеры должны игнорировать неизвестные поля.
- **Контракты между сервисами**: Consumer-Driven Contracts тесты для проверки совместимости.
- **Go-реализация**: кодогенерация gRPC; для HTTP используем роутер `gorilla/mux` с версионированными маршрутами.

```go
r := mux.NewRouter()
r.HandleFunc("/api/v1/orders", OrdersV1)
r.HandleFunc("/api/v2/orders", OrdersV2)
```

### Под капотом (internals)
- **Protobuf**: десериализатор в Go всегда игнорирует неизвестные поля, что обеспечивает forward совместимость. Поле с префиксом `reserved` гарантирует, что разработчики не переиспользуют номер.
- **gRPC версии**: пакет `service.v2` может быть зарегистрирован на том же сервере. Вызовы со старого клиента всё ещё обслуживаются `v1`.
- **Миграции: golang-migrate** позволяет атомарно накатывать изменения; поддерживает версию схемы в БД.

### Типичные ошибки кандидатов
1. **Удаление старого API немедленно после выпуска нового**
   Клиенты не успевают мигрировать. Должен быть период перекрытия.
2. **Изменение семантики существующего поля (breaking change)**
   Например, раньше поле `status` было `int`, стало `string`. Это ломает парсеры. Для эволюции добавляем новое поле и депрекейтим старое.
3. **Отсутствие инструментов для обнаружения использования старых версий**
   Без метрик невозможно понять, когда можно безопасно удалить версию. Внедряем трассировку/логирование версий API.
4. **Несогласованное версионирование данных между синхронным API и асинхронными событиями**
   События могут иметь отличную от API структуру. Используем общие схемы с версионными топиками.

### Возможные дополнительные вопросы интервьюера
*Как обрабатывать изменения в схеме, которые не являются аддитивными?*
Вводим новую версию топика/API; используем двойную публикацию событий в обе версии на переходный период.
*Как тестировать обратную совместимость автоматически?*
Инструменты вроде `buf breaking` в CI/CD проверяют изменения proto на breaking changes.
*Как версионировать не только API, но и поведение (feature flags)?*
Поведение меняется через флаги, версия API остаётся неизменной. Это ортогонально.

## Как нанимать, онбордить и развивать senior-инженеров в команде?

### Краткий ответ
Найм предполагает оценку глубины знаний (включая Go internals, архитектуру, soft skills) через структурированные интервью. Онбординг — постепенное погружение в домен, код и культуру через спарринг-партнёрство и назначение значимых задач. Развитие — через ownership критических систем, менторство и возможности для роста до Staff.

### Развёрнутый ответ
- **Найм**: помимо standard coding, проводим System Design интервью на Go, вопросы на GC/планировщик; Behavioural для проверки leadership. Используем rubrics: "Senior: способен самостоятельно вести крупный проект, менторить, принимать архитектурные решения".
- **Онбординг**: за 30 дней новый сотрудник должен задеплоить свой код в прод. Наставник (buddy) помогает с локальным окружением, архитектурой, внутренними инструментами. Предоставляем гайд по кодовой базе, best practices, performance guidelines.
- **Развитие**: индивидуальный план развития (IDP). Даём владение (ownership) важного сервиса с технической стратегией. Поддерживаем участие в конференциях, open source. Проводим тех-толки и архитектурные ревью с его участием.
- **Культура**: поощряем публикацию RFC, проблем-соувереннити, менторство джуниоров. Чекпоинты 1:1 с лидом каждую неделю.

Пример плана онбординга Go-инженера:

```yaml
Week 1-2: Environment setup, codebase tour, pair programming on simple bugs.
Week 3-4: Implement a small feature with flag, deploy to canary, monitor.
Month 2: Take ownership of a non-critical service, attend architectural meeting.
Month 3: Lead a design review, mentor an intern.
```

### Под капотом (internals)
Здесь больше про людей, но можно отметить инструменты:
- **Code review в Go**: используем `golangci-lint` в CI, чтобы автоматически обучать best practices.
- **Документация**: GoDoc как стандарт, примеры использования. Сеньор обязан писать примеры.
- **Технические споры**: использовать benchmark-баттлы (`go test -bench`) для доказательства производительности вместо субъективных мнений.

### Типичные ошибки кандидатов
1. **Найм только на знание синтаксиса Go без системного мышления**
   Senior должен понимать, как его решение влияет на систему в целом (память, сеть, отказоустойчивость).
2. **Бросание нового сеньора в хаос без поддержки**
   Даже очень опытный инженер уходит, если нет чёткого онбординга и он не понимает домен.
3. **Отсутствие возможностей для влияния на техническую стратегию**
   Senior уходит, если его идеи игнорируются. Нужно давать трибуну.
4. **Недостаточное внимание софт-скиллам**
   Senior должен уметь коммуницировать, вести переговоры, продвигать идеи. Технических навыков недостаточно.

### Возможные дополнительные вопросы интервьюера
*Как оценить потенциал роста до Staff?*
Смотрим на impact за пределами команды: вклад в общие библиотеки, архитектурные решения, менторство, выступления.
*Как удерживать senior инженеров без повышения зарплаты?*
Давать интересные, технически сложные задачи, автономию, признание, возможность влиять на продукт.
*Как встроить culture of learning?*
Организовать внутренние семинары, выделять время на самообучение (10-20%), поощрять чтение книг (выдавать гранты).

## Что такое "организационная схема" Конвея и как она влияет на архитектуру?

### Краткий ответ
Закон Конвея гласит: «Организации проектируют системы, которые являются копиями их коммуникационных структур». Иными словами, архитектура программного обеспечения отражает границы команд. Для управления этим нужно осознанно формировать команды вокруг бизнес-доменов (Inverse Conway Maneuver), чтобы получить желаемую модульность.

### Развёрнутый ответ
- **Пример**: если у вас есть команда фронтенда, команда бэкенда и команда базы данных, то система будет разделена на UI-уровень, сервис-уровень и слой данных, даже если это неэффективно.
- **Inverse Conway Maneuver**: сначала определяется целевая архитектура (микросервисы по бизнес-функциям), затем реорганизуются команды, чтобы владеть этими сервисами end-to-end. Это способствует low coupling, high cohesion.
- **Практика**: команда должна владеть всем стеком сервиса («you build it, you run it»). Это уменьшает необходимость межкомандной координации для доставки фич.
- **Go-применимость**: в Go-проектах структура пакетов должна следовать структуре команд. Если две команды пишут в один пакет, будет много конфликтов и связности. Разделяем репозитории по границам bounded context.

### Под капотом (internals)
Внутреннее устройство Go модульной системы (`go mod`) позволяет командам иметь независимые репозитории с версионированием, что физически реализует модульность, диктуемую Конвеем. Использование internal пакетов ограничивает доступ снаружи модуля.

### Типичные ошибки кандидатов
1. **Игнорирование закона и попытка насильно внедрить архитектуру, не меняя команды**
   Приведёт к архитектурному дрейфу: разработчики будут строить «мостики» для коммуникаций, разрушая модульность.
2. **Слишком частые реорганизации**
   Постоянная смена границ команд вносит хаос. Структура должна быть стабильной, как и архитектура.
3. **Недооценка влияния распределённых команд**
   Разные часовые пояса усиливают разделение; если не форсировать коммуникацию, архитектура фрагментируется еще сильнее.
4. **Понимание закона как неизбежности, а не возможности**
   Инженерные лидеры могут использовать закон как рычаг для достижения нужной архитектуры через структуру организации.

### Возможные дополнительные вопросы интервьюера
*Как масштабировать архитектуру, если не хватает людей на каждую компоненту?*
Использовать модульный монолит с чёткими границами (через internal пакеты в Go), которые позже можно выделить в сервисы, когда появятся ресурсы.
*Как Конвей проявляется в open source проектах?*
Open source проекты часто имеют слабосвязанную архитектуру, так как разработчики эфемерны и общаются через issues/PR.
*Как решить конфликт между желаемой архитектурой и существующей оргструктурой?*
Использовать прослойку платформенных команд (Platform Engineering), которые создают инструменты, поощряющие модульность независимо от оргструктуры.

## Как управлять "сложностью" в многолетнем проекте и не допустить коллапса поддерживаемости?

### Краткий ответ
Управление сложностью — это постоянное рефакторинг, соблюдение архитектурных границ, изоляция через интерфейсы, мониторинг метрик сложности кода (cyclomatic complexity, coupling), автоматизированные тесты и ответственное владение кодом (Code Ownership). Главное — дисциплина в следовании стандартам и регулярная «чистка» технического долга.

### Развёрнутый ответ
Стратегии для Go-проекта:
- **Модульность**: следование принципам Clean Architecture / Hexagonal. Каждый пакет решает одну задачу, минимизация экспортируемых символов.
- **Интерфейсы**: маленькие, определяются потребителем. В Go это упрощает замену реализаций.
- **Стандартные линтеры и анализ**: `golangci-lint` с агрессивным набором правил (govet, staticcheck, errcheck, cyclop). Внедрить проверку на сложность в CI.
- **Архитектурное ревью**: раз в квартал обзор кодовой базы на предмет нарушения границ, замусоривания.
- **Рефакторинг как часть каждого спринта**: выделять 20% ёмкости на улучшение кода, а не только на фичи.
- **Управление техническим долгом**: вести реестр долгов, оценить их влияние, приоритизировать по риску и стоимости исправления.
- **Тестирование**: высокая покрытость unit-тестами + интеграционные тесты ключевых сценариев. Это позволяет смело рефакторить.
- **Обучение**: вся команда должна понимать принципы SOLID, KISS, YAGNI на Go.

### Под капотом (internals)
Go поощряет простоту: нет классов, наследования, что уменьшает сложность. Но большие проекты страдают от болезней:
- **Цикличная сложность**: `gocyclo` считает, максимальное допустимое 10-15.
- **Зависимости пакетов**: `go mod graph` позволяет увидеть граф, выявить циклы. Циклы невозможны на уровне пакетов в одном модуле (компилятор запрещает), но могут быть на уровне модулей, что ведёт к проблемам версионирования.
- **Кодогенерация**: уменьшает шаблонный код, но может добавить сложности при отладке. Должна быть оправдана.

### Типичные ошибки кандидатов
1. **Раннее введение микросервисов**
   На старте монолит проще и быстрее. Разбиение на микросервисы без необходимости добавляет распределённую сложность.
2. **Игнорирование статического анализа**
   Разработчики игнорируют warning’и линтеров, копятся проблемы. Правило: `golangci-lint run` с zero-warning policy.
3. **Несвоевременное обновление зависимостей**
   Устаревшие версии библиотек приводят к несовместимости, уязвимостям, что позже создаёт огромную сложность обновления. Автоматизируем dependabot/renovate.
4. **Чрезмерное увлечение абстракциями «на будущее»**
   Абстракции, которые не используются, усложняют понимание. Используем принцип YAGNI.

### Возможные дополнительные вопросы интервьюера
*Как измерить уровень сложности системы?*
Метрики: время, необходимое новому разработчику для первого коммита; время на исправление багов; частота инцидентов из-за непреднамеренных побочных эффектов.
*Как убедить бизнес выделить время на снижение сложности?*
Показать cost of delay из-за долгой разработки фич: «рефакторинг этого модуля сократит время доставки фич на 30%».
*Как работать с легаси, которое страшно трогать?*
Покрыть characterization tests, потом постепенно вычленять части за интерфейсами и переписывать.

## Как спроектировать "multi-cloud" стратегию в Go?

### Краткий ответ
Multi-cloud стратегия подразумевает абстрагирование от специфики облачного провайдера через адаптеры, использование open-source/cloud-agnostic сервисов (Kubernetes, Kafka, Postgres), минимизацию использования managed-сервисов с высоким lock-in, и готовность к переносу нагрузки между облаками.

### Развёрнутый ответ
Архитектурные решения:
- **Инфраструктура**: K8s как единая платформа (EKS, AKS, GKE). Terraform для описания, разделение по провайдерам.
- **Уровень приложения на Go**: все интеграции со специфичными сервисами (S3, BigQuery) инкапсулируются за интерфейсами `BlobStorage`, `Queue`, `Database`. Реализации используют SDK разных провайдеров, выбираемые через конфигурацию.
- **Облачный storage**: вместо прямого использования S3 — MinIO client, который совместим с S3 API и может работать с GCS endpoint.
- **Секреты и конфигурации**: HashiCorp Vault, распределённый key-value store etcd; они не зависят от облака.
- **Балансировка трафика между облаками**: Global Load Balancer (Cloudflare, F5) распределяет трафик по нескольким K8s-кластерам в разных облаках. Сервисы в Go подключаются к общему брокеру сообщений (Kafka across clouds через MirrorMaker).
- **Абстракция с помощью DIP**: используем явные интерфейсы для каждой инфраструктурной зависимости.

Пример интерфейса blob store:

```go
type BlobStore interface {
    Upload(ctx context.Context, key string, data []byte) error
    Download(ctx context.Context, key string) ([]byte, error)
}
// Реализации S3, GCS, Azure в отдельных пакетах.
```

### Под капотом (internals)
Go SDK облачных провайдеров часто используют пулы HTTP-соединений и асинхронные вызовы. При multi-cloud надо управлять контекстами и таймаутами единообразно.
- **Переключение адаптеров**: используем compile-time dependency injection или конфигурационный файл, который в init() регистрирует нужную реализацию.
- **Контроль задержек**: вызовы к разным облакам имеют разную латентность. Применяем retry и circuit breaker per provider.

### Типичные ошибки кандидатов
1. **Прямое использование SDK облака в бизнес-логике**
   Это убивает переносимость. Абстракция — обязательна.
2. **Предположение одинаковых гарантий производительности**
   Network throughput, IOPS у разных провайдеров различаются; нельзя полагаться на одинаковую производительность.
3. **Игнорирование затрат на передачу данных между облаками**
   Egress traffic может быть очень дорогим. Архитектура должна минимизировать перекрёстный трафик; данные держать в одном облаке.
4. **Сложность дебага network issues**
   Необходим распределённый tracing с учётом inter-cloud вызовов.

### Возможные дополнительные вопросы интервьюера
*Как синхронизировать данные между облаками в real-time?*
Использовать Cassandra multi-DC или CockroachDB, которые сами реплицируют; либо Kafka с MirrorMaker.
*Как протестировать failover между облаками?*
Chaos engineering: отключение виртуального облака на уровне DNS/firewall, проверка, что трафик перетекает без потерь.
*Почему просто не использовать один cloud?*
Избежать vendor lock-in, повысить устойчивость к региональным сбоям конкретного провайдера, удовлетворить требования клиентов о хранении данных в определенной юрисдикции.

## Как спроектировать "lossless" ребалансировку очередей?

### Краткий ответ
Lossless ребалансировка означает перераспределение партиций/задач между консюмерами без потери или дублирования сообщений. Достигается через продуманное управление смещениями (offset), graceful shutdown, поддержку идемпотентности и использование алгоритмов консенсуса для ownership’а.

### Развёрнутый ответ
Контекст: распределённые очереди (Kafka, RabbitMQ, NATS). Ребалансировка нужна при добавлении/удалении consumer’ов.
- **Протокол**: для Kafka consumer group — стратегия `CooperativeStickyAssignor` (KIP-429), которая перераспределяет только те партиции, которые необходимо, без остановки всех consumer’ов (в отличие от eager). В Go-клиенте `sarama` поддерживается.
- **Graceful leave**: перед отключением consumer вызывает `LeaveGroup()`, чтобы партиции были перераспределены без потери сообщений. Не просто kill -9.
- **Обработка в процессе**: consumer продолжает обрабатывать назначенные партиции, пока не получит сигнал о новом поколении, затем завершает текущий батч и фиксирует offset.
- **Идемпотентность**: даже если перебалансировка произойдёт до фиксации offset, сообщение будет обработано повторно. Идемпотентность обработчика гарантирует lossless.
- **Транзакционные границы**: commit offset только после успешной обработки и фиксации результата в хранилище (outbox-паттерн).

Пример конфигурации consumer group в `segmentio/kafka-go`:

```go
r := kafka.NewReader(kafka.ReaderConfig{
    Brokers: brokers,
    GroupID: "group",
    Topic:   "orders",
    PartitionAssignmentStrategy: kafka.CooperativeSticky,
})
```

### Под капотом (internals)
- **Кооперативная ребалансировка в Go**: реализуется через периодические heartbeat и вызов `JoinGroup`/`SyncGroup`. Потребитель сохраняет ownership на партиции, пока не договорится о перераспределении.
- **Graceful shutdown**: `r.Close()` инициирует отключение, отправляет LeaveGroup запрос. Координатор группы немедленно запускает ребалансировку для оставшихся.
- **Обработка offset**: offset-менеджер хранит локально последние обработанные offset, но commmit’ит асинхронно или синхронно в зависимости от гарантий.

### Типичные ошибки кандидатов
1. **Использование только eager rebalancing (Range/Sticky)**
   При каждом изменении все потребители отзывают партиции, что вызывает stop-the-world паузу и возможную потерю сообщений в in-flight.
2. **Commit offset’а сразу после получения сообщения, но до обработки**
   Если случится сбой обработки, сообщение потеряно. Правило: commit after processing.
3. **Игнорирование `max.poll.interval.ms`**
   Если обработка длится дольше, брокер считает консюмера мёртвым и ребалансирует, что вызывает дубли. Надо настраивать таймауты или использовать паузы.
4. **Не обрабатывают ошибки commit’а offset’а**
   Если commit не удался (сеть), нужно повторить или корректно завершиться, не теряя прогресс.

### Возможные дополнительные вопросы интервьюера
*Как обеспечить exactly-once семантику в Go при использовании Kafka?*
Использовать транзакционные producer/consumer API, писать offset и результат в одной транзакции Kafka transactions. В Go — sarama transactional API.
*Что делать при долгой обработке сообщений и прерывании?*
Использовать chunked processing: сохранять промежуточное состояние, возобновлять.
*Как протестировать lossless ребалансировку?*
Запускать нагрузочный тест, добавляя/убивая поды, и проверять счётчики: общее число успешных обработок должно равняться отправленным сообщениям.

## Как спроектировать асинхронный движок рабочего процесса (workflow engine)?

### Краткий ответ
Workflow engine управляет долгими бизнес-процессами с ожиданиями событий, таймерами, компенсацией. Проектируется как конечный автомат с персистентным состоянием, реагирующий на события из очереди. Используются паттерны Saga, Routing Slip, State Machine. В Go реализуется через каналы/горутины для активных процессов и внешнее хранилище для ожидающих.

### Развёрнутый ответ
Компоненты:
- **Определение workflow**: DSL или декларативное описание шагов и переходов. Каждый шаг — выполнение действия (вызов сервиса, публикация события) или ожидание внешнего события.
- **State machine**: workflow экземпляр проходит состояния. Состояние и контекст (payload) персистентно сохраняются в БД (PostgreSQL) или в event store.
- **Обработчик событий**: engine подписан на события, по correlation ID извлекает workflow, проверяет условия перехода, выполняет следующий шаг.
- **Таймеры**: для таймаутов или отложенных действий используем scheduler сообщений (отложенная публикация в очередь) или сканирование БД с индексами.
- **Компенсация и Saga**: при ошибке выполняется компенсирующее действие для каждого выполненного шага.
- **Горутины**: для активных workflows, ожидающих ответа, можно держать горутину с блокировкой на канале. Но из-за ограничений памяти лучше использовать реактивную модель: все ожидания сохраняются в БД, горутина не держится.
- **Инструменты в Go**: Temporal (очень мощный) или собственный легковесный на основе `stateless`/`machine`.

Пример простого workflow с состояниями в Go:

```go
type State int; const (Init State = iota; AwaitingPayment; Shipped; Done)
type OrderWorkflow struct {
    ID    string
    State State
    Data  OrderData
}
func (w *OrderWorkflow) HandleEvent(event interface{}) error {
    switch w.State {
    case Init:
        if _, ok := event.(OrderPlaced); ok { w.State = AwaitingPayment }
    ...
    }
}
```

### Под капотом (internals)
- **Persistent state**: хранилище должно обеспечивать атомарное обновление и optimistic locking (version field), чтобы избежать race condition при параллельных событиях.
- **Очереди**: engine публикует команды и подписывается на события. Используем конкурентное потребление с партицированием по workflow ID для порядка.
- **Graceful shutdown**: активные workflow должны уметь сохранять промежуточное состояние и корректно восстанавливаться.
- **Тайм-ауты и тики**: в Go `time.AfterFunc` может использоваться для запуска callback в будущем, но её не сериализовать. Лучше сохранять таймер в БД и периодически сканировать.

### Типичные ошибки кандидатов
1. **Хранение состояния только в памяти горутины без персистентности**
   При падении пода workflow теряются. Персистентность — обязательна.
2. **Зацикливание компенсаций без idempotency**
   Компенсация может упасть, нужна идемпотентность и возможность повторной попытки.
3. **Неверная обработка конкурентных событий**
   Два события могут прийти одновременно и попытаться обновить состояние. Используем optimistic locks или сериализацию обработки по ID.
4. **Использование синхронных вызовов сервисов внутри workflow без таймаутов**
   Workflow зависает навечно. Все внешние вызовы должны быть асинхронными с таймаутами и обработкой ошибок.

### Возможные дополнительные вопросы интервьюера
*Как обеспечить видимость и управление запущенными процессами?*
Дашборд с поиском по ID, отображением текущего состояния и истории событий. API для ручного вмешательства (пропустить шаг, перезапустить).
*Как реализовать длительное ожидание человеческого действия?*
Workflow переходит в состояние ожидания сигнала; внешнее действие присылает событие с task ID.
*Как тестировать workflow engine в Go?*
Моки на шаги, inject событий, проверка конечного состояния и вызовов; использовать сценарные тесты.

## Как реализовать "chaos engineering" для повышения устойчивости?

### Краткий ответ
Chaos engineering — дисциплина экспериментов над продакшен-системой для выявления слабых мест. Инструменты: внедрение сетевых задержек, потерь пакетов, убийство подов/серверов, имитация сбоев зависимостей. Обязательно: steady-state гипотеза, blast radius control, автоматический rollback и мониторинг.

### Развёрнутый ответ
Цикл хаос-эксперимента:
1. **Определение steady state**: метрики, характеризующие нормальную работу (latency, error rate, throughput).
2. **Гипотеза**: «Если мы уроним 30% подов сервиса X, p95 latency останется < 200ms».
3. **Проведение**: с помощью Chaos Mesh / LitmusChaos / Gremlin на K8s, либо самописные операторы, которые выполняют `kubectl delete pod` или сетевые политики.
4. **Наблюдение**: автоматический сбор метрик, сравнение с базовым уровнем.
5. **Откат или продолжение**: если отклонение превышает порог — автоматический abort.
В Go сервисы должны быть спроектированы с учётом отказов: retry, circuit breaker, таймауты, health checks. Хаос-тесты выявляют неработающий fallback.
- **Инструменты**: LitmusChaos (оператор в K8s), `gremlin`, `toxiproxy` (можно внедрить как sidecar).
- **Безопасность**: начинать с staging, потом на прод в часы минимальной нагрузки. Минимизировать blast radius (только один шард, один регион).

Пример внедрения задержек через toxiproxy в Go тестах:

```go
proxy := toxiproxy.NewProxy()
proxy.AddToxic("latency", "latency", "downstream", 1.0, toxiproxy.Attributes{"latency": 1000})
```

### Под капотом (internals)
- **Kubernetes Eviction**: `kubectl drain node` имитирует отказ узла. PodDisruptionBudget гарантирует, что определённое количество подов остаётся доступным.
- **Сетевые хаосы**: Istio fault injection на уровне mesh позволяет задерживать трафик к конкретному сервису без изменения кода.
- **Go обработка**: критично, чтобы сервер корректно обрабатывал `SIGTERM`, завершал соединения, переподключался к базам. `net/http` server имеет `IdleTimeout`, `ReadTimeout`, но необходимо тестировать.

### Типичные ошибки кандидатов
1. **Проведение экспериментов без steady-state метрик**
   Нельзя понять, система нормально выдержала или нет, если не с чем сравнивать. Метрики обязательно.
2. **Слишком агрессивный эксперимент сразу**
   Убийство всех подов базы данных в проде — плохая идея. Постепенное увеличение радиуса.
3. **Неавтоматический abort**
   Если метрики ухудшились, эксперимент должен быть остановлен автоматически, а не ждать, пока разработчик заметит.
4. **Не привлекать команду разработки к анализу результатов**
   Chaos engineering — не про сломать, а про научиться. Результаты должны приводить к улучшению системы.

### Возможные дополнительные вопросы интервьюера
*Как убедить бизнес в необходимости хаоса на проде?*
Показать: «мы нашли 3 уязвимости, которые могли бы привести к простою на 4 часа, и исправили»; стоимость простоя выше стоимости экспериментов.
*Как реализовать chaos testing для stateful сервиса на Go?*
Отключение диска (volume fault), network partition, принудительная смена лидера (для Raft). Проверяем автоматическое восстановление.
*Можно ли использовать eBPF для тонкого хаоса?*
Да, eBPF программы могут перехватывать системные вызовы и возвращать ошибки для конкретных функций, что позволяет симулировать отказы библиотек.

## Как спроектировать "автоматический triage" для инцидентов?

### Краткий ответ
Автоматический triage — классификация и маршрутизация инцидентов на основе алертов, логов и метрик с помощью правил и ML моделей для сокращения MTTR. Система анализирует входящие алерты, обогащает данными о топологии сервисов, определяет владельца и возможную первопричину, создаёт тикет с контекстом.

### Развёрнутый ответ
Архитектура:
1. **Сбор сигналов**: алерты из Alertmanager, anomaly detection, логи ошибок из Loki/Elasticsearch.
2. **Нормализация**: единый формат события, обогащение (имя сервиса, namespace, кластер).
3. **Rules engine**: на Go реализуем обработку правил, определяющих критичность и команду. Например: `if alertname == "HighLatency" and service == "payment" then severity=P1, owner=payments`.
4. **Корреляция**: группировка алертов по метке `alertname`, `cluster`, временному окну. Используем граф зависимостей сервисов (Service Map) для обнаружения каскадных сбоев: если алерт на payment и одновременно на auth, возможно root cause в auth.
5. **Автоматические действия**: при известных проблемах запускается предопределённая runbook (рестарт пода, scale up).
6. **Интеграция с инцидент-менеджментом**: PagerDuty/Opsgenie, создание инцидента с предзаполненным описанием.
7. **Обратная связь**: ручная корректировка triage обучает систему (через флаги в БД).

Пример простого triage обработчика в Go:

```go
for alert := range alertChan {
    svc := serviceGraph.Get(alert.Service)
    if alert.Severity >= Critical && svc.Dependencies != nil {
        for _, dep := range svc.Dependencies {
            if dep.Health == "unhealthy" {
                alert.RootCause = dep.Name
                break
            }
        }
    }
    createIncident(alert)
}
```

### Под капотом (internals)
- **Передача сообщений**: используем NATS или Kafka для надёжной доставки. Горутины-обработчики конкурентно разбирают очередь.
- **Хранение состояния**: Incidents храним в PostgreSQL, граф сервисов — in-memory с периодическим обновлением из CMDB/K8s API.
- **Performance**: высокий rate алертов может быть сам по себе инцидентом; система должна справляться, поэтому используем rate limiting на входе и агрегацию.

### Типичные ошибки кандидатов
1. **Жёстко закодированные правила без возможности динамического обновления**
   Изменение правил требует перезагрузки. Правильно: хранить правила в конфигурационном файле/БД и обновлять без остановки (atomic.Value).
2. **Игнорирование случаев неопределённости**
   Неизвестный алерт падает на пол. Должен быть default route для ручной обработки.
3. **Корреляция только по времени без учёта топологии**
   Два одновременных алерта могут быть независимыми. Топология помогает точнее.
4. **Спам тикетами при масштабном сбое**
   Нужна агрегация: несколько однотипных алертов в один инцидент, обновление статуса.

### Возможные дополнительные вопросы интервьюера
*Как использовать машинное обучение для triage?*
Обучить модель на исторических данных (features: метрики, логи, время суток), предсказывать сервис-виновник; ML затруднителен из-за изменяющейся архитектуры, чаще используют эвристики.
*Как связать автоматический triage с runbook automation?*
Когда инцидент создан, система ищет matching runbook (playbook) и запускает предписанные проверки или команды через API (K8s, AWS).
*Как измерять качество triage?*
Метрики: доля корректно назначенных инцидентов (feedback от владельца), время до назначения, процент ложных эскалаций.

## Как построить систему "real-time data synchronization" между миллионами устройств?

### Краткий ответ
Real-time sync требует двунаправленного стриминга через WebSocket/gRPC bidirectional stream, управление состоянием с CRDT или Operational Transformation, шардирование по каналам/пользователям, и эффективное распределение сообщений через Pub/Sub с горизональным автомасштабированием.

### Развёрнутый ответ
Архитектура:
- **Транспорт**: постоянное соединение WebSocket (или gRPC stream) между устройством и сервером. В Go используем `gorilla/websocket` или встроенный `nhooyr/websocket`.
- **Шардирование подключений**: L7-балансировщик с sticky sessions (по userID или deviceID) направляет на конкретный экземпляр сервиса синхронизации (Sync Server). Экземпляр держит in-memory состояние подключённых устройств.
- **Pub/Sub**: когда устройство отправляет изменение, Sync Server публикует в Redis/NATS канал по topic’у (документ/канал). Другие серверы, удерживающие соединения заинтересованных устройств, подписываются и доставляют сообщение.
- **Конфликтная синхронизация**: используем CRDT (automerge, yjs) или алгоритмы OT. В Go есть библиотека `github.com/nicholasgasior/golem` для OT? Лучше интегрировать yjs через WASM или самому реализовать CRDT счётчики.
- **Оффлайн поддержка**: устройство сохраняет изменения в локальной очереди, при восстановлении связи отправляет их серверу; сервер выполняет слияние.
- **Гарантии**: at-least-once доставка; идемпотентность и порядок сообщений обеспечивается sequence number.

Пример WebSocket handler в Go:

```go
func syncHandler(w http.ResponseWriter, r *http.Request) {
    conn, _ := upgrader.Upgrade(w, r, nil)
    go readLoop(conn, pubSub)
    writeLoop(conn, sub)
}
```

### Под капотом (internals)
- **Горутины на соединение**: read и write loop на горутинах. Планировщик Go эффективно управляет миллионами горутин, но память ограничена (стек горутины 2-4KB). На 1M соединений только стеки займут ~4GB, плюс буферы. Используем оптимизации: per-connection buffer pool, epoll-based транспорт через `gnet` для extreme масштаба.
- **NATS**: обеспечивает доставку с высокой пропускной способностью, кластеризацию и интерес (subject-based). Сообщение публикуется в `sync.user.1234`, все серверы, у которых активны соединения данного пользователя, подписаны и получают.
- **Backpressure**: если запись в соединение блокируется, горутина накапливает буфер и разрывает медленного клиента.

### Типичные ошибки кандидатов
1. **Пересылка полного состояния при каждом изменении**
   Трафик огромный. Отправляем только delta (JSON patch, или CRDT операции).
2. **Игнорирование проблем устаревания данных (stale read)**
   Из-за сетевых задержек устройство может отправить изменение, сервер применил, но устройство не получило подтверждение; нужно использовать version vectors.
3. **Блокирующая обработка сообщений в одном потоке на сервер**
   Один медленный клиент не должен тормозить других. Конкурентная доставка.
4. **Отсутствие аутентификации и авторизации на уровне сообщений**
   Устройство может подписаться на чужой топик.

### Возможные дополнительные вопросы интервьюера
*Как синхронизировать миллионы устройств без шардирования по пользователю в Pub/Sub?*
Использовать интересы (NATS subjects) с wildcard; брокер сам доставляет подписчикам.
*Как бороться с рассинхронизацией при длительных разрывах?*
Использовать server-side state snapshot’ы; при переподключении клиент отправляет последний известный sequence, сервер вычисляет пропущенные изменения.
*Как обеспечить консистентность данных, если сервер с соединением падает?*
Соединение переподключается к другому экземпляру; новый экземпляр либо загружает состояние из общего хранилища, либо просит клиента переслать полное состояние.

## Как разработать стратегию развития платформы на 3 года вперед?

### Краткий ответ
Стратегия строится вокруг видения: переход от утилит к self-service платформе, увеличение абстракции, стандартизация и автоматизация. Разработка дорожной карты с учётом бизнес-целей, обратной связи от разработчиков (Internal Developer Platform), технологических трендов и эволюции Go.

### Развёрнутый ответ
Этапы:
1. **Анализ текущего состояния (Year 0)**: опрос разработчиков, метрики DORA (deployment frequency, lead time, MTTR). Выявление болевых точек.
2. **Видение**: какой должна стать платформа через 3 года — золотой путь (golden path) для типовых сервисов, полная обсервабильность из коробки, автоматический scale-to-zero.
3. **Дорожная карта**:
   - Год 1: Базовая автоматизация CI/CD, стандартная библиотека для Go (логирование, трассировка), контракты API.
   - Год 2: Self-service портал, внедрение service mesh, автоматическое управление версиями, канареечные деплои.
   - Год 3: Интеллектуальная платформа: прогнозирование отказов, автооптимизация расхода ресурсов на основе профилей, принятие архитектурных решений на основе AI.
4. **Принципы**: API-first, все компоненты платформы доступны через API и CLI. Стек Go — основа для инструментов из-за кросс-компиляции и производительности.
5. **Эволюция экосистемы Go**: следование за версиями языка (generics, arenas, PGO), внедрение их в платформенные библиотеки.
6. **Обратная связь**: регулярный сбор Net Promoter Score от разработчиков, корректировка.

### Под капотом (internals)
Внутреннее устройство платформы часто включает Kubernetes operator, написанный на Go с использованием controller-runtime. Платформа сама является распределённой системой, и для её развития применяем те же принципы надёжности: observability, graceful degradation, feature flags.

### Типичные ошибки кандидатов
1. **Стратегия, оторванная от реальных потребностей разработчиков**
   Строить платформу, которую никто не просил. Нужно исходить из user story внутренних пользователей.
2. **Чрезмерные планы на первый год без быстрых побед**
   Нужно показать ценность раньше, чтобы сохранить поддержку руководства.
3. **Игнорирование миграции легаси**
   Платформа должна предусматривать постепенную миграцию старых сервисов, иначе она будет использоваться только для новых, создавая два мира.
4. **Недостаточное внимание документированию и обучению**
   Самая лучшая платформа бесполезна, если никто не знает, как ею пользоваться.

### Возможные дополнительные вопросы интервьюера
*Как измерить успех платформы?*
Метрики: adoption rate, developer satisfaction, DORA metrics improvement, reduction in incidents caused by infrastructure, time to bootstrap new service.
*Как балансировать между стабильностью платформы и скоростью инноваций?*
Использовать canary releases для самой платформы; внутренние команды добровольно обновляются, потом обязательное.
*Как Go помогает в разработке платформенных инструментов?*
Статическая компиляция в один бинарник упрощает распространение CLI; высокая производительность; goroutines для параллельной обработки.

## Как внедрять и поддерживать "инженерные стандарты" (coding, testing, observability) в десятках команд?

### Краткий ответ
Стандарты должны быть выработаны совместно, зафиксированы как Code of Conduct, автоматизированы через линтеры/CI/CD и поддерживаться через культуру code review, эскалацию и постоянное обучение. Важна роль лидеров мнений и платформенной команды, предоставляющей готовые инструменты и шаблоны.

### Развёрнутый ответ
Подход:
- **Совместная разработка**: RFC процесс для стандартов, голосование представителей команд. Все чувствуют ownership.
- **Автоматизация**: 
  - Линтеры: `golangci-lint` с общим конфигом, включенным в каждый репозиторий.
  - Генерация кода: шаблоны сервисов с уже настроенным логированием, метриками, трейсингом (через `gonew` или внутренний шаблонизатор).
  - Pre-commit hooks для форматирования, тестов.
- **Мониторинг соблюдения**: дашборды с количеством предупреждений, покрытия тестами, статистика нарушений. Публикация leaderboard.
- **Code review guidelines**: обязательное ревью стандартов (checklist). Нарушения блокируют merge.
- **Обучение**: регулярные tech talks, "стандарты недели", onboarding documentation.
- **Механизм исключений**: для унаследованного кода стандарты могут быть смягчены, но с планом устранения.
- **Владельцы стандартов**: группа экспертов (Tech Leads), которая обновляет стандарты, решает споры.

Пример конфигурации `golangci.yml`, общей для всех:

```yaml
linters:
  enable:
    - errcheck
    - gosimple
    - govet
    - staticcheck
    - unused
    - cyclop
linters-settings:
  cyclop:
    max-complexity: 15
```

### Под капотом (internals)
- **Go tooling**: `go vet`, `staticcheck` анализируют абстрактное синтаксическое дерево. Стандарты могут быть реализованы через custom linter (на основе `go/analysis`), проверяющий специфические паттерны (например, обязательное использование `context.Context`).
- **Шаблонизация**: `go:generate` и Makefile идемпотентно генерируют код. Стандарты обязывают использовать определённую структуру каталогов.

### Типичные ошибки кандидатов
1. **Стандарты, спущенные сверху без обсуждения**
   Команды саботируют; должны участвовать в создании.
2. **Слишком жёсткие, негибкие правила**
   Если правило «все функции должны быть менее 20 строк» не учитывает специфику, разработчики найдут обходные пути.
3. **Отсутствие автоматизации контроля**
   Полагаться на ручную проверку в обзорах кода — путь к непоследовательности. Всё, что можно автоматизировать, должно быть автоматизировано.
4. **Игнорирование унаследованного кода**
   Требовать немедленного соответствия от легаси невозможно; нужен план постепенного улучшения с исключениями.

### Возможные дополнительные вопросы интервьюера
*Как убедить команду перейти на новые стандарты, если они не хотят?*
Показать выгоду: сокращение багов, ускорение онбординга. Начать с добровольных пилотных проектов.
*Как синхронизировать стандарты между бэкендом на Go и фронтендом?*
Общие стандарты именования, документации, версионирования API; регулярные встречи.
*Как часто обновлять стандарты?*
Раз в полгода-год, с учётом обратной связи; внеочередные изменения при появлении новых возможностей языка.

## Как спроектировать "систему скоринга" для оценки технического долга?

### Краткий ответ
Система скоринга вычисляет количественную оценку технического долга на основе метрик кода (сложность, дублирование, покрытие тестами), архитектурных нарушений, данных из инцидентов и времени сборки. Результат — индекс здоровья кодовой базы, помогающий приоритизировать рефакторинг.

### Развёрнутый ответ
Факторы скоринга:
- **Статические метрики**: cyclomatic complexity, глубина наследования (в Go — глубина интерфейсов), coupling between objects (зависимости пакетов), размер пакетов. Инструменты: `gocyclo`, `go mod graph`.
- **Дублирование кода**: `dupl` или собственный анализ. Дублирование увеличивает стоимость изменений.
- **Тестовое покрытие и качество**: процент покрытия, мутационное тестирование (mutesting). Сниженный coverage = риск регрессий.
- **Возраст кода и частота изменений**: модули, которые давно не менялись, могут иметь устаревшие практики, но и частые изменения без тестов — горячая точка.
- **Инциденты и баги**: количество прод-инцидентов, связанных с компонентом, среднее время исправления.
- **Архитектурные нарушения**: импорт пакета, который не должен использоваться (например, доступ из `service` к `db` напрямую, минуя репозиторий). Проверяется через `go-cleanarch` или собственные анализаторы.
- **Взвешивание и агрегация**: каждому фактору назначается вес по влиянию на продуктивность. Итоговый score = взвешенная сумма нормализованных метрик. Шкала 0-100 (0 — катастрофа).

Пример расчёта на Go: CI job собирает все метрики, скрипт вычисляет score и публикует как метрику Prometheus для отслеживания тренда.

### Под капотом (internals)
- **Сбор данных**: Go analysis API (`golang.org/x/tools/go/analysis`) позволяет писать анализаторы, которые посещают AST и собирают метрики в процессе CI. Результаты в формате SARIF или JSON.
- **Time-series DB**: храним исторические значения score для выявления трендов.
- **Пороговые значения**: настраиваются на основе baseline текущего состояния и целей.

### Типичные ошибки кандидатов
1. **Только метрики кода, без учёта operational или архитектурных аспектов**
   Технический долг не только в коде, но и в отсутствии документации, плохой инфраструктуре, устаревших зависимостях.
2. **Погоня за абсолютным значением без контекста**
   В legacy проекте невозможно достичь 90 баллов; важен тренд (улучшается или ухудшается).
3. **Использование непроверенных метрик**
   Например, количество строк кода как мера сложности — бесполезно. Комбинация метрик точнее.
4. **Не привлекать команду к определению весов**
   Разработчики не доверяют score, если не понимают, как он считается.

### Возможные дополнительные вопросы интервьюера
*Как использовать скоринг для выделения ресурсов на снижение долга?*
Ввести «бюджет долга»: если score ниже порога, команда должна тратить 20% времени на его улучшение; метрика докладывается руководству.
*Как автоматически связывать инциденты с компонентами?*
Через теги в алертах и tracing; накапливаем количество инцидентов по пакетам/сервисам.
*Можно ли включить в score состояние зависимостей (уязвимости)?*
Да, через `govulncheck` и интеграцию с базой CVE; чем больше критических уязвимостей, тем ниже score.

## В чем разница между architectural driver и architectural decision?

### Краткий ответ
Architectural driver — это фактор, влияющий на архитектуру (бизнес-цели, ограничения, атрибуты качества), а architectural decision — конкретный выбор, сделанный для удовлетворения этих драйверов (например, выбор микросервисной архитектуры из-за требования масштабируемости). Решения документируются в ADR (Architecture Decision Records).

### Развёрнутый ответ
- **Драйверы** включают: функциональные требования, нефункциональные требования (scalability, latency, security), бизнес-контекст (time-to-market, cost), технические ограничения (язык Go, существующие системы), организационные (закон Конвея).
- **Решения** — это архитектурные паттерны и технологии, выбранные в результате анализа драйверов: «Мы выбираем event-driven архитектуру, потому что драйвер real-time analytics».
- Документирование: ADR фиксирует контекст, решение, альтернативы и последствия.
- Важно: решения должны быть осознанными и пересматриваемыми при изменении драйверов.

Пример ADR по Go-микросервису:

```
Title: Use gRPC for inter-service communication
Context: Need low latency, strong typing, multi-language support. Driver: latency <50ms.
Decision: gRPC with Protobuf.
Consequences: Added complexity of schema management, better performance.
```

### Под капотом (internals)
В Go архитектурный драйвер может диктовать выбор между `net/http` и `fasthttp` в зависимости от компромисса latency vs. совместимость. Драйвер «10ms latency» ведёт к решению о zero allocation сериализации (Protobuf) и custom TCP протоколу.

### Типичные ошибки кандидатов
1. **Путаница: решение называют драйвером**
   Неправильно: «Наш драйвер — микросервисы». Правильно: «Драйвер — потребность масштабировать команды независимо, решение — микросервисы».
2. **Игнорирование драйверов при проектировании**
   Делают выбор по принципу «модно», а не по реальным потребностям. Нужно обосновывать.
3. **Отсутствие записи решений — потеря контекста**
   Через год никто не помнит, почему выбрали Cassandra. ADR решает проблему.
4. **Не различают стратегические и тактические решения**
   Стратегические — выбор архитектурного стиля; тактические — выбор библиотеки. Оба нужно фиксировать с разным уровнем детализации.

### Возможные дополнительные вопросы интервьюера
*Приведите пример, когда изменение драйвера потребовало пересмотра решения.*
Рост трафика в 10 раз (драйвер масштабирования) выявил, что текущее решение синхронных REST-вызовов не выдерживает, и пришлось перейти на асинхронную очередь.
*Как документировать решения в крупном проекте на Go?*
В репозитории, в папке `docs/adr`, рядом с кодом. Для Go-проекта добавляем ссылки на соответствующие пакеты.
*Как разрешать конфликты драйверов?*
Приоритизировать: безопасность может иметь приоритет над производительностью. Задокументировать компромисс.

## Как спроектировать систему с "zero trust" моделью безопасности?

### Краткий ответ
(Смотри также вопрос 16, но здесь более глубоко в проектирование системы на Go.) Zero Trust архитектура предполагает отсутствие неявного доверия. Каждый запрос проверяется (аутентификация, авторизация) на основе динамической политики, с учётом контекста (устройство, гео). В Go реализуется через middleware, перехватывающие каждый вызов, интеграцию с IAM, mTLS.

### Развёрнутый ответ
Архитектурные принципы:
- **Identity-aware proxy**: перед сервисами стоит envoy или OAuth2-proxy, который проверяет токен и передаёт аутентифицированные claims в заголовках или контексте gRPC.
- **Микросервисный доступ**: сервис-идентификатор через SPIFFE, mTLS на всех уровнях. В Go используем `spiffe/go-spiffe/v2` для получения X.509 SVID.
- **Динамическая авторизация**: OPA sidecar или встроенная библиотека. Политика: `allow if service == "frontend" and path == "/api/v1/orders" and user.role == "customer"`.
- **Проверка на каждую операцию**: не только на уровне endpoint, но и на доступе к данным (Row-level security).
- **Логирование и аудит**: все запросы с атрибутами безопасности пишутся в аудит-лог.
- **Принцип наименьших привилегий**: каждый сервис имеет только необходимые разрешения, выданные через систему.

### Под капотом (internals)
Go gRPC interceptors: unary/stream перехватчики позволяют внедрить универсальную проверку токенов и политик без изменения бизнес-логики. Пример:

```go
func authUnaryInterceptor(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {
    if err := authorize(ctx, info.FullMethod); err != nil {
        return nil, err
    }
    return handler(ctx, req)
}
```

Стандартный `net/http` middleware делает то же для HTTP.

### Типичные ошибки кандидатов
1. **Проверка токена только на edge, а внутри сервисов доверие**
   Внутренние сервисы должны проверять JWT или мандаты повторно (zero trust по глубине).
2. **Статическая политика без возможности динамического отзыва**
   Отозванные права должны применяться быстро; кэширование решений с коротким TTL.
3. **Игнорирование контекста канала связи**
   Без mTLS внутренний трафик может быть перехвачен, несмотря на токены.
4. **Сложность с оркестрацией прав для сервисов**
   Ручное управление приводит к ошибкам; нужна автоматическая выдача least privilege на основе анализа трафика.

### Возможные дополнительные вопросы интервьюера
*Как внедрить Zero Trust в существующую монолитную систему на Go?*
Постепенно: обернуть монолит в sidecar-прокси, который будет проверять запросы; внутри разделить на модули с межмодульной проверкой прав через интерфейсы.
*Как тестировать политики безопасности автоматически?*
Unit-тесты для middleware с разными наборами claims, интеграционные тесты с поднятым OPA.
*Как обрабатывать офлайн-сценарии в Zero Trust?*
Локальный кэш политик, подписанные разрешения с ограниченным сроком действия (offline JWT).

## Как масштабировать базу данных, которая достигла физических лимитов?

### Краткий ответ
Масштабирование БД при лимитах достигается с помощью шардирования (горизонтальное масштабирование), репликации чтения, кэширования, денормализации данных и, в конечном счёте, перехода на распределённые БД (CockroachDB, YugabyteDB). Временно можно помочь вертикальным масштабированием и оптимизацией запросов.

### Развёрнутый ответ
- **Вертикальное масштабирование**: увеличение ресурсов сервера (CPU, RAM, диски NVMe). Имеет предел; помогает выиграть время.
- **Репликация чтения**: master-slave, направляем все чтения на реплики. В Go используем `database/sql` с несколькими подключениями (`sql.Open` + балансировщик или разделение на чтение/запись через `DB.Conn`).
- **Кэширование**: Redis/Memcached слой перед БД для горячих данных. Кэш с TTL и инвалидацией.
- **Шардирование (partitioning)**: данные делятся по ключу шарда (user_id). Приложение в Go должно знать, на каком шарде находятся данные. Используем Vitess, либо собственный sharding proxy на Go (например, rqlite с учётом шардирования). Запросы направляются в нужный шард с помощью routing library.
- **Распределённые SQL БД**: CockroachDB (совместима с PostgreSQL wire protocol), YugabyteDB. Позволяют горизонтально масштабироваться и выдерживать региональные сбои.
- **Архитектурные изменения**: разбиение монолитной БД на микросервисные владения (по бизнес-доменам), каждая со своей БД. Это кардинальное решение, но снижает нагрузку на одну БД.
- **Асинхронная обработка**: запись изменений через очередь, batch вставка, материализованные представления.

Пример роутинга шарда на основе `user_id`:

```go
func getShard(userID int) *sql.DB {
    idx := userID % len(shards)
    return shards[idx]
}
```

### Под капотом (internals)
- **Connection pooling**: `sql.DB` управляет пулом соединений. Для шардированных БД имеem пул на каждый шард. В Go можно создать `[]*sql.DB` и выбирать.
- **Транзакции**: шардирование ломает ACID транзакции между шардами. Используем 2PC или избегаем транзакций между шардами.
- **Vitess**: обеспечивает управление шардами, перебалансировку, но несёт оверхед на маршрутизацию. В Go есть драйвер `github.com/vitessio/vitess/go/mysql`.

### Типичные ошибки кандидатов
1. **Неправильный выбор ключа шарда**
   Неравномерное распределение (hot shard). Выбираем ключ с высоким кардинальностью и равномерным распределением.
2. **Пренебрежение ребалансировкой при росте**
   Добавление новых шардов без перераспределения данных вызывает неравномерность. Нужна стратегия решардинга (consistent hashing).
3. **Попытка использовать шардирование без доработки приложения**
   ORM может не поддерживать маршрутизацию. Приходится менять логику запросов.
4. **Игнорирование аналитических запросов (тяжёлые JOIN’ы)**
   Их невозможно выполнить на шардированной БД без ETL. Выносим аналитику в OLAP (ClickHouse, BigQuery).

### Возможные дополнительные вопросы интервьюера
*Как проводить миграцию на новую схему шардирования без простоя?*
Использовать dual write, постепенное переключение чтения, фоновый перенос данных, аналогично миграции БД.
*Как справиться с cross-shard queries?*
Минимизировать их дизайном: все связанные данные держать на одном шарде (entity group). Если неизбежно — использовать scatter-gather (параллельные запросы ко всем шардам и агрегация), но это влияет на latency.
*Как выбрать между шардированием и готовой распределённой БД?*
Шардирование даёт больше контроля, но сложнее в эксплуатации. Распределённая БД проще, но может иметь ограничения по производительности. Решение на основе компетенций команды и требований.

## Как построить "self-service" платформу для разработчиков?

### Краткий ответ
Self-service платформа (IDP) предоставляет разработчикам золотой путь (golden path) для создания, развёртывания и эксплуатации сервисов без ручного вмешательства Ops. Строится на основе API, шаблонов, CI/CD пайплайнов, портала (Backstage), и обеспечивает абстрагирование от инфраструктуры.

### Развёрнутый ответ
Компоненты:
- **Портал разработчика**: Backstage с плагинами, отображающий сервисы, документацию, статус CI, метрики.
- **Шаблоны сервисов**: программные шаблоны (Templating) для Go-сервисов, создающие репозиторий со структурой, Dockerfile, Helm chart, пайплайнами. Используется `gonew` или внутренний `scaffolder`.
- **CI/CD**: автоматические пайплайны сборки, тестирования, деплоя на канарейку и прод. Интегрировано с ArgoCD.
- **Управление конфигурациями**: централизованное хранилище конфигов с инжектом в поды; секреты через Vault куда разработчики кладут через self-service.
- **Observability as a service**: при создании сервиса автоматически настраиваются дашборды, алерты, логирование. SDK для Go, который подключается одной строкой.
- **База данных / инфраструктура**: разработчик в портале заказывает БД, брокер очередей; автоматический provisioning через Crossplane или Service Catalog.
- **Безопасность и compliance**: встроенные проверки, автоматическое сканирование уязвимостей, политики.

Пример шаблона Go-сервиса, генерируемого платформой:

```go
// main.go
func main() {
    app := platform.NewApp(platform.Config{...})
    app.Run()
}
```

### Под капотом (internals)
- **Kubernetes Operators**: на Go реализуем операторы для автоматического provisioning ресурсов.
- **API Gateways**: центральный gateway маршрутизирует на сервисы, конфигурация через annotations.
- **Platform SDK**: библиотека на Go, которая оборачивает стандартное логирование, метрики, tracing с предустановленными параметрами.

### Типичные ошибки кандидатов
1. **Слишком жёсткий шаблон, не допускающий вариаций**
   Не все сервисы одинаковы; нужны escape hatches (возможность кастомизации вне золотого пути).
2. **Платформа, требующая постоянных запросов к платформенной команде**
   Сама становится узким местом. Цель — self-service, а не «тикет-сервис».
3. **Игнорирование UX для разработчика**
   CLI инструмент должен быть простым: `platform create service --name my-svc --template go-grpc`. Backstage дружелюбный.
4. **Недостаточная документация и примеры**
   Разработчики не будут пользоваться тем, что не понимают.

### Возможные дополнительные вопросы интервьюера
*Как измерить пригодность платформы?*
DORA метрики, скорость создания нового сервиса, удовлетворённость разработчиков.
*Как платформа справляется с легаси сервисами?*
Предоставляет путь миграции: постепенное внедрение SDK, контейнеризация, потом полный переход.
*Как обеспечить безопасность self-service provisioning БД?*
Политики OPA, ограничение по размеру, выбор из утверждённых конфигураций, автоматический аудит.

## Как работает "линейно-логарифмическое" распределение бакетов в гистограммах и почему это важно?

### Краткий ответ
Линейно-логарифмические бакеты объединяют линейное распределение для малых значений (до определённого порога) и логарифмическое для больших, что позволяет точно измерять как маленькие задержки, так и охватывать большой диапазон с разумным числом бакетов, не теряя точность на процентилях.

### Развёрнутый ответ
Обычно гистограммы используют экспоненциальные (логарифмические) бакеты: границы растут в геометрической прогрессии (1, 2, 4, 8...). Проблема: на малых значениях относительная ошибка велика (размер бакета 1ms для 10ms задержки). Линейно-логарифмическое разбиение начинается линейно (1, 2, 3, 4, 5), затем переключается на логарифмическое (10, 20, 40, …). Это даёт абсолютную точность на низких значениях и относительную — на высоких.
- **Важность для SLO**: p95 часто находится в хвосте, где нужна логарифмическая шкала, а p50 — в низком диапазоне, где линейная даёт точное значение.
- **В Go Prometheus клиенте** можно задать кастомные бакеты: `prometheus.LinearBuckets(1, 1, 10)` для линейной части, потом `prometheus.ExponentialBuckets(10, 2, 20)`.
- **SLO-метрики**: высокая точность на нижних процентилях помогает в оптимизации производительности без перерасхода памяти (меньше бакетов, чем чисто логарифмическая с тем же охватом).

Пример конфигурации:

```go
var (
    linearBuckets   = prometheus.LinearBuckets(1, 2, 5) // 1,3,5,7,9
    expBuckets      = prometheus.ExponentialBuckets(10, 2, 10) // 10,20,40,...,5120
)
buckets := append(linearBuckets, expBuckets...)
histogram := prometheus.NewHistogram(prometheus.HistogramOpts{Buckets: buckets})
```

### Под капотом (internals)
Прометей client_golang хранит кумулятивные счётчики в бакетах. При вычислении квантиля по гистограмме точность зависит от ширины бакета в окрестности квантиля. Линейно-логарифмическое разбиение оптимизирует эту точность.

### Типичные ошибки кандидатов
1. **Использование только дефолтных бакетов**
   Стандартные бакеты (напр., `DefBuckets`) могут не покрывать нужный диапазон; SLO 1ms требует более мелкой детализации. Настраивать под ожидаемые значения.
2. **Слишком много бакетов**
   Каждый бакет — это time series, увеличивает стоимость хранения и производительность Prometheus. Надо найти баланс (обычно < 50).
3. **Забывают про upper bound**
   Запросы дольше самого верхнего бакета попадают в `+Inf`, что искажает процентили. Верхняя граница должна быть выше p99.9.
4. **Неправильный выбор перехода от линейной к логарифмической шкале**
   Если переход слишком рано, теряется точность на типичных задержках; если слишком поздно, расширяется число бакетов.

### Возможные дополнительные вопросы интервьюера
*Как адаптировать бакеты, если паттерн задержек меняется?*
Пересматривать конфигурацию периодически на основе текущих значений в проде; использовать автоматизированные скрипты анализа распределения и генерации бакетов.
*Почему бы не использовать t-digest или HDR Histogram?*
Они требуют клиентской библиотеки, которая не совместима со стандартным Prometheus, но дают лучшую точность фиксированного размера. В Go есть `github.com/caio/go-tdigest`. Выбор между простотой интеграции и точностью.
*Как связаны бакеты и error budget?*
При расчёте бюджетного расхода по SLO на основе гистограммы, ошибка аппроксимации может привести к неверному срабатыванию. Правильные бакеты снижают эту ошибку.

## Как спроектировать "Rate Limiter", который понимает бизнес-логику (например, разную стоимость эндпоинтов)?

### Краткий ответ
Бизнес-ориентированный rate limiter использует взвешенные токены: каждый запрос потребляет количество токенов, пропорциональное его вычислительной «стоимости» (CPU time, сложность запроса). Коэффициенты определяются по нагрузочному тестированию или аналитике. Реализуется с помощью token bucket с переменным размером токенов.

### Развёрнутый ответ
- **Определение стоимости**: для каждого эндпоинта (или даже запроса) вычисляем вес. Например, `GET /users` — 1 токен, `POST /reports` (тяжёлый) — 10 токенов. Основа: профилирование CPU.
- **Механика лимитирования**: token bucket с максимальным количество токенов `capacity` и скоростью пополнения `rate`. При запросе вычитается `cost`. Если недостаточно токенов — 429.
- **Динамическое изменение стоимости**: вес может зависеть от параметров запроса (пагинация большого размера, фильтры). Используем middleware, вычисляющее вес до проверки лимитера.
- **Иерархические бюджеты**: общий лимит на клиента + под-лимиты на категорию операций.
- **Инструменты в Go**: расширяем `x/time/rate` — он не поддерживает взвешенный расход нативно. Можно создать обёртку, которая использует `AllowN(weight)`, либо реализовать свой bucket с atomic.

Пример кастомного взвешенного лимитера:

```go
type WeightedLimiter struct {
    tokens  int64 // текущие токены
    rate    int64 // пополнение в секунду
    max     int64
    lastTime int64
    mu      sync.Mutex
}

func (l *WeightedLimiter) Allow(weight int64) bool {
    l.mu.Lock()
    defer l.mu.Unlock()
    now := time.Now().UnixNano()
    elapsed := now - l.lastTime
    l.tokens += elapsed * l.rate / 1e9
    if l.tokens > l.max { l.tokens = l.max }
    if l.tokens >= weight {
        l.tokens -= weight
        l.lastTime = now
        return true
    }
    return false
}
```

### Под капотом (internals)
- **Высокая конкурентность**: мьютекс может стать узким местом. Используем lock-free алгоритм с `atomic` операциями или шардированные лимитеры. Например, per-client limiter хранится в `sync.Map`.
- **Контекст запроса**: middleware вычисляет вес на основе маршрута и параметров. Для этого нужна fast lookup таблица весов. Можно использовать `map[string]int` с `sync.RWMutex` для горячего обновления конфигурации.

### Типичные ошибки кандидатов
1. **Игнорирование burst’а при весовых запросах**
   Если клиент имеет burst 50 и делает 5 тяжёлых запросов по 10, всё ок. Но если burst задан без учёта веса, тяжёлые запросы могут блокироваться при полупустом bucket. Увеличиваем burst пропорционально максимальному весу.
2. **Стоимость запроса не учитывает асинхронную компоненту**
   Некоторые запросы могут потреблять мало CPU, но много I/O, и лимитер не должен ограничивать только по CPU — лучше ориентироваться на latency или ресурс-косты.
3. **Жёстко заданные веса без возможности корректировки**
   Бизнес-логика меняется, веса должны обновляться динамически (из конфига или через feature flags).
4. **Отсутствие мониторинга расхода токенов по типам**
   Не понять, какой эндпоинт самый прожорливый. Экспортируем метрики с лейблом `weight_category`.

### Возможные дополнительные вопросы интервьюера
*Как автоматически определять стоимость запроса?*
Использовать адаптивный алгоритм, измеряющий серверную задержку или потребление CPU на запрос, и автоматически корректирующий вес в фоне (как в Netflix adaptive concurrency limit).
*Как интегрировать такой лимитер с API Gateway?*
Реализовать как Gateway plugin (например, на основе Envoy WASM или внешнего авторизационного сервиса), где Go-бэкенд вычисляет вес и разрешает/запрещает запрос.
*Как совместить с приоритезацией?*
Добавить отдельный bucket или алгоритм с приоритетами: сначала тратятся токены из пула высокоприоритетных, потом низкоприоритетных.

## Как разработать стратегию отказоустойчивости для системы, развернутой в разных ЦОДах?

### Краткий ответ
Стратегия включает избыточность на уровне ДЦ (Active-Active или Active-Passive), автоматическое переключение трафика, репликацию данных с приемлемым RPO, отказоустойчивость на уровне приложения (retry, fallback) и регулярное тестирование DR-плана. Цели RTO/RPO задают архитектуру.

### Развёрнутый ответ
- **Топология ЦОДов**:
  - Active-Passive: один ЦОД обслуживает весь трафик, резервный в горячем резерве с репликацией данных. Переключение через DNS (несколько минут) или GSLB.
  - Active-Active: оба активны, пользователи маршрутизируются к ближайшему. Сложнее из-за консистентности данных, но выше утилизация.
- **Сетевая инфраструктура**: выделенные каналы между ЦОДами с низкой задержкой, BGP Anycast для виртуального IP.
- **Приложение на Go**: сервисы должны поддерживать переключение на резервный экземпляр сервиса в другом ЦОДе. Используем client-side балансировщик с DNS SRV записями как `endpoints` и failover логикой.
- **Данные**: 
  - Синхронная репликация БД между ЦОДами (Galera, CockroachDB) для RPO=0, но влияет на latency.
  - Асинхронная репликация (Kafka MirrorMaker, PostgreSQL streaming) для более высокого RPO.
- **Тестирование**: ежеквартальные учения с полным отключением ЦОДа; chaos engineering.

Пример failover в gRPC клиенте:

```go
resolver.Register(&multiDCBuilder{addresses: []string{"dc1.service:443", "dc2.service:443"}})
conn, _ := grpc.Dial("multi:///service", grpc.WithDefaultServiceConfig(`{"loadBalancingPolicy":"round_robin"}`))
```

### Под капотом (internals)
- **DNS failover**: `net.Resolver` в Go выполняет LookupHost с TTL. Можно реализовать кастомный резолвер, который перебирает адреса при ошибках подключения (similar to Java).
- **Health checking**: gRPC client-side health checking (`grpc.WithHealthCheck`), автоматически исключает нерабочие поды/ЦОД.
- **State**: для stateful сервисов используем Raft с multi-DC (например, Hashicorp Raft, но для разных ЦОД нужен координационный слой). Обычно stateful ограничиваются одним ЦОДом, а запросы маршрутизируются по принадлежности клиента.

### Типичные ошибки кандидатов
1. **Полагаться исключительно на переключение DNS**
   Кэширование DNS на клиенте может задержать переключение, а TTL не всегда соблюдается. Нужен резервный механизм: переподключение с перебором IP.
2. **Отсутствие контроля за количеством переключений**
   Флаппинг между ЦОДами (туда-сюда) ухудшает опыт. Используем hysteresis: переключаемся, только если новый ЦОД стабилен N минут.
3. **Несогласованность данных при асинхронной репликации**
   После переключения пользователь может не увидеть свои последние изменения (stale reads). Стратегия: read-your-writes через sticky routing, либо искусственная задержка переключения для завершения репликации.
4. **Не тестируют всю цепочку от DNS до приложения**
   DR тест только отключением сервера БД не выявляет проблемы на уровне сетевых правил.

### Возможные дополнительные вопросы интервьюера
*Как обеспечить консистентность данных в Active-Active?*
Использовать CRDT, бесконфликтные реплицированные типы данных; или маршрутизировать пользователя всегда к одному ЦОДу (сессионный affinity) и писать в локальную БД, асинхронно реплицируя.
*Что делать, если связь между ЦОДами потеряна (split-brain)?*
Автоматическое определение partition: если база данных чувствует потерю кворума, переходит в read-only во избежание конфликтов. Нужна координация через external arbiter (например, cloud object storage with lease).
*Как рассчитать пропускную способность каналов репликации?*
На основе пикового объёма изменений, задержки и требований RPO; при нехватке полосы — буферизация в очереди сообщений, RPO возрастает.

## Как организовать "Capacity Planning" для предстоящей крупной распродажи (Черная пятница)?

### Краткий ответ
Планирование включает сбор исторических данных пиков, прогнозирование роста, моделирование узких мест, pre-scaling ресурсов с запасом, стресс-тестирование компонентов, резервирование burst capacity, и планы действий при превышении прогнозов (controlled degradation, waiting room).

### Развёрнутый ответ
Шаги:
1. **Анализ прошлогодних пиков**: QPS, CPU, память, сеть, задержки. Определяем growth factor (например, +30% на основе бизнес-прогнозов).
2. **Бизнес-драйверы**: маркетинговые акции, ожидаемые объёмы транзакций. Строим модель: `пиковый QPS = base * growth_factor`.
3. **Unit cost расчет**: сколько CPU/памяти потребляет один запрос ключевого пути (checkout). Экстраполируем на суммарный QPS.
4. **Pre-scale**: за 1-2 дня до распродажи увеличиваем количество реплик сервисов, шардов БД согласно расчётам. Используем HPA с minReplicas уже повышенным, чтобы не ждать Horizontal Pod Autoscaler.
5. **Запас прочности**: +50% к расчётному ресурсу для абсорбирования непредвиденных всплесков.
6. **Стресс-тестирование**: на staging или изолированном проду прогоняем сценарий с ожидаемой нагрузкой. Замеряем, не упираемся ли в потолок (например, connection limits).
7. **Контрольный план**: 
   - Если нагрузка превышает capacity, включаем shed low-priority трафика (управление очередью на gateway).
   - Предоставляем статическую страницу (waiting room) для не авторизованных пользователей.
   - Отключаем некритичные функциональности (рекомендации, аналитика).
8. **Мониторинг в реальном времени**: дашборд с текущим QPS и utilisation vs capacity, алерты при приближении к критическому порогу.

Пример кода проверки ёмкости и shed:

```go
if atomic.LoadInt64(&currentConcurrency) > threshold {
    http.Error(w, "Service Unavailable", http.StatusServiceUnavailable)
    return
}
```

### Под капотом (internals)
- **Auto Scaling задержки**: HPA смотрит на среднее значение, но пик нарастает быстро; использование KEDA с event-driven autoscaling на основе числа сообщений в очереди помогает реагировать быстрее.
- **Go overhead**: стоит учитывать, что при резком увеличении горутин может увеличиться GC pressure. Используем `GOMEMLIMIT` и мониторинг GC.

### Типичные ошибки кандидатов
1. **Полагаться только на автоскейлинг во время события**
   Автоскейлинг может не успеть (холодный старт, задержка метрик). Обязательно pre-warm.
2. **Не тестировать отказоустойчивость под нагрузкой (chaos + stress)**
   Под нагрузкой отказ одного шарда может вызвать каскад. Комбинируем стресс-тест с chaos.
3. **Игнорировать лимиты downstream систем (базы данных, очереди)**
   Сервис может масштабироваться, но БД упрётся в лимит подключений. Необходимо расширить connection pool или шардировать.
4. **Не предусмотреть сброс кэша при старте пика**
   Пустой кэш создаёт лавину запросов к БД; прогреваем кэш (cache warmer) до пика.

### Возможные дополнительные вопросы интервьюера
*Как быстро отмасштабировать БД, если заранее не смогли?*
На ходу добавить read реплики (быстрее), кэширующий слой; если write — тяжело, только шардирование или переезд на более мощную машину (вертикальное, требует времени). Планируйте заранее.
*Какие метрики сигнализируют, что мы близки к пределу capacity?*
Увеличение времени обработки запроса, рост длины очереди, насыщение CPU (utilization > 80%), увеличение ошибок timeout.
*Как повысить эффективность использования ресурсов?*
Применять сжатие ответов, агрессивное кэширование, асинхронную обработку где возможно, оптимизацию сериализации (Protobuf вместо JSON).

## Как внедрить "Tracing" в систему, которая его никогда не использовала, без остановки разработки?

### Краткий ответ
Внедрение распределённой трассировки (OpenTelemetry) выполняется поэтапно: сначала инструментирование критических сервисов и шлюза, использование автоматических инструментаций для HTTP/gRPC клиентов, затем постепенное покрытие остальных сервисов через middleware и контекст. Не требует остановки разработки, поскольку добавляется неблокирующим образом.

### Развёрнутый ответ
План:
1. **Выбор стандарта**: OpenTelemetry (OTel) — вендор-нейтральный. В Go SDK `go.opentelemetry.io/otel`.
2. **Начало с Edge**: на gateway или ingress внедряем создание span’а и генерацию traceID, проброс в заголовках (`traceparent`). Все downstream сервисы, даже без инструментации, будут передавать заголовок, но не создавать своих span’ов.
3. **Автоинструментация**: OTel Go поддерживает автоматическую трассировку для `net/http`, `gRPC` через wrapper. Можно включить, добавив `otelhttp.NewHandler` или `otelgrpc`. Это лёгкое изменение middleware.
4. **Постепенное добавление кастомных спанов**: разработчики добавляют `tracer.Start(ctx, "operation")` в критических местах по мере необходимости. Не блокирует другие задачи.
5. **Сбор и хранение**: экспорт в Jaeger, Grafana Tempo, или Datadog. Экспорт асинхронный, batched, с низким оверхедом.
6. **Обучение**: включить в стандарты обязательное добавление трассировки для новых сервисов; существующие — по мере рефакторинга.
7. **Sampling**: на первых порах использовать 100% выборку в dev/staging и 10-25% в production для снижения нагрузки.

Пример простого добавления OTel HTTP:

```go
import "go.opentelemetry.io/contrib/instrumentation/net/http/otelhttp"

handler := otelhttp.NewHandler(http.HandlerFunc(actualHandler), "my-service")
```

### Под капотом (internals)
- **Context propagation**: OTel использует `context.Context` для передачи span context. Важно, чтобы все вызовы использовали один и тот же контекст. В Go это естественно, если следовать best practices.
- **Экспорт**: для production `otlptracehttp` отправляет спаны по HTTP/gRPC батчами, управляется через `BatchSpanProcessor`. При переполнении буфера спаны дропаются, а не блокируют обработку.
- **Performance impact**: при низком sampling rate и batched экспорте overhead минимален (<1% CPU). Осторожно с большим количеством атрибутов.

### Типичные ошибки кандидатов
1. **Попытка инструментировать всё сразу идеально**
   Это замедляет разработку. Лучше итеративно: сначала автоматические спаны, потом кастомные.
2. **Игнорирование контекста при асинхронных вызовах**
   Горутины должны получать контекст с span’ом, иначе связь теряется. Используйте `ctx` явно.
3. **Настройка 100% sampling в production без ограничений**
   Создаёт гигантский объём данных и замедляет сервисы. Постепенно увеличивайте sampling rate по мере масштабирования хранилища.
4. **Не связывают трассировку с логированием**
   В логи нужно включать `trace_id` и `span_id`, чтобы коррелировать. OTel интегрируется с `slog`.

### Возможные дополнительные вопросы интервьюера
*Как включить трассировку для legacy-монолита без контекста?*
Обернуть все входящие запросы в middleware, создать корневой span и передать context вглубь через глобальную переменную (костыль, но работает), постепенно переписывая функции на context-aware.
*Как анализировать трассировку для поиска узких мест?*
Использовать Jaeger/Tempo для просмотра waterfall, искать длинные промежутки между span’ами (network wait), фокусироваться на хвостовых запросах.
*Как обеспечить совместимость с системами, которые уже используют другой стандарт (Zipkin)?*
OTel поддерживает Zipkin exporter и конвертацию заголовков.

## Как спроектировать "API Gateway" с учетом пагинации, фильтрации и сортировки на уровне шлюза?

### Краткий ответ
API Gateway может предоставлять унифицированные параметры запросов (`?page=1&limit=20&sort=-created_at&filter[status]=active`) и прозрачно проксировать к нижележащим сервисам, преобразуя или добавляя заголовки, но сложную логику пагинации (особенно курсорную) лучше делегировать сервисам. Gateway должен валидировать, нормализовывать и кэшировать общие метаданные пагинации.

### Развёрнутый ответ
- **Унификация протокола**: Gateway принимает стандартные параметры `page[offset]`, `page[limit]`, `sort`, `filter`. Если бэкенд использует другой формат, gateway трансформирует (например, в headers или другой query string).
- **Валидация и безопасность**: ограничение максимального `limit` (100), фильтрация только разрешённых полей для сортировки/фильтрации (защита от недопустимых параметров).
- **Кэширование ответов**: для read-heavy эндпоинтов gateway может кэшировать ответы с учётом параметров пагинации и фильтрации (ETag).
- **Обработка ошибок**: унифицированный формат ошибок при неверной пагинации.
- **Курсорная пагинация**: сложнее прозрачно проксировать, так как курсор обычно генерируется сервисом. Gateway может лишь прокидывать курсор туда и обратно. Альтернатива: Gateway предоставляет offset-based пагинацию, а внутри преобразует в cursor (если сервис предоставляет такой mapping, что редко).
- **Реализация на Go**: промежуточный слой с `http.Handler`, который парсит query, валидирует и строит новый запрос к upstream.

Пример middleware для нормализации пагинации:

```go
func normalizePagination(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        q := r.URL.Query()
        limit := q.Get("page[limit]")
        if limit == "" { limit = "20" }
        if l, _ := strconv.Atoi(limit); l > 100 { limit = "100" }
        q.Set("page[limit]", limit)
        r.URL.RawQuery = q.Encode()
        next.ServeHTTP(w, r)
    })
}
```

### Под капотом (internals)
- **Производительность**: парсинг query и копирование URL не должны замедлять запросы. Используем `url.Values` с осторожностью.
- **Совместимость с GRPC**: для gRPC Gateway (grpc-gateway) пагинация уже определена через proto опции; можно перехватывать и модифицировать запросы через HTTP middleware.

### Типичные ошибки кандидатов
1. **Gateway сам генерирует ответ, объединяя данные от нескольких сервисов (BFF) без нужды**
   Это усложняет gateway; лучше оставить агрегацию на клиенте или специализированном BFF.
2. **Не учитывают различия в семантике пагинации между сервисами**
   Один сервис использует offset, другой — cursor; навязывание общего стандарта может сломать консистентность. Идеально — стандартизировать на уровне компании.
3. **Забывают про метаданные пагинации в ответе (total count, next link)**
   Если gateway проксирует, он должен убедиться, что нижележащий сервис возвращает эти данные, либо обогащать сам (дорого).
4. **Не кешируют ответы с фильтрами, создавая нагрузку**
   Простые фильтры могут быть закэшированы, но нужна инвалидация.

### Возможные дополнительные вопросы интервьюера
*Как реализовать пагинацию через курсор, если сервис не поддерживает?*
Gateway может запросить полный список с offset, сам построить курсор и кэшировать, но это неэффективно и нарушает согласованность. Лучше обновить сервис.
*Как передавать фильтры в формате JSON:API?*
Принимаем `filter[field]=value`, преобразуем к формату сервиса. В Go используем библиотеки типа `github.com/google/go-querystring`.
*Как бороться с дублированием логики пагинации в каждом сервисе?*
Создать общую библиотеку/модуль на Go, которую подключают все сервисы.

## Как управлять консистентностью данных, когда бизнес-логика размазана по нескольким сервисам без оркестратора?

### Краткий ответ
Консистентность обеспечивается через хореографию (события) с атомарной публикацией (transactional outbox), компенсирующими действиями (Saga), идемпотентностью и eventual consistency. Каждый сервис владеет своими данными, гарантируя локальную консистентность и публикуя события об изменениях.

### Развёрнутый ответ
Распределённая транзакция без оркестратора:
- **Outbox pattern**: сервис в транзакции с бизнес-операцией вставляет запись в outbox таблицу. Отдельный процесс (воркер) читает outbox и публикует сообщение в брокер. Это гарантирует атомарность «изменение + сообщение».
- **Saga через хореографию**: каждый сервис, услышав событие, выполняет свою локальную транзакцию и публикует следующее событие. При ошибке он публикует событие ошибки, которое триггерит компенсацию у предыдущих сервисов.
- **Идемпотентность**: обработчики событий должны быть идемпотентны (проверка по ID операции/события).
- **Гарантия доставки**: at-least-once брокер + идемпотентный потребитель дают eventual consistency без оркестратора.
- **Мониторинг состояния процесса**: для отслеживания прогресса можно собирать события в центральный лог или использовать Correlation ID.
- **Согласованность чтения**: клиент может видеть временно несогласованные данные. Используем read-your-writes через ожидание подтверждения события или polling.

Пример outbox публикации на Go:

```go
func PlaceOrder(db *sql.DB, order Order) error {
    tx, _ := db.Begin()
    insertOrder(tx, order)
    insertOutbox(tx, "OrderPlaced", marshal(order))
    return tx.Commit()
}
```

### Под капотом (internals)
- **Outbox publisher**: воркер на горутинах читает outbox таблицу с `SELECT ... FOR UPDATE SKIP LOCKED` для конкурентной обработки. После отправки удаляет запись или помечает.
- **Дедупликация**: храним обработанные event ID в таблице с TTL, либо в Redis с bloom фильтром.

### Типичные ошибки кандидатов
1. **Отсутствие компенсационной логики для всех шагов**
   Если сервис C падает после того как A и B выполнили свои действия, система останется в несогласованном состоянии. Компенсации обязательны.
2. **Публикация события до фиксации транзакции**
   Если событие уходит до commit’а, а транзакция откатилась, другие сервисы получат ложное событие. Outbox решает проблему.
3. **Игнорирование дублирования событий (at-least-once)**
   Потребитель получит событие минимум один раз -> без идемпотентности будет двойное списание и т.п.
4. **Зацикливание компенсаций (компенсация вызывает новую ошибку)**
   Компенсации должны быть идемпотентны и не приводить к повторным изменениям.

### Возможные дополнительные вопросы интервьюера
*Когда стоит использовать оркестратор вместо хореографии?*
Когда процесс сложный, с условной логикой, тайм-аутами, ветвлениями — оркестратор (Temporal, Camunda) упрощает видимость и управление.
*Как отслеживать текущее состояние распределённой транзакции?*
Ввести сервис отслеживания процесса (process manager), который слушает все события и хранит состояние процесса.
*Как обрабатывать ситуации, когда компенсация не удаётся?*
Повторять с backoff, эскалировать на ручную обработку, использовать сагу с сохранением состояния для ручного вмешательства.

## Как оценить влияние нового рантайма Go (например, переход с 1.21 на 1.24) на production?

### Краткий ответ
Оценка проводится через бенчмаркинг типовых рабочих нагрузок на тестовом стенде, сравнение профилей производительности (CPU, память, GC), чтение release notes на предмет изменений в runtime/компиляторе, и канареечный деплой с детальным мониторингом A/B тестов в проде с возможностью отката.

### Развёрнутый ответ
Процесс:
1. **Изучение changelog и известных проблем**: читаем `go1.24 release notes`, особое внимание на runtime, compiler, GC, syscall изменения. Например, в 1.22 был улучшен escape analysis, что может повысить производительность.
2. **Статический анализ совместимости**: `go fix`, `go vet` с новым компилятором на кодовой базе, поиск устаревших API.
3. **Микробенчмарки**: запуск `go test -bench` для критических пакетов на старом и новом окружении, сравнение с `benchstat`. Важно: бинарники должны быть скомпилированы соответствующими версиями на одном железе.
4. **Макротесты на изолированном стенде**: реалистичный трафик (replay production). Измеряем latency процентили, пропускную способность, потребление CPU/памяти.
5. **Канареечный деплой**: запуск 1-2% трафика на новой версии в production, автоматическое сравнение с предыдущей версией по золотым сигналам, GC паузам (`go_gc_duration_seconds`), количеству горутин.
6. **Скрипт автоматического отката**: при ухудшении любой метрики > X% возврат на старую версию.
7. **Особое внимание к PGO**: если в проекте используется Profile-Guided Optimization, необходимо перегенерировать профили на новой версии, так как изменения компилятора могут повлиять на оптимальный профиль.

### Под капотом (internals)
- **Изменения в планировщике**: в последних версиях улучшают работу с таймерами, снижают contention. Можно ожидать лучшую масштабируемость на высоком числе ядер.
- **GC pacer**: корректировки могут изменить частоту и длительность пауз; мониторим `go_memstats_gc_cpu_fraction`.
- **Стандартная библиотека**: могут быть изменения в HTTP-серверах, JSON. Тесты должны покрывать интеграции.

### Типичные ошибки кандидатов
1. **Пропуск миграции промежуточных версий**
   Переход сразу с 1.21 на 1.24 может наступить на скрытые регрессии, лучше шагать через мажорные версии и тестировать каждую.
2. **Игнорирование изменений в линкере и binary size**
   Иногда бинарник становится больше, что влияет на время развёртывания.
3. **Проверка только собственного кода, но не зависимостей**
   Сторонние библиотеки могут использовать несовместимые функции (например, `//go:linkname`). Запускать полный набор тестов.
4. **Не сравнивать сценарии с включенным `GOEXPERIMENT`**
   Некоторые улучшения требуют явного включения (arenas, новых аллокаторов). Если планируется их использовать, тестировать с ними.

### Возможные дополнительные вопросы интервьюера
*Как автоматизировать проверку на регрессии производительности в CI?*
Создать пакет бенчмарков, который запускается в CI на PR и сравнивается с базой (benchstat github action).
*Что делать, если новая версия улучшила latency, но увеличила потребление памяти?*
Оценить trade-off: стоимость дополнительной памяти vs улучшение задержки. Может быть приемлемо, если укладываемся в лимиты.
*Как оценить эффект от новой фичи, например, `arena`?*
Написать микро-сервис, использующий арены, сравнить GC паузы и пропускную способность.

## Как выстроить процесс "постмортем без виноватых" (blameless postmortem) и внедрить его в культуру?

### Краткий ответ
Blameless postmortem фокусируется на системных причинах, а не на личностях. Ключевые элементы: безопасная психологическая среда, чёткий процесс документирования (таймлайн, root cause analysis, action items), акцент на обучении и улучшении системы, исключение наказаний. Внедрение через примеры лидерства и постоянное повторение принципов.

### Развёрнутый ответ
Шаги внедрения:
- **Лидерство**: CTO и VP Engineering должны публично демонстрировать, что цель постмортема — не найти козла отпущения, а улучшить систему. Любое обвинение пресекается.
- **Шаблон документа**: включает хронологию событий, затронутые пользователи, корневую причину, что сработало хорошо, что нет, план действий. Категорически без указания виновных лиц.
- **Процесс**: сразу после инцидента собирается встреча, любой может участвовать. Ведущий управляет дискуссией, удерживая фокус на фактах и системе. Результаты публикуются для всей компании.
- **Корневой анализ**: используем методику "5 почему" или причинно-следственный анализ, чтобы докопаться до системных проблем (отсутствие мониторинга, недостаточное тестирование).
- **Action items**: каждый пункт имеет владельца и срок; обязательно отслеживать выполнение.
- **Обучение**: проводить тренинги по когнитивным искажениям, рассказывать успешные кейсы (как постмортем предотвратил повторение).
- **Практика на Go**: для Go-сервисов постмортем может выявить, что отсутствие context timeout привело к утечке горутин, и мы добавили `context.WithTimeout`. Важно зафиксировать не «разработчик забыл», а «линтер не настроен на проверку», «шаблон кода не включал таймаут».

### Под капотом (internals)
Это процесс, а не код. Но можно инструментировать:
- **Автоматический сбор дашбордов** на момент инцидента (Grafana snapshot) для постмортема.
- **Чек-листы** в виде формализованных правил проверки после инцидента (анализ алертов).

### Типичные ошибки кандидатов
1. **Формальное проведение постмортема с поиском «человеческой ошибки»**
   Рут-коз определяется как «человеческий фактор»; это останавливает на первом симптоме. Нужно копать: «почему человек ошибся? Сложный UI? Усталость? Недостаток документации?»
2. **Не выполнять action items**
   Постмортем превращается в бессмысленную бюрократию, доверие падает. Менеджмент должен отслеживать завершение.
3. **Ограничение доступа к постмортему**
   Публикация только внутри команды не позволяет другим учиться. Делиться максимально широко (с учётом чувствительных данных).
4. **Создание атмосферы страха**
   Если после инцидента виновного наказывают, люди будут их скрывать. Нужна политика «безопасности» (psychological safety).

### Возможные дополнительные вопросы интервьюера
*Как реагировать, если один и тот же человек постоянно становится причиной инцидентов?*
Анализировать системно: может быть, его неправильно обучают, его код не ревьюят, или он работает над слишком сложными компонентами в одиночку. Помогать, а не увольнять.
*Как внедрить постмортемы в культуру, где принято искать виноватых?*
Начать с «пилотного» проекта с поддержкой руководства, показать результаты (предотвращённые инциденты), постепенно расширять.
*Как интегрировать постмортем в процесс CI/CD?*
Автоматически создавать черновик постмортема из алертов и timelines, которые инженеры дополняют.

## Как спроектировать систему с "Event Sourcing" на Go, способную воспроизводить состояние на любой момент времени?

### Краткий ответ
Event Sourcing хранит все изменения (события) как источник истины. Состояние агрегата восстанавливается применением событий по порядку. Для воспроизведения на любой момент времени используется Event Store с возможностью чтения до определённого sequence number или времени, и снапшоты для ускорения.

### Развёрнутый ответ
Архитектура:
- **Event Store**: БД или специальное хранилище (EventStoreDB, PostgreSQL с таблицей событий). Каждое событие принадлежит агрегату с version/sequence.
- **Агрегат**: в Go представлен структурой с методами `Apply(event)`. При загрузке агрегата читаем все события для данного aggregateID, применяем последовательно, получаем текущее состояние.
- **Снапшоты**: периодически сохраняем состояние агрегата с версией. При восстановлении загружаем последний снапшот и применяем события после него.
- **Воспроизведение на момент времени T**: чтение событий с условием `timestamp <= T` (если хранится временная метка). Если без времени, но нужно состояние на момент X, обычно X — версия события; достаточно читать до нужной версии.
- **Прогнозы (projections)**: для запросов строятся read-модели, обновляемые подпиской на события. Их тоже можно перестроить заново.
- **Преимущества Go**: горутины для параллельного применения событий к разным агрегатам, быстрая сериализация (Protobuf).
- **Библиотеки**: нет стандартной, но можно собрать самому, используя `gocassa` идейно.

Пример загрузки агрегата:

```go
type OrderAggregate struct {
    ID      string
    Status  string
    version int
}

func (o *OrderAggregate) Apply(event Event) {
    switch e := event.(type) {
    case OrderPlaced:
        o.Status = "placed"
    }
    o.version = event.Version()
}

func LoadOrder(store EventStore, id string) (*OrderAggregate, error) {
    events, _ := store.ReadEvents(id, 0) // все события
    order := &OrderAggregate{ID: id}
    for _, ev := range events {
        order.Apply(ev)
    }
    return order, nil
}
```

### Под капотом (internals)
- **Хранилище событий**: в PostgreSQL можно сделать таблицу `events (aggregate_id, version, event_type, payload, timestamp)`. Индекс по `(aggregate_id, version)`. Вставка с проверкой уникальности версии для optimistic concurrency.
- **Сериализация**: Protobuf oneof или `any` для полиморфных событий. В Go реализуем интерфейс `Event` и реестр типов.
- **Производительность**: при большом количестве событий нужно снапшотирование. Также можно использовать кэширование агрегатов в памяти с инвалидацией.

### Типичные ошибки кандидатов
1. **Отсутствие снапшотов, приводящее к долгой загрузке агрегатов с тысячами событий**
   Необходимо периодически сохранять состояние, иначе при старте или перестройке проекций неприемлемо долго.
2. **Неправильная обработка конкурентных записей**
   Применение событий должно происходить с проверкой версии; при конфликте повторять загрузку. Используем conditional update.
3. **Изменение логики Apply для старых событий**
   Исторические события неизменны; изменения в логике должны быть обратно совместимы или через upcaster (преобразование событий).
4. **Хранение событий без схемы реестра**
   Если удалить тип события, десериализация сломается. Нужно хранить маппинг или всегда сохранять события так, чтобы можно было игнорировать неизвестные.

### Возможные дополнительные вопросы интервьюера
*Как перестроить проекции, если изменилась бизнес-логика?*
Запустить пересчёт всех событий с начала времени в новую read-модель параллельно с работой старой, потом переключить трафик.
*Как обеспечить порядок событий в распределённой системе?*
События одного агрегата должны обрабатываться в одной партиции и последовательно. Используем routing key = aggregateID.
*Как удалить данные (GDPR) в Event Sourcing?*
Тяжело; используем crypto-shredding (шифрование данных, удаление ключа) или обфускацию событий post-hoc (запись корректирующих событий).

## Как построить "Data Mesh" архитектуру на Go?

### Краткий ответ
Data Mesh — децентрализованный подход к управлению данными, где доменные команды владеют своими данными как продуктом. На Go создаются self-serve data платформы, API для доступа, стандарты контрактов (схемы), и инструменты федеративного управления (каталог, lineage). Архитектура включает data product, output port, discovery.

### Развёрнутый ответ
Ключевые компоненты:
- **Data Product**: каждый микросервис (или группа) предоставляет свои данные через чётко определённые API (синхронные или потоковые). В Go реализуется как gRPC сервис или топик Kafka с schema registry.
- **Self-serve платформа**: набор инструментов, позволяющих командам публиковать, обнаруживать, мониторить и потреблять данные. Платформа на Go предоставляет операторы Kubernetes, CLI.
- **Федеративное управление**: глобальные политики (форматы, качество, PII), реализованные через проверки в CI/CD или на уровне платформы (Policy as Code, OPA).
- **Интероперабельность**: стандартный формат данных (Protobuf, Avro), реестр схем (Apicurio, Confluent).
- **Обнаружение**: центральный каталог метаданных (DataHub, Amundsen), куда автоматически регистрируются data product’ы.
- **Мониторинг качества**: встроенные средства валидации данных, алерты на дрифт схемы.
- **Go-инструменты**: библиотеки для работы с Avro/Protobuf; SDK для взаимодействия с каталогом.

Пример регистрации data product в Go:

```go
func registerDataProduct(svc DataProductService, catalog CatalogClient) {
    dp := DataProduct{Name: "orders", Owner: "order-team", Schema: "protobuf:OrderEvent", Endpoint: "kafka:orders-topic"}
    catalog.Register(dp)
}
```

### Под капотом (internals)
- **Schema Registry клиент на Go**: для Avro (`github.com/hamba/avro`) и Protobuf; кэширование схем.
- **Потоковая передача**: Kafka consumer/producer обёртки с автоматической регистрацией схем.
- **Платформа**: операторы на основе `controller-runtime` для управления жизненным циклом data product'ов (провижининг топиков, прав).

### Типичные ошибки кандидатов
1. **Создание центральной команды данных, владеющей всеми данными**
   Это противоречит идее Data Mesh. Владение у доменных команд.
2. **Игнорирование качества данных**
   Продукты данных без проверок и мониторинга становятся «data swamps».
3. **Несовместимые схемы между продуктами без федеративного стандарта**
   Каждая команда изобретает своё, интеграция страдает. Нужен общий стандарт.
4. **Попытка внедрить Data Mesh без self-serve платформы**
   Ручное управление множеством продуктов невозможно. Платформа обязательна.

### Возможные дополнительные вопросы интервьюера
*Как гарантировать своевременность (freshness) данных продукта?*
Определить SLA на задержку доставки, мониторить и алертить; consumer’ы могут проверять метку времени.
*Как обрабатывать кросс-доменные запросы (join)?*
Использовать Data Product с агрегированной проекцией, либо federated query engine (Trino), который подключается напрямую к data product’ам.
*Как Go помогает в производительности обработки данных?*
Высокая эффективность процессорной обработки, хорошая поддержка конкурентности позволяет строить быстрые трансформации.

## Как оценить "TCO" (Total Cost of Ownership) для self-managed vs. managed решения?

### Краткий ответ
TCO учитывает затраты на инфраструктуру, лицензии, персонал (администрирование, разработка), время простоя и стоимость упущенных возможностей. Managed-решение обычно дороже по прямым затратам, но экономит на людях и рисках. Self-managed требует экспертизы и операционных затрат, но даёт контроль и потенциально меньшие переменные издержки при большом масштабе.

### Развёрнутый ответ
Компоненты TCO:
- **Инфраструктурные затраты**: compute, storage, network, резервное копирование. Для managed (RDS, Confluent Kafka) — ставка зависит от размера; для self-managed — стоимость виртуальных машин/подов.
- **Персонал**: сколько FTE инженеров нужно для управления self-managed (установка, обновление, мониторинг, бэкапы, безопасность). Managed требует меньше специалистов. Рассчитываем годовую зарплату.
- **Лицензии/платежи**: Enterprise версии self-managed могут требовать лицензий (например, Confluent Platform). Managed включает в стоимость услуги.
- **Затраты на простой и потери**: self-managed может иметь больше времени простоя из-за человеческих ошибок; оцениваем стоимость минуты простоя * вероятность.
- **Эффективность разработки**: managed сервис быстрее разворачивается, ускоряет time-to-market (недополученная прибыль из-за задержек).
- **Масштабирование**: при больших объёмах self-managed становится экономичнее, так как маржа cloud провайдера уменьшается.
- **Пример Go**: выбор между self-managed Redis on K8s в Go-приложении или ElastiCache. Self-managed требует оператора Redis, управление кластером, но даёт гибкость в конфигурации и потенциально дешевле при стабильной нагрузке.

Формула: `TCO = инфраструктура_в_год + (зарплата_инженеров) + стоимость_рисков`.

### Под капотом (internals)
- **Go инструменты для калькуляции**: можно написать модель в Go для симуляции затрат при разном масштабе.
- **Автоматизация**: если используется Kubernetes, self-managed может быть автоматизирован операторами, снижая operational burden.

### Типичные ошибки кандидатов
1. **Учёт только стоимости железа, игнорируя человеческие затраты**
   Самая дорогая часть — инженерное время. Managed-сервис может окупиться за счёт сокращения штата.
2. **Недооценка сложности операционного управления (бекапы, мониторинг, апдейты)**
   Self-managed базы данных требуют круглосуточной поддержки; стоимость дежурств может быть высока.
3. **Игнорирование cost of delay при внедрении**
   Managed решение запускается за часы, self-managed – дни/недели, что влияет на старт получения прибыли.
4. **Статичный расчёт TCO без учёта роста**
   На старте managed дешевле, с ростом объёмов self-managed становится выгоднее; нужно строить прогноз по годам.

### Возможные дополнительные вопросы интервьюера
*Как оценить окупаемость миграции с self-managed на managed?*
Посчитать текущие операционные затраты (люди + инциденты) и сравнить с будущей стоимостью managed. Если ROI > 0, миграция оправдана.
*Какие риски не покрываются TCO?*
Vendor lock-in, риск повышения цен провайдером, скрытые ограничения managed сервиса.
*Как Go-сообщество справляется с self-managed решениями?*
Много библиотек и операторов (например, VictoriaMetrics, etcd-operator), что облегчает жизнь, но всё равно требует экспертизы.

## Как управлять "раздуванием" API в микросервисной архитектуре и когда пора вводить BFF?

### Краткий ответ
«Раздувание» API происходит при разрастании числа endpoint’ов и версий, что усложняет клиентов. Управление: стандартизация API guidelines, депрекация, мониторинг использования. BFF (Backend for Frontend) вводится, когда разные клиенты (mobile, web) требуют разную агрегацию и формат данных, чтобы не усложнять общие сервисы.

### Развёрнутый ответ
Признаки необходимости BFF:
- Сильная разница в требованиях к данным между клиентами (mobile нужен сжатый ответ, web — расширенный).
- Частые запросы на изменение API от фронтенд-команд, затрагивающие бэкенд-сервисы (нарушение их стабильности).
- Сложная агрегация данных из многих микросервисов для одного экрана.
BFF — отдельный сервис (часто на Node.js/Go), который обслуживает конкретный фронтенд. Он агрегирует вызовы к микросервисам и формирует оптимальный ответ.
- **Управление раздуванием**: 
  - Полевой принцип: API возвращает только необходимые поля (sparse fieldsets).
  - Pagination по умолчанию.
  - Графический шлюз (GraphQL) может служить универсальным BFF, предоставляя клиенту возможность запрашивать только нужное. Однако GraphQL имеет свои сложности.
- **Go реализация**: BFF может быть написан на Go, используя параллельные вызовы к сервисам с `errgroup` и агрегацию.

Пример BFF агрегации:

```go
func userProfile(ctx context.Context, userID string) (*Profile, error) {
    userCh := async(func() *User { return userSvc.GetUser(ctx, userID) })
    ordersCh := async(func() []Order { return orderSvc.GetOrders(ctx, userID) })
    user, orders := <-userCh, <-ordersCh
    return &Profile{User: user, Orders: orders}, nil
}
```

### Под капотом (internals)
- **Параллельные запросы**: BFF может с помощью контекста с таймаутом и `errgroup` быстрее собрать данные.
- **Кэширование**: BFF может кэшировать ответы для снижения нагрузки.
- **Версионирование**: BFF может поддерживать несколько версий API фронтенда без изменения ядра.

### Типичные ошибки кандидатов
1. **Введение BFF на раннем этапе без необходимости**
   Это добавляет лишний слой и задержку. Пока один клиент — BFF не нужен.
2. **BFF начинает включать бизнес-логику**
   Превращается в монолитный бэкенд. BFF — только агрегация и адаптация, бизнес-логика остаётся в микросервисах.
3. **Игнорирование консистентности данных**
   Параллельные вызовы могут принести несогласованные данные (user обновился, а orders ещё нет). Нужно продумать, допустима ли eventual consistency.
4. **Отсутствие единых стандартов пагинации и линков**
   Каждый микросервис придумывает своё, BFF становится сложным адаптером. Нужны общие стандарты.

### Возможные дополнительные вопросы интервьюера
*Как GraphQL вписывается в микросервисную архитектуру?*
GraphQL gateway может выступать как универсальный BFF, делегируя запросы к gRPC сервисам через schema stitching.
*Как избежать дублирования логики в разных BFF?*
Вынести общие адаптеры в shared библиотеку; BFF разных клиентов могут переиспользовать функции преобразования.
*Как измерять эффективность BFF?*
Снижение количества запросов с клиента, уменьшение передаваемых данных, упрощение клиентского кода.

## Как использовать "формальные методы" или "моделирование" (TLA+) для верификации распределенных алгоритмов?

### Краткий ответ
Формальные методы, такие как TLA+, позволяют описать систему в виде конечного автомата и проверить свойства (инварианты) на всех возможных перестановках событий (model checking). Это помогает находить дедлоки, нарушения консистенции, гонки ещё до написания кода. Для Go-разработчика это способ убедиться в корректности алгоритма (например, лидера выборов, консенсуса).

### Развёрнутый ответ
Процесс:
- **Моделирование**: на TLA+ описываем состояние (variables), действия (операции), инварианты (свойства, которые всегда должны быть истинны). Например, для простого консенсусного алгоритма: `Invariant: ∀ node ∈ Nodes: node.status = Leader → только один лидер`.
- **Model checker (TLC)**: перебирает все возможные трассы с ограниченным множеством (model), проверяет инварианты. Находит минимальную трассу нарушения.
- **Применение в Go**: 
  - Проектирование сложного протокола (например, custom Raft).
  - Проверка взаимодействия горутин с разделяемыми ресурсами (каналы, мьютексы) через PlusCal.
- **Go integration**: хотя нет прямой кодогенерации, можно использовать модель как спецификацию и тестировать реализацию через property-based testing (gopter) для проверки соответствия свойствам.
- **Польза**: экономия времени на поиск трудноуловимых багов в распределённых системах.

Пример TLA+ простого счётчика с инвариантом: никогда не отрицательный.

### Под капотом (internals)
- **TLA+ model**: математика множеств, а не код. Переводят алгоритм на формулы.
- **Верификация**: TLC исследует пространство состояний; ограничиваем симметрией, чтобы не взорвалось.
- **Go testing**: дополнительно `go test -race` находит гонки в конкретных трассах, но не исследует все перестановки.

### Типичные ошибки кандидатов
1. **Попытка верифицировать весь код, а не алгоритм**
   Формальные методы применимы к дизайну, а не к реализации. Моделируют протокол, а не Go код.
2. **Игнорирование абстракции, приводящее к взрыву состояний**
   Моделируют низкоуровневые детали (сокеты); нужно абстрагировать сеть (доставка сообщений, дупликация).
3. **Отсутствие связи между моделью и кодом**
   Модель проверили, а код написали с отклонениями. Нужны ручные проверки соответствия.
4. **Только формальные методы без нагрузочного тестирования**
   Они не гарантируют производительность; нужны дополнительные тесты.

### Возможные дополнительные вопросы интервьюера
*Как убедить команду использовать TLA+?*
Показать примеры от Amazon (DynamoDB, S3), где формальные методы предотвратили серьёзные баги.
*Есть ли инструменты на Go для model checking?*
Существует `golang.org/x/tools/go/ssa` и `gobra` (верификация на основе аннотаций), но не такие мощные как TLA+. Для model checking каналов можно использовать `gopter`.
*Как включить TLA+ в CI?*
Запускать TLC проверку модели с определёнными параметрами на PR; если инвариант нарушен, сборка падает.

## Как внедрять "Green IT" практики в разработку и как Go помогает в этом?

### Краткий ответ
Green IT нацелено на снижение углеродного следа ПО через оптимизацию потребления ресурсов и эффективное использование аппаратуры. Go помогает благодаря компиляции в нативный код, низкому потреблению памяти и CPU по сравнению с интерпретируемыми языками, возможности тонкой настройки, что сокращает число требуемых серверов и энергии.

### Развёрнутый ответ
Практики Green IT:
- **Оптимизация ресурсоёмкости кода**: использование профилирования для снижения CPU и памяти. Меньше CPU — меньше энергопотребление.
- **Эффективное масштабирование**: автоскейлинг вниз до нуля (scale to zero) с помощью KEDA; в Go быстрый старт позволяет быстро подниматься.
- **Управление жизненным циклом данных**: удаление неиспользуемых данных, сжатие, уменьшение объёма хранилища.
- **Carbon-aware scheduling**: запуск batch-задач в регионах/временах, где углеродный коэффициент низкий (используя API, например, Electricity Maps). В Go можно написать планировщик, учитывающий это.
- **Go особенности**:
  - Бинарный файл без зависимостей снижает сложность развёртывания и размер образов (scratch образы), уменьшая трафик и хранение.
  - Эффективный сборщик мусора и управление памятью позволяют экономить RAM.
  - Кросскомпиляция даёт возможность запускать на ARM (энергоэффективные процессоры, например, Graviton) без изменений.
- **Измерение**: инструментарий для оценки энергопотребления (Kepler, Scaphandre), интеграция с Prometheus. Go-сервис экспортирует метрики и может вычислять свой углеродный след.

Пример выбора ARM-архитектуры в Docker:

```dockerfile
FROM --platform=linux/arm64 golang:1.23-alpine AS builder
...
FROM arm64v8/alpine:3
```

### Под капотом (internals)
- **Компилятор Go**: последние версии (1.22+) внедряют улучшения, снижающие размер бинарника и повышающие производительность, что прямо влияет на энергопотребление.
- **Архитектура планировщика**: эффективное использование ядер -> меньше холостых циклов.

### Типичные ошибки кандидатов
1. **Green IT воспринимается только как использование облачных carbon offset’ов, а не через код**
   Реальная экономия ресурсов через оптимизацию кода эффективнее и дешевле.
2. **Игнорирование idle-потребления**
   Сервисы, работающие 24/7, даже с нулевой нагрузкой потребляют энергию. Scale-to-zero и эффективный планировщик Go помогают.
3. **Выбор неподходящей архитектуры процессора**
   Запуск на x86 без необходимости, когда ARM более энергоэффективен.
4. **Отказ от долгосрочных накопительных улучшений**
   Маленькие правки (убрать лишнюю аллокацию) кажутся мелочью, но на 10 000 серверов экономия значительна.

### Возможные дополнительные вопросы интервьюера
*Как измерить углеродный след конкретного микросервиса?*
Использовать метрики потребления CPU/памяти, умножить на коэффициенты энергопотребления инфраструктуры и коэффициент выбросов CO2 для региона (PUE, CF).
*Какие есть библиотеки в Go для carbon-aware computing?*
Нет массовых, но можно использовать `go-carbon` или интегрироваться с API.
*Как убедить бизнес инвестировать в Green IT?*
Связать с экономией: снижение ресурсов напрямую уменьшает облачный счёт. Показать, что оптимизация окупается.
