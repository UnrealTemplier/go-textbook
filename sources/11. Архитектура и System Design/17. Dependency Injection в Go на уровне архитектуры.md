## Внедрение зависимостей как архитектурная дисциплина

В предыдущих главах мы детально препарировали многослойные структуры — от классической трёхслойки до гексагональной и чистой архитектур. Мы увидели, что краеугольным камнем гибкости, надежности и быстрой тестируемости системы является **инверсия управления (Inversion of Control)** и её главное практическое воплощение — **внедрение зависимостей (Dependency Injection, DI)**.

Однако при переходе в мир Go разработчики, воспитанные на традициях Java (Spring) или .NET (ASP.NET Core), часто испытывают когнитивный шок:
> *«Где же глобальный IoC-контейнер? Где аннотации `@Autowired` или `@Inject`? Неужели всё нужно передавать руками через аргументы конструкторов?!»*

Ответ создателей языка Go категоричен и прост: **да, зависимости должны внедряться явно**. В Go нет встроенной тяжеловесной магии рефлексии в рантайме, и это не упущение, а осознанная архитектурная победа. 

В этой главе мы исследуем Dependency Injection как строгую инженерную дисциплину. Мы разберём спектр решений — от лаконичных ручных конструкторов и функциональных опций до кодогенерации на этапе компиляции с помощью Google Wire и рантайм-графов Uber Fx. Мы выясним, как DI защищает границы слоев, почему идиома *«принимай интерфейсы, возвращай структуры»* спасает процессорные циклы и как не превратить сборку приложения в хаос скрытых связей.

### Что такое Dependency Injection и зачем оно нужно

В своей физической сути **Dependency Injection** — это элементарное инженерное правило: **компонент никогда не создаёт ресурсы, от которых зависит, самостоятельно — он смиренно получает их извне**.

Сравните два подхода из реального мира:
1. **Жесткая спайка**: Вы строите настольную лампу, намертво припаивая стеклянную колбу лампочки к электросети квартиры. Лампа светит, но когда нить накаливания перегорает, вам приходится сносить стену дома и менять проводку целиком.
2. **Внедрение через стандартный цоколь**: Лампа предоставляет универсальный патрон E27 (интерфейс). Вы можете вкрутить туда лампу накаливания, светодиодную энергосберегающую лампу или даже тестовый прибор проверки напряжения (мок). Лампе абсолютно безразлично, что именно в неё вкрутили, пока соблюдается геометрический и электрический контракт цоколя.

В архитектуре ПО внедрение зависимостей решает три фундаментальные задачи:
- **Слабая связанность (Loose Coupling)**: бизнес-логика зависит от абстрактного контракта (интерфейса), а не от капризов драйвера PostgreSQL или сетевого шлюза Stripe.
- **Молниеносная тестируемость**: в юнит-тестах вместо медленной базы данных передаётся легковесная in-memory заглушка.
- **Гибкость эволюции**: переход на новую базу данных или внедрение кэширующего слоя выполняется без правки единой строчки бизнес-правил.

В Clean Architecture ([[14. Clean Architecture и Dependency Rule]]) DI выступает главным физическим механизмом соблюдения **Правила зависимостей**: внутреннее ядро объявляет интерфейсы, внешние адаптеры реализуют их, а специальная точка сборки связывает их воедино:

### Идиоматичный DI в Go

Философия Go категорически отвергает скрытую магию и неявные эффекты. Идиоматичный DI в Go строится на трёх фундаментальных паттернах:

#### 1. Внедрение через конструктор (Constructor Injection)

Это канонический, наиболее надёжный и прозрачный способ организации зависимостей. Структура принимает все обязательные зависимости в качестве параметров функции-конструктора (`NewService`) и сохраняет их в неэкспортированных полях:

```go
// internal/order/service.go
package order

import "context"

type Repository interface {
    Save(ctx context.Context, order *Order) error
}

type Logger interface {
    Info(msg string, args ...any)
}

type Service struct {
    repo   Repository
    logger Logger
}

// NewService - конструктор делает зависимости обязательными и проверяемыми компилятором
func NewService(repo Repository, logger Logger) *Service {
    return &Service{
        repo:   repo,
        logger: logger,
    }
}

func (s *Service) Create(ctx context.Context, req CreateRequest) (*Order, error) {
    // использование s.repo, s.logger
    return nil, nil
}
```

**Преимущества:**
- **Абсолютная статическая прозрачность**: структуру невозможно создать в невалидном полуинициализированном состоянии. Если разработчик забыл передать репозиторий, программа просто не скомпилируется.
- **Нулевая магия**: при чтении кода вы мгновенно видите полный граф связей объекта.
- **Тривиальное тестирование**: подмена зависимостей на моки выполняется в одну строчку.

**Инженерный сигнал (Code Smell):**
Если ваш конструктор разрастается до 6–8 и более параметров — это громкий сигнал тревоги: структура нарушает Single Responsibility Principle (SRP) и делает слишком много. Её необходимо декомпозировать на несколько сфокусированных сервисов.

#### 2. Функциональные опции (Functional Options)

Когда у компонента появляются необязательные зависимости (трассировщик OpenTelemetry, кастомный сборщик метрик Prometheus, таймауты), раздувать конструктор десятком `nil`-параметров становится неудобно. 

Паттерн функциональных опций решает эту проблему элегантно и типобезопасно:

```go
type ServiceOption func(*Service)

func WithMetrics(m Metrics) ServiceOption {
    return func(s *Service) {
        s.metrics = m
    }
}

func WithTracer(t Tracer) ServiceOption {
    return func(s *Service) {
        s.tracer = t
    }
}

func NewService(repo Repository, opts ...ServiceOption) *Service {
    s := &Service{
        repo:   repo,
        logger: defaultLogger,
    }
    for _, opt := range opts {
        opt(s)
    }
    return s
}

// Использование в точке сборки:
svc := NewService(repo, WithMetrics(prom), WithTracer(jaeger))
```

#### 3. Потребительские интерфейсы (Consumer-Driven Interfaces)

Фундаментальный постулат архитектуры Go: **интерфейсы объявляются там, где они потребляются, а не там, где реализуются**.

В языках с явной декларацией (Java) репозиторий объявляет интерфейс `OrderRepositoryInterface`, заставляя всех потребителей зависеть от своего раздутого пакета. 
В Go компилятор проверяет соответствие структурной сигнатуре (structural subtyping). Поэтому потребитель объявляет узкий, сфокусированный интерфейс, содержащий ровно те методы, которые нужны ему:

```go
// core/domain/order/service.go - вызывающая сторона
type OrderSaver interface {
    Save(ctx context.Context, order *Order) error
}

type OrderService struct {
    saver OrderSaver
}

// adapter/postgres/repo.go - реализация
type Repo struct { 
    db *sql.DB 
}

func (r *Repo) Save(ctx context.Context, order *Order) error {
    // сохранение в PostgreSQL...
    return nil
}

// Repo автоматически удовлетворяет OrderSaver, 
// хотя явно не объявляет implements и не знает о существовании OrderSaver!
```

### Композиционный корень: main.go

Точка сборки всей системы в архитектуре называется **Композиционным корнем (Composition Root)**. 

В Go-приложении эту священную роль исполняет функция `main()` (каталог `cmd/server/main.go`). Это единственное место во всей кодовой базе, которое обладает правом знать обо всех конкретных реализациях, драйверах, портах и пакетах:

```go
// cmd/server/main.go
package main

import (
    "log"
    "myapp/internal/config"
    "myapp/internal/handler/http"
    "myapp/internal/repository/postgres"
    "myapp/internal/service/order"
    "myapp/pkg/client/stripe"
)

func main() {
    cfg := config.MustLoad()
    logger := log.New(cfg.LogLevel)
    db := postgres.MustConnect(cfg.Database)
    
    // Внедрение зависимостей явно, прозрачно и упорядоченно:
    orderRepo := postgres.NewOrderRepository(db)
    paymentClient := stripe.NewClient(cfg.StripeKey)
    
    orderSvc := order.NewService(orderRepo, paymentClient, logger)
    orderHandler := http.NewOrderHandler(orderSvc, logger)
    
    srv := http.NewServer(cfg.HTTPPort, orderHandler)
    srv.Start()
}
```

> [!warning] Ловушка / Gotcha
> Никогда не пытайтесь имитировать контейнеры типа Spring через глобальные переменные и функции `init()`. 
> Инициализация синглтонов в `init()` порождает неявные зависимости, провоцирует циклические импорты, делает невозможным параллельный запуск юнит-тестов и превращает отладку порядка загрузки пакетов в ночной кошмар. 
> В Go глобальные переменные допустимы лишь для неизменяемых констант (`const`) или системных ошибок (`var ErrNotFound = ...`). Все жизненно важные зависимости должны передаваться в открытую через стек вызовов.

### Масштабирование DI: от явного к кодогенерации

Когда приложение разрастается от небольшого микросервиса до корпоративного модульного монолита на 200+ компонентов, ручное создание конструкторов в `main.go` может выродиться в сотни строк механической рутины. 

Для масштабирования DI в Go-сообществе сложились два диаметрально противоположных, но мощных инструмента: **Google Wire** и **Uber Fx**.

#### Wire (от Google): Статическая кодогенерация без рантайм-магии

`wire` — инструмент кодогенерации времени компиляции, созданный инженерами Google. Он не использует рефлексию в рантайме. Вместо этого `wire` анализирует типы конструкторов на этапе билда и генерирует абсолютно прозрачный, человекочитаемый файл `wire_gen.go`.

Разработчик пишет декларативный манифест сборки:

```go
// +build wireinject

package main

import (
    "github.com/google/wire"
)

func InitializeApp() (*App, error) {
    wire.Build(
        postgres.NewOrderRepository,
        stripe.NewPaymentClient,
        order.NewService,
        http.NewOrderHandler,
        http.NewServer,
        // wire самостоятельно найдет связи и построит направленный ациклический граф (DAG)
    )
    return nil, nil
}
```

После выполнения команды `wire` утилита создаёт чистый скомпилированный Go-код:

```go
// Code generated by Wire. DO NOT EDIT.
func InitializeApp() (*App, error) {
    db := postgres.MustConnect()
    orderRepo := postgres.NewOrderRepository(db)
    paymentClient := stripe.NewPaymentClient()
    orderSvc := order.NewService(orderRepo, paymentClient)
    orderHandler := http.NewOrderHandler(orderSvc)
    server := http.NewServer(orderHandler)
    return &App{Server: server}, nil
}
```

**Преимущества Wire:**
- **Полная статическая безопасность**: если вы забыли объявить конструктор для логгера, ошибка возникнет ещё до компиляции бинарника.
- **Нулевой оверхед по скорости и памяти**: сгенерированный код работает так же быстро, как если бы вы написали его руками.
- Легкая интеграция с `go generate`.

#### Fx (от Uber): Рантайм-контейнер с управлением жизненным циклом

`fx` — это полноценный DI-фреймворк, использующий рефлексию при старте приложения. Он берёт на себя не только внедрение зависимостей, но и управление жизненным циклом компонентов (**Lifecycle**): регистрацию хуков старта и остановки (graceful shutdown), отслеживание фоновых воркеров и оркестрацию очередей.

```go
package main

import (
    "go.uber.org/fx"
)

func main() {
    fx.New(
        fx.Provide(
            postgres.NewOrderRepository,
            stripe.NewPaymentClient,
            order.NewService,
            http.NewOrderHandler,
            http.NewServer,
        ),
        fx.Invoke(func(*http.Server) {}),
    ).Run()
}
```

**Когда использовать Fx вместо Wire:**
- Сервису требуется глубоко оркестрованное управление жизненным циклом (запуск 10 параллельных фоновых демонов, которые обязаны гаситься в строго обратном порядке при получении сигнала `SIGTERM`).
- Проект строится на унифицированном стеке библиотек Uber (Zap, Jaeger, Fx).

> [!info] Под капотом
> С точки зрения вычислительной эффективности ручные конструкторы и Google Wire абсолютно эквивалентны: компилятор Go генерирует прямые машинные инструкции размещения структур на стеке или в куче, а линкер разрешает адреса на этапе сборки. 
> Uber Fx при запуске процесса тратит десятки миллисекунд процессорного времени на обход графа через пакет `reflect` и аллокацию метаданных. Однако после завершения этапа инициализации графа в рантайме разница в производительности между ними полностью нивелируется. Тем не менее, для serverless-функций и быстрых CLI-утилит fast boot критичен — там Wire безоговорочно выигрывает.

### DI и архитектурные границы

Стиль внедрения зависимостей неразрывно связан с выбранной макроархитектурой:

| Архитектура | Механизм DI | Где объявляются интерфейсы | Особенности связывания |
|---|---|---|---|
| **Трехслойка** | Ручные конструкторы или прямые вызовы | Редко; иногда в пакете repository | Слабо выраженный DI, частая связка по конкретным структурам |
| **Clean Architecture** | Строгий явный DI через конструкторы | В слое Use Cases | Ядро не знает о внешних адаптерах; зависимости строго внутрь |
| **Hexagonal** | Явный DI (вручную или Wire) | Порты ядра (In/Out Ports) | Адаптеры подключаются как взаимозаменяемые плагины |
| **Модульный монолит** | Модульные подграфы + Wire в `main` | Внутри каждого доменного модуля | Модули экспортируют фабрики; `main` связывает их через контракты |

В модульном монолите ([[10. Модульный монолит как компромисс]], [[12. Domain Driven Design. Bounded Context и Aggregate]]) каждый суверенный модуль экспортирует собственный изолированный конструктор, скрывая внутренние детали под `internal/`. Внешний `main.go` соединяет модули исключительно через их публичные интерфейсы.

### Тестирование с DI

Наивысшая награда за дисциплину DI — это лёгкость и скорость модульного тестирования. Вам больше никогда не придётся мучительно патчить глобальные переменные или запускать тяжеловесные Docker-контейнеры ради проверки одного условия в функции:

```go
// internal/order/service_test.go
package order_test

import (
    "context"
    "testing"
    "myapp/internal/order"
)

type mockRepo struct {
    orders map[string]*order.Order
}

func (m *mockRepo) Save(ctx context.Context, o *order.Order) error {
    m.orders[o.ID] = o
    return nil
}

func TestCreateOrder(t *testing.T) {
    // Создаем изолированный мок в оперативной памяти:
    repo := &mockRepo{orders: make(map[string]*order.Order)}
    logger := &mockLogger{}

    // Внедряем заглушки напрямую в тестируемый сервис:
    svc := order.NewService(repo, logger)

    req := order.CreateRequest{UserID: "usr-1", Amount: 500}
    created, err := svc.Create(context.Background(), req)
    
    if err != nil {
        t.Fatalf("unexpected error: %v", err)
    }
    if _, exists := repo.orders[created.ID]; !exists {
        t.Errorf("expected order to be persisted in repository")
    }
}
```

Этот тест выполняется за единицы микросекунд, полностью изолирован от внешнего мира и может безбоязненно запускаться в сотнях параллельных потоков (`t.Parallel()`).

### Mechanical Sympathy: аллокации и DI

Как внедрение зависимостей влияет на аппаратные регистры и память?

Вызов метода через интерфейс требует обращения к таблице методов `itab` (два разыменования указателя). Это ничтожная плата, но в ней кроется тонкий нюанс аллокатора Go:
Если конструктор возвращает **интерфейс**, а не конкретную структуру, escape analysis компилятора часто не может доказать время жизни объекта и вынужден аллоцировать его в куче (heap allocation), даже если он мог бы спокойно жить на стеке!

Поэтому в Go действует фундаментальное каноническое правило:
> **«Accept interfaces, return structs» (Принимай интерфейсы, возвращай структуры).**

```go
// Идиоматично: принимает абстрактный интерфейс, возвращает конкретный указатель на структуру
func NewService(repo Repository) *Service {
    return &Service{repo: repo}
}

// Антипаттерн: возвращает абстрактный интерфейс без крайней необходимости
func NewService(repo Repository) OrderService {
    return &Service{repo: repo}
}
```

Возвращая конкретную структуру `*Service`, вы даёте компилятору возможность оптимизировать машинный код, применять инлайнинг и снижать нагрузку на Garbage Collector.

### Антипаттерны DI в Go

При проектировании связей в Go-системах остерегайтесь четырёх классических антипаттернов:

1. **Service Locator (Глобальный ящик зависимостей)**:  
   Создание глобальной переменной `App.Services` или реестра `вызов `Get("order")` в коде`. Это чудовищно маскирует реальные зависимости: вызывающий код делает вид, что он автономен, но падает в рантайме с `nil pointer dereference`, если локатор не был заполнен.
2. **Интерфейсы ради интерфейсов**:  
   Штампование интерфейса на каждую структуру приложения по привычке из Java (например, `type UserServiceInterface interface`). Если у структуры есть ровно одна реализация и она не участвует в полиморфизме или модульном тестировании — интерфейс не нужен! Создавайте интерфейсы только там, где есть реальная потребность в полиморфизме или подмене моками.
3. **Внедрение через публичные поля (Field Injection)**:
   ```go
   svc := &Service{}
   svc.Repo = repo // ОШИБКА: можно забыть проинициализировать поле и получить панику в рантайме
   ```
   Всегда требуйте зависимости через явные параметры конструктора.
4. **Преждевременное усложнение (Overengineering)**:  
   Подключение тяжеловесных генераторов Wire или контейнеров Fx в микросервис из двух хэндлеров. Начинайте с простого ручного связывания в `main.go`.

---

> [!tip] Собеседование
> **Вопрос:** Как бы вы организовали внедрение зависимостей в высоконагруженном Go-проекте с 20+ сложными сервисами? Станете ли использовать Wire, Uber Fx или обойдетесь обычными конструкторами?
> **Ответ:** 
> Я выберу прагматичный поэтапный подход:
> 1. **Старт**: Для компонентов каждого доменного модуля я использую явные ручные конструкторы, строго следуя принципу «принимай интерфейсы, возвращай структуры».
> 2. **Масштабирование**: Когда количество компонентов переваливает за 15–20, а ручное связывание в `main.go` начинает занимать экраны однотипного кода, я подключаю **Google Wire**. Wire работает на этапе сборки через кодогенерацию, гарантирует статическую типизацию (ошибки ловятся до запуска), не требует рантайм-рефлексии и обеспечивает мгновенный старт бинарника.
> 3. **Альтернатива (Fx)**: Фреймворк `uber-go/fx` я выберу только в том случае, если системе требуется централизованное управление сложным параллельным жизненным циклом десятков сервисов (shutdown-хуки, фоновые потребители Kafka, очереди), а команда уже пишет на унифицированном Uber-стеке.

### Итог

Dependency Injection в Go — это не тяжеловесный фреймворк, а дисциплина чистоты связей. Выражаясь языком Кернигана: ясность, простота и явность побеждают любую магию. Конструкторы, принимающие интерфейсы и возвращающие структуры, в связке с точкой сборки в `main.go` формируют надежнейший скелет вашего приложения.

Теперь, когда мы умеем виртуозно конструировать и связывать сервисы, возникает следующий насущный вопрос: откуда эти сервисы должны черпать параметры, порты, секреты и параметры окружения?
