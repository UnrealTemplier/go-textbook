В прошлой статье [[5. Vector clocks]] мы научились с помощью строгой математики выявлять параллельные события. Мы поняли: если векторные часы двух записей конкурентны (`V1 || V2`), ни одна из них не имеет превосходства над другой. 

В этот момент распределенное хранилище отказывается принимать волевые решения и сохраняет оба варианта — создавая так называемых «братьев» (**Siblings** или ветви реальности).

Но база данных не может вечно пребывать в состоянии квантовой неопределенности. Рано или поздно эти параллельные ветки реальности обязаны сойтись в единое итоговое состояние. 

Процесс превращения набора конфликтующих версий в одно согласованное значение называется **Conflict Resolution (Разрешением конфликтов)**.

В архитектуре распределенных систем существует три принципиально разных пути решения этой дилеммы: грубый автоматический, осознанный прикладной (на стороне клиента) и элегантный математический.

---

## 1. Автоматическое разрешение: Last Write Wins (LWW)

Самый распространенный, самый быстрый и одновременно... самый коварный и опасный подход в индустрии.

При стратегии **Last Write Wins (LWW)** координатор базы данных просто смотрит на физический `timestamp` записи, проставленный сервером или клиентом. Тот, чье число оказалось больше — объявляется победителем. Все остальные конфликтующие записи просто молча удаляются из хранилища.

> [!warning] Ловушка / Gotcha: Потеря данных из-за дрейфа часов
> Как мы подробно разбирали в статье [[5. Time и clock drift]], физические кварцевые генераторы на серверах никогда не идут синхронно.
> 
> Представьте: 
> * Клиент А записал `x = 10` в 10:00:01 по реальному физическому времени на сервере А.
> * Клиент Б секундой позже записал `x = 20` в 10:00:02 на сервере Б, но на сервере Б часы отстают на 2 секунды (показывая 10:00:00).
> 
> При использовании LWW победит устаревшая запись `x = 10`, а свежая `x = 20` будет навсегда стерта! 
> 
> LWW — это сознательный, циничный компромисс: отказ от гарантии целостности данных ради простоты и минимальной задержки. Именно так по умолчанию работает Apache Cassandra.

## 2. Разрешение на стороне клиента (Application-side)

Этот подход исповедуют по-настоящему надежные децентрализованные хранилища (такие как Riak KV или Dynamo-кластеры с отключенным LWW).

База данных не пытается угадать намерения человека. Обнаружив конкурентные версии, база данных при вызове `GET` возвращает в Go-приложение **полный срез всех конфликтующих сиблингов вместе с их векторными часами**.

Ответственность за примирение версий целиком перекладывается на плечи бэкенд-разработчика, который лучше любого алгоритма понимает семантику своей предметной области.

---

### Пример: Корзина интернет-магазина

Представьте корзину покупателя интернет-магазина. Пользователь открыл приложение на смартфоне и на ноутбуке одновременно:
* На телефоне он положил в корзину: `[Apple, Banana]`.
* На ноутбуке он в ту же секунду добавил: `[Apple, Orange]`.

Векторные часы зафиксировали конфликт. Что должен сделать Go-бэкенд?  
Удалить апельсин по таймстампу LWW было бы бизнес-катастрофой (покупатель разозлится и уйдет к конкурентам).

Единственно верное бизнес-решение — выполнить **объединение множеств (Set Union)**, получив в результате: `[Apple, Banana, Orange]`.

```go
package cart

import (
	"myproject/vclock"
)

type Cart struct {
	Items  []string
	VClock vclock.VectorClock
}

// ResolveConflicts выполняет доменное слияние сиблингов
func ResolveConflicts(siblings []Cart) Cart {
	if len(siblings) == 0 {
		return Cart{}
	}
	if len(siblings) == 1 {
		return siblings[0]
	}

	// Дедупликация товаров с помощью хэш-таблицы
	finalItems := make(map[string]struct{})
	mergedVClock := vclock.New("app-resolver")

	for _, s := range siblings {
		// Объединяем товары из всех конфликтующих ветвей
		for _, item := range s.Items {
			finalItems[item] = struct{}{}
		}
		// Сливаем векторные часы, аккумулируя максимумы версий
		mergedVClock.Merge(s.VClock.Clone())
	}

	result := Cart{
		VClock: *mergedVClock,
		Items:  make([]string, 0, len(finalItems)),
	}

	for item := range finalItems {
		result.Items = append(result.Items, item)
	}

	return result
}
```

> **Важнейшее правило (Write-Back):**  
> После того как Go-бэкенд объединил сиблингов, он **обязан отправить результат обратно в базу данных (Write-Back)** с объединенным векторным часом. Только тогда база данных поймет, что конфликт исчерпан, и удалит старых сиблингов с диска!

## 3. Магия слияния: CRDT

А что, если бы мы могли изначально проектировать структуры данных так, чтобы они **сходились к единому верному результату автоматически**, без необходимости писать кастомные резолверы в Go-коде и без риска потерять данные?

Такие математические конструкции существуют и называются **CRDT (Conflict-free Replicated Data Types)**.

---

### Принцип работы CRDT

CRDT опираются на фундаментальную алгебраическую структуру — полурешетку (Join-Semilattice). 

Если операция слияния двух состояний обладает тремя свойствами:
1. **Коммутативность:** $A \cup B = B \cup A$ (порядок прихода пакетов из сети не имеет значения).
2. **Ассоциативность:** $(A \cup B) \cup C = A \cup (B \cup C)$ (группировка реплик не влияет на итог).
3. **Идемпотентность:** $A \cup A = A$ (повторная доставка дубликатов сообщений безопасна).

то распределенные узлы гарантированно придут к **абсолютно идентичному состоянию** при получении одних и тех же данных в любом хаотичном порядке!

---

#### G-Counter (Grow-only Counter)

Обычный `int64` инкремент в распределенной системе без блокировок невозможен — обновления потеряются. 

**G-Counter** решает это, превращая счетчик в вектор: каждый узел увеличивает только свой персональный слот:
* Узел А прибавляет единицу: `[A:1, B:0]`.
* Узел Б параллельно прибавляет единицу: `[A:0, B:1]`.
* Слияние выполняется тривиальной функцией `max()` по каждой ячейке: `[A:1, B:1]`.
* Текущее глобальное значение счетчика — это сумма всех ячеек: $1 + 1 = 2$. Ни один клик или просмотр не потерян!

---

#### PN-Counter (Positive-Negative Counter)

Что, если счетчик нужно не только увеличивать, но и уменьшать (например, остаток товаров на складе или баланс бонусов)?

**PN-Counter** объединяет два независимых G-Counter:
* Счётчик `P` (Positive) аккумулирует все прибавления;
* Счётчик `N` (Negative) аккумулирует все вычитания.

Итоговое значение вычисляется как детерминированная разность: $\text{Value} = \sum P - \sum N$.

---

## Mechanical Sympathy: Реализация слияния в Go

В высоконагруженных Go-сервисах наивное слияние сиблингов через регулярное создание `map` (как в коде корзины выше) способно создать колоссальное давление на Garbage Collector. 

При тысячах разрешений конфликтов в секунду постоянные аллокации бакетов карт (`bmap`) в куче вызовут спайки задержек Stop-The-World.

> [!info] Под капотом: Zero-Allocation слияние
> Для максимальной производительности в рантайме Go идиоматично использовать сортировку слайсов вместо хэш-таблиц:
> 1. Собрать все строковые идентификаторы из сиблингов в один общий слайс, переиспользуемый из пула `sync.Pool`.
> 2. Отсортировать слайс в памяти вызовом `sort.Strings(items)` (быстрый Quicksort / Pattern-defeating Quicksort без аллокаций).
> 3. Удалить повторяющиеся дубликаты за один линейный проход методом двух указателей (Two Pointers).
> 
> Это на 100% исключает нагрузку на GC и позволяет процессору эффективно задействовать L1-кэш инструкций за счет последовательного обхода непрерывной памяти.

## Итог

1. **Conflict Resolution** — неизбежная реальность любой системы с Eventual Consistency.
2. **Last Write Wins (LWW):** Привлекателен скоростью, но разрушителен для бизнеса из-за неизбежного дрейфа физических таймстемпов.
3. **Application-side Merge:** Золотой стандарт для бизнес-критичных сущностей (корзины покупок, профили), требующий дисциплины Write-Back для очистки сиблингов.
4. **CRDT:** Вершина математической мысли распределенных систем, обеспечивающая детерминированное слияние без блокировок.

Глубокому математическому устройству бесконфликтных типов данных, их видам (CvRDT и CmRDT) и реализации распределенных множеств (OR-Set) посвящена наша следующая статья: [[7. CRDT]].

А после освоения CRDT мы перейдем к фундаментальной вершине координации данных — тому, как гарантировать атомарность сразу для множества сущностей через протоколы распределенных транзакций: [[8. Distributed transactions]].
