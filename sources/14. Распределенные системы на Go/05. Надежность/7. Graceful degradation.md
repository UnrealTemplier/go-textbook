## Искусство падать с достоинством: Эскалатор становится лестницей

В американском фольклоре есть знаменитая острота комика Митча Хедберга:  
> *«Эскалатор в принципе не способен сломаться: он может лишь временно стать лестницей. Вы никогда не увидите табличку „Эскалатор сломан“, а лишь „Эскалатор временно стал лестницей. Приносим извинения за удобство“».*

Это изящное наблюдение служит эталонной метафорой для любого зрелого архитектора распределенных систем.

Все защитные рубежи, которые мы спроектировали в предыдущих главах — [[1. Circuit breaker]], [[3. Timeout]], [[4. Bulkhead]] и [[5. Load shedding]] — это инструменты сугубо инженерной самообороны. Они спасают сервер от физической гибели, аварийно разрывая соединения и выбрасывая технические системные ошибки (`503 Service Unavailable` или `context.DeadlineExceeded`).

Но с точки зрения живого пользователя и бизнеса чистый сетевой отказ — это всегда поражение. Если в крупном интернет-магазине временно вышел из строя сложный сервис расчета персональных нейросетевых рекомендаций, покупатель в мобильном приложении не должен натыкаться на пустой экран с надписью «500 Internal Server Error». Он должен увидеть обычный базовый каталог популярных товаров! Эскалатор обязан стать удобной лестницей.

Паттерн **Graceful Degradation (Плавная деградация)** — это фундаментальная продуктовая и архитектурная стратегия ответа на неизбежные частичные сбои. Это способность распределенной системы сохранять ключевую бизнес-ценность и непрерывность пользовательского опыта даже тогда, когда половина её вспомогательных микросервисов лежит в руинах.

```mermaid
flowchart TD
    Req["Запрос клиента: Собрать страницу товара"] --> Primary["1. Запрос к Recommendation Service<br/>(через Circuit Breaker)"]

    Check -->|Да (200 OK)| Fresh["Fresh Data: Персональный AI-список"]

    StaleCheck -->|Нет| Default["3. Static Fallback: Топ продаж<br/>(Zero-Allocation глобальный срез)"]
    
    Fresh --> Assembly["Финальная сборка ответа"]
    Stale --> Assembly
    Default --> Assembly
```

## Иерархия ответов: От идеала к выживанию

Когда микросервис обращается к удаленным зависимостям, в архитектуре выстраивается строгая эшелонированная иерархия деградации:

1. **Primary (Свежие данные):** Идеальный сценарий. Зависимость ответила за расчетные 15 мс, данные актуальны на 100%.
2. **Stale Data (Устаревшие данные из кэша):** Зависимость недоступна или Circuit Breaker находится в состоянии `OPEN`. Мы заглядываем в локальный in-memory кэш и отдаем снимок данных, сохраненный 15 минут назад. В терминах компромисса [[6. Consistency vs availability]] мы осознанно жертвуем строгой согласованностью ради абсолютной доступности.
3. **Default / Static Data (Статический дефолт):** Кэш пуст, зависимость мертва. Мы возвращаем жестко зафиксированный в бинарнике список бестселлеров или безопасный пустой срез `[]`, чтобы клиентский JSON-десериализатор не упал с паникой от `nil`.
4. **Feature Toggling (Мягкое отключение функциональности):** Если операцию невозможно выполнить в принципе (например, шлюз эквайринга недоступен), мы динамически скрываем кнопку «Оплатить картой онлайн» и предлагаем альтернативу «Оплатить при получении», деградируя синхронный процесс до безопасного отложенного сценария.

## Реализация в Go: Zero-Allocation Fallbacks

Золотое правило архитектуры Graceful Degradation гласит:  
> *«Код фолбэка обязан быть абсолютно бесплатным для процессора и оперативной памяти».*

Когда система переходит в режим аварийной деградации, сервер, вероятнее всего, уже находится под колоссальным давлением (захлебывается сетевая очередь, утилизация ядер CPU стремится к 100%). Если ваш код обработки ошибок начнет судорожно аллоцировать новые структуры, парсить JSON или собирать тяжелые строки, вы нанесете системе контрольный выстрел в голову, спровоцировав паралич сборщика мусора.

> [!info] Под капотом: Mechanical Sympathy
> В языке Go создание пустого среза `make([]Item, 0)` или выделение дефолтного ответа `&Response{}` внутри хендлера на каждый упавший запрос в момент пиковой аварии (когда RPS достигает десятков тысяч) — опасная ловушка. Механизм Escape Analysis компилятора Go гарантированно перенесет возвращаемую структуру из стека горутины в кучу (Heap), многократно усиливая работу Garbage Collector.
> 
> **Инженерное решение:** Использовать неизменяемые (Read-Only) глобальные переменные, инициализированные один раз при старте бинарника, либо пул переиспользуемых объектов `sync.Pool`. Указатель на предвыделенную константную память в сегменте данных не стоит процессору ни единого байта аллокаций.

### Архитектура надежного клиента

Посмотрим на эталонную реализацию клиента рекомендаций с трехуровневой плавной деградацией:

```go
package catalog

import (
	"context"
	"errors"
	"log/slog"
	"time"

	"github.com/sony/gobreaker"
)

// Item описывает товарную позицию
type Item struct {
	ID    string `json:"id"`
	Title string `json:"title"`
}

// Глобальные предвыделенные статические данные (Zero-Allocation Fallback)
// Память выделена один раз при инициализации приложения
var defaultRecommendations = []Item{
	{ID: "fallback-1", Title: "Хит продаж: Флагманский смартфон"},
	{ID: "fallback-2", Title: "Хит продаж: Беспроводные наушники"},
}

// Cache определяет интерфейс локального кэша
type Cache interface {
	Get(key string) ([]Item, bool)
	Set(key string, value []Item, ttl time.Duration)
}

// Client управляет запросами с поддержкой автоматической деградации
type Client struct {
	cb    *gobreaker.CircuitBreaker
	cache Cache
}

func NewClient(cache Cache) *Client {
	return &Client{
		cache: cache,
		cb: gobreaker.NewCircuitBreaker(gobreaker.Settings{
			Name:    "Recommendations-Client",
			Timeout: 5 * time.Second,
		}),
	}
}

// GetRecommendations возвращает рекомендации с бесшовной деградацией
func (c *Client) GetRecommendations(ctx context.Context, userID string) ([]Item, error) {
	// УРОВЕНЬ 1: Попытка получить свежие данные через Circuit Breaker
	res, err := c.cb.Execute(func() (interface{}, error) {
		return c.fetchRemote(ctx, userID)
	})

	if err == nil {
		items := res.([]Item)
		// Асинхронно прогреваем локальный кэш свежими данными
		go c.cache.Set(userID, items, 24*time.Hour)
		return items, nil
	}

	// === ФАЗА ДЕГРАДАЦИИ: Downstream недоступен ===
	slog.Warn("Сбой сервиса рекомендаций, переход в режим деградации", "user_id", userID, "err", err)

	// УРОВЕНЬ 2: Пробуем отдать Stale Data из локального in-memory кэша
	if cached, ok := c.cache.Get(userID); ok {
		slog.Debug("Отдаем устаревшие данные (Stale Cache)", "user_id", userID)
		return cached, nil
	}

	// УРОВЕНЬ 3: Абсолютный статический фолбэк
	// Возвращаем ссылку на предвыделенный срез БЕЗ единой аллокации в куче!
	slog.Debug("Отдаем статический дефолтный список", "user_id", userID)
	return defaultRecommendations, nil
}

func (c *Client) fetchRemote(ctx context.Context, userID string) ([]Item, error) {
	// Симуляция исходящего сетевого RPC-вызова
	return nil, errors.New("downstream timeout")
}
```

## Архитектурные ловушки (Gotchas)

> [!tip] Собеседование
> **Вопрос:** Что такое феномен «Poisoned Fallback» (Отравление кэша фолбэком) и как защитить от него систему?
> **Ответ:** Это классическая и крайне болезненная архитектурная ошибка, при которой результат аварийной деградации ошибочно кэшируется как легитимный и полноценный ответ.

Представьте цепочку событий:
1. Хендлер запрашивает профиль пользователя.
2. База данных профилей временно упала (Failover).
3. Код активирует деградацию и возвращает безопасный заглушечный объект: `User{Name: "Гость", Status: "Offline"}`.
4. **Катастрофическая ошибка:** Промежуточный кэширующий middleware (или внешний API Gateway) видит ответ со статусом `200 OK` и сохраняет объект «Гостя» в Redis под реальным ID пользователя с TTL в 2 часа!
5. База данных успешно восстанавливается через 15 секунд.
6. Но реальный авторизованный пользователь следующие 2 часа видит себя в профиле как неавторизованного «Гостя», потому что распределенный кэш оказался безнадежно отравлен фолбэком!

**Железное правило:** *Никогда не кэшируйте ответы, сформированные по схеме деградации.* В долговременный кэш имеют право попадать исключительно подлинные ответы от Primary-источников, завершившиеся успехом `200 OK`.

## Частичная сборка (Partial Assembly) с errgroup

В микросервисной архитектуре (см. [[5. API contracts]] и паттерн [[5. BFF]]) Backend-For-Frontend шлюз регулярно агрегирует данные из 5–10 независимых микросервисов для формирования единого экрана мобильного приложения.

Если разработчик наивно использует стандартный пакет `golang.org/x/sync/errgroup` (библиотеку `errgroup`), то возврат ошибки хотя бы из одной горутины немедленно отменяет общий родительский контекст `ctx` и обрушивает сборку всей страницы целиком! Это прямое нарушение философии Graceful Degradation.

Для отказоустойчивой сборки ошибки второстепенных компонентов должны перехватываться локально внутри горутины, а сама функция обязана возвращать в `errgroup` значение `nil`:

```go
package aggregator

import (
	"context"
	"log/slog"

	"golang.org/x/sync/errgroup"
)

type PageData struct {
	ProductInfo string // Критичные данные
	Reviews     string // Второстепенные данные
	PromoBanner string // Некритичный маркетинг
}

func AssembleProductPage(ctx context.Context, productID string) (*PageData, error) {
	page := &PageData{}
	g, groupCtx := errgroup.WithContext(ctx)

	// 1. КРИТИЧЕСКИЙ ЗАПРОС: Информация о товаре (деградация невозможна)
	g.Go(func() error {
		info, err := fetchProductDetails(groupCtx, productID)
		if err != nil {
			// Ошибка здесь фатальна: возвращаем err и отменяем группу
			return err
		}
		page.ProductInfo = info
		return nil
	})

	// 2. НЕКРИТИЧЕСКИЙ ЗАПРОС: Блок отзывов
	g.Go(func() error {
		reviews, err := fetchReviews(groupCtx, productID)
		if err != nil {
			slog.Warn("Отзывы недоступны, применяем деградацию", "err", err)
			page.Reviews = "Отзывы временно недоступны"
			// ВАЖНО: возвращаем nil, чтобы не сломать сборку страницы!
			return nil
		}
		page.Reviews = reviews
		return nil
	})

	// 3. ФОНОВЫЙ ЗАПРОС: Персональный промокод
	g.Go(func() error {
		promo, err := fetchPersonalPromo(groupCtx, productID)
		if err != nil {
			page.PromoBanner = "" // Скрываем блок баннера
			return nil           // Возвращаем nil в группу
		}
		page.PromoBanner = promo
		return nil
	})

	// Ожидаем завершения параллельных вызовов
	if err := g.Wait(); err != nil {
		// Возвращаем ошибку клиенту ТОЛЬКО если упал критический компонент
		return nil, err
	}

	return page, nil
}
```

## Итог

1. **Бизнес-ориентированная надежность:** Graceful Degradation превращает технические сбои сетевого уровня в контролируемое, незаметное для пользователя снижение второстепенной функциональности.
2. **Иерархия спасения:** Выстраивайте защиту по цепочке: Свежие данные $\to$ Устаревший кэш (Stale Data) $\to$ Неизменяемый статический дефолт $\to$ Отключение фичи.
3. **Zero-Allocation принцип:** Код аварийного фолбэка обязан быть невесомым для рантайма Go. Используйте глобальные предвыделенные структуры или `sync.Pool`, исключая нагрузку на Garbage Collector.
4. **Защита от Poisoned Fallback:** Никогда не записывайте дефолтные ответы деградации в долгоживущий кэш.
5. **Изолированная агрегация:** При частичной сборке через `errgroup` некритичные горутины обязаны возвращать `nil`, подменяя упавшие блоки безопасными заглушками.

Мы подробно изучили всю батарею защитных механизмов: от дедлайнов и семафоров до аварийного сброса балласта и плавной деградации. Но как убедиться, что эти механизмы действительно спасут систему в реальной боевой аварии, а не откажут из-за незамеченного бага в конфигурации? Настоящие инженеры не надеются на удачу — они целенаправленно ломают свой продакшен под строгим контролем. В заключительной статье подраздела мы разберем экстремальную дисциплину проверки надежности: [[8. Chaos engineering]].
