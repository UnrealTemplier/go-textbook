# Allocation profiling

> *«Представьте себе банковский счет: остаток на конец дня может составлять скромные сто долларов, но за сутки через счет прокачались миллионы, породив гору комиссий и транзакционных издержек. Точно так же ведет себя и память: мгновенный снимок процесса может показывать тихие 50 мегабайт, в то время как аллокатор ежесекундно перемалывает гигабайты временных объектов, ввергая процессор в бесконечную войну за очистку мусора. Allocation profiling — это выписка всех операций по вашему счёту».*  
> — Брайан Керниган

## От «где память» к «почему она там оказалась»

В главе [[2. Heap vs stack]] мы провели четкую грань между стремительным стеком и ресурсоемкой кучей, а в [[3. Escape analysis]] выяснили, какие именно конструкции кода вынуждают компилятор эвакуировать переменные за пределы стекового фрейма.

Однако теоретических знаний недостаточно для оптимизации боевой системы: в реальном сервисе работают сотни пакетов и тысячи сторонних функций. Чтобы направить усилия инженера в самую горячую точку, требуются **точные эмпирические измерения**:
- Сколько именно байт и объектов аллоцирует конкретная строка кода?
- Какие функции создают пиковый «тоннаж» временного мусора для трехцветного сборщика?
- Окупилась ли замена интерфейса или внедрение пула объектов?

Для ответа на эти вопросы существует **allocation profiling** — систематическое профилирование динамических выделений памяти в куче. Это ключевой мост между абстрактным анализом побега и конкретным приростом throughput в продакшене.

В этой статье мы освоим сбор, расшифровку и прикладную интерпретацию профилей аллокаций, разберем связь профиля с микроархитектурой процессора и подготовимся к продвинутому анализу через [[5. pprof memory profile]].

## Два взгляда на память: alloc_space против inuse_space

Пакет `runtime/pprof` собирает данные о куче и предоставляет разработчику две фундаментально различные проекции распределения байт:

```
[ Старт профилирования ] =====================================> [ Конец (30 сек) ]
  Объект A (+10 МБ) ------> (Освобожден GC)
  Объект B (+20 МБ) ------------------------------------------> [ ЖИВ ]
  Объект C (+30 МБ) ------> (Освобожден GC)

  => alloc_space = 10 + 20 + 30 = 60 МБ  (Общий тоннаж работы аллокатора и GC)
  => inuse_space = 20 МБ                  (Текущий живой остаток в памяти)
```

- **`alloc_space` (и `alloc_objects`):** Суммарный объем байт (и число объектов), выделенных в куче за наблюдаемый интервал времени. Сюда входят **абсолютно все** аллокации, включая короткоживущие временные структуры, которые сборщик мусора уже успел уничтожить. Это интеграл нагрузки на память.
- **`inuse_space` (и `inuse_objects`):** Объем памяти (и число объектов), удерживаемых живыми ссылками непосредственно в момент фиксации профиля.

### Когда что использовать?
Для устранения CPU-нагрузки и борьбы с задержками GC абсолютным приоритетом пользуется **`alloc_space`**. Сервис может иметь стабильный resident set size (RSS) в 100 МБ, но если его `alloc_space` генерирует 2 ГБ мусора в секунду, треть процессорного времени уйдет на работу фоновых сборщиков `gcBgMarkWorker`.

Метрика `inuse_space` незаменима для другой задачи: обнаружения утечек памяти ([[6. Утечки памяти]]) и анализа фрагментации адресного пространства ([[7. Fragmentation]]).

> [!tip] Собеседование: alloc_space vs inuse_space
> **Вопрос:** В чем принципиальное отличие между метриками `alloc_space` и `inuse_space` в профилировщике памяти Go, и какую из них следует анализировать для снижения нагрузки на CPU?  
> **Ответ:** Метрика `alloc_space` отражает совокупный объем всех аллокаций в куче за период наблюдения, включая объекты, которые уже были собраны сборщиком мусора. Именно она используется для снижения нагрузки на CPU, так как показывает функции, генерирующие максимальный поток мусора для GC и аллокатора. Метрика `inuse_space` учитывает только живые объекты, оставшиеся в памяти на момент снятия снимка, и применяется для поиска утечек памяти (memory leaks) и оценки общего потребления RAM.

## Как собрать профиль аллокаций

Для захвата аллокационного профиля в экосистеме Go предусмотрено три надежных пути:

### 1. Через net/http/pprof (для продакшен-сервисов)
В веб-сервисах достаточно подключить анонимный импорт:

```go
import _ "net/http/pprof"
```

После этого эндпоинт `/debug/pprof/heap` становится доступным по HTTP. Чтобы получить именно динамический профиль аллокаций за интервал времени, **обязательно передайте параметр `seconds`**:

```bash
curl -o alloc.prof "http://localhost:6060/debug/pprof/heap?seconds=30"
```

> [!IMPORTANT]
> Параметр `seconds=30` заставляет рантайм записать разницу (дельта-срез) аллокаций строго за эти 30 секунд. Дополнительно перед стартом и в конце замера рантайм вызывает `runtime.GC()`, отсекая старый шум. Без параметра `seconds` эндпоинт вернет мгновенный моментальный снимок (inuse_space), бесполезный для анализа потока аллокаций.

Поддерживаемые параметры эндпоинта `/debug/pprof/heap`:
- `/debug/pprof/heap?seconds=N` — сбор дельты аллокаций за $N$ секунд (`alloc_space`);
- `?debug=1` — человекочитаемый текстовый дамп спанов и статистики рантайма;
- `?gc=1` — принудительный запуск сборщика мусора перед выдачей профиля.

### 2. Через runtime/pprof в коде (для CLI, тестов и скриптов)
Если программа не имеет HTTP-сервера, профиль можно зафиксировать программно:

```go
f, _ := os.Create("alloc.prof")
defer f.Close()

// Принудительный сбор мусора для очистки старого состояния
runtime.GC()

// Запись текущего состояния кучи
pprof.Lookup("heap").WriteTo(f, 0)
```
Для непрерывного отслеживания долгосрочной динамики без HTTP можно периодически считывать счетчики через вызов `runtime.ReadMemStats`.

### 3. Через go test -bench и -memprofile
При анализе производительности алгоритмов профиль аллокаций снимается напрямую флагом `-memprofile`:

```bash
go test -bench=. -benchmem -memprofile=mem.prof
```
Сгенерированный файл `mem.prof` содержит полную информацию, позволяя переключаться между `alloc_space`, `alloc_objects`, `inuse_space` и `inuse_objects` в интерактивном режиме `pprof`.

## Параметры сбора: MemProfileRate

Выделение памяти в куче — высокочастотное событие. Если бы рантайм Go записывал трассировку стека абсолютно при каждом вызове `malloc`, накладные расходы уничтожили бы производительность продакшена.

Поэтому аллокационный профилировщик работает по принципу **вероятностного сэмплирования Пуассона**. По умолчанию рантайм фиксирует один сэмпл приблизительно на каждые 512 килобайт выделенной памяти:

```go
runtime.MemProfileRate = 512 * 1024 // 512 КБ по умолчанию
```

Это означает:
- Аллокация крупного объекта в 1 МБ гарантированно попадет в профиль (возможно, несколькими сэмплами);
- Серия из тысяч мелких аллокаций будет сэмплироваться пропорционально их общему накопительному объему;
- Профилировщик математически масштабирует значения в отчете, аппроксимируя реальный объем памяти.

Для локальной отладки и микробенчмарков, где важна абсолютная точность до каждого байта, сэмплирование можно отключить, установив шаг в 1 байт:

```bash
GODEBUG=memprofilerate=1 go test -bench=.
```
или программно:
```go
runtime.MemProfileRate = 1
```

> [!CAUTION]
> Значение `runtime.MemProfileRate = 1` заставляет рантайм перехватывать каждую аллокацию и сохранять стек вызовов. Это замедляет программу в 10–100 раз и резко раздувает память! Применяйте его **только локально**. В боевой среде оставляйте стандартные `MemProfileRate=512KB` либо понижайте до умеренных `131072 (128 КБ)` для тонкого аудита.

> [!warning] Ловушка: Статистическая слепота редких мелких аллокаций
> При стандартном `MemProfileRate=512KB` функция, которая суммарно выделила несколько мегабайт мелкими объектами, отлично видна в профиле. Но если вспомогательная функция редко создает единичный объект в 32 байта, она может ни разу не попасть в сэмпл и будет отсутствовать в профиле. Помните: pprof показывает статистически значимые очаги нагрузки.

## Анализ профиля: go tool pprof

Открываем сохраненный профиль в режиме анализа совокупных аллокаций:

```bash
go tool pprof -alloc_space alloc.prof
```

### Основные аналитические команды консоли:
- **`top`** — список функций с наибольшим собственным объемом аллокаций (`flat`).
- **`top -cum`** — список функций по кумулятивному объему памяти (с учетом дочерних вызовов).
- **`list FuncName`** — построчный листинг исходного кода целевой функции с точным указанием объема аллокаций на каждой строке.
- **`tree`** — текстовое дерево вызовов, наглядно показывающее цепочки вызовов от корня к потребителям.
- **`web`** — генерация SVG-графа вызовов в браузере.
- **`flamegraph`** — интерактивный запуск веб-интерфейса флеймграфа через флаг `-http=:8080` (аналогично [[3. Flamegraph]], но где ширина плато пропорциональна `alloc_space`).

### Пример реального отчета `top`:

```text
(pprof) top
Showing nodes accounting for 1.50GB, 85% of 1.76GB total
      flat  flat%   sum%        cum   cum%
    0.60GB 34.09% 34.09%     0.80GB 45.45%  encoding/json.Unmarshal
    0.30GB 17.05% 51.14%     0.30GB 17.05%  runtime.makeslice
    0.20GB 11.36% 62.50%     0.20GB 11.36%  bytes.makeSlice
    0.15GB  8.52% 71.02%     0.15GB  8.52%  strings.Builder.grow
```

Интерпретация:
- В `encoding/json.Unmarshal` непосредственно выделилось 0.60 ГБ (`flat`), а кумулятивно с дочерними вызовами — 0.80 ГБ (`cum`). Это главный кандидат на рефакторинг!
- Системные функции `runtime.makeslice` и `bytes.makeSlice` суммарно выделили 0.50 ГБ — явный признак динамического расширения срезов без предварительного выделения емкости (`cap`).

## Как ходить от профиля к коду

Для системного устранения аллокаций используйте 6-шаговый протокол:

1. Найти функцию-лидер по `flat` или `cum` в `alloc_space` (команда `top`).
2. Запустить `list FuncName` и обнаружить конкретную строчку кода, на которой висит пиковый объем выделений.
3. Сопоставить код со строкой: содержит ли она `make`, `append`, создание замыкания, конкатенацию строк или боксинг в интерфейс?
4. Запустить `go build -gcflags="-m"` ([[3. Escape analysis]]) и выяснить точную причину побега переменной в кучу.
5. Применить инженерный прием устранения аллокации: предвыделение `cap`, замена указателя на значение, дженерики вместо `interface{}`, либо переиспользование через `sync.Pool`.
6. Снять повторный профиль и зафиксировать падение `alloc_space` и метрики `B/op`.

> [!info] Под капотом: Агрегация сэмплов в рантайме
> Профиль памяти в Go не хранит последовательную временную ленту событий. Внутри рантайма выделена хэш-таблица `buckhash`, где ключом является стек вызовов (Call Stack), а значением — структура с четырьмя счетчиками: `alloc_bytes`, `alloc_objects`, `free_bytes`, `free_objects`. Когда вызывается внутренняя функция аллокатора `runtime.mallocgc`, рантайм обновляет соответствующий бакет. Переменные, оставшиеся на стеке, проходят мимо `mallocgc` и физически не могут попасть в профиль.

## Типичные «горячие» источники аллокаций и стратегии борьбы

Опираясь на системную классификацию горячих точек ([[4. Top functions анализ]]), выделим главных виновников кучевого мусора:

### 1. Сериализация и десериализация
Пакеты сериализации `encoding/json.Unmarshal`, `xml.Decode`, `protobuf.Marshal` часто порождают огромное количество временных слайсов и строк. Стандартный парсер `encoding/json.Unmarshal` опирается на рефлексию (`reflect`), выделяя множество мелких структур под каждое поле документа.
- **Решение:** Использование кодогенерации (easyjson) или быстрых парсеров с нулевыми аллокациями (sonic, fastjson), а также переиспользование буферов декодера через `sync.Pool` ([[2. sync Pool]]).

### 2. Конструирование строк
Конкатенация строк через оператор `+` в цикле или неаккуратные вызовы `fmt.Sprintf` порождают квадратичный поток мусора.
- **Решение:** Использование `strings.Builder` с предварительным вызовом метода `Grow(n)` (`strings.Builder.grow`), аллоцирующего весь буфер ровно один раз.

### 3. Рост слайсов
Вызов `append` в слайс с неизвестной ёмкостью заставляет рантайм постоянно вызывать `runtime.growslice` и `runtime.makeslice`, копируя память.
- **Решение:** Предварительное выделение емкости через `make([]T, 0, cap)` или `make([]T, 0, expectedCapacity)` ([[4. Предвыделение памяти]]).

### 4. Преобразования типов ([]byte и string)
Приведение строки к байтовому срезу `[]byte(s)` или обратно `string(b)` создает полную копию данных в новой аллокации кучи.
- **Решение:** Использование методов `unsafe.StringData`, `unsafe.SliceData` (Go 1.20+) или оптимизированных zero-copy подходов ([[5. Zero copy подходы]]).

### 5. Конвертация в интерфейс
Передача конкретного типа в `interface{}` боксит значение. Если это происходит в цикле — аллокации накапливаются.
- **Решение:** Параметризация функций дженериками (`[T any]`) с последующей мономорфизацией в коде.

### 6. Захват переменных в замыканиях
Асинхронные горутины и отложенные функции (`defer`), захватывающие переменные по ссылке, насильно эвакуируют их в кучу.
- **Решение:** Передача параметров явно по значению через аргументы вызова.

## Практический пример: оптимизация JSON парсинга

Рассмотрим типичный HTTP-обработчик входящих запросов:

```go
func handle(w http.ResponseWriter, r *http.Request) {
    var req Request
    json.NewDecoder(r.Body).Decode(&req)
    // обработка req
    fmt.Fprint(w, "OK")
}
```

Под нагрузкой профиль `alloc_space` за 30 секунд выдает неутешительную картину:
```text
       flat  flat%   sum%        cum   cum%
   200.00MB 40.00% 40.00%   250.00MB 50.00%  encoding/json.(*Decoder).Decode
    50.00MB 10.00% 50.00%    50.00MB 10.00%  runtime.makeslice
```

Вывод: `Decode` генерирует 200 МБ аллокаций. Выполняем `list Decode` и видим, что внутри происходит множество `make` для строк и слайсов, а внутренний буфер `json.Decoder` растет с каждым запросом.

Применим пул переиспользуемых декодеров `sync.Pool`:

```go
var decoderPool = sync.Pool{
    New: func() interface{} { return json.NewDecoder(nil) },
}

func handleOptimized(w http.ResponseWriter, r *http.Request) {
    dec := decoderPool.Get().(*json.Decoder)
    dec.Reset(r.Body)
    defer decoderPool.Put(dec)

    var req Request
    dec.Decode(&req)
    fmt.Fprint(w, "OK")
}
```

Повторный замер `pprof` демонстрирует снижение `alloc_space` на **40%**, а бенчмарки фиксируют падение `allocs/op` с 25 до 8. Сборщик мусора освобождается от постоянного сканирования буферов, стабилизируя хвостовую задержку p99 ([[7. Tail latency и почему она важна]]).

## Ловушки и частые ошибки

> [!warning] Ловушка: Анализ inuse_space вместо alloc_space
> Разработчик открывает профиль без флага `-alloc_space` и видит текущее распределение живой памяти. Если функция генерирует терабайты мусора, который мгновенно подбирается GC, она будет абсолютно невидима в `inuse_space`! Всегда начинайте аудит производительности с `-alloc_space`.

> [!warning] Ловушка: Слишком короткий интервал профилирования
> Как и при CPU-профилировании ([[2. CPU profiling в Go]]), срез за 5 секунд рискует захватить случайный всплеск или оказаться пустым из-за квантования нагрузки. Минимальный рекомендованный интервал сбора профиля под нагрузкой — **30 секунд**.

> [!warning] Ловушка: Игнорирование погрешности MemProfileRate
> При штатном значении `MemProfileRate=512KB` профилировщик может пропустить редкие точечные аллокации. Если при профилировании локального бенчмарка вы видите нулевые аллокации, но `benchmem` рапортует о `1 allocs/op`, временно форсируйте `GODEBUG=memprofilerate=1`.

> [!warning] Ловушка: Невидимые аллокации в стандартной библиотеке
> Системные функции вроде `time.Parse` или внутренности роутера `net/http` создают служебные объекты. Профиль зафиксирует их на стандартных пакетах, маскируя реальный источник в вашем бизнес-коде. Используйте команду `tree` или флеймграф, чтобы распутать цепочку вызовов.

## Mechanical Sympathy: как аллокации влияют на кэш и TLB

Каждая аллокация в куче наносит системный удар по кремнию:
1. **Блокировки спинлоков:** Если локальный кэш `mcache` исчерпан, поток вынужден обращаться к центральному `mcentral`, конкурируя с другими ядрами.
2. **Обнуление памяти:** Рантайм обязан занулить выделенную память (`memclr`), расходуя такты на запись в L1/L2 кэш.
3. **Загрязнение кэш-линий и TLB:** Объекты, разбросанные по разным страницам виртуальной памяти, вызывают шквал промахов TLB и кэш-линий ([[8. Cache friendliness]]).

Снижение темпа аллокаций защищает процессор от пауз GC ([[6. GC pause и latency]]) и удерживает рабочие структуры данных в горячем кэше.

## Итог

- **Allocation profiling** (`-alloc_space`) — главный практический инструмент инженера для выявления функций, создающих максимальный поток кучевого мусора.
- В отличие от `inuse_space`, метрика `alloc_space` фиксирует совокупный тоннаж всех выделенных байт за наблюдаемый период.
- Для долгоживущих систем профиль собирается через HTTP: `/debug/pprof/heap?seconds=30`.
- По умолчанию включено сэмплирование (`MemProfileRate = 512 КБ`). Для локальных микротестов используйте `GODEBUG=memprofilerate=1`.
- Анализ связки `top`, `list` и флеймграфа позволяет мгновенно локализовать строку, порождающую аллокации.
- Главные мишени оптимизации: JSON-парсинг, динамические срезы, конкатенация строк, боксинг в интерфейсы и замыкания.

В следующей лекции мы детально изучим сам профилировщик памяти во всех его режимах: [[5. pprof memory profile]] — разберем дифференциальный анализ, текстовые дампы и чтение графов аллокаций.
