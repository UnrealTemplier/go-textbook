## Логирование в production

Во времена зарождения языка C и операционной системы Unix мы выводили диагностические сообщения простой строкой: `printf("debug: x = %d\n", x);`. Для автономных консольных утилит и лабораторных программ этого было более чем достаточно. Однако когда разработчик переносит этот наивный процедурный майндсет в современный распределенный бэкенд на Go, обрабатывающий десятки тысяч запросов в секунду (10k+ RPS), простодушный вызов `fmt.Printf` или использование устаревшего пакета `log` превращаются в скрытый яд для всей системы.

В боевом production-окружении логи категорически перестают быть средством чтения для человеческих глаз. Они превращаются в **поток строго типизированных, структурированных событий**, потребляемый автоматизированными анализаторами: SRE-платформами мониторинга, индексаторами (Grafana Loki, Elasticsearch, ClickHouse) и алгоритмами обнаружения аномалий. В экосистеме Go это требует решительного отказа от нетипизированного вывода в пользу высокопроизводительных библиотек структурированного логирования (`log/slog`), гарантирующих нулевые лишние аллокации в куче и детерминированную передачу контекста.

### 1. Цена логирования: Механика и производительность

Начинающим инженерам кажется, что вызов логгера — практически бесплатная операция. Однако в высоконагруженных сервисах логирование нередко забирает до 20–30% всего бюджета CPU и выступает ключевым генератором мусора для Garbage Collector.

Препарируем, что физически происходит в ядре и рантайме при выполнении классической строки:
`log.Printf("User %s logged in from %s", user, ip)`:

1. **Форматирование строки**: Внутренняя функция `fmt.Sprintf` (вызываемая внутри `Printf`) парсит строку шаблона, аллоцирует в куче промежуточный байтовый буфер, выполняет преобразование типов и склеивает новую строку `string` в динамической памяти.
2. **Сериализация**: Если используется структурированный JSON-логгер, переданные поля сериализуются в байтовый срез через интерфейсы или рефлексию.
3. **Синхронизация и Mutex Contention**: Стандартный пакет `log` защищает свой внутренний буфер вывода с помощью глобального `sync.Mutex`. Когда тысячи параллельных горутин одновременно пытаются записать строку лога, они встают в жесткую очередь блокировки, порождая контеншн и заставляя планировщик Go тратить миллисекунды на парковку и пробуждение горутин.
4. **Системные вызовы ядра**: Каждая порция текста отправляется в файл или стандартный вывод через системный вызов `write`. Переключение контекста между User Space и Kernel Space на каждую запись создает избыточную нагрузку на шину процессора.

```mermaid
flowchart LR
    A["Бизнес-горутина"] --> B["slog.InfoContext"]
    B --> C["Обертка в slog.Attr<br>без аллокаций для примитивов"]
    C --> D["JSONHandler<br>запись в буфер"]
    D --> E["bufio.Writer<br>накопление порции"]
    E --> F["Syscall write<br>os.Stdout"]
    F --> G["Агент сбора<br>Vector / Fluent Bit"]
    G --> H["Хранилище<br>Loki / Elasticsearch"]
```

> [!info] Под капотом
> Начиная с версии Go 1.21, стандартная библиотека предлагает пакет `log/slog`, оптимизирующий горячий путь `slog.Info`. Для базовых примитивов (`int`, `int64`, `string`, `bool`) `slog` избегает неявной упаковки значений в пустой интерфейс `interface{}`. Вместо этого они упаковываются в структуру-объединение `slog.Attr` с типизированными полями. Однако если разработчик передает сложную структуру или задействует хелпер `slog.Any`, рантайм вынужден активировать пакет `reflect` (рефлексию). Это приводит к провалу Escape Analysis: данные гарантированно мигрируют в кучу, создавая лавинообразный шум для Garbage Collector. При миллионах запросов это превращается в гигабайты бесполезных аллокаций в секунду.

### 2. Идиоматичная структура лога

В промышленной архитектуре запись лога обязана быть машиночитаемой (индустриальный де-факто стандарт — компактный JSON). Имена ключевых полей должны быть строго зафиксированы в архитектурном стандарте компании:

```json
{
  "level": "error",
  "ts": "2026-09-13T10:00:00.123Z",
  "msg": "failed to process payment",
  "service": "payment-svc",
  "version": "v1.2.3",
  "trace_id": "a1b2c3d4e5f6",
  "user_id": "u_123",
  "error": "timeout",
  "latency_ms": 5000
}
```

Идиоматичная реализация на Go с использованием пакета `slog` и обогащением глобальными атрибутами:

```go
package main

import (
    "context"
    "log/slog"
    "os"
)

func InitLogger() *slog.Logger {
    opts := &slog.HandlerOptions{
        Level:     slog.LevelInfo, // В production строго Info, в dev — Debug
        AddSource: false,          // Захват файла и строки (runtime.Caller) слишком дорог в prod!
        ReplaceAttr: func(groups []string, a slog.Attr) slog.Attr {
            // Нормализация системного ключа времени для совместимости с парсерами
            if a.Key == slog.TimeKey {
                a.Key = "ts"
            }
            return a
        },
    }

    // JSON Handler оптимизирован для машинного парсинга
    handler := slog.NewJSONHandler(os.Stdout, opts)
    
    // Внедряем глобальные атрибуты, присутствующие в КАЖДОЙ записи
    return slog.New(handler).With(
        slog.String("service", os.Getenv("SERVICE_NAME")),
        slog.String("version", os.Getenv("APP_VERSION")),
        slog.String("env", os.Getenv("ENVIRONMENT")),
    )
}
```

### 3. Контекст и Request ID

Бессистемный лог, лишенный сквозного идентификатора транзакции, в распределенной системе бесполезен. При расследовании инцидента инженер обязан иметь возможность вытянуть полную последовательность событий от браузера клиента через API Gateway до последнего микросервиса.

Связующим звеном выступает стандартный `context.Context`:

```go
package main

import (
    "context"
    "log/slog"
    "net/http"
)

type ctxKey string
const requestIDKey ctxKey = "request_id"

func WithRequestID(ctx context.Context, id string) context.Context {
    return context.WithValue(ctx, requestIDKey, id)
}

func RequestIDFromContext(ctx context.Context) string {
    if id, ok := ctx.Value(requestIDKey).(string); ok {
        return id
    }
    return ""
}

// LoggingMiddleware внедряет контекстный логгер в цепочку HTTP-хендлеров
func LoggingMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        reqID := RequestIDFromContext(r.Context())
        if reqID == "" {
            reqID = r.Header.Get("X-Request-ID")
        }
        
        // Создаем дочерний логгер, обогащенный контекстом текущего запроса
        logger := slog.Default().With(
            slog.String("request_id", reqID),
            slog.String("method", r.Method),
            slog.String("path", r.URL.Path),
            slog.String("remote_addr", r.RemoteAddr),
        )
        
        // Передаем обогащенный контекст в следующие обработчики
        ctx := context.WithValue(r.Context(), "logger", logger)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}
```

> [!warning] Ловушка / Gotcha
> **Утечка чувствительных данных (PII/Security Leak)**: Категорически запрещено логировать необработанные тела клиентских запросов (`req.Body`), секретные заголовки авторизации `Authorization`, пароли и платежные данные. В реальном production это прямое нарушение законов о защите персональных данных (GDPR, 152-ФЗ, PCI DSS). Применяйте автоматическое маскирование персональных сведений (например: `CreditCard: ****1234`).
> **Логирование внутри горячих циклов (Hot Loop Trap)**: Запись строки лога на каждой итерации цикла по миллиону элементов гарантированно обрушит производительность вашего сервиса, забив диски и заблокировав горутины. В горячих циклах фиксируйте только агрегированные счетчики или применяйте сэмплирование.

### 4. Производительность: Асинхронность и Буферизация

Синхронная запись каждого лога напрямую в дескриптор `os.Stdout` или сокет заставляет прикладную горутину простаивать в ожидании завершения системного вызова `write`. При резких всплесках пользовательского трафика это приводит к мгновенной деградации пропускной способности.

Для максимальной пропускной способности применяют два проверенных подхода:

**Вариант 1: Буферизация через bufio.Writer (Рекомендуемый стандарт)**
По умолчанию стандартный вывод `os.Stdout` не буферизуется рантаймом. Поскольку `slog` принимает любой интерфейс `io.Writer`, оборачивание вывода в `bufio.Writer` позволяет накапливать строки в памяти и сбрасывать их на диск крупными пачками по 4–16 КБ, сокращая количество системных вызовов `write` в десятки раз.

**Вариант 2: Асинхронный логгер с очередью в памяти**
Высокопроизводительные библиотеки (такие как `uber/zap` или `zap` в связке с кольцевым буфером) помещают подготовленные структуры логов в ограниченный канал `chan`, из которого отдельная системная горутина сбрасывает данные в сокет.
- *Преимущество*: Вызов логгера никогда не блокирует бизнес-логику приложения.
- *Критический компромисс*: При аварийной панике или внезапном уничтожении процесса ядром по сигналу `SIGKILL` (OOM) последние события, находившиеся в оперативной очереди, безвозвратно теряются.

В современном Go стандартный пакет `log/slog` при грамотной настройке буферов и исключении `reflect` обеспечивает выдающуюся производительность даже в строго синхронном режиме.

### 5. Уровни логирования и Sampling

В production-среде запись каждого малозначительного события недопустима — это приводит к колоссальным расходам на хранение и сетевой трафик.

Инженерный регламент уровней:
- **ERROR**: Сбои, нарушающие бизнес-процесс и требующие немедленного вмешательства инженера. Логируются абсолютно всегда со стеком ошибки.
- **WARN**: Нештатные ситуации и пограничные состояния (сработал retry, внешний сервис временно деградировал), не приводящие к фатальному срыву запроса.
- **INFO**: Значимые вехи жизненного цикла сервиса и бизнес-транзакций (старт сервиса, успешное проведение платежа).
- **DEBUG**: Низкоуровневые диагностические данные. **В production-окружении обязаны быть полностью отключены**.

**Сэмплирование логов (Sampling)**:
При нагрузке в 100 000 RPS даже уровень `INFO` способен забить терабайты дискового пространства в сутки. Решение — применение декоратора Handler, сэмплирующего рядовые события, но пропускающего 100% ошибок:

```go
package main

import (
    "context"
    "log/slog"
    "sync/atomic"
)

type SamplingHandler struct {
    handler slog.Handler
    rate    int64
    counter atomic.Int64
}

func NewSamplingHandler(h slog.Handler, rate int64) *SamplingHandler {
    return &SamplingHandler{handler: h, rate: rate}
}

func (h *SamplingHandler) Enabled(ctx context.Context, lvl slog.Level) bool {
    return h.handler.Enabled(ctx, lvl)
}

func (h *SamplingHandler) Handle(ctx context.Context, r slog.Record) error {
    // Ошибки и предупреждения сохраняются ВСЕГДА со 100% гарантией
    if r.Level >= slog.LevelWarn {
        return h.handler.Handle(ctx, r)
    }
    
    // Для INFO/DEBUG пропускаем только каждое N-е событие
    // либо запросы со специальным флагом (например, is_slow=true)
    if h.counter.Add(1)%h.rate == 0 {
        return h.handler.Handle(ctx, r)
    }
    
    return nil
}

func (h *SamplingHandler) WithAttrs(attrs []slog.Attr) slog.Handler {
    return &SamplingHandler{handler: h.handler.WithAttrs(attrs), rate: h.rate}
}

func (h *SamplingHandler) WithGroup(name string) slog.Handler {
    return &SamplingHandler{handler: h.handler.WithGroup(name), rate: h.rate}
}
```

### 6. Агрегация и Хранение

Контейнеры в современных облачных кластерах эфемерны: под может быть пересоздан или уничтожен в любую секунду. Все, что записано на локальный диск контейнера, исчезает вместе с ним.

Поэтому стандартная архитектура сбора логов исключает запись в локальные файлы внутри пода. Go-приложение пишет строго в `os.Stdout`, откуда логи перехватываются специализированным узловым демоном (Vector, Fluent Bit, Promtail):

- **Grafana Loki**: Не производит полнотекстовую индексацию содержимого, а индексирует только структурированные метаданные (лейблы). Тело лога хранится в сжатом виде в объектном хранилище (S3/MinIO). Это многократно дешевле классического ELK и идеально подходит для Kubernetes.
- **Elasticsearch / OpenSearch**: Осуществляет глубокое построение инвертированных индексов по всем полям JSON. Обеспечивает мгновенный аналитический поиск по терабайтам данных, но требует колоссальных объемов оперативной памяти и дискового пространства.
- **Управляемые облачные сервисы**: AWS CloudWatch, Google Cloud Logging (Stackdriver).

> [!tip] Собеседование
> **Вопрос:** Почему классический пакет `log` из стандартной библиотеки Go считается архитектурным антипаттерном в современных микросервисах?
> **Ответ:** Пакет `log` пишет неструктурированный плоский текст без поддержки уровней логирования (`Info`, `Warn`, `Error`), не умеет нативно работать с `context.Context` и блокирует параллельные вызовы через глобальный мьютекс. Машинный парсинг таких логов в системах ELK или Loki дорог и хрупок. В современных микросервисах промышленным стандартом является нативный пакет `log/slog` (начиная с Go 1.21+), либо проверенные библиотеки `uber/zap` и `logrus`.
> 
> **Вопрос:** Как правильно перехватывать и логировать непредвиденные паники рантайма (`panic`), чтобы они не потерялись при сбое сервиса?
> **Ответ:** Необходимо регистрировать перехватчик в middleware через `defer recover()`. Внутри блока `recover()` извлекается полный стек вызовов горутины через функцию `runtime/debug.Stack()`, после чего паника оформляется как полноценная структурированная запись с уровнем `ERROR`, содержащая `stack_trace`, `request_id` и `trace_id`, и отправляется через основной настроенный логгер. Простого вывода в `stderr` недостаточно — неструктурированный вывод теряется или ломает парсеры систем агрегации.

### 7. Итог

1. В production логи — это поток структурированных машиночитаемых данных, а не текстовые сообщения для человека. Используйте JSON-форматирование.
2. Исключайте лишние аллокации в горячих путях: задействуйте `log/slog` с типизированными атрибутами и избегайте неявной упаковки через `slog.Any` и `interface{}`.
3. Обязательно связывайте события распределенной системы, передавая `request_id` и `trace_id` через `context.Context`.
4. Строго пресекайте утечки чувствительных данных (паролей, токенов заголовка `Authorization`, персональных сведений `CreditCard: ****1234`).
5. Используйте буферизацию через `bufio.Writer` для минимизации числа блокирующих системных вызовов `write`.
6. Отключайте уровень `DEBUG` в бою и применяйте сэмплирование (Sampling) для частых событий `INFO`, чтобы предотвратить деградацию системы под нагрузкой.
7. Доверяйте сбор и доставку логов специализированным демонам (Vector, Fluent Bit), выводя данные приложения строго в стандартные потоки `os.Stdout`.
