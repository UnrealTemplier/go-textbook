
**LeetCode 18. 4Sum.** Дан массив целых чисел `nums` и целевое значение `target`. Требуется найти все уникальные четвёрки индексов `(a, b, c, d)` с попарно различными индексами, такие что `nums[a] + nums[b] + nums[c] + nums[d] == target`. Набор четвёрок не должен содержать дубликатов.

4Sum — это прямое обобщение [[6. 3Sum]] и [[4. Two Sum II Sorted Array]]. Если 3Sum добавил один внешний цикл к встречным указателям, то 4Sum добавляет ещё один уровень. Задача проверяет, способен ли кандидат аккуратно масштабировать паттерн, не плодя лишней сложности, и как он справляется с дедупликацией на нескольких уровнях вложенности. Для Go-разработчика уровня Senior это также полигон для демонстрации того, как избежать аллокаций в горячих циклах и как обобщить решение до kSum, если интервьюер попросит follow-up.

### Формулировка и уточнения

**Условие:**
- Вход: `nums []int`, `target int`, длина `n` (1 ≤ n ≤ 200, но на LeetCode может достигать 200–400, в некоторых версиях до 2000).
- Выход: `[][]int` — список всех уникальных четвёрок, сумма которых равна `target`. Порядок четвёрок и элементов внутри произволен, но обычно ожидают неубывающий.
- Индексы различны, дубликаты четвёрок исключаются.

**Вопросы интервьюеру:**
- *Может ли массив быть пустым или длиной менее 4?* Да, тогда возвращаем пустой слайс.
- *Допустимы ли отрицательные числа?* Да.
- *Есть ли дубликаты?* Да, это основная сложность.
- *Какой возврат при отсутствии четвёрок?* Пустой слайс (в Go идиоматично `nil` или `[][]int{}`).
- *Можно ли модифицировать входной массив?* Да, сортировка in-place разрешена.

Ограничения (например, n ≤ 200) подсказывают, что O(N³) приемлемо, но мы стремимся к O(N³) с низкой константой, а не к наивному O(N⁴).

### Наивное решение: четыре вложенных цикла

Брутфорс — перебор `(i, j, k, l)` с `i < j < k < l`. Сложность O(N⁴) по времени — для N = 200 это ~64 миллиона операций, что ещё может проскочить, но для N = 400 уже ~1 миллиард — TLE. Дедупликация требует дополнительных проверок или структур. На собеседовании такое решение можно упомянуть как baseline, но сразу перейти к O(N³).

### Оптимальное решение: сортировка + два вложенных цикла + встречные указатели

**Идея.** Мы обобщаем подход из [[6. 3Sum]] на один уровень выше. Сначала сортируем массив за O(N log N). Затем фиксируем первые два элемента (`i` и `j`), а для оставшейся правой части массива запускаем встречные указатели `left` и `right` для поиска пары с суммой `target - nums[i] - nums[j]`. Чтобы избежать дубликатов четвёрок, мы пропускаем одинаковые значения на каждом уровне фиксации и после нахождения четвёрки.

Алгоритм:
1. Сортируем `nums`.
2. Внешний цикл `i` от 0 до `n-4`:
   - Пропускаем дубликаты `nums[i] == nums[i-1]`.
   - Досрочный выход? Можно проверить минимально возможную сумму `nums[i] + nums[i+1] + nums[i+2] + nums[i+3] > target` — break; максимально возможную `nums[i] + nums[n-3] + nums[n-2] + nums[n-1] < target` — continue. Это опциональные микрооптимизации, демонстрирующие заботу о производительности.
3. Вложенный цикл `j` от `i+1` до `n-3`:
   - Пропускаем дубликаты `nums[j] == nums[j-1]` (только если `j > i+1`).
   - Аналогичные проверки границ для early pruning.
4. Для фиксированных `i,j` запускаем встречные указатели: `left = j+1`, `right = n-1`.
   - Пока `left < right`, вычисляем `sum = nums[i] + nums[j] + nums[left] + nums[right]`.
   - Если `sum == target`: сохраняем четвёрку, сдвигаем `left` и `right`, пропуская дубликаты.
   - Если `sum < target`: `left++`.
   - Если `sum > target`: `right--`.

Инвариант для вложенных встречных указателей полностью аналогичен 3Sum, просто добавляется ещё один фиксированный элемент.

```go
func fourSum(nums []int, target int) [][]int {
    n := len(nums)
    if n < 4 {
        return nil
    }
    sort.Ints(nums) // O(N log N), in-place

    res := make([][]int, 0)
    for i := 0; i < n-3; i++ {
        // пропуск дубликатов первого элемента
        if i > 0 && nums[i] == nums[i-1] {
            continue
        }
        // минимальная возможная сумма с текущим i:
        if nums[i]+nums[i+1]+nums[i+2]+nums[i+3] > target {
            break
        }
        // максимальная возможная сумма с текущим i:
        if nums[i]+nums[n-3]+nums[n-2]+nums[n-1] < target {
            continue
        }
        for j := i + 1; j < n-2; j++ {
            // пропуск дубликатов второго элемента
            if j > i+1 && nums[j] == nums[j-1] {
                continue
            }
            // аналогичные проверки границ для j
            if nums[i]+nums[j]+nums[j+1]+nums[j+2] > target {
                break
            }
            if nums[i]+nums[j]+nums[n-2]+nums[n-1] < target {
                continue
            }
            left, right := j+1, n-1
            need := target - nums[i] - nums[j]
            for left < right {
                sum := nums[left] + nums[right]
                switch {
                case sum == need:
                    res = append(res, []int{nums[i], nums[j], nums[left], nums[right]})
                    // пропускаем дубликаты left
                    for left < right && nums[left] == nums[left+1] {
                        left++
                    }
                    // пропускаем дубликаты right
                    for left < right && nums[right] == nums[right-1] {
                        right--
                    }
                    left++
                    right--
                case sum < need:
                    left++
                default: // sum > need
                    right--
                }
            }
        }
    }
    return res
}
```

**Go-идиомы:**
- Предварительная сортировка `sort.Ints` in-place.
- Слайс результата через `make([][]int, 0)`.
- Имена `left`, `right` чётки.
- `switch` для трёх случаев.
- Вложенные циклы пропуска дубликатов с обязательной проверкой `left < right`.

**Почему не map?** Как и в 3Sum, map потребовал бы сложной дедупликации (например, хранить `map[[4]int]struct{}`) и дополнительную память, тогда как два указателя с пропуском дубликатов естественно решают проблему уникальности.

### Обобщение до kSum (рекурсивный подход)

На собеседовании Senior-уровня могут спросить: «А если бы нужно было решить kSum?» Тогда демонстрируется рекурсивное решение, которое сводит kSum к (k-1)Sum, и в базе 2Sum использует встречные указатели. Это показывает способность обобщать.

```go
func kSum(nums []int, target int, k int) [][]int {
    sort.Ints(nums)
    return kSumRecursive(nums, target, k, 0)
}

func kSumRecursive(nums []int, target int, k int, start int) [][]int {
    if k == 2 {
        return twoSumSorted(nums, target, start)
    }
    var res [][]int
    for i := start; i <= len(nums)-k; i++ {
        if i > start && nums[i] == nums[i-1] {
            continue
        }
        // рекурсивно ищем (k-1) элементов с суммой target - nums[i]
        subsets := kSumRecursive(nums, target-nums[i], k-1, i+1)
        for _, subset := range subsets {
            res = append(res, append([]int{nums[i]}, subset...))
        }
    }
    return res
}

func twoSumSorted(nums []int, target int, start int) [][]int {
    var res [][]int
    left, right := start, len(nums)-1
    for left < right {
        sum := nums[left] + nums[right]
        switch {
        case sum == target:
            res = append(res, []int{nums[left], nums[right]})
            for left < right && nums[left] == nums[left+1] { left++ }
            for left < right && nums[right] == nums[right-1] { right-- }
            left++
            right--
        case sum < target:
            left++
        default:
            right--
        }
    }
    return res
}
```

На собеседовании достаточно упомянуть этот подход, но самому реализовывать, скорее всего, придётся только 4Sum.

### Edge Cases

- **Длина меньше 4:** возврат пустого слайса.
- **Все элементы одинаковы:** например, `nums = [2,2,2,2,2]`, `target = 8`. Четвёрка `[2,2,2,2]` будет найдена, дубликаты отсечены.
- **Отрицательный target с отрицательными числами:** работает, так как сортировка и сравнения корректны.
- **Досрочные проверки границ:** могут быть опущены, но Senior их показывает как заботу о производительности.

> [!warning] Ловушка / Gotcha
> При проверке `j > i+1 && nums[j] == nums[j-1]` легко ошибиться с индексом начала. Важно, чтобы для `j = i+1` (первый элемент после i) дубликат не пропускался, иначе мы пропустим четвёрки, где второй элемент совпадает с первым? Первый элемент фиксирован, а второй должен быть следующим, даже если равен. Пропускать дубликаты `j` нужно только начиная со второго `j` для данного `i`.

### Анализ сложности

- **Время:** O(N³) в худшем случае. Внешний цикл O(N), вложенный O(N), внутренний цикл встречных указателей O(N). Общие проверки с пропуском дубликатов не меняют асимптотики. При N=200 получается ~8×10⁶ операций, мгновенно.
- **Память:** O(1) дополнительной, не считая результата. Сортировка in-place, указатели — целые числа.

### Mechanical Sympathy

- **Сортировка:** `sort.Ints` in-place, cache-friendly.
- **Встречные указатели:** доступ к элементам слайса последовательный с двух сторон, кэш-промахи минимальны.
- **Отсутствие map:** никаких pointer chasing и бакетов, GC не нагружен.
- **Минимизация аллокаций:** результат формируется через `append`, но четвёрок обычно немного. При необходимости можно предвыделить `make([][]int, 0, expectedCap)`, хотя точное количество неизвестно.

### Альтернативы и trade-off

- **Map с заморозкой двух элементов и поиском пары через map:** время O(N²), память O(N) для хранения сумм пар. Дедупликация усложняется. В некоторых случаях может быть быстрее для больших N, но требования к памяти нарушают философию двух указателей.
- **Обобщённый kSum с рекурсией:** уже описан выше.

> [!tip] Собеседование
> Интервьюер может спросить: «Зачем вы добавили проверки `if nums[i]+nums[i+1]+nums[i+2]+nums[i+3] > target { break }`?»
> Ответ: «Это простые границы, которые позволяют досрочно завершить цикл, если даже минимально возможная сумма для данного i превышает target. Они не меняют сложности, но на практике сокращают число итераций, что демонстрирует внимание к производительности. В production-коде такие оптимизации часто оправданы».

### Итог

4Sum масштабирует технику из 3Sum, добавляя ещё один уровень фиксации. Senior Go-разработчик реализует её, сохраняя код читаемым, без лишней памяти, с правильной дедупликацией. В решении проявляются все сильные стороны паттерна «два указателя»: сортировка, встречные указатели, пропуск дубликатов и механическая симпатия — отсутствие pointer chasing и нулевая нагрузка на GC.
