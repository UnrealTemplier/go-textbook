
Переход от DP на деревьях к DP на графах — это шаг из упорядоченного мира в хаос. В [[1. Теория. DP на деревьях]] мы опирались на тот факт, что путь от корня к любому листу всего один. В графах это правило нарушается: узлы могут иметь несколько родителей, а самое страшное — **циклы**.

Для бэкенд-инженера графы — это повседневность: микросервисные архитектуры (вызовы между сервисами), системы контроля версий (Git), таски в CI/CD и распределенные транзакции. Понимание того, как применять DP на графах, позволяет строить оптимальные маршруты и выявлять циклические зависимости.

## Главная проблема: Циклы

Классическое DP (и рекурсивный DFS) требует, чтобы задача разбивалась на *меньшие* подзадачи, и не было бесконечной рекурсии. В графе с циклом алгоритм будет бесконечно ходить по кругу: $A \to B \to C \to A \dots$

Поэтому DP на графах делится на две принципиально разные парадигмы:
1. **DAG (Directed Acyclic Graph):** Граф без циклов. Применимо классическое Bottom-Up DP через топологическую сортировку.
2. **Общий граф (с циклами):** Требует Memorization (Top-Down DFS) с обязательным отслеживанием текущего пути (цвета узлов) для детекции циклов.

## Парадигма 1. DAG и Топологическая сортировка

Направленный ациклический граф (DAG) — это по сути "расширенное дерево", где узел может иметь несколько входящих ребер. Самый известный пример в бэкенде — DAG зависимостей в Airflow или система сборки (Make, Bazel).

Чтобы применить Bottom-Up DP на DAG, нам нужно линеаризовать граф — получить порядок узлов, в котором все ребра идут строго слева направо. Это называется **топологической сортировкой**.

Как только граф отсортирован, задача превращается в обычный 1D DP: мы итерируемся по узлам в топологическом порядке, и гарантируется, что все "предки" (состояния `dp[i-1]`) уже вычислены.

```go
// Вычисление максимального пути в DAG (например, критический путь сборки)
func maxPathDAG(n int, edges [][]int) int {
    // 1. Строим граф и массив входящих степеней (in-degree)
    adj := make([][]int, n)
    inDegree := make([]int, n)
    for _, e := range edges {
        u, v := e[0], e[1]
        adj[u] = append(adj[u], v)
        inDegree[v]++
    }
    
    // 2. Топологическая сортировка (Алгоритм Кана)
    queue := []int{}
    for i := 0; i < n; i++ {
        if inDegree[i] == 0 {
            queue = append(queue, i)
        }
    }
    
    dp := make([]int, n) // dp[i] - максимальный путь до узла i
    topoOrder := []int{}
    
    for len(queue) > 0 {
        u := queue[0]
        queue = queue[1:]
        topoOrder = append(topoOrder, u)
        
        for _, v := range adj[u] {
            // 3. Переход DP: релаксация ребра
            if dp[u]+1 > dp[v] {
                dp[v] = dp[u] + 1
            }
            inDegree[v]--
            if inDegree[v] == 0 {
                queue = append(queue, v)
            }
        }
    }
    
    // Находим максимум по всем dp
    maxPath := 0
    for _, val := range dp {
        if val > maxPath {
            maxPath = val
        }
    }
    return maxPath
}
```

> [!info] Под капотом
> Алгоритм Кана (Kahn's algorithm) использует очередь. В Go для малых графов срез `[]int` работает быстро, но удаление из начала среза `queue[1:]` вызывает утечку памяти (старый базовый массив удерживает все элементы в куче, пока GC не очистит весь срез). В production-коде для очередей используют кольцевые буферы (ring buffer) или `container/list`, чтобы избежать аллокаций на каждом шаге.

## Mechanical Sympathy: Pointer Chasing в хеш-таблицах

В задачах на графы узлы часто представлены не целыми числами (0..N-1), а строками (ID сервисов). В этом случае приходится использовать `map[string][]string` для списка смежности и `map[string]int` для DP.

Это означает, что вместо предсказуемого доступа по индексу в слайсе, процессор будет бесконечно прыгать по хеш-таблицам. Каждый `dp[node]` — это вычисление хеша, поиск бакета, проверка `tophash` и переход по указателю. Это убивает локальность кэша L1/L2 и деградирует производительность в десятки раз.

**Архитектурный трюк:** Если вы пишете планировщик микросервисов, всегда мапьте строковые ID сервисов в плотные целые индексы ($0 \dots N-1$) на этапе парсинга конфигурации. Выполняйте всю математику путей на слайсах, и только в конце мапьте индексы обратно в строки. Это классический прием Space-Time Tradeoff в System Design.

## Парадигма 2. Top-Down DFS на графах с циклами

Если граф содержит циклы (например, поиск максимального пути в графе с поощрениями, где нет негативных весов), топологическая сортировка невозможна. Мы обязаны использовать DFS с мемоизацией. Но нам нужно защищаться от зацикливания.

Для этого используется **алгоритм раскраски узлов (3-color algorithm)**:
- `0` (White): Узел не посещен.
- `1` (Gray): Узел в текущем стеке вызовов (мы в него вошли, но еще не вышли). Если мы снова попали в Gray — найден цикл!
- `2` (Black): Узел полностью обработан (все его потомки посещены, `memo` заполнен).

```go
var memo map[int]int
var color map[int]int
var hasCycle bool

func dfsGraph(u int, adj [][]int) int {
    if hasCycle { return -1 }
    
    if color[u] == 1 {
        hasCycle = true // Цикл!
        return -1
    }
    if color[u] == 2 {
        return memo[u] // Уже вычислено (Memoization)
    }
    
    color[u] = 1 // Красим в серый (входим в рекурсию)
    
    maxDist := 0
    for _, v := range adj[u] {
        dist := dfsGraph(v, adj) + 1
        if dist > maxDist {
            maxDist = dist
        }
    }
    
    color[u] = 2 // Красим в черный (выходим из рекурсии)
    memo[u] = maxDist
    return maxDist
}
```

> [!warning] Ловушка / Gotcha
> В Go мапы (`map`) не потокобезопасны. Если вы запускаете обход графа из нескольких горутин (например, для распараллеливания поиска в компонентах связности), использование глобальных `color` и `memo` приведет к Data Race и фатальной ошибке. В конкурентном коде нужно передавать контекст с мапами через аргументы или использовать `sync.Map` (что медленнее обычных мап).

## System Design: Обнаружение deadlock-ов

В распределенных системах (БД, микросервисы) дедлок возникает, когда транзакция A ждет ресурс, захваченный транзакцией B, а B ждет ресурс от A. Это цикл в графе ожидания (Wait-For Graph).

Алгоритм раскраски (Gray/Black), описанный выше — это именно то, как СУБД вроде PostgreSQL или системы вроде Zookeeper детектят дедлоки. Как только DFS натыкается на "серый" узел (транзакцию, которая уже есть в стеке вызовов), система понимает, что найден цикл, и принудительно откатывает (abort) одну из транзакций для разрыва цикла.

> [!tip] Собеседование
> Если вас просят найти кратчайший путь в графе с *отрицательными* весами ребер, DP на графах приходит на помощь в виде **Алгоритма Беллмана-Форда**. По сути, это 2D DP, где `dp[k][v]` — кратчайший путь до `v` с использованием не более `k` ребер. Формула перехода: `dp[k][v] = min(dp[k-1][v], dp[k-1][u] + weight(u, v))`. Это классический вопрос на архитектуру маршрутизации с финансовыми штрафами (арбитражные сделки на биржах).

## Итог

1. **DAG для Bottom-Up:** Если граф ациклический (DAG), применяйте топологическую сортировку и решайте задачу как 1D DP за линейное время.
2. **Раскраска для Top-Down:** Если есть циклы, используйте DFS + Memoization с пометкой узлов (White/Gray/Black), чтобы избегать бесконечных циклов и кэшировать результаты.
3. **Маппинг строк в int:** Избегайте `map[string][]string` для вычислений. Маппите ID в плотные индексы, чтобы использовать кэш-линии процессора по максимуму.
4. **Deadlock Detection:** Алгоритм раскраски графов — это математическая основа поиска дедлоков в базах данных.
