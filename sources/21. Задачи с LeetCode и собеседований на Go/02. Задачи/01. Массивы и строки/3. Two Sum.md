
Это задача, с которой начинается путь в алгоритмические собеседования. Она же — идеальный полигон для демонстрации того, как Go-разработчик выбирает структуру данных, думает о памяти и не забывает уточнить крайние случаи. На первый взгляд Two Sum проста. Но именно на её примере интервьюер проверяет: мыслит ли кандидат категориями компромисса «время–память», знает ли устройство map и способен ли написать идиоматичный код, который не стыдно показать на code review.

Мы разберём наивное решение, поймём его узкое место и выведем оптимум. А затем спустимся «под капот» Go и посмотрим, как выбор map влияет на аллокации, pointer chasing и сборщик мусора.

### Формулировка и уточнения

**LeetCode 1. Two Sum.**

Дан массив целых чисел `nums` и целевое значение `target`. Нужно вернуть индексы двух элементов, дающих в сумме `target`. Гарантируется, что ровно одно решение существует. Один и тот же элемент нельзя использовать дважды.

Прежде чем писать код, Senior задаёт вопросы:
- Могут ли быть отрицательные числа? Да.
- Может ли `target` быть отрицательным? Да.
- Есть ли дубликаты в массиве? Допустим, могут быть.
- Если решение не найдено (но по условию гарантировано), что возвращать? В Go-стиле — `nil` или пустой слайс.
- Важен ли порядок индексов? Обычно нет, но обычно ожидают возрастающий.

Ответы определяют выбор структур: map справится с отрицательными числами, дубликатами и вернёт индексы в любом порядке.

### Наивное решение: двойной цикл

Брутфорс — перебор всех пар. Внешний цикл `i` от 0 до `n-2`, внутренний `j` от `i+1` до `n-1`. Сложность O(N²) по времени, O(1) по памяти (кроме результирующего слайса).

```go
func twoSumBrute(nums []int, target int) []int {
    n := len(nums)
    for i := 0; i < n-1; i++ {
        for j := i + 1; j < n; j++ {
            if nums[i]+nums[j] == target {
                return []int{i, j}
            }
        }
    }
    return nil
}
```

Почему это не подходит для серьёзного собеседования? При N = 10⁴ (типичные ограничения) алгоритм выполнит ~50 миллионов итераций — около 0.1–0.3 секунды на Go, что ещё приемлемо, но при N = 10⁵ это уже 5 миллиардов итераций и вероятный TLE. Интервьюер ожидает линейного решения.

### Оптимальное решение: хеш-таблица (map)

Идея: проходя по массиву, для текущего элемента `nums[i]` мы знаем, что ему в пару нужен `complement = target - nums[i]`. Если `complement` уже встречался ранее, мы нашли ответ. Иначе сохраняем текущее значение и его индекс в map для будущих запросов.

**Инвариант:** после каждой итерации map содержит все элементы, встреченные до текущего индекса. Проверка существования `complement` в map — O(1) в среднем.

```go
func twoSum(nums []int, target int) []int {
    // Ключ — значение элемента, значение — его индекс
    seen := make(map[int]int, len(nums))
    for i, v := range nums {
        complement := target - v
        if j, ok := seen[complement]; ok {
            return []int{j, i}
        }
        seen[v] = i
    }
    return nil
}
```

**Что здесь важно с точки зрения Go:**
- `make(map[int]int, len(nums))` — предвыделение вместимости. Без него map будет расти и эвакуировать бакеты при заполнении, что вызовет дополнительные аллокации и замедление. С указанием capacity мы сокращаем число эвакуаций до нуля (если нет дубликатов).
- `if j, ok := seen[complement]; ok` — идиоматичная проверка наличия ключа (comma-ok). Она позволяет отличить присутствие нуля от отсутствия ключа.
- Возвращаем индексы в порядке `[j, i]` — `j` встретился раньше, это соответствует возрастающему порядку.

> [!info] Под капотом
> Карта в Go — это структура `runtime.hmap` в куче. Доступ к элементу включает: вычисление хеша ключа, нахождение бакета (bucket), линейный пробег по цепочке переполнения. Это pointer chasing, который разрушает кэш-локальность. Внутри цикла мы делаем два обращения к map: `seen[complement]` и `seen[v] = i` (запись). Каждое из них потенциально вызывает промах мимо L1/L2-кэша и стоит десятки тактов. Но асимптотика O(1) в среднем делает алгоритм линейным, а при N до 10⁵ накладные расходы (~100–200 нс на доступ) укладываются в лимит.

**Trade-off памяти:** Мы платим O(N) дополнительной памяти за map. В худшем случае все элементы уникальны и попадут в map.

### Альтернатива: сортировка + два указателя

Если бы задача требовала вернуть сами значения, а не индексы, мы могли бы отсортировать массив и пройти двумя указателями ([[2. Типовые операции и приёмы]]). Это дало бы O(N log N) времени и O(1) памяти (или O(N) для копии, если исходный порядок важен). Но для исходной задачи сохранение индексов после сортировки потребовало бы хранить кортежи `(значение, исходный_индекс)`, что снова приводит к O(N) памяти и усложняет код. Поэтому map — предпочтительный выбор.

На собеседовании стоит упомянуть эту альтернативу: «Если бы память была критична и мы могли модифицировать входной массив, я бы рассмотрел сортировку с двумя указателями. Но поскольку нужны исходные индексы, map даёт лучшее сочетание простоты и O(N) времени».

### Edge cases

- **Пустой массив или длина 1:** цикл не выполнится, вернётся `nil`. По условию гарантировано решение, но корректное поведение при отсутствии — плюс.
- **Дубликаты:** `nums = [3, 3], target = 6`. На первой итерации `3` запишется в map с индексом 0. На второй итерации `complement = 3`, найдётся `j = 0`, вернётся `[0, 1]` — верно.
- **Отрицательные числа:** map работает с любыми целыми ключами.
- **Переполнение:** в Go `int` — 64 бита на 64-битных системах, при сумме двух 32-битных значений переполнения не будет. Если бы мы использовали `int32`, следовало бы упомянуть.

> [!warning] Ловушка / Gotcha
> Не делайте запись в map до проверки complement. Если `target = 2 * nums[i]`, а элемент один, вы можете найти «самого себя». Порядок в коде выше (сначала проверка, потом запись) гарантирует, что текущий элемент не используется дважды.

### Анализ сложности

- **Время:** O(N) в среднем. Каждый элемент обрабатывается один раз, каждая операция с map — O(1) амортизированно.
- **Память:** O(N) для хранения map. В худшем случае все элементы сохраняются.
- **Константы:** два обращения к map на итерацию плюс предвыделение вместимости — практически без скрытых копирований. GC будет освобождать map после возврата из функции (если она не сохраняется глобально).

### Mechanical Sympathy: map vs массив

В Two Sum ключи — произвольные целые числа, поэтому массив фиксированного размера неприменим. Но если бы значения `nums` были ограничены, скажем, `1 <= nums[i] <= 1000`, мы могли бы использовать `[1001]int` с индексами и избежать map. Тогда доступ был бы прямым (одна инструкция LEA), без pointer chasing, без аллокаций в куче, без нагрузки на GC. На собеседовании это можно озвучить: «Я выбрал map, потому что диапазон входных значений не ограничен. Если бы значения были в узком диапазоне, я бы заменил map на массив для лучшей кэш-локальности».

### Итог

Two Sum — это демонстрация базового инженерного навыка: готовность пожертвовать памятью ради времени. В Go она дополнительно подсвечивает знание устройства map и умение писать идиоматичный код с `make(map[K]V, cap)` и comma-ok. Для Senior-кандидата этого недостаточно — он обязан обсудить trade-off, упомянуть альтернативу с сортировкой и двумя указателями, а также понимать, как выбранная структура данных взаимодействует с кэш-памятью и GC.
