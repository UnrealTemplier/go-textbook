
Среди всех задач на массивы эта занимает особое место. LeetCode 53 — Maximum Subarray — не требует ни хеш-таблиц, ни сортировки, ни скользящего окна. Только один проход, одна переменная состояния и одна переменная для ответа. Но именно в этой простоте кроется глубина, которую Senior-разработчик обязан видеть: классическое динамическое программирование, сжатое до O(1) памяти, и алгоритм, настолько дружественный железу, что может обработать миллион элементов за доли миллисекунды.

На собеседовании эта задача — лакмусовая бумажка. Кандидат Middle-уровня выдаст решение и скажет «алгоритм Кадане». Senior пойдёт дальше: выведет его из наивного подхода, сформулирует инвариант, обсудит случай всех отрицательных чисел, расскажет, почему это DP, а не greedy (хотя внешне похоже), и упомянет альтернативу — Divide and Conquer — с анализом её применимости в распределённых системах.

### Формулировка и уточнения

Дан массив целых чисел `nums`. Нужно найти **непрерывный подмассив** с максимальной суммой и вернуть эту сумму. Длина массива не менее 1.

**Вопросы интервьюеру:**
- Может ли массив быть пустым? (По условию LeetCode — нет, но в реальности стоит уточнить.)
- Могут ли быть отрицательные числа? Да, в этом суть задачи. Если все элементы отрицательные, ответ — максимальный из них (наименьшее по модулю отрицательное).
- Ожидаемый возврат при пустом массиве? Если такое возможно, в Go идиоматично возвращать `0` или специальное значение, но в классической задаче `len >= 1`.

### Наивное решение: кубическое и квадратичное

**Кубический перебор.** Три вложенных цикла: `left`, `right`, и внутренний цикл для суммирования элементов от `left` до `right`. Сложность O(N³). При N=10⁵ — астрономически далеко от допустимого.

**Квадратичный перебор.** Если заметить, что сумму подмассива `[left, right]` можно получить из `[left, right-1]` добавлением `nums[right]`, третий цикл убирается:

```go
func maxSubArrayBrute(nums []int) int {
    n := len(nums)
    maxSum := math.MinInt
    for left := 0; left < n; left++ {
        curSum := 0
        for right := left; right < n; right++ {
            curSum += nums[right]
            if curSum > maxSum {
                maxSum = curSum
            }
        }
    }
    return maxSum
}
```

Сложность O(N²), память O(1). При N=10⁵ — 5×10⁹ итераций, TLE. Но это хорошая отправная точка: мы уже переиспользуем сумму, и теперь видно, что для каждого `left` мы проходим весь хвост, пересчитывая одни и те же суммы.

**Вопрос, который ведёт к прозрению:** «Что если на очередном шаге `curSum` стала отрицательной?» Если `curSum < 0`, то добавление её к следующему элементу `nums[right+1]` даст сумму меньше, чем если бы мы начали новый подмассив прямо с `nums[right+1]`. Значит, можно сбросить `curSum` в ноль и двигать `left` неявно. Это и есть ключевая идея.

### Алгоритм Кадане: DP, сжатое до O(1)

Формально это динамическое программирование. Определим `dp[i]` — максимальная сумма подмассива, заканчивающегося на индексе `i`. Тогда переход:

```
dp[i] = max(nums[i], dp[i-1] + nums[i])
```

Ответ — максимум из всех `dp[i]`. Но поскольку `dp[i]` зависит только от `dp[i-1]`, мы храним не весь массив, а одну переменную `curSum`. Это классическое сжатие DP-таблицы.

**Инвариант цикла:** после обработки элемента `i` переменная `curSum` содержит максимальную сумму подмассива, заканчивающегося на `i`; переменная `maxSum` — глобальный максимум для подмассивов, заканчивающихся на индексах `0..i`.

```go
func maxSubArray(nums []int) int {
    if len(nums) == 0 {
        return 0 // или ошибка, если контракт гарантирует len >= 1
    }
    curSum := nums[0]
    maxSum := nums[0]
    for _, v := range nums[1:] {
        // Если текущая сумма стала отрицательной, начинаем новый подмассив
        if curSum < 0 {
            curSum = 0
        }
        curSum += v
        if curSum > maxSum {
            maxSum = curSum
        }
    }
    return maxSum
}
```

**Идиоматичный вариант с явным DP-переходом (более чистый для понимания):**

```go
func maxSubArray(nums []int) int {
    if len(nums) == 0 {
        return 0
    }
    curSum, maxSum := nums[0], nums[0]
    for _, v := range nums[1:] {
        curSum = max(v, curSum+v)
        maxSum = max(maxSum, curSum)
    }
    return maxSum
}

func max(a, b int) int {
    if a > b {
        return a
    }
    return b
}
```

**Go-нюансы:**
- Используем `for _, v := range nums[1:]` — это создаёт подслайс без копирования элементов (заголовок слайса копируется, данные остаются те же). На больших массивах это предпочтительнее, чем `for i := 1; i < len(nums); i++`.
- Вспомогательная функция `max` не является встроенной до Go 1.21 (с 1.21 есть `max` в builtin, но на LeetCode может быть более старая версия). Писать свою `max` — стандартная практика.
- Проверка `len(nums) == 0` — демонстрация безопасного программирования. Даже если гарантируется, функция должна быть устойчивой.

> [!warning] Ловушка / Gotcha
> Если все элементы отрицательные, `curSum` на каждом шагу будет сбрасываться в 0 и затем увеличиваться до `v`, что даст `maxSum` равным максимальному элементу. Это корректно. Но если инициализировать `maxSum = 0`, а все элементы отрицательные, ответ будет 0, что неверно. Поэтому `maxSum` инициализируется `nums[0]`, а не нулём.

### Механическая симпатия: почему Кадане летает

Алгоритм Кадане — один из самых «железо-дружественных» алгоритмов. Всё, что он делает — это последовательный проход по непрерывному блоку памяти с двумя операциями на элемент: сложение и сравнение.

**Что происходит на уровне процессора:**
- Слайс `nums` лежит в непрерывном массиве в куче (или на стеке, если маленький и не убежал). Указатель итерации движется линейно.
- Аппаратный prefetcher распознаёт sequential access и загружает следующие кэш-линии в L1/L2 кэш заранее. Cache miss практически нулевые.
- Тело цикла содержит только `curSum = max(v, curSum+v)` — пара инструкций ADD, CMP, CMOV на x86. Никаких вызовов функций (если `max` встроена или вручную через `if`), никаких аллокаций, никаких указателей.

**Сравнение с map-решением (если бы мы решали через префиксные суммы):**
- Префиксные суммы + map заняли бы O(N) памяти и добавили pointer chasing на каждое обращение к map. Для N=10⁶ Кадане выполнится за ~1–2 мс, а map-решение за ~10–20 мс. В production-системах с жёсткими SLO это имеет значение.

**Нулевые аллокации:** внутри цикла нет `append`, нет `make`, нет взятия адреса. Escape analysis оставляет все переменные на стеке. GC не вызывается во время выполнения функции (если только не вытесняется по времени, но алгоритм настолько быстр, что не успеет).

> [!info] Под капотом
> В исходниках Go рантайма есть аналогичный подход: `runtime.memhash` — нет, это не про Кадане. Но сам принцип «один проход, одна переменная, минимум операций» — это идеал для CPU. Без ветвлений (в варианте с `max`) современный процессор может выполнять несколько итераций цикла параллельно (instruction-level parallelism), предсказывая переходы. Алгоритм Кадане — один из немногих, где это возможно в полной мере.

### Edge cases

- **Один элемент:** цикл по `nums[1:]` не выполнится, `maxSum` = `nums[0]` — верно.
- **Все отрицательные:** `curSum` будет обновляться до текущего максимума, ответ — наименьшее по модулю отрицательное. Пример: `[-3, -1, -2]` → ответ `-1`.
- **Все положительные:** `curSum` никогда не сбрасывается, ответ — сумма всего массива.
- **Нули:** не меняют сумму, корректно обрабатываются.
- **Пустой массив:** с нашей проверкой возвращается 0 (если уместно). Или можно вернуть `0, false` через множественный возврат, но это уже не LeetCode-стиль.

### Анализ сложности

- **Время:** O(N). Один проход, на каждом элементе две-три элементарные операции.
- **Память:** O(1). Две переменные `curSum` и `maxSum`, плюс счётчик цикла. Никаких дополнительных структур.

### Обсуждение альтернатив и follow-up

**Divide and Conquer.** Задачу можно решить за O(N log N) рекурсивно: разделить массив пополам, найти максимум в левой, правой части и пересекающий границу. Этот подход имеет смысл, если мы работаем не с массивом в памяти, а с распределённым набором данных (например, файл, разбитый на чанки, или поток, обрабатываемый в параллельных горутинах). Тогда каждый чанк может быть обработан отдельной горутиной, а результат собран через fan-in.

На собеседовании Senior упомянет это: «Кадане оптимален для in-memory массива. Но если бы данные поступали из нескольких источников или хранились на диске, я бы рассмотрел Divide and Conquer с параллельной обработкой чанков и слиянием результатов».

**Потоковая обработка.** Алгоритм Кадане естественно ложится на потоковую обработку: мы можем получать числа по одному и обновлять `curSum` и `maxSum` без хранения всего массива. Это O(1) памяти и O(N) времени. Идеально для стриминга.

**Подмассив с максимальным произведением.** Следующее усложнение (LeetCode 152). Там уже недостаточно одной переменной — нужно отслеживать и минимум, и максимум, потому что умножение на отрицательное число меняет знак. Это развитие идей Кадане.

> [!tip] Собеседование
> Вопрос: «Является ли алгоритм Кадане жадным или DP?»
> Ответ: «Формально это DP, потому что мы определяем состояние `dp[i]` и переход. Но выбор 'начать новый подмассив' выглядит как жадный шаг. На самом деле это DP с линейной оптимальной подструктурой. Жадность здесь безопасна, потому что локально оптимальный выбор (сброс отрицательной суммы) ведёт к глобальному оптимуму. Я могу доказать это через инвариант».
