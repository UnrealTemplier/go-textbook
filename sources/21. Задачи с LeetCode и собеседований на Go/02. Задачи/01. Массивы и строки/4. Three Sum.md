
**LeetCode 15. 3Sum.** Дан массив целых чисел `nums`. Нужно найти все уникальные тройки индексов `(i, j, k)`, такие что `nums[i] + nums[j] + nums[k] == 0`. Индексы внутри тройки должны быть различны, а набор троек не должен содержать дубликатов.

Это естественное усложнение Two Sum. Если в Two Sum достаточно было одной хеш-таблицы, то здесь добавление третьего элемента ломает линейное решение «в лоб». Задача проверяет умение вовремя отказаться от map в пользу сортировки и двух указателей, а также способность аккуратно обрабатывать дубликаты — камень преткновения большинства кандидатов. Для Go-разработчика здесь добавляется демонстрация работы со слайсами, избегание лишних аллокаций и понимание того, как сортировка влияет на память.

### Формулировка и уточнения

**Условие:**
- Вход: массив целых чисел `nums` длиной `n` (0 ≤ n ≤ 3000).
- Выход: список всех уникальных троек `[nums[i], nums[j], nums[k]]` с суммой 0, где индексы попарно различны.
- Порядок троек в ответе и элементов внутри тройки не регламентирован, но обычно ожидают возрастающий.

**Вопросы интервьюеру:**
- Может ли массив быть пустым или длиной менее 3? Да — тогда ответ пустой.
- Могут ли быть дубликаты? Да. Именно они создают основную сложность.
- Допускаются ли отрицательные числа? Да.
- Ожидаемый возврат при отсутствии троек: nil или пустой слайс? В Go идиоматично вернуть пустой слайс (не nil), если функция возвращает коллекцию, но уточнение покажет ваше внимание к деталям.

### Наивное решение: три вложенных цикла

Перебираем все возможные комбинации трёх элементов, проверяем сумму, добавляем в результат с фильтрацией дубликатов. Сложность O(N³) по времени — для N=3000 это 27 миллиардов итераций, гарантированный TLE. К тому же фильтрация дубликатов требует либо дополнительной памяти, либо дополнительных проверок.

```go
func threeSumBrute(nums []int) [][]int {
    n := len(nums)
    var res [][]int
    sort.Ints(nums) // для детекта дубликатов, но всё ещё O(N³)
    for i := 0; i < n-2; i++ {
        if i > 0 && nums[i] == nums[i-1] { continue }
        for j := i+1; j < n-1; j++ {
            if j > i+1 && nums[j] == nums[j-1] { continue }
            for k := j+1; k < n; k++ {
                if k > j+1 && nums[k] == nums[k-1] { continue }
                if nums[i]+nums[j]+nums[k] == 0 {
                    res = append(res, []int{nums[i], nums[j], nums[k]})
                }
            }
        }
    }
    return res
}
```

Этот код нежизнеспособен, но полезен как отправная точка анализа. Узкое место — третий цикл: для фиксированных `i` и `j` мы ищем `k`, такое что `nums[k] = -(nums[i] + nums[j])`. Поскольку массив отсортирован, `k` можно искать не перебором, а бинарным поиском, либо — ещё эффективнее — сжимать пространство поиска двумя указателями.

### Оптимальное решение: сортировка + два указателя

**Идея:**
1. Сортируем массив за O(N log N). Сортировка решает две задачи: позволяет использовать два указателя и упрощает пропуск дубликатов (одинаковые значения становятся соседними).
2. Фиксируем первый элемент `i` от 0 до `n-3`. Если `nums[i] > 0`, для отсортированного массива сумма с любыми положительными числами не даст 0 → досрочный выход.
3. Для фиксированного `i` ищем пару `(j, k)` с суммой `-nums[i]` двумя указателями: `j` начинает с `i+1`, `k` — с `n-1`. Указатели сходятся.
4. При нахождении тройки сохраняем её и пропускаем дубликаты `j` и `k`, сдвигая указатели.
5. После обработки `i` пропускаем дубликаты первого элемента.

**Инвариант:** для текущего `i` все возможные вторые элементы лежат в диапазоне `[j, k]`, и сумма трёх элементов монотонно зависит от сдвига `j` (увеличивается) и `k` (уменьшается). Пропуск дубликатов гарантирует уникальность троек без дополнительной памяти.

```go
func threeSum(nums []int) [][]int {
    n := len(nums)
    if n < 3 {
        return nil
    }

    sort.Ints(nums) // O(N log N), in-place

    res := make([][]int, 0) // пустой не-nil слайс для JSON-совместимости
    for i := 0; i < n-2; i++ {
        // Досрочный выход: первый элемент положителен — сумма не может быть 0
        if nums[i] > 0 {
            break
        }
        // Пропускаем дубликаты первого элемента
        if i > 0 && nums[i] == nums[i-1] {
            continue
        }

        target := -nums[i]
        j, k := i+1, n-1
        for j < k {
            sum := nums[j] + nums[k]
            switch {
            case sum == target:
                res = append(res, []int{nums[i], nums[j], nums[k]})
                // Пропускаем дубликаты второго элемента
                for j < k && nums[j] == nums[j+1] {
                    j++
                }
                // Пропускаем дубликаты третьего элемента
                for j < k && nums[k] == nums[k-1] {
                    k--
                }
                j++
                k--
            case sum < target:
                j++
            default: // sum > target
                k--
            }
        }
    }
    return res
}
```

**Что важно в этом коде с точки зрения Go:**
- `sort.Ints(nums)` модифицирует слайс in-place, не выделяя новой памяти. Если исходный порядок важен (в задаче нет), это идеально. Если бы он был важен, мы бы сделали копию.
- `res := make([][]int, 0)` создаёт пустой не-nil слайс. В случае отсутствия троек он сериализуется в JSON как `[]`, а не `null`. Мелочь, но Senior держит это в голове.
- Пропуск дубликатов реализован явными циклами `for j < k && nums[j] == nums[j+1] { j++ }`. Альтернатива с одинарным инкрементом и `continue` менее читаема и легче приводит к бесконечному циклу.
- Комбинация `switch/case` без выражения чётко разделяет три случая и убирает вложенные `if/else`.

> [!warning] Ловушка / Gotcha
> Порядок пропуска дубликатов важен. Неправильно сначала пропустить дубликаты `j`, а потом проверять выход `j` за границу. Циклы `for j < k && nums[j] == nums[j+1]` безопасны, потому что `j < k` гарантирует, что `j+1` не выйдет за `k`. Но если сначала сделать `j++`, а потом `for j < k && nums[j] == nums[j-1]`, логика усложняется. Текущий вариант — канонический.

### Альтернативное решение: хеш-таблица

Можно ли использовать map, как в Two Sum? Теоретически да: фиксируем `i`, а для оставшейся части массива решаем Two Sum через map. Но тогда для каждой тройки нужно проверять уникальность, что требует дополнительной структуры (например, `map[[3]int]struct{}`), а в худшем случае количество троек может быть O(N²), и мы рискуем переполнить память. Сортировка + два указателя решают проблему уникальности естественным образом без дополнительной памяти. На собеседовании стоит упомянуть: «Map-решение возможно, но добавляет сложность с дедупликацией и требует дополнительной памяти. Сортировка с двумя указателями чище».

### Edge cases

- **Меньше трёх элементов:** `n < 3` → сразу возвращаем пустой слайс.
- **Все элементы положительные:** первый же `nums[i] > 0` → `break`, пустой ответ.
- **Все отрицательные:** `target` положителен, но `j` и `k` отрицательны, сумма никогда не станет положительной, цикл отработает вхолостую, ответ пустой.
- **Много нулей:** `[0,0,0]` → найдена тройка `[0,0,0]`, дубликаты пропущены корректно.
- **Дубликаты всех мастей:** например, `[-1,-1,0,1,2]` → тройки `[-1,-1,2]` и `[-1,0,1]`. Пропуск дубликатов не должен заглушить поиск разных вариаций.

### Анализ сложности

- **Время:** сортировка O(N log N). Внешний цикл по `i` — O(N), внутренний цикл двух указателей — O(N) для каждого `i`, но амортизированно оба указателя проходят не более N элементов, так что общая сложность O(N²). При N=3000 это ~9×10⁶ операций, что выполняется за миллисекунды.
- **Память:** O(1) дополнительной памяти (не считая результирующего слайса, который может содержать до O(N²) троек в теории, но на практике ограничен). Сортировка in-place, два указателя используют три локальные переменные.

### Mechanical Sympathy: что происходит на уровне железа

**Сортировка.** `sort.Ints` в Go реализована на базе pdqsort (pattern-defeating quicksort) — гибрида быстрой сортировки, сортировки вставками и пирамидальной сортировки. Она работает in-place и очень дружественна кэшу: на каждом этапе данные загружаются в кэш-линии, quicksort делит массив на непрерывные сегменты, сохраняя локальность. Никаких дополнительных аллокаций.

**Два указателя.** Итерация `j` и `k` движется по отсортированному массиву последовательно (для `j`) и обратно (для `k`). Доступ `nums[j]`, `nums[k]` — это обращение к непрерывному блоку памяти, prefetcher легко предсказывает следующий кэш-лайн. Никакого pointer chasing, в отличие от map-решения.

**Слайс результатов.** Каждая тройка — это `[]int` из трёх элементов, который Go размещает в куче (слайс-заголовок на стеке, массив из трёх int'ов — в куче). Если троек много (например, для массива из 3000 нулей — около 4.5 миллиардов троек, но задача гарантирует уникальность, а нули дадут только одну тройку `[0,0,0]`). В реальных тестах количество троек значительно меньше теоретического максимума, и память не является проблемой.

> [!tip] Собеседование
> Вопрос: «Можно ли решить 3Sum без сортировки, сохранив O(N²)?»
> Ответ: «Да, через хеш-таблицу с дедупликацией, но это усложнит код и потребует дополнительной памяти. Сортировка + два указателя — это классический trade-off: O(N log N) подготовка, зато O(N²) чистое выполнение без лишней памяти и с автоматическим решением проблемы дубликатов».

### Сравнение с Two Sum

| Характеристика | Two Sum | Three Sum |
|---|---|---|
| Базовый приём | map (хеш-таблица) | сортировка + два указателя |
| Время | O(N) | O(N²) |
| Память | O(N) | O(1) |
| Дубликаты | не проблема | основная сложность |
| Досрочный выход | нет | если `nums[i] > 0` |

Переход от Two Sum к Three Sum показывает, как добавление одного элемента превращает линейную задачу в квадратичную и заставляет менять основной инструмент. На собеседовании умение провести эту параллель и обосновать выбор — сильный сигнал.

### Итог

Three Sum — это классика, на которой ломается большинство неподготовленных кандидатов. Но для Go-разработчика уровня Senior это возможность продемонстрировать владение сортировкой, двумя указателями, обработкой дубликатов и механической симпатией: почему слайс, пройденный двумя указателями, быстрее map-решения, как `sort.Ints` работает с памятью и почему мы выбираем `make([][]int, 0)` для результата.

Теперь, освоив триплеты, мы переходим к задаче, которая требует не перебора комбинаций, а одного прохода с поддержанием локального оптимума — Kadane's Algorithm для Maximum Subarray. [[5. Maximum Subarray (Kadane)]]
