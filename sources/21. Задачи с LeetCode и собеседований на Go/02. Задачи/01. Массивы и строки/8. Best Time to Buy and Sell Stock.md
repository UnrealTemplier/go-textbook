
**LeetCode 121. Best Time to Buy and Sell Stock.** Дан массив `prices`, где `prices[i]` — цена акции в день `i`. Нужно выбрать **один день** для покупки и **один будущий день** для продажи, чтобы максимизировать прибыль. Если прибыль получить невозможно, вернуть 0.

Задача стоит на границе «массивов и строк» и динамического программирования, но в действительности она решается одним линейным проходом с отслеживанием минимума. На собеседовании эта задача отделяет кандидатов, которые сразу видят накопление минимума, от тех, кто пытается применить скользящее окно или два указателя. Для Go-разработчика уровня Senior важно показать не просто работающий код, а понимание того, что алгоритм практически идеален с точки зрения работы с памятью и процессором.

### Формулировка и уточнения

На собеседовании вы получаете условие и немедленно задаёте уточняющие вопросы — это демонстрирует системное мышление.

- **Вход:** слайс целых чисел `prices` длиной `n` (гарантируется `n >= 1`).
- **Выход:** максимальная прибыль `max(0, prices[j] - prices[i])`, где `0 <= i < j < n`.
- **Ограничения:** `n` может достигать `10^5`, цены — неотрицательные целые до `10^4`. Значит, необходимо O(N) или O(N log N).
- **Поведение при невозможности прибыли:** если цены только падают, вернуть 0 (не отрицательное число).
- **Можно ли продавать и покупать в один день?** Формально `i < j`, значит, один день — нет. Ответ 0 при невозможности.

Уточнения по Go: «Пустой массив?» — по условию LeetCode нет, но хорошей практикой будет ранний возврат `0` для пустого слайса.

### Наивное решение: двойной цикл

Брутфорс: для каждого дня покупки перебираем все будущие дни продажи и считаем разность. Запоминаем максимум. Сложность O(N²).

```go
func maxProfitBrute(prices []int) int {
    n := len(prices)
    maxProfit := 0
    for i := 0; i < n-1; i++ {
        for j := i + 1; j < n; j++ {
            profit := prices[j] - prices[i]
            if profit > maxProfit {
                maxProfit = profit
            }
        }
    }
    return maxProfit
}
```

При `N = 10^5` это 5 миллиардов итераций — TLE. Узкое место очевидно: мы заново просматриваем хвост массива для каждого `i`. Но можно заметить, что для каждого дня продажи нам нужна только минимальная цена **до** него. Это наблюдение ведёт к линейному решению.

### Оптимальное решение: один проход с отслеживанием минимума

Идём по массиву слева направо. Поддерживаем `minPrice` — минимум, встреченный к текущему моменту. Для текущей цены `p` потенциальная прибыль равна `p - minPrice`. Если она больше текущего максимума, обновляем его. Затем, если `p < minPrice`, обновляем `minPrice`.

**Инвариант:** после обработки дня `i`:
- `minPrice` равен минимальной цене в `prices[0..i]`.
- `maxProfit` равен максимальной прибыли, которую можно получить, продав в один из дней до `i` включительно.

Таким образом, мы гарантированно находим максимальную разность, так как для любой оптимальной пары `(buy, sell)` день `buy` будет минимумом на префиксе до `sell`, и алгоритм проверит `prices[sell] - minPrice` в момент прохода через `sell`.

```go
func maxProfit(prices []int) int {
    if len(prices) == 0 {
        return 0
    }
    minPrice := prices[0]
    maxProfit := 0
    for _, price := range prices[1:] {
        // прибыль при продаже сегодня
        if profit := price - minPrice; profit > maxProfit {
            maxProfit = profit
        }
        // обновляем минимальную цену покупки
        if price < minPrice {
            minPrice = price
        }
    }
    return maxProfit
}
```

**Go-идиомы:**
- Проверка `len(prices) == 0` — защита от паники, даже если гарантируется непустой вход.
- Цикл `for _, price := range prices[1:]` создаёт подслайс без копирования данных (O(1)), итерирует по значениям. Это чище, чем `for i := 1; i < len(prices); i++`.
- Локальные переменные `minPrice`, `maxProfit` на стеке, никаких аллокаций.
- Осмысленные имена, никаких `i`, `j`, `tmp`.

> [!info] Под капотом
> С точки зрения процессора, этот код практически идеален: последовательное чтение слайса `prices`, простые арифметические операции и сравнения. Аппаратный prefetcher загружает следующие элементы в L1-кэш до того, как они понадобятся. Никаких указателей, ветвлений только два на итерацию, предсказатель переходов срабатывает отлично. Для массива длиной 10⁶ алгоритм выполняется за доли миллисекунды.

### Связь с алгоритмом Кадане

Задачу можно свести к поиску максимальной суммы подмассива (Maximum Subarray, [[5. Maximum Subarray (Kadane)]]). Если построить массив дневных изменений цен `diffs[i] = prices[i+1] - prices[i]`, то задача сводится к нахождению максимальной суммы непрерывного подмассива в `diffs`. Тогда алгоритм Кадане с `curSum`, сбрасываемой при отрицательных значениях, даст максимальную прибыль. Это объясняет, почему решение имеет DP-природу: мы неявно считаем `dp[i] = max(0, dp[i-1] + diff)`. Однако прямой метод с минимумом проще и не требует дополнительного массива.

> [!tip] Собеседование
> Вопрос: «Является ли это динамическим программированием или жадным алгоритмом?»
> Ответ: «Формально это DP с оптимизацией памяти: состояние `dp[i]` — максимальная прибыль, заканчивающаяся в день `i`. Но переход `dp[i] = max(dp[i-1] + diff, 0)` сворачивается в одну переменную. Это также можно трактовать как жадный алгоритм, потому что локально оптимальное действие — покупать по минимальной цене — ведёт к глобальному оптимуму. В данном случае оба взгляда корректны».

### Edge Cases

- **Пустой массив или один элемент:** прибыль невозможна, возвращаем 0. Наша проверка `len(prices) == 0` обрабатывает пустой случай; для одного элемента цикл `prices[1:]` пуст, сразу возвращается 0.
- **Строго убывающие цены:** `minPrice` обновляется на каждом шагу, `profit` всегда отрицательный, `maxProfit` остаётся 0. Верный результат.
- **Постоянные цены:** прибыль 0.
- **Максимальная прибыль при нескольких одинаковых минимумах:** алгоритм берёт первый минимум, но разница с любым другим минимумом та же, ответ корректен.
- **Большие числа:** цены до 10⁴, их разность до 10⁴, влезает в int без переполнения. В Go `int` 64-битный на большинстве платформ — абсолютно безопасно.

> [!warning] Ловушка / Gotcha
> Не пытайтесь инициализировать `minPrice` нулём или `math.MaxInt`. Инициализация `prices[0]` корректна всегда (если длина ≥ 1). При пустом массиве нужно вернуть 0 до присваивания.

### Анализ сложности

- **Время:** O(N). Один проход по массиву, на каждом шаге несколько сравнений и вычитаний.
- **Память:** O(1). Две целочисленные переменные, счётчик цикла.

### Mechanical Sympathy

Алгоритм нагружает процессор минимально:
- Последовательный доступ к слайсу: cache-friendly, предвыборка работает.
- Нет аллокаций в куче: `prices` уже в куче, но мы не создаём новых структур.
- Нет карт (map), нет указателей, нет интерфейсов.
- GC не вызывается во время работы функции (если только не прерван по времени, но функция слишком быстра).

Этот код — пример того, как высокоуровневая задача решается практически на «голом железе», без оверхеда. Senior-разработчик держит это в уме и при необходимости может обосновать выбор именно такого подхода, а не, скажем, решения с дополнительным массивом разностей.

### Альтернативы и follow-up

- **Решение с массивом разностей и Кадане:** использует O(N) памяти для `diffs` или O(1) при потоковой обработке. Идеологически идентично, но менее прямое.
- **Два указателя?** Не применимы, потому что нет сортировки и нет свойства монотонности для двух указателей, сходящихся к центру.
- **Best Time to Buy and Sell Stock II (множество сделок):** следующая задача серии, решается жадным суммированием всех положительных разностей.
- **Best Time to Buy and Sell Stock III (две сделки):** требует DP с состояниями, уже сложнее.

На собеседовании уместно упомянуть, что данное решение является фундаментом для всей линейки задач о покупке/продаже акций, и понимание этого паттерна позволяет легко переходить к более сложным вариантам.

### Итог

Best Time to Buy and Sell Stock — это лабораторный образец того, как переход от O(N²) перебора к одному проходу с отслеживанием инварианта превращает задачу из «TLE» в «Accepted». В Go алгоритм реализуется в три строки логики и демонстрирует идеальную механическую симпатию: нулевые аллокации, последовательный доступ, дружелюбие к кэшу и предсказателю переходов.
