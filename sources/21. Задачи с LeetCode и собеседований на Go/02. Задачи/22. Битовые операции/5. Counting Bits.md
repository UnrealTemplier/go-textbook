## Введение: Битовое динамическое программирование

Задача **Counting Bits** (LeetCode 338) является классическим мостом между алгоритмическим мышлением и пониманием низкоуровневой работы процессора. Условие звучит просто:
> Дано целое неотрицательное число `n`. Верните массив `ans` длины `n + 1`, где `ans[i]` — количество установленных битов (единиц) в двоичном представлении числа `i` для всех `0 <= i <= n`.
> **Требования:** $O(n)$ по времени, $O(1)$ дополнительной памяти (не считая выходной массив).

На первый взгляд задача решается тривиальным перебором, но требование линейного времени отсекает наивные подходы, требующие подсчета битов для каждого числа независимо. Решение опирается на **динамическое программирование (DP)**, где состояние текущего числа вычисляется на основе уже вычисленных состояний меньших чисел, используя фундаментальные свойства двоичной арифметики.

В этой статье мы разберём три DP-паттерна, проанализируем их влияние на кэш-линии CPU и конвейер инструкций, посмотрим, как компилятор Go разворачивает код в ассемблер, и обсудим, почему в реальных высоконагруженных системах вы бы выбрали другой подход, но на интервью обязаны показать алгоритмическую гибкость.

## Наивный подход и его ограничения

Самое очевидное решение — пройтись по каждому числу от 0 до n и посчитать биты вручную или через встроенную функцию.

```go
func countBitsNaive(n int) []int {
    ans := make([]int, n+1)
    for i := 0; i <= n; i++ {
        count := 0
        temp := i
        for temp > 0 {
            if temp&1 == 1 {
                count++
            }
            temp >>= 1
        }
        ans[i] = count
    }
    return ans
}
```

**Анализ сложности:**
*   **Время:** $O(n \cdot W)$, где $W$ — разрядность числа (32 или 64). Хотя $W$ константа, в строгой нотации Big-O это линейно от количества бит, а не от $n$. Для огромных $n$ внутренний цикл добавляет заметный оверхед.
*   **Память:** $O(1)$ дополнительно, но алгоритм не использует результаты предыдущих вычислений, игнорируя свойство смежности двоичных чисел.

> [!warning] Ловушка / Gotcha
> Использование `math/bits.OnesCount(uint(i))` в цикле формально тоже $O(n \cdot W)$ или $O(n)$ на CPU с инструкцией `POPCNT`, но интервьюеры часто запрещают встроенные функции битового подсчёта, чтобы проверить понимание рекуррентных соотношений и умение проектировать алгоритмы с нуля.

## Динамическое программирование: Три пути к линейности

Суть битового DP заключается в поиске зависимости между `ans[i]` и `ans[j]`, где $j < i$. Существует три математически эквивалентных, но архитектурно различных подхода.

### 1. Паттерн чётности и сдвига (Even-Odd)
Это самый элегантный и производительный подход. Он опирается на два факта:
*   Чётные числа (`i % 2 == 0`) в двоичной записи заканчиваются на `0`. Сдвиг вправо `i >> 1` убирает этот ноль, количество единиц **не меняется**: `ans[i] = ans[i >> 1]`.
*   Нечётные числа (`i % 2 == 1`) заканчиваются на `1`. Сдвиг вправо убирает единицу, количество единиц уменьшается на 1: `ans[i] = ans[i >> 1] + 1`.

Обе формулы объединяются в одну:
```go
ans[i] = ans[i >> 1] + (i & 1)
```

### 2. Сброс младшего бита (Brian Kernighan's Algorithm)
Операция `i & (i - 1)` всегда сбрасывает самый младший установленный бит числа в ноль. Например: `1100 & 1011 = 1000`.
Это означает, что количество битов в `i` ровно на 1 больше, чем в `i & (i - 1)`:
```go
ans[i] = ans[i & (i-1)] + 1
```

### 3. Отсечение старшего значащего бита (Highest Significant Bit)
Любое число `i` можно представить как `2^k + offset`, где `2^k` — ближайшая меньшая степень двойки. Битовое представление `i` — это единица на позиции `k` плюс биты числа `offset`.
```go
// offset = i - 2^k
ans[i] = ans[offset] + 1
```

> [!info] Под капотом
> **Почему Even-Odd выигрывает?**
> Паттерн `i >> 1` использует последовательный доступ к памяти. Когда вычисляется `ans[i]`, значение `ans[i >> 1]` уже давно вычислено и с высокой вероятностью находится в кэше L1/L2. 
> Паттерн `i & (i-1)` обращается к произвольным индексам (`i` может быть 1000, а `i & (i-1)` = 992). На больших массивах это вызывает больше промахов кэша (cache misses), так как доступ становится менее предсказуемым для аппаратного префетчера (Hardware Prefetcher).

## Идиоматичная реализация в Go

Собираем всё в production-ready решение с предвыделенной памятью и строгим типизированием.

```go
// CountBits возвращает массив количества установленных битов для всех чисел от 0 до n.
// Сложность: O(n) по времени, O(1) дополнительной памяти.
func CountBits(n int) []int {
    if n < 0 {
        // В Go предпочтительно паниковать на программистских ошибках контракта
        // или возвращать error, но по условию LeetCode n >= 0.
        panic("negative input not allowed")
    }

    // Предвыделение памяти: одна аллокация, ноль ресайзов.
    // Размер = n + 1. Элементы автоматически инициализируются нулями.
    ans := make([]int, n+1)

    for i := 1; i <= n; i++ {
        // ans[i>>1] уже вычислен, т.к. i>>1 < i
        // i&1 возвращает 1 для нечётных, 0 для чётных
        ans[i] = ans[i>>1] + (i & 1)
    }

    return ans
}
```

## Механика на уровне CPU: Кэш, префетчинг и ассемблер

Почему этот цикл работает настолько быстро, что зачастую быстрее встроенных функций на маленьких $n$?

1.  **Кэш-локальность (Cache Locality):** Запись в слайс `ans` идёт строго последовательно. CPU использует **Line Prefetcher**, который подгружает следующую кэш-линию (64 байта) в L1 заранее. Вы практически никогда не ждёте память.
2.  **Branchless выполнение:** Выражение `i & 1` заменяет условный оператор `if i % 2 == 0`. На уровне ассемблера нет инструкций `JMP` или `TEST` внутри цикла. Процессор не рискует сбросить конвейер (pipeline flush) из-за неверного предсказания ветвлений.
3.  **Ассемблерный выхлоп (amd64):** Компилятор Go генерирует крайне плотный код.

```asm
; Упрощённый ассемблер тела цикла (Go 1.21+, amd64)
; BX = i, AX = указатель на sлайс ans

.L2:
    MOVQ    BX, CX          ; CX = i
    SHRQ    $1, CX          ; CX = i >> 1
    MOVQ    (AX)(CX*8), DX  ; DX = ans[i >> 1] (загрузка из памяти)
    ANDQ    $1, BX          ; BX = i & 1 (остаток в регистре)
    ADDQ    DX, BX          ; BX = ans[i>>1] + (i&1)
    MOVQ    BX, (AX)(CX*8)  ; Сохранение результата НЕ в i, а по правильному индексу
    ; (В реальном выхлопе компилятор оптимизирует индексацию, используя регистр-счётчик)
    INCQ    CX
    CMPQ    CX, SI          ; Сравнение с лимитом
    JLE     .L2
```
Инструкции `SHRQ`, `ANDQ`, `ADDQ` исполняются за 1 такт на разных исполнительных портах CPU. Цикл выполняется с throughput ~1 итерация на такт (с учётом задержки доступа к памяти, скрытой предвыборкой).

## Go под капотом: Escape Analysis и управление памятью

При возврате слайса `ans` компилятор Go принимает решение: выделить память на стеке или в куче?

```bash
$ go build -gcflags=-m .
./main.go:10:14: make([]int, n+1) escapes to heap
```

**Почему слайс «убегает» (escapes)?**
Функция возвращает ссылку на внутреннюю память слайса. Время жизни этой памяти превышает время выполнения функции `CountBits`, поэтому рантайм обязан выделить её в куче (Heap). Это значит:
*   Аллокация проходит через **tcmalloc**-подобный аллокатор Go.
*   При выходе из функции слайс попадает в область памяти, которую будет сканировать Garbage Collector.
*   Для `n` до нескольких миллионов это приемлемо. Для `n` в порядке $10^8$ и выше вы столкнётесь с давлением на GC и потенциальным `OOM`.

> [!tip] Собеседование
> **Вопрос:** Как избежать выделения в куче, если caller гарантирует, что передаст достаточно большой буфер?
> **Ответ:** Принять слайс-приёмник или изменить сигнатуру на `func CountBitsTo(dst []int, n int)`. Caller выделяет память (возможно, в куче, возможно, через `sync.Pool`), а функция только заполняет. Это паттерн `zero-allocation` в хот-путах:
> ```go
> // Caller-side
> buf := make([]int, 0, n+1) // capacity задаётся, но len=0
> CountBitsTo(buf, n)
> ```
> В таком случае Escape Analysis может поместить `buf` на стек, если время жизни локально.

## Ловушки и Edge Cases

1.  **Нулевой ввод (`n = 0`):** Цикл `for i := 1; i <= 0` не выполнится. Функция вернёт `[]int{0}`. Корректно.
2.  **Отрицательные числа:** По условию `n >= 0`. В реальном API всегда валидируйте вход: `if n < 0 { return nil, ErrNegativeInput }`.
3.  **Потребление памяти:** `make([]int, n+1)` для `n = 10^7` требует ~80 МБ. На constrained окружениях (например, serverless с лимитом 128 МБ) это может вызвать OOM. Если нужно стримить результат, используйте канал или writer, но это нарушит требование $O(1)$ памяти на алгоритме.
4.  **32 vs 64 бит:** В Go `int` платформозависим. На 32-битных системах `int` = 32 бита. Если `n` превысит `math.MaxInt32`, цикл переполнится или вызовет панику при аллокации. Используйте `int64` для индексов в высоконагруженных системах, работающих с большими датасетами.

## Подготовка к собеседованию: Типичные вопросы

1.  **Почему не использовать `math/bits.OnesCount`?**
    *   *Ответ:* `OnesCount` использует аппаратную инструкцию `POPCNT` (x86) или быструю табличную реализацию (ARM). Это $O(1)$ на число, но алгоритмически $O(n \cdot \log W)$. DP-подход гарантирует $O(n)$ математически и часто быстрее на малых $n$ за счёт предсказуемости кэша и отсутствия вызовов функций. Интервью проверяет способность видеть рекуррентные зависимости.

2.  **Как изменить решение, если нужно вернуть только сумму всех битов для чисел от 0 до n, а не массив?**
    *   *Ответ:* Можно вывести формулу. Количество установленных битов в числах от 0 до $n$ вычисляется за $O(\log n)$通过分析 позиции каждого бита. Для позиции $k$ бит циклически повторяется блоками по $2^{k+1}$, где половину времени он равен 0, половину 1. Сумма вычисляется аналитически без массива.

3.  **Что произойдёт, если запустить этот код на 32-битной архитектуре с `n = 2_000_000_000`?**
    *   *Ответ:* `make([]int, n+1)` попытается выделить ~8 ГБ непрерывной памяти. На 32-битной системе адресное пространство процесса ограничено 2-4 ГБ. Вы получите `panic: runtime error: out of memory` или ошибку виртуальной памяти ОС до входа в цикл.

> [!warning] Ловушка / Gotcha
> **Сдвиг и приоритет операторов**
> В Go оператор сдвига `>>` имеет тот же приоритет, что и `*`, `/`, `%`, но **ниже** `+`, `-`.
> Запись `ans[i >> 1 + 1]` будет интерпретирована как `ans[i >> (1+1)]` (сдвиг на 2), а не `(ans[i>>1]) + 1`.
> Всегда используйте явные скобки при комбинировании арифметики и сдвигов, чтобы код самодокументировался и избегал коварных багов.

## Итог

1.  **Counting Bits** решается за $O(n)$ через динамическое программирование, использующее свойства двоичного сдвига (`ans[i] = ans[i>>1] + (i&1)`).
2.  **Производительность:** Паттерн Even-Odd идеален для CPU благодаря последовательному доступу к памяти, отсутствию ветвлений и предсказуемой работе аппаратного префетчера.
3.  **Go-специфика:** Слайс-результат «убегает» в кучу. Для высоконагруженных систем рассмотрите инъекцию буфера от caller или `sync.Pool` для снижения нагрузки на GC.
4.  **Архитектурные ограничения:** Помните о платформозависимости `int` и лимитах виртуальной памяти на 32-битных системах при больших $n$.
5.  **На интервью:** Умейте объяснить рекуррентное соотношение, сравнить с `POPCNT` и обсудить trade-offs между алгоритмической чистотой и практическими ограничениями памяти.
